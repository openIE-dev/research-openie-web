## 要約

本論文は Reality Code Engine（RCE）を記述する。これはプログラムを状態機械、すなわち形式として一度だけ書き、他の言語のコードをそこから生成するシステムである。10,000 個の形式と公開バグデータセットで測定した内容を報告し、主張をどのように偽と示せるかを述べる。

**平易な言葉で**

1. プログラムは一度だけ、一つの精密な形式で書かれ、コンピュータはそこから多くの言語で同じプログラムを生成する。
2. 形式は宣言されたものだけを許すので、壊れた入力は後で直されるのではなく、入口で拒否される。
3. 検査を通過した修正は保存されて再利用されるので、同じ問題に時間やエネルギーを二度払わずに済む。

## 1. 主張

自律的なコンピュータ自動化は、多くの点を含む設計空間である。どの手法も、五つの連続的な軸のどこかに位置する。正しい結果一つあたりに費やすエネルギー、システムが実行時に解消しなければならないエントロピーとそれに伴う出力の決定性の度合い、結果を受け入れる検証の強さ、受け入れられた各結果がどこまで再利用され複利的に積み上がるか、そして手法がどれだけモデルに依存するか、の五つである。プロンプトから個々の変更を書く大規模言語モデル（LLM）、すなわち統計的なテキストモデルは、この空間の一つの隅の近くに位置する。それはどのタスクでもモデルに依存し、毎回高エントロピー分布から新しい標本を引き、どのタスクでも生成の費用を改めて支払う。検索、規則、合成、検証、キャッシュは他の多くの点を占め、実際のシステムはそれらを組み合わせる。

Reality Code Engine（RCE）はこの空間の一つの点であり、本論文はそれを記述し測定する。RCE はプログラムをデータベース関数型状態機械としてモデル化する。Lopes らは GitHub 上のコードの約 70% が以前のファイルのクローンであることを測定した [33]。したがって RCE はまず既存の適合を取り出し、適合させ、検査することを試し、より安いものでタスクを閉じられないときにだけモデルを呼び出す。

**中心的な主張。** RCE は、プログラムが意図からネイティブに書かれる完全なコード・エコシステムである。意図は一度だけ、形式として書かれる。すなわち、一つの状態、一組のイベント、そして純粋で全域的な遷移である。形式はその意図の可逆（無損失）な符号化である。すべてのターゲット（ステートチャート、Rust、Python、XState、SCXML、WASM）は形式の射影であり、各射影は形式のトレースをバイト単位で再生する。形式が宣言していない状態は書くことができず、契約の外にある入力は入口で拒否される。したがって、エコシステム内のプログラムは、一般的な言語のプログラムがコメントやテストや他の実装からずれていくようには、その意図からずれることがなく、事後の差分比較もエラー追跡も必要としない。ゲートを通過したすべての適合は保存されて再利用されるので、エコシステムは成長とともに複利的に積み上がる（[§2.4](#24-gated-verified-recursive-self-improvement)）。他の言語で書かれたコードは入口の一つであり、持ち上げ（lift）によって入る（[§6](#6-lift-entering-the-ecosystem-from-other-languages)）。

空間のどの点も同じゲートに向き合う。ゲートは正しさである。すなわちタスクの完了述語 $C(z)$ であり、ここではタスクのテスト、証明、または一致トレースを指す。ゲートを通過した実行の中で、システムは完了までのジュール $J^*$ によって順位づけられる。正しさは制約であって、得点ではない。

RCE の仕組み、すなわちギアは費用の順に動き、ゲートを通過した最初のギアがタスクを閉じる。

エネルギーの数値は出所によってラベル付けされる。`est_j` は解析的な推定値である。`reported_j` はオペレーティングシステムまたはチップ上のカウンタである。`measured_j` は壁面電力計のために予約されており、本論文のすべての結果で空欄である。

## 2. 自律的コーディングの設計空間

*図1. 意図のエントロピーと機械の床。[PNG 版](/figures/rce/intent-entropy.png)も用意している。出典：Shannon (1951)；Lopes et al. (2017)；626 言語という数は著者による未公表の調査であり、本論文のいかなる主張も支えない。Python と C の結果は言語仕様上の挙動であり、C の符号付きオーバーフローは未定義動作である。*

**意図は高エントロピーである。** 「チェックアウトを速くして」には多くの意味がある。ページ読み込みの短縮、手順の削減、カード承認の高速化、カートのキャッシュ、あるいはある機種群での高速化。文脈は含意されるだけで、書かれることはない。Shannon は印刷された英語を1文字あたり約 0.6 から 1.3 ビットと測定した [1]。文字は予測できる。意味は予測できない。

**どの変換も情報を失う。** 意図が仕様になると、文脈が失われる。仕様が数百ある表層言語の一つになると、代替案と境界ケースが失われる。ソースが中間表現（IR）になると、名前、スタイル、作者の理由が失われる。IR が機械語になると、型はサイズに、ループはジャンプになる。

**床は低エントロピーである。** どのプログラムも最後はロード、ストア、算術、ジャンプになる。行き先には少数の形しか入る余地がないので、コードはそこへ曲がっていく。収束は設計によるものである。

**意味が分かれるのは境界である。** 同じ一行が端では異なる答えを返す。Python では `-3 % 2` は 1、`-7 / 2` は -3.5 である。C では `-3 % 2` は -1、`-7 / 2` は -3 であり、符号付きオーバーフローは未定義である。境界ごとにコードを生成し直すシステムは、境界ごとに推測している。

**軸を量として述べる。**

| 軸 | 一方の端 | もう一方の端 | RCE の位置 |
|---|---|---|---|
| 正しい結果あたりのエネルギー | タスクごとに全額を改めて支払う | 新しいケースごとに一度支払い、その後はハンドラの床 | 覆われたタスクでは床にある |
| 実行時に解消されるエントロピーと決定性 | プロンプトの分布全体、毎回新しい標本 | 保存済みの適合が覆わない残差のみ、一つの決定的な出力 | 残差のみ。すべての射影は決定的 |
| 検証の強さ | 目視で出力を受け入れる | テスト、カバレッジ、証明の証明書 | すべての結果に完全なゲート |
| 再利用と複利 | 各結果は一度だけ使われる | 受け入れられた各適合が保存され再利用される | ゲートを通過したすべての適合が保存される |
| モデル依存 | すべてのタスクにモデル | モデルなし | モデルは最後のギアとしてのみ |

手法は各軸の上で程度によって異なり、軸どうしは相互に作用する。再利用はエネルギーと解消すべき残りのエントロピーを下げ、強い検証こそが再利用を安全にする。 RCE は意味を一つの正準形式に一度だけ書く。すべての表層言語はその形式の射影であり、形式と一致するかを検査される。等価な形式の中で、最も安い正しいものが実行される。

### 2.1 プログラミングは符号理論である

本節の主張は、プログラミングを符号理論として読める、というものである。プログラマは意図を、二つのエントロピー領域の間の勾配に沿って変換する。意図は高エントロピーであり、意味の上の分布である。コードは低エントロピーであり、状態ごとに一つの決定的な遷移である。要求からレジスタに至るまで、ソフトウェア作業の一歩一歩はその変換の一歩である。文献はこのことを七十年にわたり、多くの言語で、断片として述べてきた。本節はその断片を一つの議論に組み立て、RCE の各ギアをその上に位置づける。

**尺度。** Shannon は情報源のエントロピーと通信路の容量を定義し [40]、印刷された英語を1文字あたり約 0.6 から 1.3 ビットと測定した [1]。Kolmogorov は1965年、ロシア語の *Problemy Peredachi Informatsii* において情報量への三つのアプローチを示し、アルゴリズム的なものを第一とした。対象のもつ情報とは、それを生成する最短プログラムの長さである [41]。Solomonoff は帰納推論の理論として同じ対象に到達しており [42]、Chaitin はプログラムサイズが Shannon のものと形式的に同一の恒等式に従うことを示した [43]。Rissanen はこの考えをモデル選択の規則、最小記述長にした [44]。これらを合わせると、プログラムは符号語である。つまり振る舞いの記述であり、最短の正しい記述が床である。等価な適合の中で最小ジュールのものを残すという RCE の抽出規則（命題3）は、ビットの代わりにジュールを置いたこの規則である。

**コードは低エントロピー領域にあり、人々はそれを測った。** Hindle、Barr、Su、Gabel、Devanbu は、コードが「非常に反復的であり、実際、自然言語以上にそうである」ことを、同じ n-gram モデルの下でのより低い交差エントロピーとして見出した [35]。Gabel と Su はプロジェクトの行の大半がすでに他所に存在することを [34]、Lopes らは GitHub のファイルの大半がクローンであることを見出した [33]。Tu、Su、Devanbu はコードが局所的でもあること、すなわち近くに書かれたものが次に来るものを予測することを見出した [46]。Ray らはバグのある行は自然さが低くエントロピーが高いこと、そしてバグが修正されるとエントロピーが下がることを見出した [45]。2025年に Yang、Kolak、Hellendoorn、Martins は、パッチが引き起こすエントロピー変化を用いて修復候補を順位づけ、正しいパッチと過適合したパッチを区別した [51]。Allamanis、Barr、Devanbu、Sutton はこの分野を自然さ（naturalness）の名の下に概観した [47]。この結果は英語圏だけのものではない。Prem Devanbu は2013年の India Software Engineering Conference の基調講演でこれを述べた [50]。IBM Research India の Sridhara、Sinha、Mani は同じ会議で、コードを取り巻く自然言語の成果物を測定し、コミットメッセージが最も規則的で、Stack Overflow の文章は通常の英語のように振る舞うことを見出した [49]。中国では *Journal of Software*（软件学报）が2022年にコードの自然さ研究のレビューを掲載し、交差エントロピーの尺度と、欠陥のあるコードのエントロピーが高いという知見を述べている [48]。日本では大阪大学の土居、肥後、有馬、下仲、楠本が n-gram の自然さを用い、まず日本語の電子情報通信学会技術研究報告で、次いで ICPC 2018 で、機械生成されたソースファイルと人間が書いたものを判別した [73, 74]。生成されたコードは人間のコードよりさらにエントロピーの尺度で低い位置にある。生成器は固定された変換だからである。ブラジルでは Arrebola の博士論文が、プロジェクトと保守者で分割した n-gram モデルとトピックモデルの上にコード補完を構築し、交差エントロピー、すなわち次のトークンを符号化するのに必要なビット数で評価した [75]。二つの領域は一つのリポジトリの中に見える。コードを取り巻く文章は高エントロピーであり、コードは低エントロピーである。

**尺度が重要である。** ベネズエラとメキシコを拠点とする Febres、Jaffé、Gershenson は、英語、スペイン語、プログラムテキストをメッセージ長あたりの語彙多様性で比較し、プログラムテキストの方が多様であることを見出した [76]。Rahman、Palani、Rigby は、コードの n-gram 予測可能性の多くが構文トークンに由来し、それらを除いてもコードはなお反復的であるが、当初の報告ほどではなく、API の使用が最も反復的な部分であることを見出した [77]。どちらの結果も主張を覆すのではなく、鋭くする。記号の多様性は予測可能性ではなく、低エントロピー領域とは次の一歩の条件付き分布の性質であり、それこそが決定的な遷移が固定するものである。RCE の G0 が表層トークンではなく形状をキーにするのはこのためである。

**意図は高エントロピー領域にある。** Zave と Jackson は、要求は環境についての言明であり、仕様はインタフェースにおける言明であって、両者の隔たりはしばしば書かれていない領域知識によってのみ埋められることを示した [64]。Brooks はソフトウェアの困難を本質と偶有に分けた。本質は概念的な構築物であり、その大部分は表現ではなく仕様と設計である [61]。Naur は、プログラムはそのプログラマたちが保持する理論の目に見える部分であり、理論はテキストから完全には回復できないと論じた [62]。Shannon を通して読むと、三者は同じことを言っている。意図はどの一つのプログラムよりも多くの不確実性を担い、プログラムを書くことはそれを取り除く行為である。コードが書かれた後にプログラマの頭に残るものは、コードが符号化しなかった意図の部分である。

**変換は詳細化であり、詳細化は絞り込みである。** Hoare はプログラムに論理を与え、そこではプログラムは事前条件と事後条件に相対的に正しい [54]。Wirth は段階的詳細化を教えた。タスクを逐次的な決定によって命令へ分解し、各決定が仕様の残した選択を一つ固定する [53]。Dijkstra のガード付きコマンドは、残された選択を非決定性として明示し、それを取り除くことで仕様からプログラムを導いた [52]。ミュンヘンでは Bauer と Wössner の CIP プロジェクトが、仕様からプログラムへの正しさを保存する変換の列としてプログラム開発を構築した [58]。フランスでは Abrial の B メソッド、次いで Event-B が、各段階に証明責務を伴う詳細化を産業規模にまで広げた [55, 56]。フィンランドでは Back と von Wright が詳細化に束論的な計算体系を与えた [57]。いずれにおいても、仕様は許容される振る舞いの集合を表し、詳細化の各段階はその集合を縮め、最後に一つの決定的な振る舞いが残る。それは各段階に証明を伴うエントロピーの削減である。RCE の形式はその連鎖の最後の要素である。すなわち、すべての選択が解消された、データベース状態上の全域的で決定的な遷移 $\delta$ である（[§3.2](#32-definitions)）。

**合成は仮説空間を絞り込む探索である。** Gulwani の FlashFill は、整合するすべてのプログラムの集合を表現し、新しい例ごとにそれと交わりをとることで、少数の入出力例から文字列プログラムを学習する [59]。Gulwani、Polozov、Singh はプログラム合成一般を、意図に制約されたプログラム空間の探索として捉え [60]、Solar-Lezama のスケッチングは部分的なプログラムの穴をソルバで埋める [27]。各例や各制約は仮説を取り除く測定である。Shannon の尺度は、そうした測定がいくつ必要かを数える。RCE の G2 がそのギアである。

**変換が生み出すものは一つの形をもつ。** Gurevich は、すべての逐次アルゴリズムがそれ自身の抽象度の抽象状態機械（ASM）によって捉えられることを証明した [2]。Codd は状態を関係にし [5]、イベントソーシングは状態を追記専用ログの畳み込みにする [14]。Curry と Howard の下では証明はプログラムであり命題は型である [18, 72]。したがって検証された適合はその仕様の証明である。これらが、低エントロピー領域に形が少ない理由である。表層言語が何であれ、行き先はデータベース上の状態機械である。

**低エントロピーはゲートがなければ崩れる。** Lehman は数十年にわたる大規模システムの観察から、使われているプログラムは変わり続けねばならず、複雑さを減らす作業をしない限りその複雑さは増大することを見出した [63]。Torres、Baltes、Treude、Wagner は25プロジェクトのコミット履歴にわたって構造的エントロピーとテキストのエントロピーを測定し、両者がともに上昇することを見出した [78]。エントロピーは環境からコードへ流れ戻る。コードを低エントロピー領域に保つシステムには、すべての変更にゲートが必要であり、RCE のゲートは正しさである（[§4.3](#43-the-gate)）。

**コンパイラはすでに情報源符号化を行っている。** Franz と Kistler はプログラムを圧縮された抽象構文木として配布し、読み込み時にネイティブコードを生成した。これはプログラム自身の文法上での情報源符号化である [67]。Fraser はコーパスからコードの統計モデルを推定してそれを圧縮した [68]。二村は1971年、日本の学術誌 *Systems, Computers, Controls* において、インタプリタをプログラムに特化するとコンパイル済みプログラムが得られ、特化器を特化するとコンパイラが得られることを示した [70]。ノヴォシビルスクの Ershov は同じ考えを混合計算として発展させた [71]。Cousot 夫妻の抽象解釈は、プログラムのすべての振る舞いについて健全で情報量の少ない記述を計算する [69]。通信路符号化との類比は本論文の読み方であり、引用された定理ではない。型、テスト、証明は検査された冗長性を加え、パリティ検査が壊れた語を検出するように、誤ったプログラムを実行前に検出する。

**ジュールが費やされるのは消去においてである。** Landauer は、論理的に不可逆な一歩、すなわち1ビットの消去が少なくとも $k_B T \ln 2$ を散逸することを示した [65]。Bennett は計算が原理的には論理的に可逆にできること、したがって限界を担うのは計算ではなく消去であることを示した [66]。高エントロピーの意図を一つの低エントロピーのプログラムに変換すると、意図が許していたすべての代替案が捨てられる。その破棄は代替案についての情報の消去であり、熱力学的な床をもつ。RCE は新しいケースごとに一度だけ破棄の費用を払い、結果を保存するので、繰り返されるケースは何も新しく消去しない。

### 2.2 RCE はどう変換し、各ギアはどこに位置するか

符号理論として読むと、タスクはメッセージとして到着し、その残る不確実性とは、保存済みのどの適合もまだ解消していない部分である。各ギアは異なる価格で不確実性を取り除き、ギアはその価格の順に並べられている（[§4.2](#42-the-gears)）。

| ギア | 不確実性に対して行うこと | 上の議論における系譜 |
|---|---|---|
| G0 ルックアップ | 意図がすでに符号化されていたことを認識し、取り出しによってハンドラの床で解消する | 反復性とクローン [33, 34, 35]；局所性 [46] |
| G1 規則 | 既知のガード付き書き換えを適用し、繰り返し現れる残差を探索なしで解消する | 正しさを保存する変換 [52, 58]；証明責務を伴う詳細化 [55, 56] |
| G2 合成 | 仮説空間を探索し、例、制約、ソルバによって絞り込む | 探索としてのプログラム合成 [27, 59, 60] |
| G3 から G5 モデル | 下位のギアが隔たりを埋められないとき、学習されたコードの分布から標本化する。提案者に限る | コードの交差エントロピーモデル [35, 47] |
| ゲート | テスト、カバレッジ、証明の証明書がそろった候補のみを受理する | Hoare 論理 [54]；Curry-Howard [18, 72] |
| 昇格 | 受理された適合を保存し、同じ残差が次回は G0 の費用で済むようにする | 最小記述長 [44]；一度だけ支払われる Landauer 消去 [65] |

第2節の軸の上の位置は、変換の費用をどこで払うかが異なる。タスクごとにプロンプトの分布全体を標本化する手法は、高エントロピー側の費用を毎回払い直す。受け入れられた適合を保存して再利用する手法は、残差の分だけを、一度だけ払う。ほとんどのシステムはその両端の間にあり、RCE は再利用の端にある。

### 2.4 ゲート付きで検証された再帰的自己改善

Good（1965）[111] は超知能機械を、より優れた機械を設計できる機械と定義し、それによって改善は再帰すると考えた。Yudkowsky（2013）[113] はこの問いを収穫の問題として定式化した。すなわち、改善の各単位が次の単位を安くするのか高くするのかである。Schmidhuber のゲーデルマシン（2007）[112] は保証つきの最初の形式的な答えを与えた。プログラムは、書き換えが期待効用を高めることを証明した後でのみ、自分自身の探索を含むあらゆる部分を書き換える。Löb の定理（1955）[114] は自分を信頼する証明器が出会う障害であり、Yudkowsky と Herreshoff（2013）[115] はこれを Löb の障害と名づけた。すなわち、システムは一般に、自らの証明体系を使う後継者の健全性を証明できない。最近のシステムは証明の要求を捨て、測定されたスコアで選択する。STOP（Zelikman ら、2023）[116] はコードを改善する足場そのものを改善し、Darwin Gödel Machine（Zhang ら、2025）[117] はベンチマークのスコアで選ばれた自己改変コーディングエージェントのアーカイブを保持し、AlphaEvolve（Novikov ら、2025）[118] は自動評価器の下でプログラムを進化させ、Voyager（Wang ら、2023）[119] は後のタスクが再利用する検証済みスキルのライブラリを育てる。

RCE はゲーデルマシンの構造と Voyager のライブラリを取り入れるが、障害を取り除く二つの違いがある。第一に、改善される対象は証明器ではない。RCE が昇格させるのはハンドラ、書き換え、ギアであり、それぞれは固定され別途認証されたカーネルに照らして検査される。Kani のハーネスと SMT エンコーディングは昇格を通じて決して変わらないので、どのステップも後継者の証明体系を信頼する必要がない。第二に、ゲートは境界における正しさの証明であって、スコアではない。スコアはインターフェースの仮定が壊れている間にも上がりうるが、境界での証明は、それを壊す変更によって通過されることはない。

**命題 R1（単調な正しさ）。** 昇格されたすべての変更がその境界の検査を通過し、ほかの境界の検査が変わらないならば、昇格前にそれらの検査が確立したすべての性質は、昇格後も成り立つ。

**命題 R2（複利的な積み上げ）。** ワークロードをタスクの多重集合とし、昇格されたハンドラがその形のすべてのタスクを閉じるとする。このとき第 t ラウンドのエスカレーション数は t について非増加であり、第1ラウンドより前に昇格された修正は、あらゆる期間の累積エスカレーション数を、それ以後の各ラウンドで閉じるエスカレーションの分だけ減らす。プレイグラウンドの参照ワークロードでは、八ラウンドにわたる累積エスカレーション数は、シンクでの一つの修正によって 21 から 15 に下がり、どちらの場合も最終ラウンドでゼロに達する。すべてのタスクは正しく閉じられ、拒否された昇格はない。

図4は命題 R1 と R2 の仕組みを、参照ワークロードの合計とともに描く。

![RCE スタックを六つの階層として描いた図。上の意図から、形式、ゲート、射影、ランタイムを経て、ハードウェアとエネルギーに至る。境界の検査に合格した後にランタイム階層で昇格された修正が、その上のすべての階層を上へ貫く矢印で示されている。横の小さな棒グラフは、playground の参照ワークロードの八ラウンドにわたる累積エスカレーション数を示す。修正なしで 21、シンクに一つの修正ありで 15 である。](/figures/rce/stack-compounding.svg)

二村の射影（1971年、1999年に再掲）[120] と Turchin のスーパーコンパイル（1986）[121] は、この過程の極限を与える。インタプリタをあるプログラムに特化するとコンパイル済みプログラムが得られ、特化器自身を特化するとコンパイラが得られる。RCE の昇格は、一般的なエスカレーション経路を実際に生じる形へと特化するので、エンジンはそのワークロードの残余プログラム、すなわちモデルや人がなお供給しなければならない計算の部分へと収束する。ゲートの下での再帰的自己改善とは、この収束を検査済みのステップで行うことである。[RCE Playground](/playground/rce/#compounding) の Compounding レイヤーは、このワークロードをブラウザで実行する。

## 3. 形式

### 3.1 「同じ形式」の最も強い形式的言明

まず定理の範囲を述べる。Gurevich の逐次公理は逐次アルゴリズムを対象とする。並列アルゴリズムと対話的アルゴリズムには Blass と Gurevich のさらなる公理が必要である [3]。Blass、Dershowitz、Gurevich は、アルゴリズム上のただ一つの同値関係があらゆる目的に合うことはないと論じ [79]、Moschovakis と Vardi はアルゴリズムとは何かをめぐる論争を整理している [80, 81]。入出力を行う Web ハンドラは逐次定理の外にある。形式は対話を、対話的系譜と同じやり方で扱う。各入力は $E$ のイベントであり、状態機械はそれに対して一歩進む。したがって「一つの形式」は、逐次定理に根拠をもち慣習によって拡張されたモデル化上の選択であり、本番環境での先例として Elm アーキテクチャ [83]、耐久ワークフローのイベント履歴 [84]、Flo のようなストリーム意味論 [82] がある。第3.4節の命題はその選択について述べられている。

Gurevich の抽象状態機械（ASM）定理は、すべてのアルゴリズムが一つの形をもつことの最も強い形式的言明である [2]。抽象状態機械とは、状態が一階構造であり、一歩がガード付き更新の有限集合である機械である。Gurevich は三つの公理を述べる。逐次時間：アルゴリズムは状態、初期状態、一歩写像 $\tau$ をもつ。抽象状態：状態は一つの固定された語彙上の一階構造であり、同型の下で閉じている。有界探索：有限個の項が各一歩を決める。彼の主定理（Theorem 6.13）はこう述べる。「すべての逐次アルゴリズム A に対して、等価な逐次抽象状態機械 B が存在する。」Blass と Gurevich はこれを並列アルゴリズムへ拡張した [3]。Dershowitz と Gurevich は第四の公理、初期操作が計算可能であることを加え、そこから Church のテーゼを導いた [4]。

### 3.2 定義

**定義1（形式）。** プログラムは組

$$P = (S, E, \delta, D, \lambda)$$

である。

- $S$、状態空間：固定された語彙 $\Sigma$ 上の構造。各状態は Codd の意味でのデータベースインスタンスである [5]。
- $E$、イベントアルファベット：論理クロックの刻みを含む。
- $\delta : S \times E \to S$、遷移：全域的、決定的かつ純粋であり、ガード付き更新「if $\varphi$ then $f(\bar t) := t_0$」の有限集合として書かれ、各一歩は有界な位置の集合を読む。
- $D = (s_0, L)$、耐久ストア：初期状態と追記専用のイベントログ $L = e_1, \dots, e_n$。
- $\lambda : S \times E \to O$、出力写像。Mealy 機械は両方の引数を読み [6]、Moore 機械は状態のみを読む [7]。

**定義2（形式と適合）。** *形式*とは、四つの不変条件をもつ組の形である。$\delta$ は決定的かつ純粋である。探索は有界である。語彙は固定されている。状態はログの畳み込みである。

$$\mathrm{state}(D) = \mathrm{foldl}(\delta, s_0, L).$$

*適合*とは、その形を満たすデータである。語彙 $\Sigma$、アルファベット $E$ と $O$、$\delta$ を定める規則プログラム $\Pi$、$\lambda$ を定める出力規則、そして初期データ $s_0$ である。Gurevich の用語では、適合は語彙、ASM プログラム、初期構造である。Codd の用語では $\Sigma$ はスキーマであり $s_0$ はインスタンスである。プロダクトラインの用語では適合は機能の選択である [8]。構文誘導合成（SyGuS）の用語では適合は仕様を満たす文法の項である [9]。

**定義3（適合の等価性）。** 二つの適合は、すべてのログ $L$ について $\lambda$ の下での出力列が等しいとき、等価である。

**定義4（適合言語）。** 項が適合を表す文法。プログラミング言語、SCXML 文書、XState の設定、`.rce` 仕様は適合言語である。適合言語は、$\Sigma$ 上のすべての ASM プログラムがその中に項をもつとき完全である。

**定義5（制御射影）。** $\Sigma = \Sigma_c \cup \Sigma_d$ を有限の制御記号とデータ関係に分ける。$P$ のステートチャートとは $\delta$ の $\Sigma_c$ への射影である。状態は $\Sigma_c$ の値であり、遷移はイベントと $\Sigma_d$ 上のガードを伴い、アクションは $\Sigma_d$ への更新である。Harel のステートチャートが階層と直交領域を与える [10]。

**定義6（適合 e-graph）。** 適合 $F$ と健全な書き換えの集合 $R$ に対し、適合 e-graph $EG(F, R)$ は $R$ の下での $F$ の規則項の飽和 e-graph である [11, 12]。各 e-class は定義3の意味で等価な適合を保持する。

**定義7（ジュールコスト）。** $\mathrm{cost}_J(t)$ は、名前を付けた基盤上で項 $t$ を一度実行するための推定エネルギー（`est_j`）に、期待実行回数で重みを付けたものである。

### 3.3 なぜ「データベース関数型状態機械」なのか

有限の関係構造はデータベースインスタンスであるから、Gurevich の状態はデータベースであり、各一歩は有界なトランザクションである。*データベース*：$S$ は関係構造である。*関数型*：$\delta$ と $\lambda$ は純粋である。*状態機械*：実行はイベント上の $\delta$ の畳み込みである。Moseley と Marks はアーキテクチャにおいて同じ線を引いている [13]。イベントソーシングはアプリケーション状態において線を引く。「アプリケーション状態へのすべての変更をイベントの列として捕捉せよ」[14]。Dedalus は論理において線を引き、そこでは可変状態は時間で添字づけられた関係である [15]。

### 3.4 命題

**命題1（形式はすべての逐次アルゴリズムを捉える）。** すべての逐次アルゴリズム $A$ に対し、その実行が $A$ の実行である形式インスタンス $P$ が存在する。

*証明の概略。* Theorem 6.13 により、$A$ の状態、初期状態、一歩写像をもつ ASM $B$ が得られる。$E = \{\varepsilon\}$、$\delta(s, \varepsilon) = \tau_B(s)$、$D = (s_0, \varepsilon^n)$ とし、$\lambda$ を恒等写像とする。$n$ 刻み後の畳み込みは $\tau_A^n(s_0)$ である。Gurevich の Corollary 3.3 により、$P$ と $A$ は同じ実行をもつ。∎

**命題1b（対話的プログラム）。** $\Sigma$ を、各一歩の前に $e$ に設定される零項の入力記号で拡張する。すると $\delta(s, e) = \tau(s[\mathit{in} := e])$ は拡張された語彙上の逐次アルゴリズムとなり、命題1が適用できる。この構成は我々によるものである。

**命題1c（計算可能性）。** Dershowitz と Gurevich の公理の下で、すべての形式インスタンスはチューリング計算可能な関数を計算する [4, 16, 17]。形式は能力を何も加えない。形式はそのクラスのすべてのプログラムに一つの形を与える。

**命題1d（証明は適合である）。** 「与えられた命題の各証明に対して、対応する型のプログラムが存在する」[18]。型は仕様であり、証明はそれを満たす適合である。正しさのゲートとは、その証明または合格する受け入れテストが存在することである。

**命題2（一つの生成器）。** 一つの関数 $G : \mathrm{Fit} \to \mathrm{Program}$ が、すべての適合に対して実行可能なプログラムを生成し、どの領域も読まない。*根拠：* すべてのプログラムは形式インスタンスであるから、$G$ は型付きストア、イベント型、コンパイルされた規則、畳み込みを伴うログ、出力ディスパッチャを出力する。Rails のジェネレータ、JHipster、Yeoman のようなスキャフォールダは、小さな適合言語に制限された $G$ である。プロダクトライン工学は「関連するソフトウェアシステム間の共通性の体系的な発見と活用」から出発する [8]。その共通性が形式である。

**命題3（最小エネルギーの抽出）。** $\mathrm{cost}_J$ による抽出は、$F$ の e-class の中で抽出器が見つける最小ジュールの項を返す。*証明の概略。* 書き換えは健全であるから、e-class のすべての項は $F$ の観測可能な振る舞いをもち、同じゲートを通過する。抽出はコストを最小化し、コストはジュールである。∎ これはコードに適用された Mixture of Limits である。タスクを果たす最小の適合を残し、残りは無駄である。

**命題4（再生の決定性）。** $\delta$ が壁時計を読まず、名前に依らずに更新を順序づけ、すべての入力をログに記録するならば、一つの $D$ の二度の再生はすべての一歩で同一の状態ハッシュを与える。

**命題5（ステートチャート射影は健全である）。** 実行の各状態を $\Sigma_c$ へ射影する。その結果は、同じイベントの下での出力されたステートチャートの実行である。

**命題6（調整予算）。** 単調とタグ付けされた規則は調整なしにレプリカ上で実行できる。調整点を必要とするのは非単調な規則のみである。*根拠：* CALM 定理、「一貫した、調整不要の分散実装をもつプログラムは、ちょうど単調論理で表現できるプログラムである」[19]。

**命題7（ジュール微分としての知能）。** $X$ をゲートを通過したタスク数、$J$ を費やしたジュールとする。$\iota = dX/dJ$ は、すべてのイベントとその `est_j` を記録する $D$ から事後的に読み取られる。$\mathrm{cost}_J$ の下での抽出はゲートを固定したまま $J$ を増やさないので、等しい $X$ において $\iota$ を下げない。

### 3.5 グラフ、e-graph、ステートチャート

| 構造 | 形式のどの部分か | 何を決めるか |
|---|---|---|
| ステートチャート | $\Sigma_c$ 上の $\delta$ のガード | どの遷移が発火するか |
| データフローグラフ | $\delta$ と $\lambda$ の読み書き依存（Kahn プロセスネットワーク [20]） | 何が、どの順序で実行されるか |
| E-graph | 適合の同値類 | どの等価な適合が実行されるか |

ステートチャートとグラフは一つの適合を記述する。e-graph はそれと等価なすべての適合を記述する。抽出はそれらの中からジュールで選ぶ。

### 3.6 一つのエコシステム、可逆性、そして普遍性テーゼ

**構成による可逆性。** Shannon の情報源符号化定理は、可逆な符号の下限を情報源のエントロピーに定める [40]。形式は、検査可能な狭い意味で、意図の可逆な符号である。形式の正準シリアライズは単射なので、いずれかの状態、イベント、遷移が異なる二つの形式は異なる形状ハッシュをもち、シリアライズを復号すると同じ形式が戻る。ターゲットへの各射影は形式だけの関数である。双方向変換は往復を精密にする。Foster、Greenwald、Moore、Pierce、Schmitt はレンズを、ビューとそのソースを一致させる往復条件をもつ get と put の関数の対として定義し [122]、Hofmann、Pierce、Wagner はその条件を対称レンズへ拡張し [123]、Czarnecki らはモデル工学、データベース、プログラミング言語にわたる同じ整合性条件を概観している [124]。RCE の往復条件は、プログラム全体の水準での GetPut 条件である。射影を持ち上げ直しても、形状ハッシュは変わらない。

**構成による正しさ。** Dijkstra は 1968 年に、プログラムとその証明を一緒に開発し、正しさをテストで確かめるのではなく設計に組み込むことを提案した [125]。Hall と Chapman はこの方法を、各段階に形式仕様と詳細化をもつ商用のセキュアシステムに持ち込んだ [126]。型付き関数型プログラミングに関する Minsky の規則、不正な状態を表現不能にせよ、は型の水準で同じことを述べている。悪い値を保持できない型は、その値の検査を不要にする [127]。Turner の全域関数型プログラミングは、すべての関数がすべての入力で停止することを求め、プログラムが隠れた失敗をもたない数学的関数を表すようにする [128]。RCE の形式は Turner の意味で全域であり、その契約型は Minsky の意味で宣言されていない状態を表現不能にし、[§2.1](#21-programming-is-coding-theory) の詳細化の連鎖は Dijkstra の意味でそこに行き着く。その帰結は [§1](#1-thesis) で述べたとおりである。誤りは入口で拒否されるので、事後に差分を取ったり追跡したりするものは何も残らない。

**普遍性テーゼ。** 理論の言葉で述べれば、テーゼは一つの普遍的な形式がある、ということである。プログラムはその中でネイティブに書かれ、既存のすべての言語はそこから忠実な射影として到達でき、既存のすべてのプログラムは持ち上げによってそこに入る。Gurevich のテーゼが根拠を与える。すべての逐次アルゴリズムは、それ自身の抽象度で、抽象状態機械によって一歩ずつ捉えられ [2]、並列アルゴリズムも同様である [3]。形式は、データベース状態の上のそのような機械である。

**命題 U1（捕捉）。** 言語 $L$ のプログラムが Gurevich の意味での逐次または並列アルゴリズムであるならば、そのプログラムの抽象度でそれを一歩ずつ模倣する遷移をもつ形式が存在する [2, 3]。

**命題 U2（忠実な射影）。** 形式の $L$ への射影 $\pi_L$ が契約内のすべての入力で形式のトレースを保存するならば、トレースのあらゆる観測者にとって形式とその射影は交換可能であり、$L$ は形式に欠けているものを何も付け加えない。

**命題 U3（構成による持ち上げ）。** 使われているすべてのプログラミング言語は、形式文法、具象構文木を生成するパーサ、抽象構文木、そして仕様または参照実装によって定まる意味論をもつ。持ち上げ $\lambda_L$ は言語ごとに三段階で構築される。文法、次に抽象構文木、次に形式であり、$L$ の各構成要素は $L$ の意味論に従って形式のルールを与えられる。このように構築された持ち上げは、振る舞いについて $\pi_L(\lambda_L(p)) \equiv p$ を、形状ハッシュについて $\lambda_L(\pi_L(F)) = F$ を満たすので、この対は [122] の意味でのレンズであり、$L$ のプログラムは損失なく形式として保持される。

**命題 U4（置き換え）。** 言語 $L$ について U2 と U3 が成り立つならば、どのプログラムも $L$ で書く必要はない。プログラムは形式として一度書かれ、プラットフォームが求める場所で $L$ として出力される。

U1 は定理である。U2 はターゲットごとに差分テストで検査され（[§5.1](#51-differential-testing-across-five-targets)）、[§2.3](#23-the-ecosystem-at-large-n) では大きな N で検査される。U3 は構成であり、言語ごとに文法から積み上げて構築される。[§8.7](#87-lift-coverage-across-languages) は、構築しながらその構成をどう測るかを述べる。

## 4. エンジン：ギア、ゲート、レシート

### 4.1 エンジンは形式である

RCE はソフトウェアを小さな決定的ハンドラのグラフとして実行する。決定できないハンドラはエスカレーションを発する。リゾルバがそのエスカレーションに一度答え、その答えは恒久的なハンドラとしてインストールされるので、同じ形の次のケースはリゾルバなしで実行される。エンジンは形式のすべての不変条件を満たし、各条件は `tests/form_laws.rs` の名前付きテストで検査される。

| 不変条件 | エンジンが行うこと |
|---|---|
| 再読み込みは検証済みの畳み込みである | 再読み込みはログをそのまま読み、すべてのハッシュとリンクを再計算し、残りを $\delta$ で畳み込む。何も打刻し直さない。壊れた連鎖は読み込みを拒否する。 |
| 名前に依らない刻み順序 | ハンドラはトポロジカル順位の順に、次いで名前に依らないノードキーの順に実行される。出力はステージングされ、ASM 意味論と同様に、すべてのハンドラの実行後に配送される。すべてのノードの名前を変えても、各エントリで同じ匿名状態ハッシュが得られる。 |
| 黙った破棄をしない | 満杯のメールボックスはメッセージを順序付きキューに保持し、`Backpressure` を記録する。容量1でタスク10件の場合、`Backpressure` エントリが9件記録され、10件すべてのタスクが閉じる。 |
| ペイロードはログにある | 入力、刻み、外部ハンドラの結果、インストール、障害はログエントリである。1,000 個のランダムなログにおいて、各エントリ後の状態ハッシュは空のエンジンからの畳み込みと一致する。 |
| 論理クロック | 活性は壁時計ではなく刻みを数える。 |
| 安定したハッシュ | エントリ、状態、形状、規則 ID について、すべての深さでキーを整列した正準 JSON 上の SHA-256（Secure Hash Algorithm、256 ビット）。 |

### 4.2 ギア

各ギアは、その下のギアがゲートを通過しないときにのみ試される。その順序は一つの固定カスケードである。

| ギア | 方法 | 系譜 |
|---|---|---|
| G0 ルックアップ | SHA-256 形状ハッシュをキーとする共有ハンドラライブラリ。コード修復では順位づけられた関数への局所化 | コード検索と取り出し [21] |
| G1 規則 | 決定的なガード付き修復テンプレートとスキーマ由来の検証器。それぞれ変異感度を検査済み | PAR、TBar、AVATAR、FixMiner [22, 23, 24, 25]；Coccinelle のようなコードモッド [26] |
| G2 合成 | ハンドラ文法上の列挙、ソルバ、e-graph | スケッチング、SyGuS、egg [27, 9, 12] |
| G3 から G5 モデル | 型付き決定モデル、ローカルの小型モデル、最後にリモートモデル | モデルカスケード [28] |

### 4.3 ゲート

候補はゲートを通過したときにのみ昇格される。ゲートはノードの記録された入力を再生し、カバレッジ境界（宣言された誤差予算における3の規則）の下で新しい標本に対して候補をシャドー実行し、出力スキーマを検査し、第5節の証明の証明書を要求する。却下された候補は反例とともに記録される。

### 4.4 レシート

すべての昇格、拒否、延期、インストールは、SHA-256 で連鎖した追記専用ログの中の変更であり、過去のどのエントリを改ざんしても連鎖が壊れる [29, 30]。各ハンドラのコストは、flowG のネイティブコードバックエンドである FGIR のホストコスト表を用いてインタプリタの演算回数から価格づけられ、`est_j` とラベル付けされる。各フォアマン呼び出しはそのレシートを伴う。ラダーの実行では部分標本にパッケージのエネルギーカウンタを追加し、`reported_j` とラベル付けする。

### 4.5 形式コンパイラ

`rce form` は仕様とその適合を受け取り、一つの Form IR から五つのターゲットを出力する。

```
.rce spec + fit
  lower ─► normalize ─► egg e-graph, equality saturation (+ admitted proposals)
  ─► extract (cost = est_j) ─► Form IR (typed relations, regions, rules with SHA-256 ids)
     ├─ Rust crate (pure step, typed state, SHA-256 log and fold, tests)
     │  └─ WASM (the same crate on wasm32-wasip1)
     ├─ Python (standard library only)
     ├─ XState v5 machine
     └─ SCXML document, executed by SCION
```

IR はすべての数値の端で一つの振る舞いを固定する。検査付き64ビット整数のオーバーフローはエラーであり、決して折り返さない。整数の `/` はゼロ方向に切り捨てる（$-7/2 = -3$）。`%` は被除数の符号をとる（$-3 \bmod 2 = -1$）。ゼロ除算はエラーである。浮動小数点数は IEEE 754 binary64 であり、非有限の結果はエラーである。null と不在は区別される。時間は論理クロックのみである。すべてのターゲットは生成される。手で書かれたものは一つもない。

プロセス、HTTP、クロージャのハンドラは項をもたないので、記録されたその結果は、正準入力の SHA-256 をキーとする記録済みオラクルにコンパイルされる。`rce scan DIR --form` は既存の Rust、Python、TypeScript、Go を形式のスキーマへ持ち上げ、持ち上げられた各要素は構文的な持ち上げとしてラベル付けされる。

### 4.6 方法：スタック全体を評価し、すべてのインターフェース仮定を明示する

プログラムは階層のスタックである。トークンと文。ハンドラ。形式、すなわち型付き関係、制御領域、時計からなるデータベース状態の上の単一のステップ関数 δ。各イベントを、それが生んだ状態のハッシュとともに記録するログ。形式を変換する書き換え。そしてそれを実行する基盤。各階層は下の階層についての仮定の上に立っている。RCE はどの階層も固定とはみなさない。スタック全体を評価し、各インターフェース仮定を検査可能な命題として書き下し、実行のたびにそれを検査する。

| 境界 | 仮定 | 検査 |
|---|---|---|
| ソースからハンドラへ | 入力はそのソース契約を満たす | δ の入力イベントでの契約検査 |
| ハンドラからシンクへ | すべての Ok 出力は出力スキーマを満たす | ハンドラ証明（verify::handler_proof）、Kani で検査されたカーネル評価器により全域的かつ決定的 |
| ログから状態へ | すべてのエントリは、それが生んだ状態のハッシュを持つ | カーネルの畳み込み。ハッシュが一致しない最初のエントリを拒否する（Kani ハーネス `fold_rejects_wrong_state`） |
| 書き換えから形式へ | 書き換えはすべての入力に対して出力を保つ | ランダム化検査、続いて Z3 による SMT 証明 |
| スタブから監督役へ | 決定できないハンドラは推測せずにエスカレーションする | スタブハンドラはエスカレーションを発し、解決は昇格経路を通じてのみ昇格される |
| 形式からターゲットへ | 出力されるすべてのターゲットは同じ δ を計算する | すべてのターゲットは同じ参照トレースを持つ |

検査が失敗すると、破綻はそれが起きた境界に特定される。修正はその階層で行われ、その境界の検査を通され、昇格される。修正された階層より上のすべての階層は、それ以上の変更なしにその修正を受け継ぐ。上の各階層は、修正された階層を、仮定がいまや検査されているインターフェースを通じてのみ利用するからである。修正が上へ伝わり、複利的に積み上がるというのはこの意味である。[RCE Playground](/playground/rce/) は、WebAssembly にコンパイルした RCE コアの上でこれをブラウザで実行する。その Interfaces レイヤーは各仮定を壊し、それを検出する検査を示し、Compounding レイヤーは修正が後のすべてのラウンドへ引き継がれる様子を示す。

### 5.2 Z3 で証明された書き換え

検証済みの書き換え規則には系譜がある。Ruler はループにモデルを置かず、等式飽和によって書き換え規則を推論し検査する [87]。したがって第5.5節で受理された、モデルが提案した16規則のうち3規則は、13規則を拒否したゲートについての言明であり、モデルが最良の規則源であるという主張ではない。

組み込みのすべての e-graph 書き換えは、Z3 SMT ソルバ（satisfiability modulo theories）[31] において、形式の項評価と算術の量化子なしの符号化に対して証明される。値はデータ型として、64ビットのビットベクトルは検査付きオーバーフローとして、符号付き除算と剰余は被除数の符号として、浮動小数点数は binary64 として表される。オーバーフロー、エスカレーション順序、またはメッセージを変える書き換えには証明が与えられない。提案された等価性は証明を伴う場合にのみ e-graph に入る。

### 5.3 カーネルの Kani による証明

エンジンのカーネル（ハッシュ連鎖、畳み込み、名前に依らない位置、ハンドラ評価）は Rust 向けの Kani モデル検査器で検査される [32]。ハンドラ評価は非再帰的な一歩の不動点であり、Kani はその一歩がコンストラクタごとに全域的かつ決定的であることを構造帰納法で証明する。10個のハーネスが検証され、505 個の検査のうち失敗は 0 である。

| ハーネス | 性質 |
|---|---|
| `chain_appended_verifies` | 追記されたハッシュ連鎖が検証される |
| `chain_detects_tampering` | 変更されたエントリが連鎖を壊す |
| `fold_equals_replay` | 畳み込みは再生に等しい |
| `fold_rejects_wrong_state` | 保存された状態と食い違う畳み込みは拒否される |

### 5.4 証明の証明書に基づく昇格ゲート

Kani の実行は証明書を書き出し、そのハッシュは `proofs/kani.cert` に保存される。エンジン、ログ、規則 ID、ハンドラ評価は証明済みカーネルを経由し、昇格には証明書が必要である。

### 5.5 検査の後ろに置かれた提案者としてのモデル

モデルは等価性を提案してよい。受理してはならない。デモ用仕様上で、ローカルの15億パラメータのコーディングモデル（llama.cpp 上の Qwen2.5-Coder-1.5B）を用いたところ、提案者は16個の等価性を提示した。検査はランダム試行と Z3 証明によって3個を受理し、13個を却下した。よく知られた87個の恒等式からなる決定的な提案者は9個が受理され、すべて構造的なものであり、算術の恒等式はいずれも障害順序、非数値、オーバーフローのために却下された。

### 5.6 既存コードとの一致

持ち上げは、Rust、Python、TypeScript、Go のフィクスチャから同じ注文機械を読み取り、元のコードを30呼び出しからなる40個のシード付き列で実行し、各言語で 1,200 呼び出しすべてについて一致する。どの結果よりも前に事前登録された凍結ベンチマークは、既存の三つの営業アウトリーチプログラムを形式として表し直した。形式は記録された 4,500 個の入力のうち 4,500 個で元のコードと一致し、抽出はそれぞれで `est_j` を下げる（例えば $1.69 \times 10^{-8}$ J から $1.49 \times 10^{-8}$ J へ）。

## 6. 持ち上げ：他の言語からエコシステムに入る

<div id="6-importing-legacy-code-from-other-languages" class="anchor-alias" aria-hidden="true"></div>

持ち上げは、他の場所で書かれたコードがエコシステムに入るための入口である。それは構成であり、どの言語もすでにもっている道具を使って言語ごとに作られる。すなわち、形式文法、構文木を生成する [tree-sitter](https://tree-sitter.github.io/tree-sitter/) のようなパーサ、抽象構文木、そして言語サーバーのツールが解決するシンボル（[Language Server Protocol](https://microsoft.github.io/language-server-protocol/)）である。`rce scan DIR --form` は Rust、Python、TypeScript、Go について、その木から形式を構築する（[§4.5](#45-the-form-compiler)、[§5.6](#56-brownfield-agreement)）。持ち上げられたプログラムはそのソースの障害を引き継ぐので、持ち上げには修復が含まれ、以下では位置を与えた公開バグコーパスで測定する。エコシステムの内部では、これらの障害は書くことができない。

率は意図ビットとして読める。L0 では欠けたビットのほとんどがその行の上にあり、事前分布で順序づけた単一トークン近傍が中央値 2.3 ビットでそれを供給する。ハンクのみの L1 行では、エンジンは7行のハンクしか見ない。ビットがハンクの中にあるカテゴリは閉じ（Java：演算子の変更 91%、真偽値リテラルの入れ替え 84%、引数の入れ替え 82%；Python：真偽値リテラルの変更 98.8%、引数の入れ替え 99.4%）、ビットがその外にあるカテゴリは開いたまま残る。メソッド名（22%）と識別子（37%）にはファイルとその型が必要であり、新しい連言（3% から 7%）と文全体の書き換え（Python、コーパスの34%を占めるカテゴリのうち 1.2%）は新しい意図である。新しい意図とは、供給者（仕様、テスト、人、またはローカルモデル）が一度だけ提供するものであり、その後その適合は索引に入る。

**方法。** 各コーパスは固定シードでシャッフルされる。各シャッフルの最初の 2,000 位置、および L0 については三つのリポジトリ全体（commons-lang、requests、flask）が開発用分割をなし、そこではギアを調整してよい。開発用の結果は報告しない。残りのすべてのタスクはテスト用分割に入る。テスト実行の前にエンジンはコミットされ、そのバイナリハッシュが記録され、実行中にギアは一切変わらない。本節のすべての行は、テストタスクのみに対する、モデル呼び出し 0 回の凍結エンジンの結果である。事前登録（`PREREG.json`）、タスクごとの行、報告スクリプトは[公開リポジトリ](https://github.com/openIE-dev/openie-research-experiments/tree/main/rce/bench/ladder/)にある。

**ゲート。** L0 と L1 では位置が与えられ、ゲートはトークン同一性である。修復された行または文は、開発者のものとトークン単位で等しくなければならない。これはテストに合格するより厳しい。パッチは弱いテストスイートに合格しても誤っていることがあるからである。Qi らは、GenProg が修正として報告したパッチの大半がもっともらしいが誤っていることを見出した [92]。テストへの過適合は探索ベースおよび意味ベースの修復で記録されており [93, 94]、生成テストによって対処されている [95]。ツールは調整に使ったベンチマークでより高い得点を出し [96]、障害局所化は比較を偏らせる [97]。トークン同一性はこれらの段におけるもっともらしさの隔たりを取り除き、位置を与えることは局所化の項を取り除くので、率は修復ギアのみを測る。L2 以上はテストをゲートとし、もっともらしい件数と正しい件数を別々に報告する（第8.1節）。

### 6.1 L0：1トークンの障害

L0 コーパスは、固定コミットにおける9つの実リポジトリ（Java 5、Python 4）で、有効な置換トークンをもつすべての PIT 型ミュータント [109] である。547,448 件中 520,821 件のテストタスクである。エンジン（コミット `65571d0`、ギア G0-T と G1-J）は 520,541 件を復元し、率は 0.9995（95% Wilson 区間 0.9994 から 0.9995）、探索ビットの中央値は 2.3 である。未解決の 280 件のうち、108 件は浮動小数点リテラル内の変異した数字であり、2 件は Python の集合リテラル内にある。浮動小数点リテラル用のギア（G0-F、コミット `ecfe5a1`）は、調整に一度も使っていない四つのリポジトリ（commons-text、commons-io、more-itertools、httpx）で試験された。23,015 件中 23,015 件、1.0000（0.9998 から 1.0000）、探索ビットの中央値 2.0 である。ミュータントは実際の1トークン障害の代用であり、Just らはそれが実際の障害と結びついていることを見出した [110]。

### 6.2 L1：実際の履歴からの1文バグ

L1 は、オープンソースの履歴から採掘された実際の単一文バグ修正の二つの公開データセットを用いる。ManySStuBs4J 2.0 [107] は 24,072 件の Java テストタスクを与え、エンジン（コミット `f2701b7`）は 9,288 件を解決し、率は 0.386（0.380 から 0.392）である。TSSB-3M v1.0.0 [108] はシャード14と15から 157,089 件の Python テストタスクを与え、同じエンジンは 27,266 件を解決し、率は 0.174（0.172 から 0.175）である。エンジンは7行のハンクのみを受け取るので、この Java の率はハンクのみの結果である。親コミット時点のファイル全体を与え、プロジェクトのメソッドとガード条件の索引、そしてメソッド名の変更、引数の追加、ガード条件、throws、修飾子のためのギアを加えると（コミット `62fb7a0`、バイナリの sha256 接頭辞 `3682c6515acdf722`、実行前に事前登録）、エンジンはファイルとバグのある文を特定できた 21,320 件の Java テストタスクのうち 13,586 件を解決し、率は 0.637（0.631 から 0.644）である。カテゴリ別では、演算子の変更（95.9%）、オペランドの変更（92.1%）、誤った呼び出し元（87.9%）、真偽値リテラルの入れ替え（88.4%）、引数の削除（85.1%）、引数の入れ替え（83.3%）を閉じる。メソッド名の変更は 61.4%、引数の追加は 51.4% に達し、新しい条件や狭められた条件（43.5% と 51.7%）が主要な未解決の意図として残る。層ごとの完全な表はリポジトリにある。これらのデータセットには、このゲート（ハンクのみ、トークン同一性、位置は既知）の下で公表された修復のリーダーボードがないので、学習型修復の数値は並べていない。リーダーボードをもつ Defects4J は、第8.1節で TBar と比較する。

すべての行は `est_j`、すなわち CPU 秒に 10 W を掛けた推定値を伴う。解決タスクあたり L0 で 0.40 J、新しいリポジトリで 0.13、ManySStuBs4J で 0.10、TSSB-3M で 0.27 である。部分標本は、Intel i9-13900H を搭載した Linux ノートパソコン（ホスト名 `jetson-hub`。NVIDIA Jetson ではない）上で、プロセッサのチップ上パッケージカウンタである RAPL [105] により読み取った。ハーネスは固定した4つの CPU 上で動作し、`reported_j` は Python ドライバを含む実行全体にわたるパッケージの差分から、直前に取った 10 s の標本によるアイドル電力に実行時間を掛けたものを引いた値である。継続的インテグレーションのランナーが稼働していたため、アイドルは 40 W から 44 W であり、不確かさは約 ±1 W に時間を掛けたもの、これらの合計で ±10 J である。

## 7. 再利用の証拠

再利用の軸における RCE の位置は、一つの工学的事実の上に立つ。コードはあらゆる規模で再利用されている。以下の各方法はそれを異なるやり方で測る。

| 方法 | 出典 | 知見 |
|---|---|---|
| ファイル水準のクローン写像 | DéjàVu, Lopes et al. 2017 [33] | フォークでない 450 万の GitHub プロジェクトにある 4 億 2,800 万ファイルのうち、一意なものは 8,500 万である。「GitHub 上のコードの70%は、以前に作られたファイルのクローンからなる。」JavaScript では、ファイルの6%が固有である。 |
| 行水準の冗長性 | Gabel and Su 2010 [34] | 4 億 2,000 万行に対して、約1行の粒度で「各プロジェクトの50%から100%が冗長である」。 |
| 統計的言語モデル | Hindle et al. 2012 [35] | コードは「非常に反復的であり、実際、自然言語以上にそうである」。 |
| コーパスの近似重複除去 | The Stack [36] | 近似重複除去により The Stack v1 の54.7%（6.4 TB から 2.9 TB）、v2 の52.4%（67.5 TB から 32.1 TB）が除かれる。 |
| アーカイブ全体の保存 | Software Heritage | 4 億 4,500 万の起源からの約 300 億のソースファイルが、それぞれバイトのハッシュによって一度だけ保存されている。 |
| 採掘された修正パターン | PAR, TBar [22, 23] | PAR は 60,000 を超える人間のパッチの中に「いくつかの共通の修正パターン」を見出した。TBar の15のパターンカテゴリは、学習なしで、標準パイプラインで Defects4J のバグ43件を正しく修正し、完全な障害局所化の下では 101 件中 74 件を修正する。 |
| 言語横断のタスク | Rosetta Code | 1,360 のタスク。それぞれ一つの概念が、既知の 1,009 言語の多くで実装されている。 |

各行はエンジンへの入力である。クローンと重複除去は適合がたいてい存在することを示し、それが G0 である。繰り返し現れる修正は、適合の大半がガード付き書き換えの小さなカタログであることを示し、それが G1 である。行水準の冗長性は G2 の探索空間を縮める。エコシステムは昇格したすべての適合でこれを測り（第2.3節）、持ち上げたコードでの修復ラダーは保留分割上の大規模な測定でこれを測る（第6節）。二つの注意が読み方を鋭くする。重複は除去しない限り取り出しとモデルの得点を水増しする [104]。またバグのある行は修正後の行より自然さが低い [45] ので、バグそのものはルックアップが最も予測しにくいケースである。G0 と G1 がキーにすべきは、バグのある行ではなく修正の形状である。これを大規模に行う規則採掘の系譜は、GenProg の生成と検証による探索 [88] と Prophet の学習された正しさモデル [89] から、Facebook の Getafix [90]、静的解析違反に対する Sorald のモデル不要の修復 [91] に至るまで、互いに素な履歴からテンプレートを導き、未見のケースでの適合率を報告する [98]。それが第8.4節の採用する基準である。

## 8. 次に来るものの測定プロトコル

各プロトコルは実行前に固定される。事前登録をコミットし、シードとソルバのコミットを記録し、すべての成果物を保存する。ゲートが第一、ジュールが第二、ラベルは常に付ける。

### 8.1 Defects4J

Defects4J は 854 件の有効な実際の Java バグを保持し、それぞれに再現テストがある [37]。

1. `defects4j checkout` を通じて、オフラインで 100 件のバグの部分集合上で開発する。保留結果のみを、実行前に凍結した互いに素な 288 件のバグの集合（`FROZEN-heldout-v1`）について報告する。
2. G0、次に G1、次に G2、最後にローカルモデルを実行する。各バグを閉じたギアを記録する。
3. ゲート：トリガとなるテストと全スイートが合格すること。もっともらしい件数と正しい件数を別々に報告する。正しいとは、レビューで開発者のパッチと等価であることを意味する。
4. 正しい修正あたりのモデル呼び出しと、正しい修正あたりのジュールを、ラベル付きで報告する。
5. 参照点：TBar の正しい修正43件と、完全な局所化の下での 101 件中 74 件。
6. 汚染検査：修正が G0 の索引にそのまま現れるすべてのバグに印を付け、印付きのバグを含む場合と除く場合で報告する。

### 8.2 SWE-bench Lite、オフライン

SWE-bench Lite は、隠しテストで解決される実際の GitHub イシューの 300 タスクの部分集合である [38]。

1. ネットワークなしで公式の Docker ハーネスを用いる。
2. 第一の実行：G0 と G1 のみ、モデル呼び出しゼロ。これがモデルなしで解く床である。
3. 第二の実行：最後のギアとしてローカルモデルを加える。
4. 解決率、解決タスクあたりのモデル呼び出し、解決タスクあたりのジュールを、ラベル付きで報告する。
5. 汚染検査は 8.1 と同様。SWE-Bench+ は、成功したパッチの32.67%でイシュー本文に解答が含まれていたことを見出した [39]。

### 8.3 壁面電力計

1. ホストの電源に壁面電力計またはシャント計を取り付け、明示した速度で記録し、その時計を実行ログと同期させる。
2. アイドル状態の機械：CI ランナーと他のビルドを停止し、各ブロックの前に静穏期間のゲートを検査して記録する。
3. 測定したアイドル基準値を差し引き、その方法を明示する。
4. `measured_j` は電力計のみから埋める。`reported_j`（RAPL）と `est_j` を別々の列で横に並べて報告する。ラベルをまたいで合計してはならない。
5. 第6.3節の RAPL 部分標本を電力計の下で繰り返し、次いで Defects4J の保留セットを測る。

### 8.4 ギアを凍結した保留実行

これは第6節の方法を新しいコーパスに拡張したものである。

1. G0、G1、G2 をタグ付きコミットで凍結し、バイナリハッシュを記録し、規則集合をその作成時刻とともに公開する。
2. 互いに素な保留スライスを抽出する。Multi-SWE-bench [102] と BugsInPy [103] の Rust と Python のインスタンスを、G0 の索引に対して重複除去したもの [104]。
3. 最初の実行の前に、スライス、シード、仮説を事前登録する。
4. 解決、もっともらしい、バイト同一の件数を、それぞれ 95% 区間とともに別々に報告する。

### 8.5 同じ表に置くベースライン

1. モデル不要：`cargo fix` と clippy [106]、および Sorald または TBar の移植 [91]。
2. 安価なモデル：ローカルモデルを用いた Agentless [99]。
3. リモートモデル：フロンティアモデルを用いたエージェント。そのエネルギーは提供者の開示から推定し、`est_j` とラベル付けする。
4. すべての行について、Kapoor らが求めるようにコストを統制したうえで [100]、cost-of-pass [101] をジュールとドルで報告する。

### 8.6 大きな N におけるモデル呼び出しの収束

昇格は、モデルがループから去る仕組みである。リゾルバは新しいケースに一度だけ支払われ、ゲートはその適合をハンドラとして受理し、同じ形の以後のケースはすべて G0 または G1 で閉じる（[第4.2節](#42-the-gears)）。収束とは、固定された仕様の上で実トラフィックの下、ラウンドあたりのモデル呼び出しがゼロに落ちるという主張である。それは次のように測定する。

1. 公開リポジトリから言語と規模で層別して少なくとも 1,000 の仕様を抽出し、最初のラウンドの前にエンジンとリゾルバを凍結する。
2. 記録された本番トラフィックを、仕様ごとに少なくとも 10,000 イベント、固定サイズのラウンドで再生する。
3. ラウンドごとに記録する：新しいエスカレーション、モデル呼び出し、昇格、延期、閉じたタスクあたりのジュール。それぞれラベル付き（`est_j`、`reported_j`、`measured_j`）。
4. 主要評価項目：20 ラウンド以内にモデル呼び出しゼロのラウンドに到達する仕様の割合と、その 95% Wilson 区間。副次評価項目：ラウンドごとの閉じたタスクあたりのモデル呼び出し、および最後のモデル呼び出しのラウンド。
5. 収束しない仕様をその原因（行き詰まった入力、欠けた依存関係、新しい意図）とともに報告し、行き詰まった入力の延期を事前登録された群として実行する。

**命題8（床への接近）。** G0 と G1 のカバレッジが増えるにつれ、解決タスクあたりのジュールは、既知の修正を適用してテストを実行するという金の床に近づく。壁面電力計の下でのラダーの段と Defects4J の保留セットがこれを検証する。

### 8.7 言語をまたぐ持ち上げのカバレッジ

<div id="87-coverage-of-real-programs-across-languages" class="anchor-alias" aria-hidden="true"></div>

持ち上げは構築しながら測定する。言語 $L$ について、$\pi_L(\lambda_L(p))$ がそのプログラム自身のテストに合格し、記録されたトレースをバイト単位で再生し、かつ $\lambda_L(\pi_L(\lambda_L(p)))$ が $\lambda_L(p)$ と同じ形状ハッシュをもつとき、そのプログラムは持ち上げ済みと数える。標本は少なくとも十の言語について言語ごとに少なくとも 10,000 個のプログラムであり、固定されたシードで、版を固定した公開コーパスから抽出する。各実行の前に持ち上げ器を凍結してそのバイナリハッシュを記録し、モデル呼び出しは 0 回とする。各実行は持ち上げ済みの割合を Wilson 95% 区間とともに報告し、まだ持ち上げられていない各構成要素は、その言語の持ち上げ器に対する作業項目となり、次の実行の前に構築されて凍結される。目標は、すべての言語のすべてのプログラムである。

## 11. 結論

RCE はネイティブなコード・エコシステムである。プログラムは意図から一度だけ、形式として書かれる。形式は状態、イベント、純粋な遷移の可逆な符号化であり、すべてのターゲット言語はその忠実な射影である。不正な状態は書くことができず、不正な入力は入口で拒否されるので、エコシステム内のプログラムはその意図からずれることがなく、事後の差分比較もエラー追跡も必要としない。ゲートを通過したすべての適合は保存されて再利用され、エコシステムは正しさが単調であるゲートのもとで複利的に積み上がる。事前登録された 10,000 個の形式について、エンジンを凍結しモデル呼び出し 0 回で、すべての形式は往復して同一のバイトに戻り、すべての射影は決定的であり、すべての不正な入力と仕様は入口で拒否され、Python 射影は 9,999 個で参照トレースを再生する。他の言語のコードは持ち上げによって入る。それは各言語の文法からその構文木を経て形式へ至る構成である。持ち上げたコードでは、修復ギアが 520,821 件の1トークン障害の 99.95% と、21,320 件の単一文 Java バグの 63.7% を復元する。第3.6節と第8.7節が普遍性の命題と、その構成をどう測るかを述べる。
