## Abstract

This paper describes the Reality Code Engine (RCE), a system in which a program is written once as a state machine, called a Form, and code in other languages is generated from it. It presents the written specification of the language, the reference checker that implements it and emits Rust, Python, JavaScript and Scala, the Lean proofs of its theorems, registered measurements of the dimension of its programs, and the design of the engine that finds, checks and reuses solutions. It states how the claims could be shown false and the protocols of the measurements still to be made.

**In plain words**

1. A program is written once, in one precise form, and the computer produces the same program in many languages from it.
2. Everything a program can do is declared in its form, and the language requires every input to have a declared outcome, a step or a recorded refusal, rather than an undefined one that is found and fixed later.
3. In the design of the engine, a fix that passes the checks is saved and reused, so that the same problem does not cost time or energy twice.

## 1. Thesis

Autonomous computer automation is a design space with many points in it. Every approach sits somewhere along five continuous axes: the energy spent per correct result; the entropy the system must resolve at run time, and with it how deterministic its output is; the strength of the verification that accepts a result; how far each accepted result is reused and compounds; and how much the approach relies on a model. A large language model (LLM), a statistical text model, that writes each change from the prompt sits near one corner of that space: it relies on the model for every task, draws a fresh sample from a high-entropy distribution each time, and pays for generation again on every task. Retrieval, rules, synthesis, verification and caching occupy many other points, and real systems combine them.

The Reality Code Engine (RCE) is one point in the space. This paper describes it, and the measurements it reports are of its language and the language's tools. RCE models a program as a database functional state machine. Lopes and colleagues measured that about 70% of the code on GitHub consists of clones of earlier files [33], so RCE first tries to retrieve an existing fit, adapt it and check it, and calls a model only when nothing cheaper closes the task.

**The core claim.** RCE is a complete code ecosystem in which programs are authored natively from intent. Intent is written once, as a Form: a state, a set of events and a pure, total transition. The Form is a lossless encoding of that intent. Every target language is a projection of the Form, and each projection must replay the Form's trace byte for byte; the reference checker emits Rust, Python, JavaScript and Scala today. Every state a program can be in is declared in its Form, and the language requires every input to have a declared outcome: a step that takes it, or a refusal by its contract that leaves the state unchanged and is recorded in the log (T8). A program that meets these requirements cannot drift from its intent the way a program in a common language drifts from its comments, its tests or its other implementations, and it needs no after-the-fact diffing or error tracking. The input contract that makes the reference checker meet the second requirement at entry is listed in [§10](#10-work-to-finish). In the engine's design, every fit that passes the gate is stored and reused, so the ecosystem compounds as it grows ([§2.4](#24-gated-verified-recursive-self-improvement)). Code written in other languages is one door in: it enters by lift ([§6](#6-lift-entering-the-ecosystem-from-other-languages)).

Every point in the space faces the same gate. The gate is correctness: a task's completeness predicate $C(z)$, here the task's tests, a proof or an agreement trace. Among runs that pass the gate, systems are ranked by joules to completion, $J^*$. Correctness is a constraint, not a score.

In the engine's design, RCE's mechanisms, called gears, run in order of cost, and the first gear whose candidate passes the gate closes the task.

Energy figures are labeled by source. `est_j` is an analytical estimate. `reported_j` is an operating-system or on-chip counter. `measured_j` is reserved for a wall meter and is empty in every result here.

**Intent is high entropy.** "Make the checkout faster" carries many meanings: shorter page load, fewer steps, faster card approval, a cached cart, or faster on one device class. Context is implied and never written. Shannon measured printed English at about 0.6 to 1.3 bits per letter [1]. The letters are predictable. The meaning is not.

**Every conversion loses information.** Intent becomes a specification, and context is lost. The specification becomes one of hundreds of surface languages, and alternatives and edge cases are lost. The source becomes an intermediate representation (IR), and names, style and the author's reasons are lost. The IR becomes machine code, and types become sizes and loops become jumps.

**The floor is low entropy.** Every program ends as loads, stores, arithmetic and jumps. The destination has room for only a few shapes, so code bends toward them. Convergence is by design.

**Boundaries are where meaning diverges.** The same line gives different answers at the edges. In Python, `-3 % 2` is 1 and `-7 / 2` is -3.5. In C, `-3 % 2` is -1, `-7 / 2` is -3, and signed overflow is undefined. A system that regenerates code at every boundary guesses at every boundary.

**The axes, stated as quantities.**

| Axis | One end | Other end | Where RCE's design sits |
|---|---|---|---|
| Energy per correct result | Paid again in full on every task | Paid once per new case, then the handler floor | At the floor on covered tasks |
| Entropy resolved at run time, and determinism | The full distribution of the prompt, a fresh sample each time | Only the residual no stored fit covers, one deterministic output | The residual only; every projection deterministic |
| Verification strength | Output accepted on inspection | Tests, coverage and a proof certificate | The full gate on every result |
| Reuse and compounding | Each result used once | Each accepted fit stored and reused | Every fit that passes the gate is stored |
| Model reliance | A model on every task | No model | A model only as the last gear |

Approaches differ by degree on each axis, and the axes interact: reuse lowers energy and the entropy left to resolve, and strong verification is what makes reuse safe. RCE writes the meaning once, in one canonical Form. Every surface language is a projection of that Form, checked to match it. Among equivalent forms, the cheapest correct one runs.

### 2.1 Programming is coding theory

The thesis of this section is that programming can be read as coding theory. A programmer converts intent along a gradient between two entropic regimes. Intent is high entropy, a distribution over meanings. Code is low entropy, one deterministic transition per state. Every step of software work, from a requirement to a register, is a step of that conversion. The literature has said so in pieces for seventy years, in many languages. This section assembles the pieces into one argument and places each RCE gear on it.

**The measure.** Shannon defined the entropy of a source and the capacity of a channel [40], and measured printed English at about 0.6 to 1.3 bits per letter [1]. Kolmogorov, writing in Russian in *Problemy Peredachi Informatsii* in 1965, gave three approaches to the quantity of information and made the algorithmic one primary: the information in an object is the length of the shortest program that produces it [41]. Solomonoff had reached the same object as a theory of inductive inference [42], and Chaitin showed that program size obeys identities formally identical to Shannon's [43]. Rissanen turned the idea into a rule for choosing models, the minimum description length [44]. Together they say that a program is a code word: a description of a behavior, and the shortest correct one is the floor. RCE's extraction rule, keep the least-joule fit among equivalent fits (Proposition 3), is that rule with joules in place of bits.

**Code sits in the low-entropy regime, and people measured it.** Hindle, Barr, Su, Gabel and Devanbu found that code is "very repetitive, and in fact even more so than natural languages," at lower cross-entropy under the same n-gram models [35]. Gabel and Su found that most lines of a project already exist elsewhere [34], and Lopes et al. found that most files on GitHub are clones [33]. Tu, Su and Devanbu found that code is also local: what was written nearby predicts what comes next [46]. Ray and colleagues found that buggy lines are less natural, with higher entropy, and that the entropy falls when the bug is fixed [45]. In 2025 Yang, Kolak, Hellendoorn and Martins used the entropy change a patch induces to rank repair candidates and to separate correct patches from overfitting ones [51]. Allamanis, Barr, Devanbu and Sutton surveyed the field under the name naturalness [47]. The result is not only an English-language one. Prem Devanbu stated it as a keynote at the India Software Engineering Conference in 2013 [50]. Sridhara, Sinha and Mani at IBM Research India measured the natural-language artifacts around code at the same venue and found that commit messages are the most regular and Stack Overflow prose behaves like ordinary English [49]. In China, the *Journal of Software* (软件学报) published a review of code naturalness research in 2022, which states the cross-entropy measure and the finding that defective code has higher entropy [48]. In Japan, Doi, Higo, Arima, Shimonaka and Kusumoto at Osaka University used n-gram naturalness, first in a Japanese-language IEICE technical report and then at ICPC 2018, to tell machine-generated source files from human-written ones [73, 74]. Generated code sits even lower on the entropy scale than human code, because a generator is a fixed conversion. In Brazil, Arrebola's doctoral thesis built code suggestion on n-gram and topic models segmented by project and maintainer, and evaluated it by cross-entropy, the bits needed to encode the next token [75]. The two regimes are visible in one repository: the prose around the code is high entropy, and the code is low.

**The measure matters.** Febres, Jaffé and Gershenson, working from Venezuela and Mexico, compared English, Spanish and program text by vocabulary diversity per message length and found the program text more diverse [76]. Rahman, Palani and Rigby found that much of the n-gram predictability of code comes from syntax tokens, and that code is still repetitive, less than first reported, once those are removed, with API usage the most repetitive part [77]. Both results sharpen the claim rather than reverse it. Diversity of symbols is not predictability, and the low-entropy regime is a property of the conditional distribution of the next step, which is what a deterministic transition fixes. RCE's G0 keys on shapes, not on surface tokens, for that reason.

**Intent sits in the high-entropy regime.** Zave and Jackson showed that a requirement is a statement about the environment, a specification is a statement at the interface, and the gap between them is filled only by domain knowledge that is often unwritten [64]. Brooks split the difficulty of software into essence and accident: the essence is the conceptual construct, and most of it is specification and design, not representation [61]. Naur argued that a program is the visible part of a theory held by its programmers, and that the theory is not fully recoverable from the text [62]. Read through Shannon, all three say the same thing. Intent carries more uncertainty than any one program, and writing the program is the act that removes it. What remains in a programmer's head after the code is written is the part of the intent the code did not encode.

**The conversion is a refinement, and refinement is a narrowing.** Hoare gave programs a logic in which a program is correct relative to a pre- and postcondition [54]. Wirth taught stepwise refinement: decompose a task into instructions by successive decisions, each one fixing a choice the specification left open [53]. Dijkstra's guarded commands made the open choices explicit as nondeterminacy, and derived programs from specifications by removing it [52]. In Munich, Bauer and Wössner's CIP project built program development as a sequence of correctness-preserving transformations from specification to program [58]. In France, Abrial's B method and then Event-B carried refinement to industrial scale, with proof obligations at each step [55, 56]. In Finland, Back and von Wright gave refinement its lattice-theoretic calculus [57]. In each, a specification denotes a set of acceptable behaviors and each refinement step shrinks the set, until one deterministic behavior remains. That is entropy reduction with a proof at every step. RCE's Form is the last element of that chain: a total, deterministic transition $\delta$ over database states, with every choice resolved ([§3.2](#32-definitions)).

**Synthesis is search that narrows a hypothesis space.** Gulwani's FlashFill learns a string program from a few input-output examples by representing the set of all consistent programs and intersecting it with each new example [59]. Gulwani, Polozov and Singh frame program synthesis in general as search through a space of programs constrained by intent [60], and Solar-Lezama's sketching fills holes in a partial program with a solver [27]. Each example or constraint is a measurement that removes hypotheses. Shannon's measure counts how many such measurements are needed. RCE's G2 is that gear.

**What the conversion produces has one shape.** Gurevich proved that every sequential algorithm is captured by an Abstract State Machine at its own level of abstraction [2]. Codd made the state a relation [5], and event sourcing makes the state the fold of an append-only log [14]. Under Curry and Howard, a proof is a program and a proposition is a type [18, 72], so a verified fit is a proof of its specification. These are the reasons the low-entropy regime has few shapes: the destination is a state machine over a database, whatever the surface language.

**Low entropy decays without a gate.** Lehman observed over decades of large systems that a program in use must keep changing, and that its complexity grows unless work is done to reduce it [63]. Torres, Baltes, Treude and Wagner measured structural and textual entropy over the commit histories of 25 projects and found the two rise together [78]. Entropy flows back into code from the environment. A system that keeps code in the low-entropy regime needs a gate on every change, and RCE's gate is correctness ([§4.3](#43-the-gate)).

**Compilers already do source coding.** Franz and Kistler shipped programs as compressed abstract syntax trees and generated native code on load, which is source coding of a program over its own grammar [67]. Fraser inferred statistical models of code from a corpus to compress it [68]. Futamura showed in 1971, in the Japanese journal *Systems, Computers, Controls*, that specializing an interpreter to a program yields a compiled program, and that specializing the specializer yields a compiler [70]. Ershov in Novosibirsk developed the same idea as mixed computation [71]. The Cousots' abstract interpretation computes a sound, lower-information description of every behavior of a program [69]. The analogy to channel coding is this paper's reading, not a cited theorem: types, tests and proofs add checked redundancy so that a wrong program is detected before it runs, as a parity check detects a corrupted word.

**Erasure is where the joules go.** Landauer showed that a logically irreversible step, the erasure of one bit, dissipates at least $k_B T \ln 2$ [65]. Bennett showed that computation can in principle be made logically reversible, so the erasure, not the computation, carries the bound [66]. Converting high-entropy intent to one low-entropy program discards every alternative the intent allowed. That discard is an erasure of information about the alternatives, and it has a thermodynamic floor. RCE pays the discard once per new case and stores the result, so a repeat case erases nothing new.

**What the surface costs, measured.** The naturalness result has two corrections that this paper now carries, and a third finding that bears on the name-free Form. First, the raw entropy gap between code and prose shrinks substantially once syntax tokens are removed [77], and Casalnuovo, Lee, Morgan and Devanbu found that part of what remains is a familiarity effect: in top-starred Java and Python projects the original code had lower surprisal than meaning-preserving rewrites, and 50 human raters agreed with the language model's preference 61.9% of the time [132]. What reads as natural is what the reader has seen most, so a canonical Form moves the equilibrium of that loop rather than escaping it. Second, the only quantities that track measured comprehension load are textual size, vocabulary size and data-flow dependency reach: in the one study that tested code metrics against brain activation, those three correlated at Kendall τ ≈ 0.4 while McCabe cyclomatic complexity correlated with nothing (τ ≈ 0.09) [133]; across 121 readability metrics and 444 evaluations, no single metric reached |τ| > 0.16 with measured understandability [134]; and pretty-printed against disrupted layout showed no fMRI difference [135], consistent with the finding that formatting is 13 to 15% of the tokens of brace languages and can be stripped for ten language models with no significant change in accuracy [136]. Third, names are a low-agreement, high-dependency channel: two developers choose the same name with median probability 6.9% [137], comments co-evolve with the code they describe in 7 to 13% of cases [138], and yet frontier models lose 11 to 29 points of summarisation accuracy and up to 24 points of execution-prediction accuracy when identifiers are removed or replaced [139]. Humans, by contrast, do not process identifiers as language at the neural level: swapping English identifiers for Japanese changed the language-system response by Δβ = 0.03 [140]. The consequence for RCE is stated in [§3.8](#38-behaviour-equivalence-and-dimension): positions stay in the hash (T7) and names stay outside it, but the side table that holds them must carry the *concept* a name encodes, because the only authors that will matter read through names and the Form has not yet shown that a model can reason from a nameless one.

### 2.2 How RCE converts, and where each gear sits

Read as coding theory, a task arrives as a message whose remaining uncertainty is what no stored fit already resolves. Each gear removes uncertainty at a different price, and the gears are ordered by that price ([§4.2](#42-the-gears)).

| Gear | What it does to the uncertainty | Lineage in the argument above |
|---|---|---|
| G0 Lookup | Recognizes that the intent was already encoded; resolves it by retrieval, at the handler floor | Repetitiveness and clones [33, 34, 35]; localness [46] |
| G1 Rules | Applies a known guarded rewrite; resolves a recurring residual with no search | Correctness-preserving transformation [52, 58]; refinement with proof obligations [55, 56] |
| G2 Synthesis | Searches a hypothesis space and narrows it by examples, constraints and a solver | Program synthesis as search [27, 59, 60] |
| G3 to G5 Models | Samples from a learned distribution over code when no lower gear closes the gap; a proposer only | Cross-entropy models of code [35, 47] |
| Gate | Accepts a candidate only with tests, coverage and a proof certificate | Hoare logic [54]; Curry-Howard [18, 72] |
| Promotion | Stores the accepted fit, so the same residual costs G0 next time | Minimum description length [44]; Landauer erasure paid once [65] |

Positions on the axes of Section 2 differ in where the conversion is paid. An approach that samples the full distribution of the prompt on every task pays the high-entropy side again each time. An approach that stores and reuses accepted fits pays only for the residual, and only once. Most systems sit between those ends, and RCE sits at the reuse end.

### 2.3 The ecosystem at large N

The claim of [§1](#1-thesis) is to be tested directly, at large N, under the protocol below, registered before its run. A seeded generator writes at least 10,000 Forms, each a module of the language with one state region, one event with integer fields, and a step whose body is a random arithmetic term of bounded depth over a fixed set of operators. The reference checker and its emitters are frozen at a public commit before the run, and no model is called. The projections are the four program emitters of the reference checker: Rust, Python, JavaScript and Scala. Five properties are checked on every Form:

| Property | What is checked per Form |
|---|---|
| Lossless encoding | The Form's canonical JSON (`rce emit form`), decoded to source (`rce unform`) and encoded again, gives the same bytes |
| Deterministic projection | Two emits of one target give the same bytes |
| Faithful projection | Each emitted program (Rust, Python, JavaScript and Scala) prints the reference trace byte for byte on seeded events |
| Gate at entry, inputs | Malformed payloads (a wrong type, a missing field, an extra field, a nested value) and undeclared events are all refused, with the state unchanged and the refusal recorded |
| Gate at entry, specifications | A module that uses a name it does not declare is refused before emit (W-NAME-1) |

Section 9 states the observation that defeats the claim, RCE-F0: on a preregistered run of at least 10,000 Forms, any of the four projections prints a trace that differs from the Form's reference trace, or any malformed input is accepted. A target added to the emitters later enters the protocol only by a new registration. The generated Forms are small, so such a run measures the encoding, the projections and the gate. Lifted Forms from real programs are measured under the protocol of [§8.7](#87-lift-coverage-across-languages).

### 2.4 Gated, verified recursive self-improvement

Good (1965) [111] defined the ultraintelligent machine as one that could design better machines, so that improvement would recurse. Yudkowsky (2013) [113] cast the question as one of returns: whether each unit of improvement makes the next unit cheaper or dearer. Schmidhuber's Gödel machine (2007) [112] gave a formal answer with a guarantee: a program rewrites any part of itself, including its own search, only after proving that the rewrite improves its expected utility. Löb's theorem (1955) [114] is the obstacle a self-trusting prover meets, which Yudkowsky and Herreshoff (2013) [115] named the Löbian obstacle: a system cannot in general prove the soundness of a successor that uses its own proof system. Recent systems drop the proof requirement and select by measured score: STOP (Zelikman et al., 2023) [116] improves the scaffold that improves code, the Darwin Gödel Machine (Zhang et al., 2025) [117] keeps an archive of self-modified coding agents chosen by benchmark score, AlphaEvolve (Novikov et al., 2025) [118] evolves programs under automatic evaluators, and Voyager (Wang et al., 2023) [119] grows a library of verified skills that later tasks reuse.

RCE takes the structure of the Gödel machine and the library of Voyager, with two differences that avoid the obstacle for the objects it promotes. First, the object that improves is not the prover. In the design, RCE promotes handlers, rewrites and gears, and each is checked against a fixed kernel and a fixed proof rule: the properties the kernel is model-checked against ([§5.3](#53-model-checking-of-the-kernel)) and the encoding of the Form's arithmetic for a satisfiability modulo theories (SMT) solver ([§5.2](#52-the-proof-rule-for-rewrites)) never change through promotion, so no step needs to trust a successor's proof system. Second, the gate is a proof of correctness at the boundary, not a score. A score can rise while an interface assumption breaks; a proof at the boundary cannot be passed by a change that breaks it.

**Proposition R1 (monotone correctness).** If every promoted change passes the check of its boundary, and the checks of the other boundaries are unchanged, then every property established by those checks before the promotion still holds after it.

**Proposition R2 (compounding).** Let a workload be a multiset of tasks and let a promoted handler close every task of its shape. Then the number of escalations in round t is nonincreasing in t, and a correction promoted before round 1 lowers the cumulative escalations of every horizon by the escalations it closes in each later round.

**Proposition R3 (falling cost).** Since a promoted handler is executed in place of a model call, and its cost is the op count of the handler priced by the substrate table, the energy of a round falls toward the energy of the handlers alone as escalations fall toward zero.

Futamura's projections (1971, republished 1999) [120] and Turchin's supercompilation (1986) [121] give the limit of this process. Specializing an interpreter to a program yields a compiled program; specializing the specializer yields a compiler. RCE's promotions specialize the general escalation path to the shapes that actually occur, so the engine converges toward the residual program of its workload: the part of the computation that a model or a person must still supply. Recursive self-improvement under a gate is that convergence, made with checked steps.

## 3. The Form

### 3.1 The strongest formal statement of "same form"

The scope of the theorem is stated first. Gurevich's sequential postulates cover sequential algorithms; parallel and interactive algorithms need the further postulates of Blass and Gurevich [3]. Blass, Dershowitz and Gurevich argue that no single equivalence relation on algorithms fits every purpose [79], and Moschovakis and Vardi set out the debate over what an algorithm is [80, 81]. A web handler that does input and output sits outside the sequential theorem. The Form handles interaction the way the interactive line does: each input is an event in $E$, and the state machine steps on it. So "one Form" is a modelling choice grounded in the sequential theorem and extended by convention, with production precedents in the Elm architecture [83], durable workflow event histories [84] and stream semantics such as Flo [82]. The propositions of Section 3.4 are stated for that choice.


Gurevich's Abstract State Machine (ASM) theorem is the strongest formal statement that every algorithm has one shape [2]. An abstract state machine is a machine whose states are first-order structures and whose step is a finite set of guarded updates. Gurevich states three postulates. Sequential Time: an algorithm has states, initial states and a one-step map $\tau$. Abstract State: states are first-order structures over one fixed vocabulary, closed under isomorphism. Bounded Exploration: a finite set of terms decides each step. His Main Theorem (Theorem 6.13) reads: "For every sequential algorithm A, there exists an equivalent sequential abstract state machine B." Blass and Gurevich extend it to parallel algorithms [3]. Dershowitz and Gurevich add a fourth axiom, that initial operations are computable, and from it derive Church's thesis [4].

### 3.2 Definitions

**Definition 1 (the Form).** A program is a tuple

$$P = (S, E, \delta, D, \lambda)$$

- $S = \Sigma_c \times \Sigma_d$, the state space: structures over a fixed vocabulary $\Sigma$, split into control regions $\Sigma_c$ and data $\Sigma_d$. $\Sigma_d$ holds the logical clock, the input count and the typed relations (in the language, also the declared regions). Each state is a database instance in Codd's sense [5].
- $E$, the event alphabet, including the logical clock tick.
- $\delta : S \times E \to S \times O^*$, the transition: total, deterministic and pure, written as a finite set of guarded updates "if $\varphi$ then $f(\bar t) := t_0$", each step reading a bounded set of locations. It returns the next state and the outputs of the step. Write $\delta_1 = \pi_1 \circ \delta$ for its state component.
- $D$, the durable log: a sequence of entries $\{\mathit{seq}, \mathit{event}, \mathit{prev\_hash}, \mathit{state\_hash}, \mathit{hash}\}$, where $\mathit{state\_hash}$ is the SHA-256 of the canonical JSON of the state after the step, $\mathit{hash}$ is the SHA-256 of the canonical JSON of the first four fields, and the first $\mathit{prev\_hash}$ is 64 zeros. The log is a hash chain, so changing any past entry changes every later $\mathit{hash}$.
- $\lambda = \pi_2 \circ \delta : S \times E \to O^*$, the output map. A Mealy machine reads both arguments [6]; a Moore machine reads the state only [7].

**Definition 2 (Form and fit).** The *form* is the tuple shape with four invariants: $\delta$ is deterministic and pure; exploration is bounded; the vocabulary is fixed; state is the fold of the log,

$$\mathrm{state}(D) = \mathrm{foldl}(\delta_1, s_0, D).$$

A log may also carry each entry's outcome, outputs and state. These are derived: they are not hashed, and they must equal replay (T1 and T3 of [§3.7](#37-the-language-one-text-costs-and-theorem-status)). Two kinds of rejection are distinct. In the engine profile that Appendix D of the specification defines, every event is applied, and an input that fails its contract produces a `reject` output and an error row (D.6). In the language a refused event leaves the state unchanged (T8) and is recorded as refused.

The *fit* is the data that fills the shape: the vocabulary $\Sigma$, the alphabets $E$ and $O$, the rule program $\Pi$ that defines $\delta$, the output rules that define $\lambda$, and the initial data $s_0$. In Gurevich's terms the fit is the vocabulary, the ASM program and the initial structures. In Codd's terms $\Sigma$ is the schema and $s_0$ is the instance. In product-line terms a fit is a feature selection [8]. In syntax-guided synthesis (SyGuS) terms a fit is a term from a grammar that meets a specification [9].

**Definition 3 (fit equivalence).** Two fits are equivalent when, for every event sequence $L$, their output sequences under $\lambda$ are equal.

**Definition 4 (fit language).** A grammar whose terms denote fits. Programming languages, statechart documents in State Chart XML (SCXML), XState configurations and `.rce` specifications are fit languages. A fit language is complete when every ASM program over $\Sigma$ has a term in it.

**Definition 5 (control projection).** Split $\Sigma = \Sigma_c \cup \Sigma_d$ into finite control symbols and data relations. The statechart of $P$ is the projection of $\delta$ onto $\Sigma_c$: states are values of $\Sigma_c$, transitions carry an event and a guard over $\Sigma_d$, and actions are updates to $\Sigma_d$. Harel's statecharts give the hierarchy and the orthogonal regions [10].

**Definition 6 (fit e-graph).** For a fit $F$ and a set $R$ of sound rewrites, the fit e-graph $EG(F, R)$ is the saturated e-graph of $F$'s rule terms under $R$ [11, 12]. Each e-class holds fits equivalent by Definition 3.

**Definition 7 (joule cost).** $\mathrm{cost}_J(t)$ is the estimated energy (`est_j`) to run term $t$ once on a named substrate, weighted by the expected number of runs.

### 3.3 Why "database functional state machine"

A finite relational structure is a database instance, so a Gurevich state is a database and each step is a bounded transaction. *Database*: $S$ is a relational structure. *Functional*: $\delta$ and $\lambda$ are pure. *State machine*: runs are folds of $\delta$ over events. Moseley and Marks draw the same line in architecture [13]. Event sourcing draws it in application state: "Capture all changes to an application state as a sequence of events" [14]. Dedalus draws it in logic, where mutable state is a relation indexed by time [15].

### 3.4 Propositions

**Proposition 1 (the Form captures every sequential algorithm).** For every sequential algorithm $A$ there is a Form instance $P$ whose runs are the runs of $A$.

*Proof sketch.* Theorem 6.13 gives an ASM $B$ with the states, initial states and one-step map of $A$. Set $E = \{\varepsilon\}$, $\delta(s, \varepsilon) = \tau_B(s)$, $D = (s_0, \varepsilon^n)$ and $\lambda$ the identity. The fold after $n$ ticks is $\tau_A^n(s_0)$. By Gurevich's Corollary 3.3, $P$ and $A$ have the same runs. ∎

**Proposition 1b (interactive programs).** Extend $\Sigma$ with a nullary input symbol set to $e$ before each step; then $\delta(s, e) = \tau(s[\mathit{in} := e])$ is a sequential algorithm over the extended vocabulary, and Proposition 1 applies. The construction is ours.

**Proposition 1c (computability).** Under the Dershowitz and Gurevich axiom, every Form instance computes a Turing-computable function [4, 16, 17]. The Form adds no power. It gives every program in the class one shape.

**Proposition 1d (proofs are fits).** "For each proof of a given proposition, there is a program of the corresponding type" [18]. A type is a specification and a proof is a fit that meets it. The correctness gate is the existence of that proof or of a passing acceptance test.

**Proposition 2 (one generator).** One function $G : \mathrm{Fit} \to \mathrm{Program}$ generates a runnable program for every fit and reads no domain. *Basis:* every program is a Form instance, so $G$ emits a typed store, an event type, compiled rules, a log with a fold and an output dispatcher. Scaffolders such as Rails generators, JHipster and Yeoman are $G$ restricted to small fit languages. Product-line engineering starts from "the systematic discovery and exploitation of commonality across related software systems" [8]; the commonality is the Form.

**Proposition 3 (least-energy extraction).** Extraction with $\mathrm{cost}_J$ returns the least-joule term the extractor finds in the e-class of $F$. *Proof sketch.* The rewrites are sound, so every term in the e-class has $F$'s observable behavior and passes the same gate. Extraction minimizes the cost, and the cost is joules. ∎ This is Mixture of Limits applied to code. Mixture of Limits, Part II of the companion paper [Metered Commit Gates](/papers/gates/), states that a task needs a minimal expected energy to close and that energy spent after the task is complete buys no verified progress; applied to code, it says: keep the minimal fit that does the task, and the rest is waste.

**Proposition 4 (replay determinism).** If $\delta$ reads no wall clock, orders updates without names and logs every input, two replays of one $D$ give identical state hashes at every step.

**Proposition 5 (statechart projection is sound).** Project each state of a run onto $\Sigma_c$. The result is a run of the emitted statechart under the same events.

**Proposition 6 (coordination budget).** Rules tagged monotone run on replicas without coordination; only non-monotone rules need a coordination point. *Basis:* the CALM theorem, "the programs that have consistent, coordination-free distributed implementations are exactly the programs that can be expressed in monotonic logic" [19].

Appendix D.5 of the specification derives the tag from the rule, never from a declaration, and has the IR check of the engine profile refuse a Form whose stored tag differs from the derived one:

| Rule has | Tag | Reason |
|---|---|---|
| no resolve, read, join or scan | monotone | its writes only add keys and grow counters |
| a resolve | not monotone | it deletes escalation rows |
| a read of its own sink | not monotone | read, modify, write |
| a keyed join | not monotone | the joined row may be absent now and present later, or overwritten |
| a scan | not monotone | it observes the whole relation, including what is absent |

The tag is sound and not complete: a join against an insert-only relation would be monotone, but the profile does not prove that a relation is insert-only, so the tag does not claim it. A Form is coordination-free when every rule is monotone. Every read, join and scan sees the state at the event's entry, so the post-state of an input event does not depend on the order in which rules for different sinks run; only the output order does, and it is fixed by content hash.

**Proposition 7 (intelligence as a joule derivative).** Let $X$ count tasks through the gate and $J$ the joules spent. $\iota = dX/dJ$ is read in hindsight from $D$, which records every event, and, in the engine's design, from its receipts ([§4.4](#44-receipts)), each of which carries the `est_j` of one gear call. Extraction under $\mathrm{cost}_J$ holds the gate fixed and does not raise $J$, so at equal $X$ it does not lower $\iota$.

### 3.5 Graph, e-graph and statechart

| Structure | Part of the Form | What it decides |
|---|---|---|
| Statechart | Guards of $\delta$ over $\Sigma_c$ | Which transition fires |
| Dataflow graph | Read and write dependencies of $\delta$ and $\lambda$ (Kahn process networks [20]) | What runs, and in what order |
| E-graph | The equivalence class of the fit | Which equivalent fit runs |

The statechart and the graph describe one fit. The e-graph describes every fit equivalent to it. Extraction chooses among them by joules.

### 3.6 One ecosystem, lossless, and the universality thesis

**Lossless by construction.** Shannon's source coding theorem fixes the floor for a lossless code at the entropy of the source [40]. A Form is a lossless code for intent in a narrow sense that can be checked: the canonical serialization of the Form is injective, so two Forms that differ in any state, event or transition have different shape hashes, and decoding the serialization gives back the same Form. Each projection to a target is a function of the Form alone. Bidirectional transformations make the round trip precise. Foster, Greenwald, Moore, Pierce and Schmitt define a lens as a pair of get and put functions with round trip conditions that make a view and its source agree [122], Hofmann, Pierce and Wagner extend the conditions to symmetric lenses [123], and Czarnecki and colleagues survey the same consistency conditions across model engineering, databases and programming languages [124]. RCE's round trip condition is the GetPut condition at the level of the whole program: lift a projection back and the shape hash is unchanged.

**Correct by construction.** Dijkstra proposed in 1968 that a program and its proof be developed together, so that correctness is designed in rather than tested for [125]. Hall and Chapman carried the approach into a commercial secure system with formal specification and refinement at every step [126]. Minsky's rule for typed functional programming, make illegal states unrepresentable, says the same at the type level: a type that cannot hold a bad value removes the need to check for it [127]. Turner's total functional programming requires every function to terminate on every input, so that a program denotes a mathematical function with no hidden failure [128]. RCE's Form is total in Turner's sense, its contract types make undeclared states unrepresentable in Minsky's sense, and the refinement chain of [§2.1](#21-programming-is-coding-theory) ends in it in Dijkstra's sense. The consequence is the one stated in [§1](#1-thesis): what a program does is what its Form declares, so there is nothing to diff or track after the fact.

**The universality thesis.** Stated in theory terms, the thesis is that there is one universal Form. Programs are authored in it natively, every existing language is reachable from it as a faithful projection, and every existing program enters it by lift. Gurevich's thesis gives the ground: every sequential algorithm is captured, step for step, by an Abstract State Machine at its own level of abstraction [2], and parallel algorithms likewise [3]. A Form is such a machine over a database state.

**Proposition U1 (capture).** If a program in language $L$ is a sequential or parallel algorithm in Gurevich's sense, then there is a Form whose transition simulates it step for step at the program's level of abstraction [2, 3].

**Proposition U2 (faithful projection).** If the projection $\pi_L$ of a Form to $L$ preserves the Form's trace on every input in the contract, then the Form and its projection are interchangeable for every observer of the trace, and $L$ adds nothing the Form lacks.

**Proposition U3 (lift by construction).** Every programming language in use has a formal grammar, a parser that yields a concrete syntax tree, an abstract syntax tree and a semantics fixed by its specification or reference implementation. A lift $\lambda_L$ is built per language in three stages: the grammar, then the abstract syntax tree, then the Form, with each construct of $L$ given its Form rule by the semantics of $L$. A lift so built satisfies $\pi_L(\lambda_L(p)) \equiv p$ on behavior and $\lambda_L(\pi_L(F)) = F$ on shape hash, so the pair is a lens in the sense of [122], and a program in $L$ is held as a Form with no loss.

**Proposition U4 (replacement).** If U2 and U3 hold for language $L$, then no program needs to be written in $L$: it is written once as a Form and emitted as $L$ where a platform requires it.

**Every language is a target and a source.** The Form places no bound on targets. A target language is a row of the emit registry (the proposal `spec/proposals/emit-targets.md` in the specification repository): one emitter over the Form IR, the intermediate representation of a Form's terms that Appendix D.7 of the specification defines, and one table per language fixing how that language keeps the numeric and text contract of specification 6.3, each row passing the same gate, the reference trace of every example program byte for byte (T9). The lift $\lambda_L$ is the reverse map, from the language's pinned grammar and a semantics table into the Form, so every language is both an output of the Form and an input to it. The reference checker emits Rust, Python, JavaScript and Scala today, and the registry's tiers list the systems, platform, dynamic and non-von-Neumann languages that follow, including the new entrants of 2024 to 2026 catalogued in [§3.7](#37-the-language-one-text-costs-and-theorem-status).

U1 is a theorem. U2 is checked per target by the tests of the program emitters ([§5.1](#51-differential-testing-of-the-program-emitters)) and is to be checked at large N under the protocol of [§2.3](#23-the-ecosystem-at-large-n). U3 is a construction, built language by language from the grammar up, and [§8.7](#87-lift-coverage-across-languages) states how the construction is measured as it is built.

**Two qualifications.** The lift of U3 is a construction, and its domain is smaller than the sentence above suggests. The Form requires that every program finishes (T2), so the lift from any Turing-complete language is at best a map from the terminating fragment of that language, and membership in that fragment is undecidable (Rice's theorem applied to a total target [141]). On the terminating fragment the lift is still not canonical: closure representation, which sub-terms become control states, and evaluation order are free choices, and the inverse exists only for programs in defunctionalized form [142, 143]. So $\lambda_L$ is a construction on the image of a partial map whose domain is undecidable, the lens round-trip conditions hold on that image, and "every existing program enters it by lift" is a statement about the fragment the construction reaches, measured as [§8.7](#87-lift-coverage-across-languages) measures it. The second qualification concerns the hash over which the injectivity claim is made. Specification 6.1 hashes the positional forms of the state and of the event (regions and fields as lists in declaration order, a variant by its index, an event by its index among the module's events); the stored entry keeps its readable `event` and `state`, and a trace repeats the hashed forms under `hashed` (trace format `rce-trace/2`). The Lean module `RCE/NameFree.lean` hashes De Bruijn keys, and `RCE/Positional.lean` models the positional embedding (records of declared types as field lists in declaration order, variants as index and fields, events by index, undeclared records by name) and proves it unchanged under any renaming that is injective and fixes undeclared names, which is what the nameless projection performs, so the state hash and the entire entry chain are unchanged for every hash function; the event index it hashes is by definition the declaration index of the De Bruijn model, so the two encodings agree on the component they share. The reference checker and the Python, JavaScript and Rust runtimes agree on the hashes, and a test checks that a program and its nameless projection have the same log hashes, as T7 states; at public commit `f2bd7222`, which adds `RCE/Positional.lean`, the audit passes at 5,052 theorems with standard axioms only. An earlier reference checker hashed the named canonical JSON, so its log hashes depended on names while the model's did not; the specification's register of proposals records that finding, the test that demonstrated it, and its resolution as an erratum under C.15 (the log entry is outside a program's meaning), with the trace fixtures, application goldens, 130 conformance pins and the standard library's feed vectors regenerated.

### 3.7 The language: one text, costs and theorem status

The RCE language is defined by a written specification ([/rce/spec/](/rce/spec/); source in the [rce repository](https://github.com/openIE-dev/rce)). There is one language, the text of the specification at one commit, and every module of a program is in it (specification 2.7). Sections 2 to 10 define the core; Appendix C defines concurrency (`par`, `for ... par`, `with budget`, workgroups, LVars, sessions and supervisors) and applies to every module; Appendix D defines the engine profile: the handler specs and fits of the engine's design. No declaration selects a dialect: a first-line `# rce-version:` comment is a release label that names the specification commit a module was written against, is ignored by the checker and is not hashed, and a construct the checker does not implement is refused as reserved, not implemented (W-RES-1, Appendix F.12). The language is in development and changes as the project learns: a form can be added, generalised or replaced, and the change and every program of the repository it touches move together in one commit, never as a per-module choice, so a program never depends on the version of another program or library: everything checked at one commit agrees with the specification at that commit.

**Why one text and no version selection.** The record on versioning supports this rule rather than the per-module selection that earlier drafts had. Dependency resolution with one version per package and arbitrary constraints is NP-complete, established for Linux distributions [176], restated in 2020 for every non-trivial component model [177] and proved independently for language package managers by reduction from 3-SAT [178]. A semantic version number does not carry the promise it makes: about one third of Maven Central releases over seven years introduced a breaking change, in minor and patch releases about as often as in major ones [179], a replication on 119,879 upgrades still found 20.1% of non-major releases breaking [180], and the Google engineering text concludes that semantic versioning is a lossy summary of the risk of adopting a change and keeps one version of everything in one repository [181]. Exposure is a property of the transitive graph: for more than 80% of the 35,863 Maven artifacts affected by the Log4j vulnerability the dependency was more than one level deep [182]. Where the record converges is on identity derived from content, so that two different things never share a name and variants coexist [183, 184], on change by accretion under names that are never reused [185], and on a direct proof that a change preserved behaviour rather than a number asserting it [186]; hardware design has run such a proof, equivalence checking, as the gate on every revision for two decades [187], and reproducible builds tie an artifact to its source by its hash [188]. The RCE design takes each of these as a rule: one text at one commit, definition hashes with a closed compatibility table (F.4.3), a manifest that pins by hash with no resolver (F.5.3), name-free log hashes (T7) and behaviour as the only sense of two programs being the same ([§3.8](#38-behaviour-equivalence-and-dimension)). The survey of 24 October 2026 that reads the record against these rules, with the gaps it lists (a whole-program hash, the equivalence check run as a gate on every change, provenance in emitted code), is in the data repository ([/data/](/data/#rce)) and its proposal is `spec/proposals/one-commit-change.md`.


**Budgets count work.** A `with budget` block charges each operation a fixed cost from the table of Appendix C.6.4 and traps with `budget` when the count runs out. The count is a proxy for work, not a measurement of time or energy; `est_j` is separate.

| Operation | Cost |
|---|---|
| call of a user function or a closure, $c_{call}$ | 4 |
| standard library method on receiver size $n$, first-argument size $k$ | $4 + w(m, n, k)$ |
| channel send or receive | 8 |
| `spawn` | 32 |
| one `par` branch or `for ... par` chunk | 16 |
| list or map literal, or comprehension, with $n$ results; `[x; n]` | $4 + n$ |
| index, slice, member access; unary operators; `and`, `or`; integer, bool and text operators and comparisons | 1 |
| float `+`, `-`, `*` | 2 |
| float `/`, `%` | 8 |

Sizes are the UTF-8 byte length of a text, the length of a list and the number of entries of a map; any other value has size 0. The method work $w$ is fixed by the method's complexity class in the reference evaluator: $n + k$ for the linear methods on text, lists and maps (maps are ordered association lists), $n \lceil \log_2 n \rceil$ for `sort` (0 when $n \le 1$), and 0 for the remaining methods. The calls that `map`, `filter` and `fold` make to their function argument are charged as calls in addition. The arithmetic saturates at the largest 128-bit integer, and $w$ never decreases when $n$ or $k$ grows. The reference evaluator and the emitted Rust, Python and JavaScript runtimes compute the same function, and a test checks that the budget trap falls on the same operation in all four.


**One cost rule.** The cost of a standard library method call is the one cost of the text, in every module and wherever the call is executed from (specification 2.7, C.15). The rule is lexical to the text, not to a module, so linking modules changes no cost; tests check it at module boundaries in both directions on the reference evaluator and on the emitted Rust, Python and JavaScript programs.

This is an observation that choices recur and where; it is not evidence that they are correct, and this paper makes no comparison of quality with those projects. The emit registry of the specification repository takes every entrant as a target and a source on the same terms as every other language.

### 3.8 Behaviour, equivalence and dimension

Definition 3 says two fits are equivalent when their output sequences agree on every event sequence. This section gives that definition a universal property, defines the dimension of a program as a computed number, and reports the registered measurements of it. The normative text is section 6.10 of the specification (draft 0.9, commit `45fc95c`), with theorems T57 to T61 and the command `rce dim`.

**Behaviour as a point in the final coalgebra.** Fix a program $P$ with state space $S$, event alphabet $E$ and $\delta : S \times E \to S \times O^*$, and write $\delta_1 = \pi_1 \circ \delta$ and $\lambda = \pi_2 \circ \delta$ as in Definition 1. The behaviour of a state $s$ is the function $\mathrm{beh}_P(s) : E^* \to (O^*)^*$ with $\mathrm{beh}_P(s)(\varepsilon) = \varepsilon$ and $\mathrm{beh}_P(s)(e \cdot w) = \lambda(s, e) \cdot \mathrm{beh}_P(\delta_1(s, e))(w)$: the per-step outputs along any event sequence. $(S, \langle \lambda, \delta_1 \rangle)$ is a coalgebra of the functor $F(X) = (O^* \times X)^E$; $F$ has a final coalgebra $\mathrm{Beh}$ whose carrier is the set of causal stream functions, and $\mathrm{beh}_P$ is the unique coalgebra morphism $S \to \mathrm{Beh}$ (Rutten [144], Theorem 2.3). Two fits are equivalent, $F \equiv G$, when $\mathrm{beh}_F(s_0^F) = \mathrm{beh}_G(s_0^G)$. This is Definition 3 restated; the new content is that $\equiv$ is equality in one object that every Form, in every fit language, maps into by the same construction. Behaviour space is not a manifold: it carries the prefix ultrametric $d(b_1, b_2) = 2^{-n}$, $n$ the length of the shortest distinguishing event sequence, under which it is complete and totally disconnected [145]. Trace agreement on every sequence of length at most $k$ therefore certifies $d \le 2^{-(k+1)}$: a ball around the behaviour, not the behaviour. That is what the differential tests of [§5.1](#51-differential-testing-of-the-program-emitters) establish, and it never enters a hash.

**Two proof methods.** A relation $R \subseteq S \times S$ is a bisimulation for $P$ when $s\,R\,t$ implies, for every $e$, $\lambda(s, e) = \lambda(t, e)$ and $\delta_1(s, e)\,R\,\delta_1(t, e)$. T58 states that $\mathrm{beh}_P(s) = \mathrm{beh}_P(t)$ if and only if some bisimulation relates $s$ and $t$: to show two fits equivalent, exhibit the relation; to show them different, exhibit a distinguishing sequence, which also gives the distance. T1 and T2 (totality and determinism) are exactly the completeness and determinism that make the minimal machine unique; an incompletely specified machine has no unique minimum [146].

**Dimension.** $\mathrm{reach}(P)$ is the set of states reachable from $s_0$; it is finite because $S$ is finite under the value and size limits of the specification (N9). The dimension of $P$ is

$$\dim(P) = |\{\mathrm{beh}_P(s) : s \in \mathrm{reach}(P)\}|,$$

the number of distinct behaviours $P$ can be in, which is the Nerode index of its minimal Mealy machine [147], computable for an explicit alphabet in $n \log n$ [148]. $\log_2 \dim(P)$ is the bits of state the behaviour needs; $\log_2 |\mathrm{reach}(P)| - \log_2 \dim(P)$ is the *redundancy* of the fit, the bits of state that change no future output. A control dimension $\dim_c(P) \le \dim(P)$ is defined on the projection that replaces every guard over $\Sigma_d$ by its predicate symbol, a symbolic finite automaton [149], and its minimal machine, numbered by a breadth-first traversal in the canonical event order, has a unique name-free string [150]; its SHA-256 over canonical JSON is `shape_ctl`, a third key beside the name-free term hash and the e-class key of Definition 6. Equality at any key implies equivalence; inequality implies nothing.

What is and is not a theorem here should be said plainly. $S$ and $E$ are finite by the value limits and astronomically large: $|S| \le 256^{\mathrm{VALUE\_LIMIT}}$ per field, so finiteness makes every behavioural question decidable and none of them tractable. The minimal machine is a canonical form for the finite-control projection, where symbolic-automata minimisation is unique up to predicate equivalence [149]; for fields that are only compared and copied, register automata give a Myhill–Nerode theorem [151]; the moment $\delta$ does integer arithmetic into state, the only canonical object is the term itself. "Every Form is a finite Mealy machine, and its minimal machine is its canonical form" is therefore true as stated for $\Sigma_c$ plus guard predicates and is not a computable claim for $\Sigma_d$. That is also the honest reading of Proposition 3: the least-joule extraction returns the least-joule term *the extractor finds*, and three distinct functions are defined on one e-class: the target-blind budget units of specification C.6, which place the budget trap on the same operation in every runtime and are never joules; `est_j`, which is per target ([§6.3](#63-energy)); and the hashed representative, chosen by tree cost with a canonical-JSON tie-break for reproducibility. The emitted term and the hashed term of one e-class may differ; neither may differ across engines given the same log.

**Status of the theorems.** T57 (finality: $\mathrm{beh}_P$ is the unique coalgebra morphism), T58 (equivalence is bisimilarity), T59 (trace agreement to length $k$ bounds the distance by $2^{-(k+1)}$), T60 (for finite $S$ the quotient of $\mathrm{reach}(P)$ by the largest bisimulation is the minimal machine, with $\dim(P)$ states) and T61 (`shape_ctl` is invariant under renaming and under predicate-equivalent rewrites of guards) are stated in chapter 10 of the specification, and `spec/lean/RCE/Behaviour.lean` is in `lake build` (Lean 4.12.0; at public commit `f2bd7222`, `scripts/lean-audit.sh` reads 5,052 theorems with standard axioms only and no `sorry`). What is proved, in the chapter's exact scope: the morphism equation of T57 (`beh_cons`; uniqueness of the morphism is stated, unproved); T58 for one program and for two (`bisim_beh`, `beh_bisim`, `behEq_iff_bisim`, `bisim2_beh`, `beh_bisim2`); and T59 in both directions over an explicit finite alphabet, the declared events over the boundary sets that `rce dim` explores (`trace_ball`, `ball_trace`), with the statement over all of $E$ stated, unproved. T60 is stated, with a model proof by partition refinement as the next step. T61 is tested for renaming only, against the name-free projection `rce fmt --nameless`, which prints a program with positional names by kind in first-declaration order and is accepted whenever the source is, with the same trace hashes by T7; its invariance under guard rewrites is stated, unproved, and the symbolic quotient is not implemented.

**`rce equiv`: the equivalence check as a tool.** `rce equiv A B` explores two programs from their initial states over the same event instances, compares every step by its name-free output (emitted values in positional form, a refusal by its error's declaration index, T7), refines the two graphs together and reads whether the two initial states fall in one class (T58); when they do not it prints the shortest distinguishing event sequence and the two outputs at its end. `rce change OLD NEW` combines it with the export diff of F.4.3 and classifies a change as an erratum (every export compatible, every behaviour kept), a meaning change or an interface change, which is the rule of C.15 decided by the tool. Run between every corpus program and its name-free projection as a continuous-integration step, the check found one program whose projection was refused (a state field named like a standard library method had renamed the method); the projection was corrected and the sweep reports every corpus Form equivalent to its projection, as T7 states. It is the Form's version of the equivalence check that hardware design runs on every revision ([§3.7](#37-the-language-one-text-costs-and-theorem-status)): a change under which every program keeps its behaviour is an erratum, any other a meaning change, decided by the tool rather than by a version number. With `rce hash`, which prints a program hash over the name-free projection (one hash for a program and its renaming, a different one for a changed step), and the provenance line that every emitted file now carries, the three mechanisms the record calls rare in new languages (section 3.7) are commands of the reference checker.

**`rce dim`, and the registered runs.** `rce dim FILE [--fuel n] [--control]` explores $\mathrm{reach}(P)$ breadth-first over the declared events with payloads drawn from each field's refinement type or, without one, from the boundary set of specification 6.3, up to `--fuel` states, then runs Hopcroft partition refinement with the outputs as the initial partition (100,000 states in 10 to 40 s; the first Moore iteration was quadratic and did not finish), and reports states explored, behaviours (exact when the bound is not reached, else a lower bound), redundancy in bits per region, and with `--control` the control states and `shape_ctl`. Three examples were written with known values: a counter with an unread flag (1.00 bit of redundancy), a mod-6 counter that emits parity (1.58 bits), and a door with three reachable states and no redundancy. The preregistration (`openie-research-experiments/rce/bench/dimension/PREREG.json`, registered 22 October 2026 before the command had been built and amended before each later run, with a hashed sidecar) fixes the populations and three hypotheses about bounded programs whose explored steps emit or refuse: H0, that at least half of them carry more than 0.5 bit of redundancy; H1, that a program with one emit site carries more redundancy than a program with several; and H2, that one region carries at least 80% of the redundancy when it exceeds 1 bit. Its falsifier is RCE-F6 of [§9](#9-falsifiers), a median redundancy below 0.1 bit. The runs reported here, `dim-r2` to `dim-r5`, were each made once with `--fuel 100000 --control`, against a build of a public commit of openIE-dev/rce, with the binary hash recorded in every row; the first registered run, `dim-r1`, and the pilot before it are listed in [§10](#10-work-to-finish). The control label is the refusal or the emitted constructors only, and $\dim_c \le \dim$ holds on every row of these runs. In a state machine whose examples read state it never emits, the intent is carried by the examples and by no output; a report from `rce check` that names such an `example` (one that reads a field no step ever emits or refuses on) is an open proposal.

**The frozen runs.** The run `dim-r2` of 23 October 2026 (commit `1107442b` of openIE-dev/rce, registered as a second amendment of the same preregistration before the run, with the stratum read from the key that `rce dim` reported as `observable` at that commit, now `has_output`) samples the output-bearing stratum by rule: every program of the merged repository under its examples, programs, applications and book listings that is accepted standalone, has a state region and contains an emit or a fail statement. That is 25 programs, 24 of them output-bearing, 14 bounded within 100,000 states. Among them, `ring_buffer` has 12,500 reachable states, 781 behaviours and five control states; four bits of its state change no output, all in one region, and its control projection, which records only which steps fire, has five states. Excluding the three programs written for `rce dim` and their book copies leaves 8 bounded output-bearing programs, of which 6 carry more than 0.5 bit (Wilson 95% interval 0.41 to 0.93), with a median redundancy of 1.79 bits (interquartile range 0.25 to 3.37); over all 14, 10 of 14 (0.45 to 0.88) and a median of 1.29 bits. RCE-F6 (a median below 0.1 bit) is not triggered; the interval's lower end is below one half, so H0 is supported and not established at this size. H1 is not supported (the two single-emit-site programs carry 1.58 and 4.00 bits, the two multi-site programs 2.51 and 3.65), and H2 holds on 8 of 9 qualifying rows only because 8 have one state region; the one two-region program attributes 62% of its redundancy to its larger region. The run's substantive addition is three application-sized measurements. The chat application explores 100,000 states with 176 behaviours and 69 control states, so at least 9.15 bits of its state change no output, the largest redundancy measured and a lower bound; the selective forwarding unit (40,218 states, 7,038 behaviours, 2.51 bits) and the terminal (3,390 states, 270 behaviours, 3.65 bits) are exact. The ratio of control states to behaviours varies by an order of magnitude across the population (5 to 781 for the ring buffer, 69 to 176 for the chat, 5,095 to 7,038 for the forwarding unit), which measures how much of a program's behaviour is which steps fire against which values flow. The run also shows that the stratum needs a finer registered rule: the tool's flag is true for a program whose every output is the same (a constant, or a refusal every state gives), so a third run should register "output-bearing, with more than one distinct output" before sampling. Rows, intervals and the amendment are in the experiments repository under `rce/bench/dimension/` (`results/dim-r2.jsonl`, `RESULTS.md`). A third run, `dim-r3` (23 October 2026, registered before it), applied the finer rule the second run asked for: `rce dim` reports the number of distinct outputs (`distinct_outputs`; emitted values and refusals counted separately as `emits` and `refuses`), and the stratum is output-bearing with at least two of them. On 28 programs (the second run's population plus the three accepted programs with two or more state regions), 22 are strictly output-bearing and 12 of those are bounded; the median redundancy is 1.29 bits (8 of 12 above 0.5 bit, Wilson 0.39 to 0.86), and 2.05 bits over the 6 not written for the tool. The three programs the finer rule removed (a thermostat, a reconciler and a cart) are each observable only by a constant, so the second run's medians had counted bits that change an output which never changes at all. H2 is tested where it can be, on the one strictly output-bearing multi-region program above 1 bit, whose larger region carries 62%, below the 80% threshold; it stays open on one row. A fourth run over the 86 conformance programs with state (registered before it) measured the five harvested host-contract programs for the first time, all bounded within the fuel and carrying from 0.01 bit (the terminal driver) to 2.16 bits (the channel driver) with control quotients in the thousands, and answered the multi-region question for this corpus: the only strictly output-bearing multi-region programs are data-distinguished copies of one capability example, so H2 cannot be decided from existing public material and the next step is authoring observable multi-region programs, registered as a population before the run. That step was taken on 24 October 2026: twelve two-region programs (an elevator, a vending machine, a crossing, a car park, a printer, a lobby, a bank card, a washer, a session, a player, a climate controller and a reservoir) were written into the programs corpus and registered as the fifth run, with the disclosure that the tool had been run on the drafts. All twelve are strictly output-bearing, bounded and explored in milliseconds; eleven have zero redundancy and the twelfth, the climate controller, keeps 1.58 bits in two flags that record its last action and that nothing reads. The median is 0.00 bits, so RCE-F6 is triggered on this population: accidental state is not common in small Forms whose caps are enforced by refusals and whose phases emit. Read with the earlier runs (1.29 bits over the strictly output-bearing hand-written examples, 0.01 to 2.16 bits for the host programs, at least 9 bits for the chat application), the quantity grows with program size and with the number of fields nothing reads. The claim the data supports is the falsifier's own: `rce dim` is a diagnostic for larger programs and for regions added without an observer, not a property of small Forms in general.

**The concept record.** Specification 6.6 now describes an unhashed side table keyed by the name-free keys of a program and holding its names, intent strings and doc comments, and `rce emit form` prints it under `names`, keyed by declaration index (the index `shape_ctl` uses), after the hashed fields. Projections render it; $\delta$ never reads it; it is the complement that makes the projection of a Form a symmetric lens [123] rather than a retraction. The evidence of [§2.1](#21-programming-is-coding-theory) says the table must hold the concept a name stands for and not only its spelling, because word choice and ordering are the two steps developers disagree on at 6.9% [137] and the step they agree on is the concept. Whether a model can reason from the Form with the record attached as well as from a named surface is the first of the three registered experiments of [§12.3](#123-why-human-written-code-is-redundant) and is open.

## 4. The engine: gears, gate and receipts

This section describes the design of the engine, which Appendix D of the specification and its proposals define.

### 4.1 The engine is a Form

RCE runs software as a graph of small deterministic handlers. A handler that cannot decide raises an escalation. A resolver answers the escalation once, and the answer is installed as a permanent handler, so the next case of the same shape runs with no resolver. The design requires the engine to meet every Form invariant:

| Invariant | What the design requires of the engine |
|---|---|
| Reload is a verified fold | Reload reads the log verbatim, recomputes every hash and link, and folds the rest with $\delta$. Nothing is re-stamped. A broken chain refuses to load. |
| Name-free tick order | Handlers run in topological rank order, then by a name-free node key. Outputs are staged and delivered after all handlers run, as in ASM semantics. Renaming every node gives the same anonymous state hash at every entry. |
| No silent drop | A full mailbox holds the message in an ordered queue and logs `Backpressure`, and every task still closes. |
| Payloads are in the log | Inputs, ticks, external handler results, installs and faults are log entries. The state hash after every entry matches a fold from an empty engine. |
| Logical clock | Liveness counts ticks, not wall time. |
| Stable hashes | SHA-256 (Secure Hash Algorithm, 256-bit) over canonical JSON, keys sorted at every depth, for entries, states, shapes and rule ids. |

### 4.2 The gears

Each gear is tried only when the gear below it does not pass the gate. That order is one fixed cascade.

| Gear | Method | Lineage |
|---|---|---|
| G0 Lookup | A shared handler library keyed by SHA-256 shape hash; for code repair, localization to ranked functions | Code search and retrieval [21] |
| G1 Rules | Deterministic, guarded repair templates and schema-derived validators, each checked for mutation sensitivity | PAR, TBar, AVATAR, FixMiner [22, 23, 24, 25]; codemods such as Coccinelle [26] |
| G2 Synthesis | Enumeration over the handler grammar, solvers and e-graphs | Sketching, SyGuS, egg [27, 9, 12] |
| G3 to G5 Models | A typed decision model, a local small model, then a remote model, last | Model cascades [28] |

### 4.3 The gate

A candidate is promoted only when it passes the gate. The gate replays the node's recorded inputs, runs the candidate in shadow on fresh samples with a coverage bound (the rule of three at a declared error budget), checks the output schema, and requires the proof certificate of Section 5. A rejected candidate is logged with its counterexample.

Four gear boxes stacked from cheapest to costliest: G0 Lookup, a shared handler library keyed by SHA-256 shape hash; G1 Rules, guarded repair templates and schema-derived validators; G2 Synthesis, enumeration over the handler grammar, solvers and e-graphs; G3 to G5 Models, a typed decision model, a local small model and a remote model, marked as proposers only. Each gear sends its candidate to one gate with five checks: replay of recorded inputs, a shadow run with a coverage bound, an output schema check, the certificate of the kernel's model checking with Kani, a model checker for Rust, and for rewrites a randomized check then a proof by the Z3 SMT solver. ### 4.4 Receipts

Every promotion, refusal, deferral and install is a mutation in an append-only log chained with SHA-256, so tampering with any past entry breaks the chain [29, 30]. Each handler's cost is priced from interpreter operation counts with a per-host cost table and labeled `est_j`. The foreman is the engine's resolver of escalations, which runs the gears in order on each one, and each of its calls carries a receipt. A receipt names the gear, the method of the estimate (`basis`), the candidates tried and whether the gear resolved the escalation. Its `est_j` field is required: it is a finite non-negative number, or null, and null is allowed only when `basis` says `unpriced`, as for a model call with no energy figure. A receipt with the field missing does not parse. An unpriced cost is never read as zero, so a total over receipts reports its priced and unpriced invocations separately, and a saving that depends on an unpriced resolution is reported as unknown.

Bottom: a gear receipt with fields gear, gear_name, est_j, basis, candidates_tried and resolved, beside the rule that est_j is required and is either a finite non-negative number or null, with null allowed only when basis says unpriced; unpriced cost is never read as zero joules.](/figures/rce/receipt-chain.svg)

### 4.5 The compilers

The language's compiler is the reference checker's `rce emit TARGET FILE` (specification 10.5). It translates a module that passes `rce check` to one of five outputs: `form`, the Form $P = (S, E, \delta, D, \lambda)$ as one line of canonical JSON, a deterministic function of the program text; and four programs, `rust` (one Rust source file), `python` (one Python 3 file), `js` (one JavaScript module for Node) and `scala` (one Scala 3 file for the Java virtual machine). The program emitters translate the checked module, not the Form, and each output is self-contained. Every target is generated. None is authored.

Specification 6.3 fixes one behavior at every numeric edge, which every target must reproduce: checked integer arithmetic traps on overflow of the static type and never wraps; integer `/` truncates toward zero ($-7/2 = -3$); `%` takes the dividend's sign ($-3 \bmod 2 = -1$); division by zero traps; floats are IEEE 754 binary64, correctly rounded once per operator, and a non-finite result traps; time is the logical clock only.

In the engine's design a second compiler lowers a handler spec and its fit through an e-graph to a Form IR and projects it to further targets; its test is listed in [§10](#10-work-to-finish).

### 4.6 Method: the whole stack evaluated, every interface assumption explicit

A program is a stack of levels: tokens and statements; handlers; the Form, a single step function $\delta : S \times E \to S \times O^*$ over $S = \Sigma_c \times \Sigma_d$ (control regions; data: the clock, the input count and typed relations); the log, a SHA-256 hash chain whose entries record each event, the hash of the state it produced and the hash of the previous entry; the rewrites that transform the Form; and the substrate that executes it. Each level rests on assumptions about the level below. RCE does not treat any level as fixed. It evaluates the whole stack, writes each interface assumption down as a checkable statement, and checks it on every run.

| Boundary | Assumption | Check |
|---|---|---|
| source to handler | an input satisfies its source contract | the contract check at the input event of δ |
| handler to sink | every Ok output satisfies the output schema | handler proof: evaluation by the kernel evaluator, which the design requires to be total and deterministic and checks with a model checker ([§5.3](#53-model-checking-of-the-kernel)) |
| log to state | every entry carries the hash of the state it produced | kernel fold, which refuses the first entry whose hash does not match ([§5.3](#53-model-checking-of-the-kernel)) |
| rewrite to Form | a rewrite preserves the output for every input | randomized check, then an SMT proof ([§5.2](#52-the-proof-rule-for-rewrites)) |
| stub to foreman | a handler that cannot decide escalates instead of guessing | stub handlers emit escalations; resolutions are promoted only through the promotion path |
| Form to target | every emitted target computes the same δ | every target carries the same reference trace |

A failed check locates the break at the boundary where it occurs. The correction is made at that level, passed through the check of that boundary, and promoted. Every level above the corrected one inherits the correction without further change, because each level above consumes the corrected level only through the interface whose assumption is now checked. This is the sense in which corrections carry upward and compound.

## 5. Verification

<div id="51-five-targets-one-trace" class="anchor-alias" aria-hidden="true"></div>

<div id="51-differential-testing-across-five-targets" class="anchor-alias" aria-hidden="true"></div>

### 5.1 Differential testing of the program emitters

T9-L states that the program emitters `rust`, `python` and `js` agree with the reference evaluator. For the Rust emitter it is proved on a core, as a verified translation into MiniRust, a deep embedding of the emitted Rust subset; that `rustc` implements MiniRust is trusted and tested. For the Python and JavaScript emitters it is tested: the emitted program must print the reference trace of every example program byte for byte, which is the gate every row of the emit registry passes ([§3.6](#36-one-ecosystem-lossless-and-the-universality-thesis)). The reference evaluator and the emitted Rust, Python and JavaScript runtimes also compute the same budget function, and a test checks that the budget trap falls on the same operation in all four ([§3.7](#37-the-language-one-text-costs-and-theorem-status)); the order-preserving ANF pass before every emitter is tested differentially on every target, including a sweep of budgets across the trap point (theorem T34). This is differential testing in the line of McKeeman and of Csmith [86]: agreement among independent implementations on a stated input set. It is not translation validation [85], and outside the proved core of the Rust emitter it is not a verified compiler. It says nothing about inputs outside the tested set.

<div id="52-rewrites-proved-in-z3" class="anchor-alias" aria-hidden="true"></div>

### 5.2 The proof rule for rewrites

Verified rewrite rules have a lineage. Ruler infers and checks rewrite rules by equality saturation with no model in the loop [87]. The model-proposed rewrite admitted in Section 5.5 repeats a rule the engine already had, so that record is a statement about the gate, which refused 15 of 18 proposals, and not a claim that a model is a good rule source.

In the design of the engine, every e-graph rewrite must be proved in the Z3 SMT solver [31] against a quantifier-free encoding of the Form's term evaluation and arithmetic: values as a datatype, 64-bit bit-vectors with checked overflow, signed division and remainder with the dividend's sign, and binary64 floats. A rewrite that changes overflow, escalation order or a message gets no proof. A proposed equivalence enters the e-graph only with a proof.

<div id="53-kani-proofs-of-the-kernel" class="anchor-alias" aria-hidden="true"></div>

### 5.3 Model checking of the kernel

The design checks the engine's kernel (hash chain, fold, name-free positions and handler evaluation) with the Kani model checker for Rust [32]. Handler evaluation is the fixed point of a non-recursive step, so a proof that the step is total and deterministic per constructor carries to evaluation by structural induction. The design names ten properties, one harness each:

| Harness | Property |
|---|---|
| `chain_appended_verifies` | An appended hash chain verifies |
| `chain_detects_tampering` | A changed entry breaks the chain |
| `fold_equals_replay` | The fold equals replay |
| `fold_rejects_wrong_state` | A fold that disagrees with the stored state is refused |
| `position_is_name_independent` | Rule positions do not depend on node names |
| `reason_tokens_are_name_independent` | Reasons are name-free by whole tokens |
| `handler_core_leaves` | Leaf handlers are total and deterministic |
| `handler_core_validate` | Validation is total and deterministic |
| `handler_core_pipeline` | Pipelines are total and deterministic |
| `handler_core_ifhas` | Guards are total and deterministic |

### 5.4 Promotion gate on the proof certificate

In the design, the model-checking run writes a certificate whose hash is stored with the engine. The engine, the log, rule ids and handler evaluation route through the kernel, and promotion requires the certificate.

### 5.5 The model as a proposer behind the check

A model may propose equivalences. It may not admit them. A local 1.5-billion-parameter coding model was run as a proposer on the specification `orders-form`, and the public record of the run ([`rce/bench/results/llm-proposer-form-demo.form.json`](https://github.com/openIE-dev/openie-research-experiments/blob/main/rce/bench/results/llm-proposer-form-demo.form.json)) holds 18 proposals, 13 of them distinct. The record gives the source of each proposal only as `llm`; the model, Qwen2.5-Coder-1.5B under llama.cpp, is named by this paper and by no public record. The check refused 15 proposals, 12 of them distinct: four that do not parse, two that put a value where a term belongs, and nine commutations of arithmetic operators, each refused with a counterexample on which the two sides fail differently. The 3 it admitted are one rewrite, `(pipe pass ?a) => ?a`, under three names, and that rewrite repeats a rule the engine already had. The record shows the gate refusing what is wrong; it shows no new rule from the model.

## 6. Lift: entering the ecosystem from other languages

<div id="6-importing-legacy-code-from-other-languages" class="anchor-alias" aria-hidden="true"></div>

Lift is the door into the ecosystem for code written elsewhere. It is a construction, made per language from tools every language already has: a formal grammar, a parser such as [tree-sitter](https://tree-sitter.github.io/tree-sitter/) that yields the syntax tree, the abstract syntax tree and the symbols that language-server tooling resolves ([Language Server Protocol](https://microsoft.github.io/language-server-protocol/)). The engine profile specifies a lift, `rce scan DIR --form`, that builds the Form from that tree for Rust, Python, TypeScript and Go and labels every lifted element as unproven (Appendix D.8). A lifted program carries the faults of its source, so lift includes repair, and the protocol below measures repair on public bug corpora with the location given.

<div id="60-the-repair-ladder-on-lifted-code" class="anchor-alias" aria-hidden="true"></div>

### 6.0 The repair ladder

<div id="23-per-rung-ladder-results" class="anchor-alias" aria-hidden="true"></div>

A coding task is measured here by the **intent bits** it needs: the bits that must be supplied from outside what the engine already holds (the program around the edit, the libraries, the tests, the index of known fixes). Writing $H_{task}$ for the bits that pin the target artifact down and $H_{corpus}$ for the bits the corpus already fixes, the supplied bits are $I = H_{task} - H_{corpus}$. A gear that ranks the right edit at rank $r$ among its candidates has supplied $\log_2 r$ bits of search, and the gate supplies the rest. The ladder orders tasks by edit size, an objective proxy for $I$: one token (L0), one statement (L1), one hunk (L2), several hunks in one file (L3), several files (L4), a function from a specification or tests (L5), an issue-level change (L6) and a program from a specification (L7). The rungs, corpora, splits and hypotheses are preregistered; the files are in the [public repository](https://github.com/openIE-dev/openie-research-experiments/tree/main/rce/bench/ladder/).

L2 to L4 are to be measured on a Defects4J held-out set ([Section 8.1](#81-defects4j)), and L5 to L7 under the protocols of [Section 8.2](#82-swe-bench-lite-offline). The method and the gate of L0 and L1 follow.

**Method.** Each corpus is shuffled with a fixed seed. The first 2,000 positions of each shuffle, and for L0 three whole repositories (commons-lang, requests, flask), form the development split, on which the gears may be tuned; development results are not reported. Every remaining task is in the test split. Before a test run the solver is committed and its binary hash recorded, and no gear changes during the run, so every row to be reported is a frozen-solver result on test tasks only, with 0 model calls. The preregistration (`PREREG.json`) and the report script are in the [public repository](https://github.com/openIE-dev/openie-research-experiments/tree/main/rce/bench/ladder/).

**Gate.** At L0 and L1 the location is given and the gate is token identity: the repaired line or statement must equal the developer's, token for token. This is stricter than passing the tests, because a patch can pass a weak test suite and still be wrong. Qi and colleagues found that most patches GenProg reported as fixes were plausible but incorrect [92]; overfitting to tests is documented in search-based and semantics-based repair [93, 94] and addressed with generated tests [95]; tools score higher on the benchmark they were tuned on [96]; and fault localization biases comparisons [97]. Token identity removes the plausibility gap on these rungs, and giving the location removes the localization term, so the rate measures the repair gears alone. L2 and above use the tests as the gate and report plausible and correct counts separately (Section 8.1).

### 6.1 L0: one-token faults

The L0 corpus is every PIT-style mutant [109] with a valid replacement token in real repositories at pinned commits, five Java (commons-math, commons-collections, jsoup, joda-time, gson) and four Python (click, attrs, pydantic, sympy), with four repositories never used for tuning (commons-text, commons-io, more-itertools, httpx) as a second test set. Mutants are a stand-in for real one-token faults that Just and colleagues found to be coupled with real faults [110]. If the neighbourhood that restores a one-token fault is built from the same operator tables that produced the mutants, a high rate partly reflects that overlap and not repair ability on faults that arise in practice. A plain operator-inversion search, run on the same mutants, is the baseline that shows how much of the rate the overlap explains, and an L0 rate is read beside it.

### 6.2 L1: one-statement bugs from real histories

L1 uses two public datasets of real single-statement bug fixes mined from open-source histories: ManySStuBs4J 2.0 [107] for Java and TSSB-3M v1.0.0 [108], shards 14 and 15, for Python. The solver receives either the 7-line hunk only or the whole file at the parent commit, with indexes of the project's methods and guard conditions, and the two are reported as separate rows. These datasets have no published repair leaderboard under this gate (hunk only, token identity, location given), so no learned-repair number is set beside them; Defects4J, which does have one, is compared with TBar in Section 8.1.

### 6.3 Energy

Every row of the ladder carries `est_j`, an estimate of central processing unit (CPU) seconds times 10 W, and a subsample is read on RAPL [105], the processor's on-chip package counter, as `reported_j`: the package delta over the whole run, less idle power from a sample taken just before, times the run's duration. `measured_j`, a wall meter on a named rail, follows the protocol of Section 8.3.

**Two regimes and a calibrated vector.** The estimate above, CPU seconds times 10 W, is one substrate table and cannot tell targets apart, so least-joule extraction never chooses a target. The measurement literature says what the fix must look like. On an in-order core, joules are linear in operation counts: a six-counter model on Cortex-M0 reaches R² ≈ 0.99 and 2.8 to 4.3% mean absolute error, with coefficients such as 0.96 nJ per instruction and 2.1 nJ per taken branch [152]. On an out-of-order core the model collapses to time: with one core pinned and turbo off, a Xeon Gold 6430 drew 189.8 ± 0.5 W across every implementation and benchmark of a language-energy replication, and the ranking that had put Python at 75.88 times C disappeared once library choice, parallelism, warm-up and measurement bugs were controlled [153]. The counters themselves are of uneven worth: Intel RAPL predicts plug power to 1.8% mean absolute percentage error once DRAM is included, but updates about every millisecond and drifted 10 to 12% with package temperature on one generation [105]; polling it faster than 10 ms produces up to 50% stale reads [154]; NVIDIA's NVML samples about a quarter of the run time and single naive runs erred by up to 70% against an external meter [155]. Gas-style unit metering correlates with CPU time at only Pearson ≈ 0.51 on Ethereum [156], so "energy scales with the operations counted" is an assumption the `reported_j` subsample has to test. A proposal to the specification keeps three objects apart: the C.6 budget units stay deterministic, target-blind and in the log; `est_j` becomes $\langle \mathrm{count}(\mathit{term}), E[\mathit{target}] \rangle$ plus idle power times time in regime A (microcontrollers, field-programmable gate array (FPGA) lanes, in-order cores) and $P_{\mathrm{active}} \cdot t + E_{\mathrm{llc}} \cdot \mathit{misses}$ in regime B (out-of-order CPUs and graphics processing units (GPUs)); and the coefficient vector $E[\mathit{target}]$ is a `host.Calibrated` log entry with its protocol, sample count and standard error per coefficient, written by `rce host calibrate` under a normative protocol (at least 30 interleaved A/B pairs against the idle baseline, blocks of at least 60 s or $10^9$ operations, warm-up discarded, temperature recorded, gross and net reported, the meter named with its validation reference, RAPL sampled no faster than 10 ms), so that extraction under `est_j` is a function of the log and replays. Receipts gain a `calibration` hash and a `stale_fraction`, the share of a step's operations with no calibrated row, priced `unpriced`; totals keep the four labels in separate columns. The falsifier is RCE-F5 in [§9](#9-falsifiers). The first calibration to run is the KV260 rung of the energy ladder on its core rail with $N \ge 30$, which turns the stand-in `E_LUT_READ = 1e-12` of the specification into a coefficient with a standard error.

## 8. Measurement protocols for what comes next

Each protocol is fixed before its run: preregistration committed, seeds and solver commit recorded, every artifact kept. Gate first, joules second, labels always.

### 8.1 Defects4J

Defects4J holds 854 active real Java bugs, each with reproducing tests [37].

1. Develop on a 100-bug subset, offline, through `defects4j checkout`; report held-out results only, on a disjoint set drawn from the active bugs by a seeded rule registered before the run, which excludes the development subset and every bug already run with any gear, and frozen before the run.
2. Run G0, then G1, then G2, then a local model last. Record the gear that closed each bug.
3. Gate: the triggering tests and the full suite pass. Report plausible and correct counts separately; correct means equivalent to the developer patch on review.
4. Report model calls per correct fix and joules per correct fix, labeled.
5. Reference points: TBar's 43 correct fixes and its 74 of 101 under perfect localization (figures as read from [23], with the denominator not rechecked here). This section is a protocol. No Defects4J result of this engine is reported in this paper.
6. Contamination check: flag every bug whose fix appears verbatim in G0's index, and report with and without flagged bugs.

### 8.2 SWE-bench Lite, offline

SWE-bench Lite is a 300-task subset of real GitHub issues resolved by hidden tests [38].

1. Use the official Docker harness with no network.
2. First run: G0 and G1 only, zero model calls. This is the floor of solving without a model.
3. Second run: add a local model as the last gear.
4. Report the resolve rate, model calls per resolved task and joules per resolved task, labeled.
5. Contamination check as in 8.1. SWE-Bench+ found that 32.67% of successful patches had the solution in the issue text [39].

### 8.3 A wall meter

1. Attach a wall meter or a shunt meter on the host's supply, logged at a stated rate with its clock synchronized to the run log.
2. Idle machine: CI runners and other builds stopped, and a quiet window gate checked before each block and recorded.
3. Subtract a measured idle baseline, and state the method.
4. Fill `measured_j` from the meter alone. Report `reported_j` (RAPL) and `est_j` beside it in separate columns. Never sum across labels.
5. Run the RAPL subsample of the ladder (Section 6.3) under the meter, then the Defects4J held-out set.

### 8.4 A held-out run with the gears frozen

This is the method of Section 6, extended to new corpora.

1. Freeze G0, G1 and G2 at a tagged commit, record the binary hash, and publish the rule set with its authoring timestamps.
2. Draw a disjoint held-out slice: the Rust and Python instances of Multi-SWE-bench [102] and BugsInPy [103], de-duplicated against G0's index [104].
3. Preregister the slice, the seeds and the hypotheses before the first run.
4. Report resolved, plausible and byte-identical counts separately, each with a 95% interval.

### 8.5 Baselines in the same table

1. Model-free: `cargo fix` and clippy [106], and Sorald or a TBar port [91].
2. Cheap model: Agentless with a local model [99].
3. Remote model: an agent with a frontier model, its energy estimated from provider disclosures and labeled `est_j`.
4. Report cost-of-pass [101] in joules and in dollars for every row, with cost controlled as Kapoor and colleagues require [100].

### 8.6 Convergence of model calls at large N

Promotion is the mechanism by which the model leaves the loop: a resolver is paid once for a new case, the gate admits the fit as a handler, and every later case of the same shape closes in G0 or G1 ([Section 4.2](#42-the-gears)). Convergence is the claim that model calls per round fall to zero on a fixed specification under live traffic. It is measured as follows.

1. Draw at least 1,000 specifications from public repositories, stratified by language and size, and freeze the engine and the resolver before the first round.
2. Replay recorded production traffic, at least 10,000 events per specification, in rounds of fixed size.
3. Record per round: new escalations, model calls, promotions, deferrals and joules per closed task, each labeled (`est_j`, `reported_j`, `measured_j`).
4. Primary endpoint: the share of specifications reaching a round with zero model calls within 20 rounds, with a 95% Wilson interval. Secondary: model calls per closed task by round, and the round of the last model call.
5. Report specifications that never converge with their cause (a stuck input, a missing dependency, new intent), and run stuck-input deferral as a preregistered arm.

**Proposition 8 (floor approach).** As G0 and G1 coverage grows, joules per solved task approach the gold floor of applying a known fix and running the tests. The ladder rungs and the Defects4J held-out set under the wall meter test it.

### 8.7 Lift coverage across languages

<div id="87-coverage-of-real-programs-across-languages" class="anchor-alias" aria-hidden="true"></div>

Lift is measured as it is built. For language $L$, a program counts as lifted when $\pi_L(\lambda_L(p))$ passes the program's own tests and replays its recorded traces byte for byte, and $\lambda_L(\pi_L(\lambda_L(p)))$ has the same shape hash as $\lambda_L(p)$. The sample is at least 10,000 programs per language for at least ten languages, drawn with a fixed seed from pinned public corpora, with the lifter frozen and its binary hash recorded before each run, and 0 model calls. Each run reports the share lifted with a Wilson 95% interval, and each construct not yet lifted is a work item for the lifter of that language, built and frozen before the next run. The target is every program in every language.

## 11. Conclusion

RCE is a native code ecosystem by design. A program is authored once, from intent, as a Form: a lossless encoding of state, events and pure transitions, of which every target language is a projection that must replay its trace. Every state a program can be in is declared in its Form, and a refused event leaves the state unchanged (theorem T8), so a program in the ecosystem does not drift from its intent and needs no after-the-fact diffing or error tracking. The language is one written specification at one commit. The reference checker implements it and emits Rust, Python, JavaScript and Scala; the specification records the level of each theorem's proof exactly; and the dimension of a program is a computed number, measured in registered runs at public commits, which triggered RCE-F6 on one population and not on the others. In the engine's design every fit that passes the gate is stored and reused, and the ecosystem compounds under a gate whose correctness is monotone (Proposition R1). Code from other languages enters by lift, a construction from each language's grammar to its syntax tree to the Form. Sections 3.6 and 8.7 state the universality propositions and how their construction is measured, Section 9 states the observations that would defeat the claims, and Section 10 lists the work that remains, including the results of the engine being rebuilt on public code.

## 12. The Form against the record

This section places the Form against three bodies of evidence: the theory and tooling of each area the design touches, the history of programming-language design read as a comparison of what each language fixes and what it leaves free, and the measured causes of redundancy in human-written code. Each subsection states what the evidence shows, with its source, and then the position this paper takes and the reason. Where a position is a judgement rather than a measured result, the text says so. The three surveys behind this section were conducted in October 2026; their full texts and working notes are published in the experiments repository ([openie-research-experiments/rce/surveys](https://github.com/openIE-dev/openie-research-experiments/tree/main/rce/surveys)).

### 12.1 Seven areas of the design

**Canonical forms.** For a complete, deterministic machine over a finite alphabet the minimal machine is unique up to isomorphism, and a fixed traversal order turns that into a unique string [150]. The Form supplies completeness and determinism (T1, T2), so the finite-control projection of [§3.8](#38-behaviour-equivalence-and-dimension) has a canonical form. The data component does not: symbolic finite automata have a canonical minimum up to predicate equivalence [149], register automata over equality or dense order admit a Myhill–Nerode theorem [151], and a state updated by integer arithmetic has no canonical representative but the term itself. Extraction from an e-graph under a cost that charges shared sub-terms once is NP-hard and not approximable to a constant factor [159], so a hashed representative must use a cost that is reproducible across extractors. Position: three shape keys, each naming its tier in the hashed input (the name-free term hash, the control form of [§3.8](#38-behaviour-equivalence-and-dimension), and the e-class key with its saturation budget); equivalence defined once, as bisimulation; guarded step bodies checked first by the nearly linear decision procedure of guarded Kleene algebra with tests [158]. Refused: any claim that the minimal machine is *the* canonical form of a Form with arithmetic state; a hashed representative chosen by shared-sub-term cost. Open: for which fragment equal meaning implies an equal control form (the converse of T61).

**Content-addressed intermediate representation.** Unison's five-year experience with hash-identified definitions reduced to one invariant, that the hash covers semantics and never names, and one cost, re-hashing dependents under edit [160]; Dhall hashes the normal form of a total language [161]; Nix's attempt to content-address build outputs stayed experimental for fifteen years because self-references and non-determinism broke it [162]. Position: definitions keyed by the digest of the α-erased, normalised body, with names, source positions and literal spellings in an unhashed table rendered by the projections; one emitter that walks the intermediate representation through a per-target table, replacing four emitters that walk the surface syntax; every runtime that serialises checked against the canonical-JSON vectors. Refused: replacing canonical JSON as the hashed bytes with RFC 8785 (which cannot carry an integer distinct from a float, negative zero or an exact 64-bit unsigned integer) or with deterministic CBOR (whose two specifications disagree on float width and key order); content-addressing emitted artefacts as identity; full β-normalisation before hashing, since a recursive function then has no finite term. Open: component-level keys for mutual recursion.

**The log as a partial order.** A trace in the sense of Mazurkiewicz is a word modulo the commutation of independent events, and all linearisations of one configuration read off the same trace. The consistency-as-logical-monotonicity theorem states which programs need no coordination [19], and its extension to reads says that observations of convergent state are unsafe unless they are threshold-shaped [82]. Position: an entry of the log hashed over its chain, sequence number, event and the hashes of the entries it causally observed, with the state hash recorded only at cuts, so that the digest is the same under every linearisation the semantics admits; the monotone tag extended to reads; every taken arm of a cross-chain `select` logged. The theorem that any order consistent with the dependencies folds to the same cut state (T62) is proved on a model and is a proposal, not normative text. Refused: letting a target choose the linearisation of a non-monotone event. Open: the extension of the model proof to the full evaluator.

**Synthesis from intent.** A verifier checks only soundness: a postcondition that is always true verifies. The completeness of a specification has to be measured, and the measure that works is the share of mutated outputs the specification rejects; removing that measure from the gate in the study that introduced it dropped verifiability to 1.56% [164]. Type-directed enumeration over equality-constrained tree automata raised the solved share of a library-search benchmark from 64% to 88% [165], and self-refinement and majority voting rarely justify their cost once cost per correct result is accounted for [166]. Position: intent as a program with holes carrying obligations, examples, a named set of usable definitions and a budget; a rule that refuses an intent whose obligations reject no behaviour; a measured completeness reported with every intent; a derivation record per hole giving the candidates before and after each check. Refused: promotion by score; refinement loops inside one model call. Open: a corpus-independent measure of the information an intent carries.

**Energy cost models.** The measurement literature is summarised in [§6.3](#63-energy): joules are linear in operation counts on an in-order core [152] and linear in time on an out-of-order core [153]; on-chip counters differ in worth by an order of magnitude [105, 154, 155]; unit metering of the kind used by Ethereum correlates with CPU time at only 0.51 [156]. Position: three distinct objects, never merged — the deterministic, target-blind budget units of the specification; an estimate that is a calibrated per-target coefficient vector applied to the counts (in-order) or to time (out-of-order); and the receipt labels, kept in separate columns. Refused: joules in the budget table; per-language constants; a counter read as a wall-meter measurement.

**Languages designed for machine authors.** A catalogue of 42 such languages, 36 of them first listed in 2026, shows every one of this paper's mechanisms with a peer: hash-chained evidence, mandatory contracts split into proved and run-time-checked, a proof-assistant core, syntax trees as the source of truth with hashed definitions [168]. The convergence observation of [§3.7](#37-the-language-one-text-costs-and-theorem-status) stands. What distinguishes this design is not any mechanism but that replay and injectivity are theorems (T3, T7) rather than run-time promises, and that examples are typed event traces over the same semantics replay uses, so the oracle a model cannot bypass is the program itself. Position: a versioned registry of rule codes with machine-readable diagnostics and repair plans; test-validated translation pairs manufactured from the emitters and the checker, which is the recipe that recovered low-resource languages in [167] run in reverse. Refused: any claim to be first or only.

**Proof engineering.** The standards that closed the gap between a specification and its mechanised model did so by generating prose, checker tables and definitions from one authored source: SpecTec for WebAssembly found ten errors in five proposals and was adopted for all future editions [169]. The projects that proved an implementation correct by refinement paid for it: about twelve person-years for 8,700 lines of C [171]. CompCert's maintainers list every trusted item with its reason [170]. Position: one authored rule source generating the specification text, the checker tables and the Lean definitions, with a check that fails on any divergence; the Lean core as the executor of record for the subset it covers, with the count of unsupported constructs published and bounding every theorem's stated scope; a chapter listing every trusted component with its test. Refused: a refinement proof from the Lean core to the Rust interpreter; theorem counts as a measure of assurance; two authored semantics of anything.

### 12.2 The Form among programming languages

About a hundred languages in twelve families were placed on eight coordinates — state layout, event alphabet, transition, order, resource, trust, binding time and intent — recording for each whether the author fixes it, the compiler or runtime chooses it, or the language has no word for it. Three regularities follow. Only three families obtain global determinism without the author's effort, by three different theorems: the synchronous languages by a causality check, the stream and logic languages by monotonicity, and guarded-atomic-action languages by one-rule-at-a-time scheduling with static conflict analysis. Every family that reached safety certification did so by removing the same three coordinates the Form removes: dynamic allocation, unbounded recursion and nondeterministic choice. And the two coordinates no family fixes well are trust and intent; the Form's intent and example blocks and its capability values fix both.

The five designs nearest the Form are Dedalus, whose time-indexed relations are the log and whose next-step rules are the transition [15]; Bluespec, whose guarded atomic rules are scheduled by a compiler-chosen order proved equal to one-rule-at-a-time execution; the Elm architecture, which is the Form's four components under other names [83]; Lustre, whose bounded-memory, statically scheduled discipline has been certified in about a hundred avionics systems; and Unison, on identity [160]. The record also fixes five constraints, each a place where an earlier language paid for the opposite choice. Concurrent tasks must lower to state machines without a stack, as Rust's asynchronous functions do, because a stackful coroutine cannot be logged step by step. Parallel composition must be emitted as a structured step, never as an explicit product of automata, which in Esterel's compilers failed beyond about a thousand lines of concurrent source. Effect handlers must be one-shot, as OCaml 5 chose, and the reason is ownership and the totality bound (each additional resumption copies captured state a data-dependent number of times), not loggability. The only dimension of a program that is a theorem is the index of its finite-control projection ([§3.8](#38-behaviour-equivalence-and-dimension)). And the lift from a Turing-complete language is a partial map whose domain is undecidable ([§3.6](#36-one-ecosystem-lossless-and-the-universality-thesis)). The vocabulary of differential geometry that an earlier working draft of this project used (charts, gauge, holonomy, geodesics) has no counterpart in the literature of programming languages and is not used here; the objects that exist are the final coalgebra, functors from syntax into it, the groupoid of rewrite proofs whose connected components are e-classes, and minimum description length with joules in place of bits.

The universality propositions of [§3.6](#36-one-ecosystem-lossless-and-the-universality-thesis) are made measurable by an encapsulation criterion. The Form encapsulates a language $L$ when, for every program $p$ of $L$ in a fixed corpus, the lifted Form is no worse than $p$ on five coordinates and strictly better on at least one: joules measured on the same tasks and host; redundancy in the sense of [§3.8](#38-behaviour-equivalence-and-dimension) against the state bits $p$ declares; decidability, meaning every property decided for $p$ is decided for the Form; the round trip, meaning behaviour agreement to a stated length and the lens condition on the shape hash; and the cost for a model to reach a gate-passing program from the same intent. The claim that the Form is better than a programming language is the conjunction of this criterion over the corpus, one registered run per language, and nothing else: it claims neither expressiveness, since a Form cannot say more than $p$, nor readability, which is a property of a projection, nor adoption. A language on which the Form is strictly worse on any coordinate after two registered runs is not encapsulated, and the record of what that language fixes that the Form does not becomes a work item for the Form.

### 12.3 Why human-written code is redundant

Human-written code carries redundancy wherever the medium gives the author no channel for what is meant, and the redundancy is each author's private substitute. The measured evidence sorts it into three layers. Formatting is 13 to 15% of the tokens of brace-delimited languages and can be removed without loss of accuracy for ten language models [136], and layout has no measured effect on human comprehension [135]. The only quantities that track measured comprehension load are textual size, vocabulary size and the reach of data-flow dependencies, each at Kendall's τ ≈ 0.4, while cyclomatic complexity tracks nothing (τ ≈ 0.09) [133]; and 97% of real concurrency bugs other than deadlocks are unenforced assumptions about atomicity or order, 96% of them involving at most two threads, because sequential text cannot state a partial order and the author writes a total one [172]. Names are chosen with a median agreement of 6.9% between developers and decoded at 97% [137]; comments stop tracking the code they describe within a few commits [138]; yet language models lose up to 29 points of accuracy when identifiers are removed [139]. Two further causes are organisational. Developers do not delete: in three production systems 54 to 60% of files were never executed over six to sixteen months, developers removed 20% of the code they were shown to be unnecessary, and the caution was reasonable, since the detector was 32% precise [173]. And organisations ship their boundaries: eight organisational metrics predicted failure-prone binaries at 86.2% precision and 84.0% recall, ahead of every code metric [174].

The position that follows has four parts. The Form takes order, locality, idiom and reachability, each decidable over a state, an event set and a total step. The projection takes layout and idiom, rendered per community, because an expert's advantage is confined to code written in familiar plans and a projection that emits merely correct code costs them it. Intent stays a structured, checked record, from which the projection renders names ([§3.8](#38-behaviour-equivalence-and-dimension)). And the specification is governed by a mechanical admission check, because authorship by models raises the rate of proposals without changing the rule. Three questions on which the design depends had no measurement in the literature and have been registered as experiments with sealed protocols: whether a model reasons as accurately from a nameless Form with its concept record as from a named surface; what share of adjacent statements in ordinary code commute under the Form's dependencies, which is the size of the slack whose cost the 97% figure measures; and whether deletion that is checked by replay and reversible by one command moves the 20% deletion rate. Two claims that circulated in the project's working material have no traceable source and are not used: a 2014 study of language-manual page counts, and the statement that experienced programmers write less code, which traces to a weblog post citing an unnamed study.

### 12.4 How the language grows and shrinks

Every language that stayed small replaced the taste of reviewers with a rule about what counts as admissible. Go's process is slanted towards declining, and in one study declined 40.9% of 1,095 proposals with a published set of reasons [175]; Lua's rule of mechanisms rather than policies held its implementation at about 25,000 lines of C; Elm stopped. The regime that grows is also documented by its own chair: the benefit of a feature is private and immediate, its cost diffuse and deferred, and it is easier to summon enthusiasm for something new than for opposing it [175]. In RCE the Form grows inside the one text. When a program needs a form the text lacks, including one nobody foresaw, the form is written into the specification itself, with no version and no macro, flag, directive or plugin. The specification repository states seven rules for how a form enters the text, each naming the artefact that enforces it. A construct enters the normative grammar only with an accepted and a refused example, a Lean statement of the theorem it relies on linked to the checker by a generated rule table or by test vectors, and no parsing conflicts; anything less is a proposal. A second spelling of something the Form already says is declined on that ground alone. Change runs both ways: any construct can be changed, generalised, replaced or removed when a better form is found, and the change moves together with every program, example and library module of the repository it touches in one commit, with a ledger row saying what changed and why. Each interface has one decision locus, because an organisational boundary that runs through an interface is a predicted defect site [174]. The decisions and their reasons are published in a ledger with a fixed set of reasons, so the decline rate is a number anyone can read. The market does not prune, so use is never a reason to keep a construct. And authorship by a model changes the rate, not the rule.

### 12.5 The library and the compute fabric

Whether a language should ship a large library ("batteries included") or a small specified core with a free registry is usually argued as convenience against flexibility. The record shows both positions failing at the same point [193]. A library shipped with the language ties its interface to the language's compatibility promise and loses flexibility [195]. Its modules are removed once an installer exists: Python Enhancement Proposal 594 removed 22 of them, citing maintenance cost and the ease of installing from the registry [194]. A free registry produces deep transitive graphs: half of the dependent packages in Cargo, npm and NuGet have at least 41, 21 and 27 transitive dependencies [196]. A specification with many implementations diverges at its edges, as more than 30 JSON parsers do on one under-specified grammar [197]. Where the record converges, it converges on a curated tier that is delivered and changed as one unit.

The same failure appears across compute fabrics. On graphics processors, single-source models match native code on streaming kernels and lose on reductions: on the dot product, the performance-portability scores of Kokkos, RAJA and SYCL lie between 0.80 and 0.91 [198]. On an FPGA, one SYCL source migrated from CUDA and tuned for a GPU reaches 0.2% to 47% of the speed of its FPGA-optimised version, by ratios derived from the published timings at the largest problem size [193, 199]. The surveyed systems that give one meaning in software and in hardware achieve it by cutting their source language down to what their hardware can mean (state of statically known size, no heap or recursion in the hardware part, a logical tick), and their proofs cover parts of the chain, not all of it [193, 200]. Portable code formats work where they fix semantics [201]. Bit-identical results cost little when designed in [202]. Soundness results for memory models are pairwise [203]. Placement from measured costs is nondeterministic unless each decision is recorded and replayed, or the run is simulated in virtual time [193, 204]. For machine authors the question is also one of knowledge: of the packages named by code that 16 models generated in Python and JavaScript, 19.7% did not exist [205].

Both debates ask where a library's meaning is held: by one implementation, by each registry package, by a specification checked with tolerances, or by a vendor binary for one fabric. The RCE position holds it in the one text.

- **The library is part of the text.** It is written in the language and built into every tool (specification 4.1). It is pinned by the hash of its manifest, which a program names as its one dependency (F.5.3).
- **It has no platform variant.** It performs input and output only through adapters.
- **Its cost is the cost of its source on every binary.** A step therefore means the same on every host (HC-7).
- **The per-target choice belongs to the host.** The host admits a fabric for a class of operations only after a logged bit-exactness probe against the CPU reference (HC-13), and it logs every placement for replay (HC-12).
- **What is available is a list a tool prints, complete at each commit and growing in the same text.** Whether a function exists becomes a lookup rather than a recollection.

The Form does this as a shape, not as a gate. The systems of the record cut their source language down because it says more than their hardware can mean. The Form P = (S, E, δ, D, λ) is the shape every program already has: the state it keeps, the events it answers, its step, its log and its outputs. That is why programs of other languages enter it by lift, within the domain [§3.6](#36-one-ecosystem-lossless-and-the-universality-thesis) states, and why no part of this position sorts programs into admitted and refused ones.

The Form is rigid at each commit, with one text and one meaning. It is flexible across commits. When a program needs a form the shape does not have, the shape gains it in the text, never through a macro, flag, directive or plugin beside it. A change may extend, generalise or replace a form. It moves together with the programs of the repository in one commit, and the program hashes, the equivalence check of [§3.8](#38-behaviour-equivalence-and-dimension) and the log record what moved. Behaviour and equivalence (specification 6.10) and the host's fabric entries were added inside the text without changing the meaning of any accepted program, and the log as a partial order and intent with holes are proposed the same way. Under the proposal, hardware follows the same rule: the engine reads a Form's state sizes and step costs to realise it, with a statically sized state in registers and a growing state in memory the circuit addresses.

Batteries included and specification-and-free then stop being alternatives: the batteries are part of the specification, and the program is free of any fabric.

The library half of this position holds in the repository in its main parts: the library is written in the language, built into every tool and pinned by hash. Two of its parts remain: one definition of the standard library across the sections of the specification, and `use` as the one way to bring in the four modules that a directive still reaches. The fabric half is a contract and a reference executor proved to replay, exercised on CPUs only. The proposal "one library and one Form on every compute fabric" lists what remains [193]:

- one definition of the standard library, and `use` as the one way to bring a library in;
- probe evidence re-derived on replay;
- placement on every execution path;
- one reduction tree per construct;
- calibration runs;
- integer and binary32 operation classes;
- hardware realisation read from each Form's shape;
- a host without an operating system;
- two measurements the record lacks: one kernel's energy across device classes under one boundary, and the share of library functionality that model assistants reuse rather than reimplement.

## 13. Programme of work and its gates

Two independent reviews of the public repositories in October 2026 reached the same diagnosis. The checker is not itself verified: nothing refines the Lean semantics to the Rust interpreter, the two Lean cores have no theorem relating them, and the conformance suite's report for the mechanised core (`conformance/reports/results-lean-core.json` at public commit `d91a9fc8`) records 210 tests passing, 1 failing and 1,766 unsupported of 1,977, so about a tenth of the suite is under the theorem the overview advertises. Emitted code is a dynamic-value runtime per target, four hand-written runtimes of about 2,000 lines each. The energy estimate cannot tell targets apart, so least-joule extraction never chooses one. The lift covers four languages and the universality claim needs ten. And the engine — the gears, the e-graph, the rewrites and their proofs, the kernel and its model checking, and the lift — is not public, so the results it produced enter this paper only as each is rebuilt on public code; [§10](#10-work-to-finish) lists them with their rebuild tracks. For a project whose stated reason for working in the open is traceability, that is the largest risk in the programme.

The programme is ordered by dependence: reproducibility first; then the encoding and the cost model that every later measurement rests on; then the proof chain; and only then breadth. Each phase ends at a gate that is a falsifier registered before the run, reported with a confidence interval; a phase closes when its gate observation is published, never on effort. The gates are stated in [§9](#9-falsifiers) and the table below.

| Phase | Deliverables | What defeats the phase |
|---|---|---|
| 0 Reproduce | Every result that depends on the engine rebuilt on public code at a tagged commit, as [§10](#10-work-to-finish) lists; the per-task records of every rebuilt run; the held-out Defects4J set completed; every registration sealed by hash; one version string; the specification errata closed; one spelling each of termination, authority and error; a published measure of surface redundancy (distinct constructs per Form over the example corpus) | A number in this paper that cannot be rebuilt from a public commit with one command |
| 1 Freeze the Form | Content-addressed definitions as the only intermediate form; typed relations as a Form value; one lowering that every emitter consumes; the round-trip condition checked per target; a per-target cost model calibrated as [§6.3](#63-energy) states | A definition refused for size; a target whose round trip changes a shape hash; the cost model ranking two targets opposite to the wall meter |
| 2 One core, verified gate | A single Lean core with T1 to T9 restated on it; the typing rules generated from the checker's rule table so that a rule without a Lean counterpart fails the build; the checker and the interpreter extracted from Lean and used as the gate, with the Rust checker as a cross-checked front end | The extracted gate and the Rust checker disagreeing on any program; a restated theorem needing an admitted step; unsupported conformance tests above 10% |
| 3 Targets priced in joules | Rank-n arrays and bulk operations as the one spelling for numeric work; Zig and Fortran emitters with fixed floating-point and overflow modes; layout hints in the fit and never in the Form; a translation-validation certificate per emitted module; the wall-meter protocol of [§8.3](#83-a-wall-meter) | RCE-F3 and RCE-F5; a module emitted without a certificate; extraction choosing the same term for every pair of targets |
| 4 Lift as the entry | A lift per language, Go and Python first, then TypeScript and Rust, then C and Zig; 10,000 programs per language with the lift frozen; the encapsulation criterion of [§12.2](#122-the-form-among-programming-languages) run per language; a public, append-only log of admitted shape hashes with their certificates | Lift coverage under 10% on any of the first four languages after the second registered run; the Form strictly worse on any coordinate of the criterion |
| 5 The ecosystem compounds | Synthesis from intents with holes; the first gears public with their verification certificate; the convergence protocol of [§8.6](#86-convergence-of-model-calls-at-large-n) on 1,000 public specifications; baselines in one table with cost per correct result in joules and dollars | RCE-F1, RCE-F2, RCE-F4; the tools unable to check or emit themselves |

Three positions where the reviews differed from the surveys of [§12](#12-the-form-against-the-record) are resolved as follows. Canonical JSON remains the only hashed encoding, for the reasons given in [§12.1](#121-seven-areas-of-the-design); a binary encoding may mirror it for transport only if it is a bijection to those bytes, checked on the same vectors. The one spelling of termination is a declared decreasing measure, with the loop and recursion limits as the semantics; the content-addressed form still needs a bounded fixed point for recursion, and the measure is what bounds it. Reducing the concurrency vocabulary to two primitives is recorded as an open proposal rather than a decision, because the theorems of the two primitives must first be proved on the checker rather than on a model. Not on the programme at all: a self-hosting compiler before phase 2, further targets before phase 1, any construct of the appendices before its theorem, and a production compiler, which the specification's own overview says should not be built until the document stops moving.

Since the reviews, the six repositories that must agree with the specification — the book, the example programs, the standard library, the conformance suite, the grammar package and the editor — have been merged into the specification repository with their histories, and each is checked by a workflow that builds the checker from the same commit. Nothing in the project pins or vendors an older specification; the editor's vendored checker, six commits behind, was the last such pin. The research site and the experiments repository remain separate and read the specification repository; it never reads them.
