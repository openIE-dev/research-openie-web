## 摘要

本文描述了 Reality Code Engine（RCE），这是一个将程序作为状态机（称为形式，Form）一次性编写、并由此生成其他语言代码的系统。本文给出该语言的书面规范、实现该规范并生成 Rust、Python、JavaScript 和 Scala 的参考检查器、其定理的 Lean 证明、其程序维度的已登记测量，以及查找、检查和重用解决方案的引擎设计。本文还说明了如何证伪这些主张，以及尚未进行的测量协议。

**用白话说**

1. 一个程序只以一种精确的形式编写一次，计算机便可由此生成多种语言的同一程序。
2. 程序能做的一切都在其形式中声明，语言要求每个输入都有一个声明的结果：要么是执行一步，要么是保持状态不变的已记录保持步骤，而不是事后才发现并修复的未定义结果。
3. 在引擎的设计中，通过检查的修复会被保存并重用，因此相同的问题不会耗费两次时间和能量。

## 1. 论文

自主计算机自动化是一个设计空间，其中包含许多点。每种方法都位于五个连续轴上的某处：每项正确结果所消耗的能量；系统在运行时必须解决的熵，以及由此决定其输出的确定性；接受结果的验证强度；每个被接受的结果被重复使用和复合的程度；以及方法对模型的依赖程度。一个大型语言模型（LLM），一种统计文本模型，它从提示中写出每次更改，位于该空间的一个角落：它依赖模型完成每项任务，每次从高熵分布中抽取新样本，并在每项任务上再次支付生成费用。检索、规则、合成、验证和缓存占据了许多其他点，而实际系统将它们结合起来。

Reality Code Engine（RCE）是该空间中的一个点。本文描述了它，其报告的测量结果是其语言及其工具的测量结果。RCE 将程序建模为数据库函数式状态机。Lopes 及其同事测量到 GitHub 上约 70% 的代码是早期文件的克隆 [33]，因此 RCE 首先尝试检索现有的契合，对其进行调整并检查，仅在没有更便宜的方法能够关闭任务时才调用模型。

**核心主张。** RCE 是一个完整的代码生态系统，其中程序从意图原生编写。意图只编写一次，写成一个形式（Form）：一个状态、一组事件和一个纯的、完全的转换。形式是对该意图的无损编码。每种目标语言都是形式的投影，每个投影都必须逐字节重放形式的轨迹；参考检查器目前可生成 Rust、Python、JavaScript 和 Scala。程序可以处于的每个状态都在其形式中声明，语言要求每个输入都有一个声明的结果：要么是采纳它的步骤，要么在事件根据其契约不适用时是一个保持步骤，即状态保持不变并将该步骤记录在日志中（T8）。满足这些要求的程序不会像常见语言中的程序偏离其注释、测试或其他实现那样偏离其意图，因此不需要事后差异比较或错误跟踪。使参考检查器在入口处满足第二个要求的输入契约在 [§10](#10-work-to-finish) 中列出。在引擎的设计中，每个通过门槛的契合都会被存储并重用，因此生态系统随着增长而复合（[§2.4](#24-gated-verified-recursive-self-improvement)）。用其他语言编写的代码是进入系统的一扇门：它通过提升进入（[§6](#6-lift-entering-the-ecosystem-from-other-languages)）。

该空间中的每个点都面临相同的门槛。门槛是正确性：任务的完成性谓词 $C(z)$，在这里是任务的测试、证明或协议轨迹。在通过门槛的运行中，系统按完成所需的焦耳数 $J^*$ 进行排名。正确性是一个约束，而不是一个分数。

在引擎的设计中，RCE的机制，称为档位，按成本顺序运行，第一个候选通过门槛的档位完成任务。

能量数据按来源标记。`est_j` 是分析估计值。`reported_j` 是操作系统或片上计数器。`measured_j` 保留给墙式功率计，在此处的每个结果中均为空。`openIE-dev/rce` 主分支 `09b2bdfb` 上的公开代码所提供的范围更窄。检查器以整数成本单位和每次输入的燃料来统计工作量，规范 C.6 指出它们“不是对时间或能量的测量”。收据中的焦耳项仅填写为 `est` 或 `unpriced`，没有任何收据保存实测读数。用于记录计数器读数的日志条目 `host.Energy` 已在规范中定义，但没有任何检查器代码写入它。`host.Calibrated` 记录的是计算织物的开销与吞吐量，而非焦耳。按每单位焦耳进行的校准是一项提议（[§6.3](#63-energy)）。

**意图具有高熵。** “加快结账流程”包含许多含义：缩短页面加载时间、减少步骤、加快信用卡批准、缓存购物车，或在某一设备类别上加快速度。上下文是隐含的，从未被写入。Shannon测量印刷英语约为每个字母0.6到1.3比特 [1]。字母是可预测的，但含义不是。

**每次转换都会丢失信息。** 意图变成规范，上下文丢失。规范变成数百种表面语言之一，备选方案和边缘情况丢失。源代码变成中间表示（IR），名称、风格和作者的原因丢失。IR变成机器代码，类型变成大小，循环变成跳转。

**底层具有低熵。** 每个程序最终都变成加载、存储、算术和跳转。目标层只能容纳几种形状，因此代码会向它们弯曲。收敛是设计的结果。

**边界是意义分歧的地方。** 相同的代码行在边界处给出不同的答案。在Python中，`-3 % 2` 是 1，`-7 / 2` 是 -3.5。在C中，`-3 % 2` 是 -1，`-7 / 2` 是 -3，且有符号溢出是未定义行为。一个在每个边界重新生成代码的系统会在每个边界进行猜测。

**轴线，以数量形式陈述。**

| 轴线 | 一端 | 另一端 | RCE设计的位置 |
|---|---|---|---|
| 每个正确结果的能量 | 每个任务都重新支付全部费用 | 每个新情况只支付一次，然后进入处理层 | 在已覆盖任务上处于底层 |
| 运行时解决的熵和确定性 | 提示的完整分布，每次都是新样本 | 仅保留无已存储契合覆盖的残差，一个确定性输出 | 仅残差部分；每个投影都确定 |
| 验证强度 | 通过检查接受输出 | 测试、覆盖率和证明证书 | 每个结果都有完整的验证门槛 |
| 重用和复合 | 每个结果仅使用一次 | 每个接受的契合存储并重用 | 每个通过门槛的契合都存储 |
| 模型依赖 | 每个任务都有一个模型 | 没有模型 | 仅在最后一个档位使用模型 |

在每个轴线上，方法的差异程度不同，轴线之间相互作用：重用降低了能量和待解决的剩余熵，而强验证使重用变得安全。RCE 在一种规范形式中一次性写出含义。每种表面语言都是该形式的投影，并经过检查以确保与之匹配。在等价形式中，最便宜的正确形式得以运行。

### 2.1 编程是编码理论

本节的论点是，编程可以被解读为编码理论。程序员沿着两个熵制度之间的梯度转换意图。意图是高熵，是意义的分布。代码是低熵，每个状态有一个确定的转换。软件工作的每一步，从需求到寄存器，都是这一转换的步骤。文献在七十年来，用多种语言说过这一点。本节将这些片段整合成一个论点，并将每个RCE档位放在上面。

**度量。** Shannon定义了源的熵和信道的容量 [40]，并测量了印刷英语约为每个字母0.6到1.3比特 [1]。Kolmogorov在1965年用俄语在《Problemy Peredachi Informatsii》中给出了信息量的三种方法，并将算法方法作为主要方法：对象中的信息是生成它的最短程序的长度 [41]。Solomonoff通过归纳推理理论达到了同样的对象 [42]，而Chaitin展示了程序大小在形式上与Shannon的相同 [43]。Rissanen将这一想法转化为选择模型的规则，即最小描述长度 [44]。他们一起说，程序是一个码字：行为的描述，最短的正确程序是下限。RCE的提取规则，即在等价契合中保留焦耳最少的契合（命题3），就是用焦耳代替比特的那条规则。

**代码位于低熵制度，人们已经测量过它。** Hindle、Barr、Su、Gabel和Devanbu发现代码是“非常重复的，事实上甚至比自然语言更重复”，在相同的n-gram模型下，其交叉熵更低 [35]。Gabel和Su发现项目中的大多数行已经在其他地方存在 [34]，而Lopes等人发现GitHub上的大多数文件都是克隆的 [33]。Tu、Su和Devanbu发现代码也是局部的：附近写的内容预测了接下来的内容 [46]。Ray及其同事发现有错误的行更不自然，熵更高，而当错误修复后，熵会下降 [45]。2025年，Yang、Kolak、Hellendoorn和Martins使用补丁引起的熵变化来对修复候选进行排序，并将正确补丁与过拟合补丁区分开来 [51]。Allamanis、Barr、Devanbu和Sutton在名为自然性的研究中对这一领域进行了综述 [47]。结果不仅限于英语。Prem Devanbu在2013年印度软件工程会议上将其作为主题演讲 [50]。IBM Research India的Sridhara、Sinha和Mani在同一场所测量了代码周围的自然语言工件，并发现提交信息是最规则的，而Stack Overflow的文本表现得像普通英语 [49]。在中国，《软件学报》（软件学报）于2022年发表了一篇关于代码自然性的研究综述，指出交叉熵度量和缺陷代码熵更高的发现 [48]。在日本，大阪大学的Doi、Higo、Arima、Shimonaka和Kusumoto使用n-gram自然性，首先在日语IEICE技术报告中，然后在2018年ICPC上，区分了机器生成的源文件和人工编写的源文件 [73, 74]。生成的代码在熵尺度上甚至比人类代码更低，因为生成器是一个固定的转换。在巴西，Arrebola的博士论文基于按项目和维护者分割的n-gram和主题模型构建了代码建议，并通过交叉熵（编码下一个词元所需的比特数）进行了评估 [75]。这两个制度在一个仓库中可见：代码周围的文本是高熵的，而代码是低熵的。

**度量很重要。** Febres、Jaffé和Gershenson，来自委内瑞拉和墨西哥，通过每条消息长度的词汇多样性比较了英语、西班牙语和程序文本，发现程序文本更具多样性 [76]。Rahman、Palani和Rigby发现代码的n-gram可预测性很大程度上来自于语法词元，一旦去除这些，代码仍然重复，但比最初报告的要少，API使用是最重复的部分 [77]。这两个结果都加强了这一主张，而不是逆转它。符号的多样性不是可预测性，低熵制度是下一个步骤的条件分布的属性，这是确定性转换所固定的。出于这个原因，RCE的G0依据形状而非表面词元建立索引。

**意图位于高熵制度。** Zave和Jackson表明，需求是对环境的陈述，规范是在接口上的陈述，而它们之间的差距只能通过通常未写明的领域知识来填补 [64]。Brooks将软件的难度分为本质和偶然：本质是概念构造，其中大部分是规范和设计，而不是表示 [61]。Naur认为，程序是程序员所持理论的可见部分，而该理论无法完全从文本中恢复 [62]。通过Shannon的视角，三者都表达了同样的意思。意图比任何单一程序都携带更多的不确定性，而编写程序是消除这种不确定性的行为。代码编写完成后，程序员脑海中剩下的部分是代码未编码的意图部分。

**转换是一个细化过程，细化是一个缩小过程。** Hoare为程序提供了一种逻辑，其中程序相对于前条件和后条件是正确的 [54]。Wirth教授了逐步细化：通过连续的决策将任务分解为指令，每个决策都解决了规范中留下的选择 [53]。Dijkstra的受保护命令将开放选择明确为非确定性，并通过去除它从规范中推导出程序 [52]。在慕尼黑，Bauer和Wössner的CIP项目将程序开发构建为从规范到程序的正确性保持转换序列 [58]。在法国，Abrial的B方法和随后的Event-B将细化扩展到工业规模，每一步都有证明义务 [55, 56]。在芬兰，Back和von Wright为细化提供了格理论的计算 [57]。在每种情况下，规范表示一组可接受的行为，每个细化步骤都会缩小该集合，直到只剩下一个确定的行为。这是每一步都有证明的熵减少。RCE的形式是该链的最后一个元素：一个完全确定的数据库状态上的转换$\delta$，每个选择都已解决（[§3.2](#32-definitions)）。

**合成是缩小假设空间的搜索。** Gulwani的FlashFill通过表示所有一致程序的集合，并与每个新例子相交，从几个输入输出例子中学习字符串程序 [59]。Gulwani、Polozov和Singh将程序合成一般地表述为通过意图约束的程序空间的搜索 [60]，而Solar-Lezama的草图用求解器填充部分程序中的空缺 [27]。每个例子或约束都是一个去除假设的测量。Shannon的度量计算需要多少这样的测量。RCE的G2就是这个档位。

**转换产生的结果只有一个形状。** Gurevich证明每个顺序算法都可以在自己的抽象层次上被抽象状态机捕获 [2]。Codd将状态设为关系 [5]，而事件溯源将状态设为仅追加日志的折叠 [14]。在Curry和Howard下，证明是一个程序，命题是一个类型 [18, 72]，因此经过验证的契合就是其规范的证明。这就是为什么低熵制度的形状很少：目的地是数据库上的状态机，无论表面语言是什么。

**没有门槛，低熵会衰减。** Lehman在几十年的大型系统观察中发现，正在使用的程序必须不断变化，除非采取措施减少其复杂性，否则其复杂性会增长 [63]。Torres、Baltes、Treude和Wagner测量了25个项目提交历史中的结构和文本熵，发现两者一起上升 [78]。熵从环境中流回代码。一个保持代码在低熵制度的系统需要在每个更改上设置一个门槛，而RCE的门槛是正确性（[§4.3](#43-the-gate)）。

**编译器已经进行了源编码。** Franz和Kistler将程序作为压缩的抽象语法树进行传输，并在加载时生成本地代码，这是程序在自身语法上的源编码 [67]。Fraser从语料库中推断代码的统计模型以压缩它 [68]。Futamura在1971年日本期刊《Systems, Computers, Controls》中展示了将解释器专门化为程序会产生编译程序，而将专门化器专门化会产生编译器 [70]。Novosibirsk的Ershov将这一想法发展为混合计算 [71]。Cousots的抽象解释计算了程序每个行为的健全、信息较少的描述 [69]。与信道编码的类比是本文的解读，而不是引用的定理：类型、测试和证明添加了被检查的冗余，以便在程序运行之前检测到错误程序，就像奇偶校验检测到损坏的字一样。

**擦除是焦耳的去向。** Landauer证明了一个逻辑不可逆的步骤，即擦除一个比特，至少会耗散$k_B T \ln 2$ [65]。Bennett证明计算原则上可以是逻辑可逆的，因此擦除，而不是计算，承载了界限 [66]。将高熵意图转换为一个低熵程序会丢弃意图允许的每一个替代方案。这种丢弃是对替代方案信息的擦除，它有一个热力学下限。RCE对每个新案例只支付一次丢弃代价并存储结果，因此重复案例不会擦除任何新内容。

**表面成本的度量。** 自然性结果有两个修正，本文现在携带，还有一个与无名形式有关的发现。首先，一旦去除语法词元，代码和散文之间的原始熵差距显著缩小 [77]，Casalnuovo、Lee、Morgan和Devanbu发现剩余部分的一部分是熟悉效应：在顶级星级的Java和Python项目中，原始代码的意外性低于意义保持的重写，50个人评分者61.9%的时间与语言模型的偏好一致 [132]。读起来自然的是读者见过最多的，因此一个规范形式改变了那个循环的平衡，而不是逃离它。其次，跟踪测量理解负载的唯一数量是文本大小、词汇大小和数据流依赖范围：在一项测试代码度量与大脑激活的研究中，这三个相关性Kendall τ ≈ 0.4，而McCabe圈复杂度与任何东西都不相关（τ ≈ 0.09） [133]；在121个可读性度量和444次评估中，没有一个度量达到|τ| > 0.16与测量理解度相关 [134]；并且与破坏布局的漂亮打印相比，没有fMRI差异 [135]，与发现格式化是括号语言的13到15%的词元，并且可以剥离10个语言模型而不会显著影响准确性一致 [136]。第三，名称是一个低一致性、高依赖性的通道：两个开发人员选择相同名称的中位概率为6.9% [137]，在7到13%的情况下，评论与它们描述的代码共同演化 [138]，而前沿模型在删除或替换标识符时，摘要准确性损失11到29点，执行预测准确性损失高达24点 [139]。相比之下，人类在神经层面上并不将标识符作为语言处理：用日语标识符替换英语标识符改变了语言系统响应Δβ = 0.03 [140]。对RCE的后果在[§3.8](#38-behaviour-equivalence-and-dimension)中陈述：位置保留在哈希中（T7），名称保留在哈希之外，但保存它们的侧表必须携带名称编码的概念，因为唯一重要的作者会通过名称阅读，而形式尚未表明模型可以从无名形式推理。

### 2.2 RCE如何转换，以及每个档位的位置

从编码理论的角度来看，任务以消息的形式到达，其剩余的不确定性是任何已存储契合尚未解决的部分。每个档位以不同的代价消除不确定性，各档位按这一代价排序（[§4.2](#42-the-gears)）。

| 档位 | 对不确定性的处理 | 上述论证中的谱系 |
|---|---|---|
| G0 查找 | 识别意图已被编码；通过检索解决，位于处理器底层 | 重复性和克隆 [33, 34, 35]；局部性 [46] |
| G1 规则 | 应用已知的受保护重写；通过无搜索解决重复的残差 | 保持正确性的转换 [52, 58]；带有证明义务的细化 [55, 56] |
| G2 合成 | 在假设空间中搜索，并通过示例、约束和求解器缩小范围 | 作为搜索的程序合成 [27, 59, 60] |
| G3 到 G5 模型 | 当没有更低档位关闭差距时，从学习到的代码分布中采样；仅提议者 | 代码的交叉熵模型 [35, 47] |
| 门槛 | 仅在测试、覆盖率和证明证书通过后接受候选方案 | 霍尔逻辑 [54]；柯里-霍华德 [18, 72] |
| 晋升 | 存储已接受的契合，使相同残差下次只需付出G0的代价 | 最小描述长度 [44]；兰道尔擦除仅支付一次 [65] |

第2节坐标轴上的位置差异在于转换代价的支付位置。一种方法在每个任务上对提示的完整分布进行采样，每次都会再次支付高熵侧的代价。存储并重用已接受契合的方法只需为残差付费，且仅付一次。大多数系统位于这两端之间，而RCE位于重用端。

### 2.4 有门槛的、经过验证的递归自我改进

Good（1965）[111] 将超智能机器定义为能够设计出更好机器的机器，因此改进将递归进行。Yudkowsky（2013）[113] 将问题表述为收益问题：即每一次改进是否使下一次改进变得更便宜或更昂贵。Schmidhuber 的 Gödel 机器（2007）[112] 给出了一个带有保证的正式答案：一个程序只有在证明重写能提高其预期效用后，才会重写自身的一部分，包括其自身的搜索。Löb 定理（1955）[114] 是一个自我信任的证明者所遇到的障碍，Yudkowsky 和 Herreshoff（2013）[115] 将其命名为 Löbian 障碍：一般来说，一个系统无法证明其继任者使用其自身证明系统的正确性。最近的系统放弃了证明要求，而是通过测量得分来选择：STOP（Zelikman 等，2023）[116] 改进了改进代码的支架，Darwin Gödel 机器（Zhang 等，2025）[117] 保存了一个由基准得分选择的自修改编码代理的档案，AlphaEvolve（Novikov 等，2025）[118] 在自动评估器下进化程序，Voyager（Wang 等，2023）[119] 增长了一个被后续任务重用的已验证技能库。

RCE 采用了 Gödel 机器的结构和 Voyager 的技能库，但有两个区别，使其能够避免对所推广对象的障碍。首先，被改进的对象不是证明者。在设计中，RCE 推广处理器、重写和档位，每个都与一个固定的内核和一个固定的证明规则进行检查：内核所模型检查的属性（[§5.3](#53-model-checking-of-the-kernel)）和用于可满足性模理论（SMT）求解器的 Form 算术编码（[§5.2](#52-the-proof-rule-for-rewrites)）在推广过程中不会改变，因此不需要信任继任者的证明系统。其次，门槛是边界处的正确性证明，而不是得分。得分可能在接口假设被打破时上升；边界处的证明无法被打破它的变化所通过。

**命题 R1（单调正确性）。** 如果每个被推广的更改都通过了其边界的检查，且其他边界的检查保持不变，那么推广前由这些检查建立的每个属性在推广后仍然成立。

**命题 R2（复合性）。** 设工作负载是任务的多重集合，设被推广的处理器关闭了其形状的每个任务。那么在第 $t$ 轮中，升级的次数随 $t$ 非递增，且在第 1 轮之前被推广的纠正会通过在后续每一轮中关闭的升级次数，降低每个时间范围的累计升级次数。

**命题 R3（下降成本）。** 由于被推广的处理器替代了模型调用，其成本是根据基板表定价的处理器操作次数，因此随着升级次数趋于零，一轮的估计能量（`est_j`）将趋近于仅运行处理器的估计能量。该命题针对的是估计值；没有实测读数支持它。

Futamura 的投影（1971，1999 年再版）[120] 和 Turchin 的超级编译（1986）[121] 给出了这一过程的极限。将解释器专门化为程序会生成一个编译后的程序；将专门化器专门化会生成一个编译器。RCE 的推广将通用升级路径专门化为实际发生的形状，因此引擎会收敛到其工作负载的残余程序：即模型或人仍需提供的计算部分。在门槛下的递归自我改进就是这种收敛，通过已检查的步骤实现。

### 3.1 “相同形式”的最强形式化表述

首先陈述定理的范围。Gurevich 的顺序公理涵盖了顺序算法；并行和交互算法需要 Blass 和 Gurevich 的进一步公理 [3]。Blass、Dershowitz 和 Gurevich 认为，没有一种算法的等价关系适用于所有目的 [79]，而 Moschovakis 和 Vardi 则阐述了关于算法本质的争论 [80, 81]。一个处理输入和输出的网络处理器位于顺序定理之外。形式以交互线的方式处理交互：每个输入是 $E$ 中的一个事件，状态机根据它进行步骤。因此，“一个形式”是一个基于顺序定理并由惯例扩展的建模选择，其生产先例包括 Elm 架构 [83]、持久工作流事件历史 [84] 和如 Flo [82] 这样的流语义。第 3.4 节的命题是针对这一选择陈述的。

Gurevich 的抽象状态机（ASM）定理是关于每个算法都有一个形状的最强形式化表述 [2]。抽象状态机是一种状态为一阶结构、步骤为有限个受保护更新的机器。Gurevich 提出了三个公理。顺序时间：算法具有状态、初始状态和一个一步映射 $\tau$。抽象状态：状态是一阶结构，基于一个固定词汇，且在同构下封闭。有界探索：有限个项决定每一步。他的主要定理（定理 6.13）表述为：“对于每个顺序算法 $A$，存在一个等效的顺序抽象状态机 $B$。” Blass 和 Gurevich 将其扩展到并行算法 [3]。Dershowitz 和 Gurevich 添加了第四个公理，即初始操作是可计算的，并由此推导出 Church 的论题 [4]。

### 3.2 定义

**定义 1（形式）。** 一个程序是一个元组

$$P = (S, E, \delta, D, \lambda)$$

- $S = \Sigma_c \times \Sigma_d$，状态空间：基于固定词汇表 $\Sigma$ 的结构，分为控制区域 $\Sigma_c$ 和数据 $\Sigma_d$。$\Sigma_d$ 包含逻辑时钟、输入计数和类型化关系（在语言中，也包括声明的区域）。每个状态都是 Codd 意义上的数据库实例 [5]。
- $E$，事件字母表，包括逻辑时钟的滴答。
- $\delta : S \times E \to S \times O^*$，转移：总、确定性和纯，写成有限的受保护更新集合“如果 $\varphi$ 那么 $f(\bar t) := t_0$”，每一步读取一组有限的位置。它返回下一个状态和该步骤的输出。写 $\delta_1 = \pi_1 \circ \delta$ 为其状态部分。
- $D$，持久日志：一个条目序列 $\{\mathit{seq}, \mathit{event}, \mathit{prev\_hash}, \mathit{state\_hash}, \mathit{hash}\}$，其中 $\mathit{state\_hash}$ 是步骤后状态的规范 JSON 的 SHA-256，$\mathit{hash}$ 是前四个字段的规范 JSON 的 SHA-256，第一个 $\mathit{prev\_hash}$ 是 64 个零。日志是一个哈希链，因此更改任何过去的条目会更改所有后续的 $\mathit{hash}$。
- $\lambda = \pi_2 \circ \delta : S \times E \to O^*$，输出映射。一个 Mealy 机读取两个参数 [6]；一个 Moore 机只读取状态 [7]。

**定义 2（形式与契合）。** *形式* 是具有四个不变量的元组形状：$\delta$ 是确定性和纯的；探索是有限的；词汇表是固定的；状态是日志的折叠，

$$\mathrm{state}(D) = \mathrm{foldl}(\delta_1, s_0, D).$$

日志还可以携带每个条目的结果、输出和状态。这些是派生的：它们不被哈希，且必须等于重放（[§3.7](#37-the-language-one-text-costs-and-theorem-status) 中的 T1 和 T3）。两种结果是不同的。在规范附录 D 定义的引擎配置文件中，每个事件都会被应用，未能满足其契约的输入会产生 `reject` 输出和一个错误行（D.6），而不是保持步骤。在语言中，不适用的事件会保持状态（T8：原子性，状态不变），并被记录为保持步骤。

*契合* 是填充形状的数据：词汇表 $\Sigma$、字母表 $E$ 和 $O$、定义 $\delta$ 的规则程序 $\Pi$、定义 $\lambda$ 的输出规则，以及初始数据 $s_0$。用 Gurevich 的术语，契合是词汇表、ASM 程序和初始结构。用 Codd 的术语，$\Sigma$ 是模式，$s_0$ 是实例。用产品线的术语，契合是一个特性选择 [8]。用语法引导合成（SyGuS）的术语，契合是一个符合规范的语法中的项 [9]。

**定义 3（契合等价）。** 当对于每个事件序列 $L$，它们在 $\lambda$ 下的输出序列相等时，两个契合是等价的。

**定义 4（契合语言）。** 一个语法，其项表示契合。编程语言、State Chart XML（SCXML）中的状态图文档、XState 配置和 `.rce` 规范是契合语言。当每个 $\Sigma$ 上的 ASM 程序都有一个项时，契合语言是完整的。

**定义 5（控制投影）。** 将 $\Sigma = \Sigma_c \cup \Sigma_d$ 分为有限的控制符号和数据关系。$P$ 的状态图是 $\delta$ 在 $\Sigma_c$ 上的投影：状态是 $\Sigma_c$ 的值，转移携带一个事件和一个 $\Sigma_d$ 上的守卫，动作是对 $\Sigma_d$ 的更新。Harel 的状态图给出了层次结构和正交区域 [10]。

**定义 6（契合 e 图）。** 对于一个契合 $F$ 和一组健全的重写 $R$，契合 e 图 $EG(F, R)$ 是 $F$ 的规则项在 $R$ 下的饱和 e 图 [11, 12]。每个 e 类包含根据定义 3 等价的契合。

**定义 7（焦耳成本）。** $\mathrm{cost}_J(t)$ 是在命名基质上运行项 $t$ 一次的估计能量（`est_j`），乘以预期运行次数。

### 3.3 为什么是“数据库功能状态机”

有限关系结构是一个数据库实例，因此 Gurevich 状态是一个数据库，每个步骤是一个有界事务。*数据库*：$S$ 是一个关系结构。*功能*：$\delta$ 和 $\lambda$ 是纯的。*状态机*：运行是 $\delta$ 在事件上的折叠。Moseley 和 Marks 在架构中画出相同的线 [13]。事件溯源在应用状态中画出这条线：“将应用状态的所有更改捕获为事件序列” [14]。Dedalus 在逻辑中画出这条线，其中可变状态是按时间索引的关系 [15]。

### 3.4 命题

**命题 1（形式捕捉每一个顺序算法）。** 对于每一个顺序算法 $A$，存在一个形式实例 $P$，其运行与 $A$ 的运行相同。

*证明概要。* 定理 6.13 给出一个 ASM $B$，其状态、初始状态和一步映射与 $A$ 相同。设 $E = \{\varepsilon\}$，$\delta(s, \varepsilon) = \tau_B(s)$，$D = (s_0, \varepsilon^n)$，$\lambda$ 为恒等映射。经过 $n$ 次计时器触发后的折叠为 $\tau_A^n(s_0)$。根据 Gurevich 的推论 3.3，$P$ 和 $A$ 具有相同的运行。∎

**命题 1b（交互式程序）。** 在每一步之前，将一个空元输入符号集扩展到 $\Sigma$ 中的 $e$；然后 $\delta(s, e) = \tau(s[\mathit{in} := e])$ 是一个扩展词汇表上的顺序算法，命题 1 适用。该构造是我们提出的。

**命题 1c（可计算性）。** 在 Dershowitz 和 Gurevich 公理下，每一个形式实例计算一个图灵可计算函数 [4, 16, 17]。形式并未增加任何能力。它为该类中的每一个程序赋予了一种形状。

**命题 1d（证明是契合）。** “对于每一个命题的证明，存在一个相应类型的程序” [18]。类型是一种规范，而证明是一种契合，它满足该规范。正确性门槛是该证明的存在或通过接受测试。

**命题 2（一个生成器）。** 一个函数 $G : \mathrm{Fit} \to \mathrm{Program}$ 为每一个契合生成一个可运行的程序，且不读取任何领域。*基础：* 每一个程序都是一个形式实例，因此 $G$ 会发出一个类型化的存储、一个事件类型、编译后的规则、一个带有折叠和输出分发器的日志。如 Rails 生成器、JHipster 和 Yeoman 这样的框架生成器是 $G$ 限制在小契合语言上的实例。产品线工程始于“对相关软件系统之间共性的系统发现和利用” [8]；共性是形式。

**命题 3（最小能量提取）。** 使用 $\mathrm{cost}_J$ 进行提取，返回提取器在 $F$ 的 e 类中找到的估计能量最小的项。*证明概要。* 重写是可靠的，因此 e 类中的每一个项都具有 $F$ 的可观测行为并通过相同的门槛。提取最小化成本，而成本是 `est_j`，即以焦耳为单位的估计值，而非实测读数。∎ 该顺序是否对实测焦耳成立，正是 RCE-F5 所测试的内容（[§9](#9-falsifiers)）。这是将 Mixture of Limits（极限混合）应用于代码。伴随论文[计量提交门槛](/papers/gates/)的第二部分 Mixture of Limits 指出，一个任务需要最小预期能量来完成，而任务完成后所花费的能量不会带来任何经过验证的进展；应用于代码时，它表示：保留完成任务的最小契合，其余部分都是浪费。

**命题 4（重放确定性）。** 如果 $\delta$ 不读取墙钟时间，按无名顺序排列更新并记录每一个输入，那么对同一个 $D$ 的两次重放会在每一步给出相同的状态哈希。

**命题 5（状态图投影是可靠的）。** 将运行中的每一个状态投影到 $\Sigma_c$。结果是在相同事件下运行的所发射状态图。

**命题 6（协调预算）。** 标记为单调的规则在副本上运行时无需协调；只有非单调规则需要协调点。*基础：* CALM 定理，“具有一致、无协调分布式实现的程序恰好是可以用单调逻辑表达的程序” [19]。

规范附录 D.5 从规则而非声明中推导出标签，并且在引擎配置文件的 IR 检查下，存储标签与推导标签不同的形式需要修改：

| 规则具有 | 标签 | 原因 |
|---|---|---|
| 无 resolve、read、join 或 scan | 单调 | 其写入仅添加键并增长计数器 |
| 一个 resolve | 非单调 | 它删除升级行 |
| 对其自身 sink 的一个 read | 非单调 | 读取、修改、写入 |
| 一个 keyed join | 非单调 | 被连接的行现在可能不存在，之后可能再次出现或被覆盖 |
| 一个 scan | 非单调 | 它观察整个关系，包括缺失的部分 |

标签是可靠的但不完整：对一个仅插入关系的 join 会是单调的，但配置无法证明一个关系是仅插入的，因此标签不会声称这一点。当每一个规则都是单调时，形式是无协调的。每一个 read、join 和 scan 都看到事件进入时的状态，因此输入事件的后状态不依赖于不同 sink 的规则运行顺序；只有输出顺序依赖，且由内容哈希固定。

**命题 7（智能作为焦耳导数）。** 设 $X$ 统计通过门槛的任务数，$J$ 为所花费的焦耳数。$\iota = dX/dJ$ 将从记录每一个事件的 $D$ 中事后读取，并且在引擎的设计中从其收据（[§4.4](#44-receipts)）中读取，每张收据都携带一次档位调用的 `est_j`。目前 $D$ 中没有焦耳条目，因为没有任何检查器代码写入 `host.Energy`，而收据中的焦耳项为 `est` 或 `unpriced`；从中读取的 $J$ 是估计值，$\iota$ 也是如此。在 $\mathrm{cost}_J$ 下的提取固定门槛且不会提高 $J$，因此在 $X$ 相等时不会降低 $\iota$。

### 3.6 一个生态系统、无损以及普遍性假说

**构造上无损。** Shannon 的信源编码定理将无损编码的下限固定在信源的熵上 [40]。一个 Form 是一种在狭义上可以验证的无损编码，用于意图：Form 的规范序列化是单射的，因此任何状态、事件或转换不同的两个 Form 都会有不同的形状哈希，而解码序列化会得到相同的 Form。每个到目标的投影都只是 Form 本身的函数。双向转换使往返过程精确。Foster、Greenwald、Moore、Pierce 和 Schmitt 将镜头定义为一个 get 和 put 函数对，其往返条件使视图和源一致 [122]，Hofmann、Pierce 和 Wagner 将条件扩展到对称镜头 [123]，而 Czarnecki 及其同事则在模型工程、数据库和编程语言中对相同的条件进行了综述 [124]。RCE 的往返条件是在整个程序层面的 GetPut 条件：将投影提升回来，形状哈希保持不变。

**构造上正确。** Dijkstra 在 1968 年提出，程序和其证明应一起开发，因此正确性是设计出来的，而不是测试出来的 [125]。Hall 和 Chapman 将这种方法带入了一个商业安全系统，每一步都有形式化规范和精化 [126]。Minsky 的类型化函数编程规则“使非法状态不可表示”在类型层面表达了同样的意思：一个不能持有坏值的类型消除了检查它的必要性 [127]。Turner 的完全函数编程要求每个函数在每个输入上都终止，因此程序表示一个没有隐藏失败的数学函数 [128]。RCE 的 Form 在 Turner 的意义上是完全的，其契约类型在 Minsky 的意义上使未声明的状态不可表示，而 [§2.1](#21-programming-is-coding-theory) 的精化链在 Dijkstra 的意义上以它结束。结果如 [§1](#1-thesis) 所述：程序所做的就是其 Form 所声明的，因此事后没有需要 diff 或跟踪的内容。

**普遍性假说。** 从理论角度表述，假说是存在一个通用的 Form。程序在其中原生编写，每种现有语言都可以通过忠实的投影从它到达，而每种现有程序都可以通过提升进入它。Gurevich 的假说提供了基础：每种顺序算法都可以通过抽象状态机在它自己的抽象层次上逐步捕获 [2]，并行算法也是如此 [3]。一个 Form 是数据库状态上的这种机器。

**命题 U1（捕获）。** 如果语言 $L$ 中的程序是 Gurevich 意义上的顺序或并行算法，那么存在一个 Form，其转换在程序的抽象层次上逐步模拟它 [2, 3]。

**命题 U2（忠实投影）。** 如果 Form 到 $L$ 的投影 $\pi_L$ 在合同中的每个输入上都保留了 Form 的轨迹，那么对于每个轨迹观察者，Form 及其投影是可互换的，而 $L$ 没有 Form 缺少的内容。

**命题 U3（构造性提升）。** 每种正在使用的编程语言都有一个形式语法、一个生成具体语法树的解析器、一个抽象语法树和一个由其规范或参考实现固定的语义。每个语言的提升 $\lambda_L$ 分三个阶段构建：语法，然后是抽象语法树，然后是 Form，其中 $L$ 的每个构造都由 $L$ 的语义给出其 Form 规则。这样构建的提升在行为上满足 $\pi_L(\lambda_L(p)) \equiv p$，在形状哈希上满足 $\lambda_L(\pi_L(F)) = F$，因此这对是 [122] 意义上的镜头，而 $L$ 中的程序以 Form 形式保存，没有损失。

**命题 U4（替换）。** 如果 U2 和 U3 对语言 $L$ 成立，那么不需要用 $L$ 编写任何程序：它只需一次作为 Form 编写，然后在平台需要时作为 $L$ 发出。

**每种语言既是目标也是来源。** Form 对目标没有限制。每种目标语言都是发出注册表（规范仓库中的提案 `spec/proposals/emit-targets.md`）中的一行：在规范附录 D.7 所定义的形式项中间表示 Form IR 之上设立单一发出器，并为每种语言配一张表，固定该语言如何遵守规范 6.3 的数值与文本契约，每一行都通过同一道门槛，即逐字节匹配每个示例程序的参考轨迹（T9）。提升 $\lambda_L$ 是反向映射，从语言的固定语法和语义表进入 Form，因此每种语言既是 Form 的输出，也是它的输入。参考检查器目前可发出 Rust、Python、JavaScript 和 Scala，注册表的各层级列出了随后跟进的系统语言、平台语言、动态语言和非冯·诺依曼语言，包括 [§3.7](#37-the-language-one-text-costs-and-theorem-status) 中编目的 2024 至 2026 年新加入者。

U1 是一个定理。U2 按目标由程序发出器的测试进行检查（[§5.1](#51-differential-testing-of-the-program-emitters)），并通过 [§2.3](#23-the-ecosystem-checked-per-program) 的检查在每个程序上进行检查。U3 是一个从语法开始逐语言构建的构造，[§8.7](#87-lift-coverage-across-languages) 说明了该构造在构建过程中如何进行测量。

**两个限定条件。** U3 的提升是一个构造，其定义域比上面的句子所暗示的要小。Form 要求每个程序都完成（T2），因此从任何图灵完备语言的提升最多只是该语言终止片段的映射，而属于该片段的成员是不可判定的（将 Rice 定理应用于一个完全目标 [141]）。在终止片段上，提升仍然不是规范的：闭包表示（子项成为控制状态）和评估顺序是自由选择的，而逆映射仅存在于去函数化的程序中 [142, 143]。因此，$\lambda_L$ 是一个构造，其定义域是不可判定的部分映射的图像，镜头往返条件在该图像上成立，而“每个现有程序通过提升进入它”是关于该构造所达到的片段的陈述，该片段的测量方式如 [§8.7](#87-lift-coverage-across-languages) 所述。第二个限定条件涉及哈希，该哈希用于声明单射性。规范 6.1 对状态和事件的位置形式进行哈希（声明顺序中的区域和字段作为列表，变体通过其索引，事件通过其在模块事件中的索引）；存储的条目保留其可读的 `event` 和 `state`，而轨迹在 `hashed` 下重复哈希形式（轨迹格式 `rce-trace/2`）。Lean 模块 `RCE/NameFree.lean` 对 De Bruijn 键进行哈希，而 `RCE/Positional.lean` 模型化了位置嵌入（声明类型作为字段列表在声明顺序中记录，变体作为索引和字段，事件通过索引，未声明记录通过名称），并证明其在任何单射且固定未声明名称的重命名下保持不变，这正是无名投影所执行的操作，因此状态哈希和整个条目链对每个哈希函数都保持不变；它哈希的事件索引定义为 De Bruijn 模型的声明索引，因此两种编码在其共享的组件上一致。参考检查器和 Python、JavaScript 和 Rust 运行时在哈希上达成一致，一个测试检查了程序及其无名投影是否具有相同的日志哈希，如 T7 所述；在公共提交 `f2bd7222`，该提交添加了 `RCE/Positional.lean`，审计在仅使用标准公理的情况下通过了 5,052 个定理。早期的参考检查器对命名规范 JSON 进行哈希，因此其日志哈希依赖于名称，而模型的不依赖；规范的提案注册表记录了这一发现、演示该发现的测试，以及其作为 C.15 的勘误（日志条目在程序意义之外），包括轨迹固定件、应用程序黄金标准、130 个符合性钉和标准库的馈送向量重新生成。

### 3.7 语言：一个文本，成本和定理状态

RCE 语言由书面规范定义（[/rce/spec/](/rce/spec/)；源代码在 [rce 仓库](https://github.com/openIE-dev/rce) 中）。存在一种语言，即某一提交版本的规范文本，每个程序模块都使用它（规范 2.7）。第 2 至 10 节定义了核心内容；附录 C 定义了并发（`par`、`for ... par`、`with budget`、工作组、LVars、会话和监督器），并适用于每个模块；附录 D 定义了引擎配置：引擎设计的处理器规范和契合。没有声明选择方言：第一行的 `# rce-version:` 注释是一个发布标签，命名了模块编写所依据的规范提交版本，被检查器忽略且不进行哈希处理，检查器未实现的构造作为保留且未实现的构造需要修改（W-RES-1，附录 F.12）。该语言正在开发中，并随着项目的深入认识而变化：一种形式可以被添加、泛化或替换，而该变化以及它所触及的仓库中的每个程序都在同一提交中一起移动，从不作为每个模块的选择，因此程序从不依赖于另一个程序或库的版本：在某一提交中检查的所有内容都与该提交时的规范一致。

**为何使用一个文本且不选择版本。** 版本记录支持这一规则，而非早期草稿中每个模块的选择。每个包一个版本并具有任意约束的依赖关系解析是 NP 完全问题，已在 Linux 发行版 [176] 中建立，2020 年重新表述为每个非平凡组件模型 [177]，并独立地通过从 3-SAT 的归约证明了语言包管理器 [178]。语义版本号并不承载它所承诺的内容：在七年的时间里，Maven Central 超过三分之一的发布引入了破坏性变更，在次要和补丁版本中，破坏性变更的频率与主要版本相当 [179]，对 119,879 次升级的复制研究仍发现 20.1% 的非主要版本存在破坏性变更 [180]，Google 工程文本得出结论，语义版本控制是对采用变更风险的有损摘要，并在单一仓库中保留所有版本 [181]。暴露性是传递图的属性：在受 Log4j 漏洞影响的 35,863 个 Maven 工件中，超过 80% 的依赖关系深度超过一层 [182]。记录的收敛点是基于内容的标识，因此两个不同的事物从不共享名称，变体可以共存 [183, 184]，基于从未重复使用的名称的累积变化 [185]，以及直接证明变更保留了行为而非数字断言 [186]；硬件设计已经运行了这样的证明，等价检查，作为二十年来每个修订版本的门槛 [187]，可重复构建通过哈希将工件与其源代码绑定 [188]。RCE 设计将这些作为规则：一个提交版本的一个文本，定义哈希与封闭兼容性表（F.4.3），一个通过哈希固定且无解析器的清单（F.5.3），无名称的日志哈希（T7）以及行为作为两个程序相同的意义（[§3.8](#38-behaviour-equivalence-and-dimension)）。2026 年 10 月 24 日的调查，将记录与这些规则进行比对，列出其列出的空白（一个完整的程序哈希、每次变更时作为门槛运行的等价检查、生成代码中的出处），在数据仓库中（[/data/](/data/#rce)），其提议是 `spec/proposals/one-commit-change.md`。

**预算计算工作。** `with budget` 块从附录 C.6.4 的表中为每个操作收取固定成本，并在计数用尽时通过 `budget` 报错。计数是工作的代理，而非时间或能量的测量；`est_j` 是独立的。

| 操作 | 成本 |
|---|---|
| 用户函数或闭包的调用，$c_{call}$ | 4 |
| 接收器大小为 $n$、第一个参数大小为 $k$ 的标准库方法 | $4 + w(m, n, k)$ |
| 通道发送或接收 | 8 |
| `spawn` | 32 |
| 一个 `par` 分支或 `for ... par` 块 | 16 |
| 列表或映射字面量，或推导式，有 $n$ 个结果；`[x; n]` | $4 + n$ |
| 索引、切片、成员访问；一元运算符；`and`、`or`；整数、布尔和文本运算符和比较 | 1 |
| 浮点 `+`、`-`、`*` | 2 |
| 浮点 `/`、`%` | 8 |

大小是文本的 UTF-8 字节长度、列表的长度和映射的条目数；其他任何值的大小为 0。方法工作 $w$ 由参考评估器中方法的复杂度类固定：对于文本、列表和映射（映射是有序的关联列表）的线性方法，$n + k$；对于 `sort`，$n \lceil \log_2 n \rceil$（当 $n \le 1$ 时为 0）；其余方法为 0。`map`、`filter` 和 `fold` 对其函数参数的调用将被额外计为调用。算术在最大的 128 位整数上饱和，且 $w$ 在 $n$ 或 $k$ 增加时从不减少。参考评估器和生成的 Rust、Python 和 JavaScript 运行时计算相同的函数，测试检查预算陷阱在所有四种运行时中都落在相同的操作上。

**一个成本规则。** 标准库方法调用的成本是文本的单一成本，每个模块和无论调用从何处执行（规范 2.7，C.15）。该规则是文本的词法规则，而非模块的，因此链接模块不会改变任何成本；测试在参考评估器和生成的 Rust、Python 和 JavaScript 程序的模块边界上双向检查它。

### 3.8 行为、等价性和维度

定义 3 表示当两个契合的输出序列在每个事件序列上一致时，它们是等价的。本节为该定义赋予一个普遍性质，定义程序的维度为一个计算出的数字，并报告其注册的测量结果。规范性文本是规范第 6.10 节（草案 0.9，提交 `45fc95c`），包含定理 T57 到 T61 以及命令 `rce dim`。

**行为作为最终余代数中的一个点。** 固定一个程序 $P$，其状态空间为 $S$，事件字母表为 $E$，且 $\delta : S \times E \to S \times O^*$，并按照定义 1 写出 $\delta_1 = \pi_1 \circ \delta$ 和 $\lambda = \pi_2 \circ \delta$。状态 $s$ 的行为是函数 $\mathrm{beh}_P(s) : E^* \to (O^*)^*$，其中 $\mathrm{beh}_P(s)(\varepsilon) = \varepsilon$，且 $\mathrm{beh}_P(s)(e \cdot w) = \lambda(s, e) \cdot \mathrm{beh}_P(\delta_1(s, e))(w)$：沿任何事件序列的每一步输出。$(S, \langle \lambda, \delta_1 \rangle)$ 是余代数 $F(X) = (O^* \times X)^E$ 的一个余代数；$F$ 有一个最终余代数 $\mathrm{Beh}$，其载体是因果流函数的集合，且 $\mathrm{beh}_P$ 是唯一的余代数同态 $S \to \mathrm{Beh}$（Rutten [144]，定理 2.3）。当 $\mathrm{beh}_F(s_0^F) = \mathrm{beh}_G(s_0^G)$ 时，两个契合是等价的，即 $F \equiv G$。这是定义 3 的重述；新内容是 $\equiv$ 是一个对象中的等同，每个形式在每种契合语言中都通过相同的构造映射到该对象。行为空间不是一个流形：它携带前缀超度量 $d(b_1, b_2) = 2^{-n}$，其中 $n$ 是最短区分事件序列的长度，且在该度量下它是完整且完全不连通的 [145]。因此，所有长度最多为 $k$ 的序列上的轨迹一致可以认证 $d \le 2^{-(k+1)}$：围绕行为的一个球，而不是行为本身。这就是 [§5.1](#51-differential-testing-of-the-program-emitters) 中的微分测试所建立的，且它从未进入哈希。

**两种证明方法。** 一个关系 $R \subseteq S \times S$ 是 $P$ 的一个双模拟，当 $s\,R\,t$ 时，对于每个 $e$，$\lambda(s, e) = \lambda(t, e)$ 且 $\delta_1(s, e)\,R\,\delta_1(t, e)$。T58 表示 $\mathrm{beh}_P(s) = \mathrm{beh}_P(t)$ 当且仅当某个双模拟关联 $s$ 和 $t$：要证明两个契合等价，展示该关系；要证明它们不同，展示一个区分序列，该序列也给出距离。T1 和 T2（完全性和确定性）正好是使最小机器唯一的完全性和确定性；一个未完全指定的机器没有唯一的最小值 [146]。

**维度。** $\mathrm{reach}(P)$ 是从 $s_0$ 可达的状态集合；由于规范中的值和大小限制（N9），$S$ 是有限的，因此 $\mathrm{reach}(P)$ 也是有限的。$P$ 的维度是

$$\dim(P) = |\{\mathrm{beh}_P(s) : s \in \mathrm{reach}(P)\}|,$$

即 $P$ 可以处于的不同行为的数量，这正是其最小 Mealy 机器的 Nerode 指数 [147]，对于显式字母表可以在 $n \log n$ 中计算 [148]。$\log_2 \dim(P)$ 是行为所需的状态位数；$\log_2 |\mathrm{reach}(P)| - \log_2 \dim(P)$ 是契合的冗余度，即改变未来输出的状态位数。一个控制维度 $\dim_c(P) \le \dim(P)$ 是在将 $\Sigma_d$ 上的每个守卫替换为其谓词符号的投影上定义的，这是一个符号有限自动机 [149]，其最小机器通过在规范事件顺序中的广度优先遍历编号，具有唯一的无名字符串 [150]；其在规范 JSON 上的 SHA-256 是 `shape_ctl`，这是名称无名项哈希和定义 6 的 e 类键之外的第三个键。任何键上的相等意味着等价；不相等意味着什么也没有。

这里应明确说明哪些是定理，哪些不是。$S$ 和 $E$ 由于值限制是有限的，但非常巨大：每个字段的 $|S| \le 256^{\mathrm{VALUE\_LIMIT}}$，因此有限性使每个行为问题可判定，但没有一个是可处理的。最小机器是有限控制投影的规范形式，其中符号自动机的最小化在谓词等价下是唯一的 [149]；对于仅被比较和复制的字段，寄存器自动机给出了一个 Myhill-Nerode 定理 [151]；当 $\delta$ 将整数算术引入状态时，唯一的规范对象是项本身。因此，“每个形式都是一个有限的 Mealy 机器，其最小机器是其规范形式”在 $\Sigma_c$ 加上守卫谓词时是正确的，但不是 $\Sigma_d$ 的可计算声明。这也是对命题 3 的诚实解读：最小焦耳提取返回的是提取器找到的最小焦耳项，且在一个 e 类上定义了三个不同的函数：规范 C.6 中的目标盲预算单位，它们在每个运行时的相同操作上放置预算陷阱，且从不焦耳；`est_j`，它是每个目标的（[§6.3](#63-energy)）；以及通过树成本选择的哈希代表，使用规范 JSON 作为可重复性的平局解决者。一个 e 类的发出项和哈希项可能不同；在给定相同日志的情况下，它们在引擎之间可能不会不同。

**定理的状态。** T57（最终性：$\mathrm{beh}_P$ 是唯一的余代数同态），T58（等价性是双模拟性），T59（轨迹一致到长度 $k$ 限制距离为 $2^{-(k+1)}$），T60（对于有限 $S$，$\mathrm{reach}(P)$ 通过最大双模拟的商是具有 $\dim(P)$ 状态的最小机器）和 T61（`shape_ctl` 在重命名和守卫谓词等价重写下是不变的）在规范第 10 章中陈述，且 `spec/lean/RCE/Behaviour.lean` 在 `lake build` 中（公开提交 `f87d6af2` 处为 Lean 4.36.0，在仅使用标准公理且无 `sorry` 的条件下通过了覆盖 5,393 个定理常量的 `scripts/lean-audit.sh` 与六内核 `lake check --paranoid`；更早于提交 `f2bd7222` 在 Lean 4.12.0 上记录为 5,052 个定理常量）。在该章的确切范围内证明的内容：T57 的同态方程（`beh_cons`；同态的唯一性被陈述，未证明）；T58 对于一个程序和两个程序（`bisim_beh`，`beh_bisim`，`behEq_iff_bisim`，`bisim2_beh`，`beh_bisim2`）；以及 T59 在显式有限字母表上双向，`rce dim` 探索的边界集上声明的事件（`trace_ball`，`ball_trace`），在所有 $E$ 上声明，未证明。T60 被陈述，下一步是通过分区细化的模型证明。T61 仅针对重命名进行测试，使用无名投影 `rce fmt nameless`，该投影按首次声明顺序按类型打印位置名称的程序，并在源代码接受时接受，具有相同的轨迹哈希（T7）；其在守卫重写下的不变性被陈述，未证明，且符号商未实现。

**`rce equiv`：作为工具的等价性检查。** `rce equiv A B` 从初始状态在相同的事件实例上探索两个程序，通过其无名输出（以位置形式发出的值，保持步骤由其错误的声明索引表示，T7）比较每一步，联合细化两个图，并读取两个初始状态是否属于同一类（T58）；当它们不属于时，打印最短区分事件序列及其末端的两个输出。`rce change OLD NEW` 将其与 F.4.3 的导出差异结合，并将更改分类为勘误（每个导出兼容，每个行为保持）、含义更改或接口更改，这是由工具决定的 C.15 规则。作为持续集成步骤在每个语料库程序与其无名投影之间运行时，该检查发现了一个投影需要修改的程序（一个命名得像标准库方法的状态字段把该方法也重命名了）；投影修正后，扫描报告每个语料库形式均与其投影等价，正如 T7 所述。这是硬件设计在每次修订上运行的等价性检查在形式上的版本（[§3.7](#37-the-language-one-text-costs-and-theorem-status)）：每个程序保持其行为的更改是勘误，其他更改则是含义更改，由工具而非版本号决定。加上打印无名投影上程序哈希的 `rce hash`（一个程序及其重命名对应同一哈希，步骤改变则对应不同哈希），以及每个发出文件如今携带的出处行，记录中称为在新语言中罕见的这三项机制（第 3.7 节）都已是参考检查器的命令。

**`rce dim`，以及注册的运行。** `rce dim [control] [fuel n] FILE` 在声明的事件上以广度优先方式探索 $\mathrm{reach}(P)$，有效载荷取自每个字段的精化类型，无精化类型时取自规范 6.3 的边界集，最多探索 `fuel` 个状态，然后以输出作为初始分区运行 Hopcroft 分区细化（100,000 个状态耗时 10 到 40 秒；第一版 Moore 迭代是二次的，未能跑完），并报告已探索状态数、行为数（未达上限时为精确值，否则为下界）、每个区域的冗余比特数，以及在指定 `control` 时的控制状态数和 `shape_ctl`。编写了三个已知值的示例：一个带有未读标志的计数器（1.00 位冗余）、一个发出奇偶性的模 6 计数器（1.58 位），以及一个具有三个可达状态且无冗余的门。预注册（`openie-research-experiments/rce/bench/dimension/PREREG.json`，在命令构建之前于 2026 年 10 月 22 日注册，并在后续每次运行前修订，配有哈希侧车文件）固定了总体以及关于已探索步骤会发出或保持状态的有界程序的三个假设：H0，至少一半的程序携带超过 0.5 位冗余；H1，单发出点程序比多发出点程序携带更多冗余；H2，当冗余超过 1 位时，单一区域携带至少 80% 的冗余。其证伪者为 [§9](#9-falsifiers) 中的 RCE-F6，即中位冗余低于 0.1 位。此处报告的运行 `dim-r2` 到 `dim-r5` 均针对 `openIE-dev/rce` 公开提交的构建各执行一次，参数为 `--fuel 100000 --control`（自将命令行改为位置参数的 openIE-dev/rce `a5df5be7` 起写作 `fuel 100000 control`），每行均记录二进制哈希；第一次注册运行 `dim-r1` 及此前的试点列于 [§10](#10-work-to-finish)。控制标签仅为保持步骤的错误或发出的构造子，在这些运行的每一行中 $\dim_c \le \dim$ 均成立。对于示例读取了状态却从不发出的状态机，意图仅由示例承载而无任何输出承载；由 `rce check` 报告指出此类 `example`（读取了没有任何步骤发出或据以保持状态的字段）仍是一项开放提案。

**概念记录。** 规范 6.6 现在描述了一个未哈希的侧表，其键为程序的无名键，保存其名称、意图字符串和文档注释，且 `rce emit form` 在 `names` 下打印它，按声明索引（`shape_ctl` 使用的索引）键，哈希字段之后。投影渲染它；$\delta$ 从不读取它；它是使形式的投影成为对称镜头 [123] 而非收缩的补集。[§2.1](#21-programming-is-coding-theory) 的证据表明，表必须保存一个名称所代表的概念，而不仅仅是其拼写，因为词汇选择和顺序是开发者在 6.9% 的情况下不同意的两个步骤 [137]，而他们同意的步骤是概念。一个模型是否可以从附加记录的表中以及从命名表面中推理，是 [§12.3](#123-why-human-written-code-is-redundant) 中注册的三个实验中的第一个，且是开放的。

## 4. 引擎：档位、门槛和收据

本节描述了引擎的设计，该设计由规范的附录 D 及其提议所定义。

<div id="41-the-engine-is-a-form" class="anchor-alias" aria-hidden="true"></div>

### 4.1 引擎是一个形式

RCE 以小的确定性处理器的图形式运行软件。无法决定的处理器会引发升级。解析器一次回答升级，并将答案安装为永久处理器，因此相同形状的下一个案例在没有解析器的情况下运行。设计要求引擎满足每一个形式不变量：

| 不变量 | 设计对引擎的要求 |
|---|---|
| 重载是一个验证的折叠 | 重载逐字读取日志，重新计算每一个哈希和链接，并使用 $\delta$ 折叠其余部分。没有任何内容被重新盖章。损坏的链不会加载。 |
| 无名的时钟顺序 | 处理器按照拓扑等级顺序运行，然后按照无名节点键运行。输出在所有处理器运行后分阶段进行并交付，如 ASM 语义所示。重命名每个节点在每个入口处产生相同的匿名状态哈希。 |
| 没有静默丢弃 | 一个完整的邮箱将消息放入有序队列并记录 `Backpressure`，并且每个任务仍然关闭。 |
| 载荷在日志中 | 输入、时钟、外部处理器结果、安装和故障是日志条目。每个条目后的状态哈希与从空引擎折叠的结果匹配。 |
| 逻辑时钟 | 活性计数时钟，而不是墙时间。 |
| 稳定的哈希 | 对规范 JSON 上的 SHA-256（安全哈希算法，256 位），在每个深度上排序键，用于条目、状态、形状和规则 id。 |

<div id="42-the-gears" class="anchor-alias" aria-hidden="true"></div>

### 4.2 档位

只有当下方的档位未能通过门槛时，才会尝试当前档位。该顺序是一个固定的级联。

| 档位 | 方法 | 系谱 |
|---|---|---|
| G0 查找 | 一个以 SHA-256 形状哈希为键的共享处理器库；用于代码修复，定位到排名函数 | 代码搜索和检索 [21] |
| G1 规则 | 确定性、受保护的修复模板和模式派生的验证器，每个都检查对突变的敏感性 | PAR, TBar, AVATAR, FixMiner [22, 23, 24, 25]; 诸如 Coccinelle 的代码修改 [26] |
| G2 合成 | 在处理器语法上的枚举，求解器和 e-图 | 草图，SyGuS，egg [27, 9, 12] |
| G3 到 G5 模型 | 一个类型化的决策模型，一个本地小型模型，然后是一个远程模型，最后 | 模型级联 [28] |

这一顺序遵循一条原则：自动化的第一条规则是先拥有一个行之有效的手工流程。只有在该任务已有一个行之有效的手工版本或确定性自动版本之上，引入模型才值得。因此，精确档位 G0 到 G2 首先运行，模型仅作用于它们留下的残差，提出交由同一道门槛裁决的编辑。减少随机模型所需承担的工作会缩小其动作空间，从而使其更易掌控。该阶梯的公开形式是 [openIE-dev/rce](https://github.com/openIE-dev/rce) 中的 `rce repair`，它在 [openie-research-experiments](https://github.com/openIE-dev/openie-research-experiments) 中有三次运行，每次均在运行前登记。前两次运行了四级（重用、按类型查找、`rce fmt` 决定的重写，以及至多 2000 个候选的单处小编辑有界枚举）。第一次运行 [225] 在零模型调用下关闭了 120 个任务中的 118 个，但 120 个任务中有 119 个是运算符与整数字面量突变，有界枚举按构造即可将其反转，且其中 9 个关闭案例虽通过示例和检查却并非原始程序。第二次运行 [226] 不含此类突变。在其 151 个任务中，它在零模型调用下关闭了 31 个（20.5%）：来自 openIE-dev/rce git 历史的 41 个变更中的 1 个（其中 39 个是跟随语言本身的变更，仅 2 个是程序缺陷）；全部 27 个守卫取反，每一个都由移除 `not` 的枚举编辑关闭，按构造反转了该突变；以及 83 个重命名中的 3 个，但没有一个恢复为原始程序。若除去守卫取反，124 个任务中仅关闭了 4 个。第二次运行的预测 P3 失败且其证伪条件 F1 被满足：第一次运行的关闭率无法迁移到真实历史。第三次运行 [227] 在 openIE-dev/rce `8a5d90ea` 上原封不动地运行了第二次运行的 151 个任务，并在有界枚举之后增加了第五级：重命名，即将某处对一个值名称的单次使用改为该作用域内的另一个值名称，或将一个绑定改为检查器报告所指出的名称，至多 2000 个候选。其登记记录载明，重命名正是第二次运行之后为构建这一级所针对的类别。在仅给出任务的普通组中，阶梯在零模型调用下关闭了 151 个任务中的 111 个（73.5%），其中 103 个恢复为原始程序：全部 83 个重命名（80 个在第五级关闭，3 个由有界枚举关闭），其中 77 个恢复；全部 27 个守卫取反，结果均与第二次运行相同；以及 41 个历史任务中的同一个 1 个。若除去守卫取反，124 个任务中关闭了 84 个。已知正确组同时向阶梯提供每个任务的原始程序：它关闭了 151 个任务中的 116 个，其中 114 个恢复，包括全部 83 个重命名均恢复为原样以及 41 个历史任务中的 6 个。其预测 P6（每个守卫任务和历史任务在已知正确组中保持其普通组结果）失败：多关闭了 5 个历史任务，且普通组中关闭的那 1 个任务改在第五级而非第三级关闭。该阶梯关闭了其各级所能反转的突变类别以及真实历史 41 个变更中的 1 个，因此需要模型介入的残差几乎涵盖了每一个真实缺陷。

### 4.4 收据

每一次提升、门槛失败、延迟和安装都是一个仅追加日志中的突变，该日志通过SHA-256进行链接，因此篡改任何过去的条目都会破坏链 [29, 30]。每个处理器的成本根据解释器操作计数，通过每主机成本表进行定价，并标记为 `est_j`。主管是引擎的升级解决者，它按顺序在每个升级上运行档位，其每次调用都携带一个收据。收据命名了档位、估计值的方法（`basis`）、尝试的候选者以及档位是否解决了升级。其 `est_j` 字段是必需的：它是一个有限的非负数，或为 null，且仅当 `basis` 为 `unpriced` 时允许为 null，例如对于没有能量数值的模型调用。缺少该字段的收据无法解析。未定价的成本永远不会被读作零，因此对收据的总计会分别报告已定价和未定价的调用，而依赖于未定价解决的节省则报告为未知。

![图示。顶部：三个日志条目，序号 0、1 和 2，每个条目包含字段 seq、event、prev_hash、state_hash 和 hash。第一个 prev_hash 是 64 个零；每个后续的 prev_hash 等于前一个条目的 hash，用箭头表示。state_hash 是步骤后状态的 SHA-256；hash 是 event、prev_hash、seq 和 state_hash 的规范 JSON 的 SHA-256。底部：一个档位收据，包含字段 gear、gear_name、est_j、basis、candidates_tried 和 resolved，旁边是规则：est_j 是必需的，且为有限的非负数或 null，仅当 basis 为 unpriced 时允许为 null；未定价的成本永远不会被读作零焦耳。](/figures/rce/receipt-chain.svg)

*图 5。日志是一个哈希链；每个成本都带有依据。图示：持久日志 D 的条目为 `{seq, event, prev_hash, state_hash, hash}`。`state_hash` 是步骤后状态的规范 JSON 的 SHA-256；`hash` 是 `{event, prev_hash, seq, state_hash}` 的规范 JSON 的 SHA-256；第一个 `prev_hash` 是 64 个零，因此更改任何过去的条目会更改所有后续的哈希。档位收据包含 `gear`、`gear_name`、`est_j`、`basis`、`candidates_tried` 和 `resolved`。`est_j` 是必需的，且为有限的非负数，或当 `basis` 为 unpriced 时为 null；模型调用收据在相同规则下包含 `est_uj`（微焦耳）。未定价的成本永远不会被读作 0 J。哈希标签是象征性的。来源：规范 6.1 和第 4.4 节。提供了一个 [PNG 复制](/figures/rce/receipt-chain.png)。*

### 4.5 编译器

该语言的编译器是参考检查器的 `rce emit TARGET FILE`（规范 10.5）。它将通过 `rce check` 的模块转换为五种输出之一：`form`，即形式 $P = (S, E, \delta, D, \lambda)$ 作为一行规范 JSON，是程序文本的确定性函数；以及四个程序，`rust`（一个 Rust 源文件）、`python`（一个 Python 3 文件）、`js`（一个用于 Node 的 JavaScript 模块）和 `scala`（一个用于 Java 虚拟机的 Scala 3 文件）。程序发出器转换的是已检查的模块而非形式，每个输出都是自包含的。每个目标都是生成的，没有一个是人工编写的。

规范 6.3 修复了每个数字边缘的一个行为，每个目标都必须重现：检查的整数算术在静态类型溢出时会触发陷阱，且从不环绕；整数 `/` 向零截断（$-7/2 = -3$）；`%` 采用被除数的符号（$-3 \bmod 2 = -1$）；除以零会触发陷阱；浮点数是 IEEE 754 binary64，每个操作符正确舍入一次，非有限结果会触发陷阱；时间仅是逻辑时钟。

在引擎的设计中，第二个编译器将处理器规范及其契合通过 e-graph 降低到形式 IR，并将其投影到进一步的目标；其测试列在 [§10](#10-work-to-finish) 中。
<div id="46-method-the-whole-stack-evaluated-every-interface-assumption-explicit" class="anchor-alias" aria-hidden="true"></div>

### 4.6 方法：对整个栈进行评估，每个接口假设都明确

一个程序是一个层次的栈：词元和语句；处理器；形式，一个单一的步进函数 $\delta : S \times E \to S \times O^*$，其中 $S = \Sigma_c \times \Sigma_d$（控制区域；数据：时钟、输入计数和类型化关系）；日志，一个 SHA-256 哈希链，其条目记录每个事件、该事件产生的状态的哈希和前一条目的哈希；转换形式的重写；以及执行它的基质。每一层都基于对下一层的假设。RCE 不将任何一层视为固定的。它对整个栈进行评估，将每个接口假设写成可检查的陈述，并在每次运行时进行检查。

| 边界 | 假设 | 检查 |
|---|---|---|
| 源到处理器 | 输入满足其源契约 | 在 $\delta$ 的输入事件处的契约检查 |
| 处理器到终点 | 每个Ok输出满足输出模式 | 处理器证明：由内核评估器进行评估，设计要求其为完全和确定的，并通过模型检查器进行检查（[§5.3](#53-model-checking-of-the-kernel)） |
| 日志到状态 | 每个条目携带其产生的状态的哈希 | 内核折叠，在第一个哈希不匹配的条目处停止并报告（[§5.3](#53-model-checking-of-the-kernel)） |
| 重写到形式 | 重写对每个输入保持输出 | 随机检查，然后是SMT证明（[§5.2](#52-the-proof-rule-for-rewrites)） |
| 存根到主管 | 无法决定的处理器会升级而不是猜测 | 存根处理器发出升级；解决方案仅通过晋升路径晋升 |
| 形式到目标 | 每个生成的目标计算相同的 $\delta$ | 每个目标都携带相同的参考轨迹 |

检查失败会定位在发生错误的边界处。更正在该层进行，通过该边界的检查后提升。所有更正层以上的每一层都会继承更正，而无需进一步更改，因为每一层都仅通过其接口假设的检查来消费更正后的层。这是更正向上传递并累积的意义。

### 5.1 程序生成器的差异测试

T9-L 指出，程序生成器 `rust`、`python` 和 `js` 与参考评估器一致。对于 Rust 生成器，它在一个核心上得到证明，作为向 MiniRust（所生成 Rust 子集的深度嵌入）的经验证翻译；`rustc` 实现 MiniRust 这一点受信任并经过测试。对于 Python 和 JavaScript 生成器则进行了测试：生成的程序必须逐字节打印每个示例程序的参考轨迹，这是发出注册表的每一行都通过的门槛（[§3.6](#36-one-ecosystem-lossless-and-the-universality-thesis)）。参考评估器和生成的 Rust、Python 和 JavaScript 运行时还计算相同的预算函数，一项测试检查预算陷阱在所有四者中都落在同一操作上（[§3.7](#37-the-language-one-text-costs-and-theorem-status)）；在每个生成器之前执行的保持顺序的 ANF 传递在每个目标上都经过了差异测试，包括跨越陷阱点的预算扫描（定理 T34）。这是沿袭 McKeeman 和 Csmith [86] 路线的差异测试：独立实现在指定输入集上达成一致。它不是翻译验证 [85]，并且在 Rust 生成器已证明的核心之外，它也不是经验证的编译器。它对测试集之外的输入不作任何说明。

### 5.2 重写的证明规则

经过验证的重写规则有其谱系。Ruler通过等价饱和推断并检查重写规则，且模型不在循环中 [87]。第5.5节中接受的模型提出的重写重复了引擎已有的规则，因此该记录是关于门槛的陈述，该门槛未准入18项提案中的15项，并不是声称模型是好的规则来源。

在引擎的设计中，每个e-图重写必须在Z3 SMT求解器 [31] 中进行证明，针对形式的项评估和算术的无量化编码：值作为数据类型，带检查溢出的64位位向量，带被除数符号的有符号除法和余数，以及二进制64浮点数。改变溢出、升级顺序或消息的重写无法获得证明。提出的等价性只有在有证明的情况下才能进入e-图。

### 5.3 内核的模型检查

设计使用 Kani 模型检查器 [32] 对引擎的内核（哈希链、折叠、无名位置和处理器评估）进行检查。处理器评估是非递归步骤的不动点，因此证明该步骤对于每个构造函数是完全且确定的，可以通过结构归纳法推广到评估。设计命名了十个属性，每个属性都有一个测试用例：

| 测试用例 | 属性 |
|---|---|
| `chain_appended_verifies` | 附加的哈希链可以验证 |
| `chain_detects_tampering` | 更改的条目会破坏链 |
| `fold_equals_replay` | 折叠等于重放 |
| `fold_rejects_wrong_state` | 与存储状态不一致的折叠会失败 |
| `position_is_name_independent` | 规则位置不依赖于节点名称 |
| `reason_tokens_are_name_independent` | 原因码通过整个词元是无名的 |
| `handler_core_leaves` | 叶子处理器是完全且确定的 |
| `handler_core_validate` | 验证是完全且确定的 |
| `handler_core_pipeline` | 管道是完全且确定的 |
| `handler_core_ifhas` | 保护是完全且确定的 |

### 5.5 模型作为检查背后的提议者

模型可以提出等价性，但不能准入它们。一个本地的 15 亿参数编码模型在规范 `orders-form` 上作为提议者运行，运行的公开记录（[`rce/bench/results/llm-proposer-form-demo.form.json`](https://github.com/openIE-dev/openie-research-experiments/blob/main/rce/bench/results/llm-proposer-form-demo.form.json)）包含 18 个提议，其中 13 个互不相同。记录仅将每个提议的来源标为 `llm`；该模型（llama.cpp 下的 Qwen2.5-Coder-1.5B）由本文指名，未见于公开记录。检查未准入 15 个提议，其中 12 个互不相同：4 个无法解析，2 个在应放项的位置放了值，以及 9 个算术运算符交换律，每个都由一个两边失败方式不同的反例证明有误。它准入的 3 个提议是同一个重写 `(pipe pass ?a) => ?a` 的三个不同名称，且该重写重复了引擎已有的规则。记录显示门槛拦下了错误的内容；它没有显示模型给出了任何新规则。

## 6. 提升：从其他语言进入生态系统

<div id="6-importing-legacy-code-from-other-languages" class="anchor-alias" aria-hidden="true"></div>

提升是其他地方编写的代码进入生态系统的入口。它是一种构造，针对每种语言利用其已有的工具构建：形式语法、生成语法树的解析器（如 [tree-sitter](https://tree-sitter.github.io/tree-sitter/)）、抽象语法树，以及语言服务器工具链所解析的符号（[Language Server Protocol](https://microsoft.github.io/language-server-protocol/)）。引擎配置文件规定了一项提升操作 `rce scan DIR --form`，它从该语法树为 Rust、Python、TypeScript 和 Go 构建 Form，并将每个提升的元素标记为未经证明（附录 D.8）。提升后的程序会携带其源代码的缺陷，因此提升包含修复，下面的协议在给定故障位置的公开错误语料库上测量修复效果。

### 6.0 修复阶梯

<div id="23-per-rung-ladder-results" class="anchor-alias" aria-hidden="true"></div>

此处通过其所需的**意图位**来衡量一个编码任务：必须从引擎已持有的内容之外（编辑周围的程序、库、测试、已知修复的索引）提供的位。将固定目标工件所需的位表示为 $H_{task}$，将语料库已修复的位表示为 $H_{corpus}$，则提供的位为 $I = H_{task} - H_{corpus}$。一个档位在候选编辑中将正确的编辑排在第 $r$ 位，其提供的搜索位为 $\log_2 r$，其余由门槛提供。阶梯按照编辑大小对任务进行排序，这是 $I$ 的客观代理：一个词元（L0），一个语句（L1），一个块（L2），一个文件中的多个块（L3），多个文件（L4），从规范或测试中提取的一个函数（L5），一个问题级别的更改（L6）和从规范中提取的一个程序（L7）。档位、语料库、分割和假设均已预先注册；文件位于[公开仓库](https://github.com/openIE-dev/openie-research-experiments/tree/main/rce/bench/ladder/)中。

L2 到 L4 将在 Defects4J 留出集上进行测量（[第 8.1 节](#81-defects4j)），L5 到 L7 将按照 [第 8.2 节](#82-swe-bench-lite-offline) 的协议进行测量。L0 和 L1 的方法和门槛如下。

**方法。** 每个语料库使用固定种子进行洗牌。每个洗牌的前 2,000 个位置，以及 L0 的三个完整仓库（commons-lang、requests、flask），构成开发分割，齿轮可以在该分割上进行调整；开发结果不报告。所有剩余任务均在测试分割中。在测试运行之前，求解器被提交并记录其二进制哈希，运行过程中齿轮不会改变，因此所有报告的行仅是测试任务上的冻结求解器结果，模型调用次数为 0。预先注册（`PREREG.json`）和报告脚本位于[公开仓库](https://github.com/openIE-dev/openie-research-experiments/tree/main/rce/bench/ladder/)中。

**门槛。** 在 L0 和 L1 中，位置已给定，门槛为词元恒等：修复后的行或语句必须逐词元等于开发者的行或语句。这比通过测试更严格，因为补丁可以通过弱测试套件但仍可能错误。Qi 及其同事发现，GenProg 报告为修复的大多数补丁看似合理但实际上是错误的 [92]；基于搜索和语义的修复中存在对测试的过拟合 [93, 94]，并使用生成的测试进行解决 [95]；工具在它们被调优的基准上得分更高 [96]；故障定位也会使比较产生偏差 [97]。词元恒等在这些级上消除了合理性差距，给出位置则消除了定位项，因此比率仅衡量修复档位本身。L2 及以上使用测试作为门槛，并分别报告合理和正确的数量（第 8.1 节）。

### 6.1 L0：单词元故障

L0 语料库包括所有 PIT 风格的突变体 [109]，这些突变体在固定提交的现实仓库中具有有效的替换词元，包括五个 Java（commons-math、commons-collections、jsoup、joda-time、gson）和四个 Python（click、attrs、pydantic、sympy）仓库，其中四个仓库（commons-text、commons-io、more-itertools、httpx）从未用于调整，作为第二个测试集。突变体是 Just 及其同事发现的与真实故障相关联的真实单词元故障的替代品 [110]。如果修复单词元故障的邻域是使用生成突变体的相同操作符表构建的，那么高修复率部分反映了这种重叠，而不是对实际中出现的故障的修复能力。在相同突变体上运行的普通操作符反转搜索是基线，显示重叠解释了修复率的多少，L0 修复率在旁边读取。

### 6.2 L1：来自真实历史的单语句错误

L1 使用两个从开源历史中挖掘出的真实单语句错误修复公开数据集：Java 的 ManySStuBs4J 2.0 [107]，以及 Python 的 TSSB-3M v1.0.0 [108] 第 14 和 15 分片。求解器接收父提交处的 7 行块或整个文件，外加项目方法和守卫条件的索引，两者作为单独的行报告。这些数据集在该门槛（仅块、词元恒等、给出位置）下没有已发布的修复排行榜，因此旁边没有列出学习型修复的数字；拥有排行榜的 Defects4J 将在第 8.1 节中与 TBar 进行比较。

### 6.3 能量

在协议中，阶梯的每一行都携带 `est_j`，即中央处理器（CPU）秒数乘以 10 W 的估计值，并将从处理器的片上封装计数器 RAPL [105] 读取一个子样本作为 `reported_j`：整个运行期间的封装能量增量，减去紧接运行前采样所得空闲功率乘以运行持续时间。`measured_j` 为命名供电轨上的墙式功率计读数，遵循第 8.3 节的协议。目前尚未在公开代码上产生任何 `reported_j` 或 `measured_j` 数据；重建工作列于 [§10](#10-work-to-finish)。

**两种制度和一个校准向量。** 上述估计值，即 CPU 秒数乘以 10 W，是一个基表，无法区分目标，因此最小焦耳提取从不选择目标。测量文献说明了修复必须是什么样子。在顺序核心上，焦耳与操作次数呈线性关系：在 Cortex-M0 上，一个六计数器模型达到了 R² ≈ 0.99 和 2.8 到 4.3% 的平均绝对误差，系数如每条指令 0.96 nJ 和每条已取分支 2.1 nJ [152]。在乱序核心上，模型退化为时间：当一个核心固定且涡轮关闭时，Xeon Gold 6430 在每种语言-能量复制的实现和基准测试中都消耗了 189.8 ± 0.5 W，一旦控制了库选择、并行性、预热和测量错误，将 Python 放在 C 的 75.88 倍的排名就消失了 [153]。计数器本身的价值不均：Intel RAPL 在包含 DRAM 后，预测插头功率的平均绝对百分比误差为 1.8%，但每毫秒更新一次，且在一代产品中封装温度变化时漂移了 10 到 12% [105]；以比 10 ms 更快的频率轮询它会产生高达 50% 的陈旧读数 [154]；NVIDIA 的 NVML 采样了约四分之一的运行时间，单次简单运行与外部计量器相比误差高达 70% [155]。在以太坊上，Gas 风格的单位计量与 CPU 时间的相关性仅为 Pearson ≈ 0.51 [156]，因此“能量与所计数的操作成比例”是 `reported_j` 子样本必须测试的假设。对规范的提议将三个对象分开：C.6 预算单位保持确定性、目标盲和在日志中；`est_j` 变为 $\langle \mathrm{count}(\mathit{term}), E[\mathit{target}] \rangle$ 加上空闲功率乘以时间在制度 A（微控制器、现场可编程门阵列（FPGA）通道、顺序核心）和 $P_{\mathrm{active}} \cdot t + E_{\mathrm{llc}} \cdot \mathit{misses}$ 在制度 B（乱序 CPU 和图形处理单元（GPU））；系数向量 $E[\mathit{target}]$ 是一个 `host.Calibrated` 日志条目，带有其协议、样本数和每个系数的标准误差，由 `rce host calibrate` 在规范协议下编写（至少 30 个 A/B 对与空闲基线交错，至少 60 秒或 $10^9$ 操作的块，丢弃预热，记录温度，报告毛和净，计量器以其验证参考命名，RAPL 采样不超过 10 ms），因此在 `est_j` 下的提取是日志和重放的函数。收据获得一个 `calibration` 哈希和一个 `stale_fraction`，即步骤操作中没有校准行的比例，定价为 `unpriced`；总计在单独的列中保留四个标签。证伪条件是 [§9](#9-falsifiers) 中的 RCE-F5。第一个要运行的校准是能量阶梯上 KV260 级在其核心供电轨上的运行（$N \ge 30$），它将替代占位符 `E_LUT_READ = 1e-12` J（这是[计量提交门槛](/papers/gates/)中的一个 OpCounter 常量，RCE 规范中并不包含它）转换为一个带有标准误差的系数。这些都尚未构建：在主分支上，`host.Calibrated` 保存的是用于放置决策的计算织物、操作类别、开销和吞吐量，而非焦耳，且不存在 `rce host calibrate` 命令。

## 8. 对接下来内容的测量协议

每个协议在运行前都已固定：预先注册提交，种子和求解器提交记录，所有工件保留。首先设置门槛，其次设置焦耳，标签始终保留。

<div id="81-defects4j" class="anchor-alias" aria-hidden="true"></div>

### 8.1 Defects4J

Defects4J 包含 854 个活跃的 Java 缺陷，每个缺陷都有重现测试 [37]。

1. 在 100 个缺陷的子集上离线开发，通过 `defects4j checkout`；仅报告留出结果，从活跃缺陷中通过运行前注册的种子规则抽取的不相交集合中抽取，该规则排除开发子集和每个已用任何档位运行过的缺陷，并在运行前冻结。
2. 运行 G0，然后运行 G1，然后运行 G2，最后运行本地模型。记录关闭每个缺陷的档位。
3. 门槛：触发测试和完整测试套件通过。分别报告可能和正确的计数；正确意味着在审查时等同于开发人员的补丁。
4. 报告每个正确修复的模型调用和每个正确修复的焦耳，标记。
5. 参考点：TBar 的 43 个正确修复和其在完美定位下的 101 个中的 74 个（数据如 [23] 所读，此处未重新检查分母）。本节是一个协议。本文未报告此引擎的任何 Defects4J 结果。
6. 污染检查：标记每个修复内容在 G0 索引中逐字出现的缺陷，并报告有和无标记缺陷的情况。
<div id="82-swe-bench-lite-offline" class="anchor-alias" aria-hidden="true"></div>

### 8.2 SWE-bench Lite，离线

SWE-bench Lite 是一个包含 300 个真实 GitHub 问题的子集，这些问题通过隐藏测试得到解决 [38]。

1. 使用官方的 Docker 框架，且不使用网络。
2. 首次运行：仅使用 G0 和 G1，模型调用次数为零。这是在没有模型的情况下解决问题的最低水平。
3. 第二次运行：添加一个本地模型作为最后一个档位。
4. 报告解决率、每个解决任务的模型调用次数和每个解决任务的焦耳数，并进行标注。
5. 污染检查，如 8.1 所述。SWE-Bench+ 发现 32.67% 的成功补丁在问题文本中已经包含了解决方案 [39]。

<div id="83-a-wall-meter" class="anchor-alias" aria-hidden="true"></div>

### 8.3 墙上计量表

1. 在主机的供电线上安装一个墙上计量表或分流表，以指定的速率记录，其时钟与运行日志同步。
2. 空闲机器：CI 运行器和其他构建停止，每次块处理前检查并记录一个安静窗口门槛。
3. 减去测量的空闲基线，并说明方法。
4. 仅从计量表中填充 `measured_j`。在单独的列中报告 `reported_j`（RAPL）和 `est_j`。从不跨标签求和。
5. 在计量表下运行阶梯（第 6.3 节）的 RAPL 子样本，然后运行 Defects4J 留出集。

<div id="84-a-held-out-run-with-the-gears-frozen" class="anchor-alias" aria-hidden="true"></div>

### 8.4 冻结档位的留出运行

这是第 6 节方法的扩展，适用于新的语料库。

1. 在标记的提交上冻结 G0、G1 和 G2，记录二进制哈希，并发布带有其创作时间戳的规则集。
2. 绘制一个互不重叠的留出切片：Multi-SWE-bench [102] 和 BugsInPy [103] 的 Rust 和 Python 实例，与 G0 的索引 [104] 去重。
3. 在首次运行之前，预先注册切片、种子和假设。
4. 分别报告已解决、合理和字节相同数量的计数，每个计数都带有 95% 的区间。

<div id="85-baselines-in-the-same-table" class="anchor-alias" aria-hidden="true"></div>

### 8.5 同一表格中的基线

1. 无模型：`cargo fix` 和 clippy [106]，以及 Sorald 或 TBar 端口 [91]。
2. 便宜模型：使用本地模型的无智能体 [99]。
3. 远程模型：一个带有前沿模型的智能体，其能量估计来自提供者的披露，并标注为 `est_j`。
4. 每一行都以焦耳和美元报告通过成本 [101]，并按照 Kapoor 和同事的要求控制成本 [100]。

<div id="86-convergence-of-model-calls-at-large-n" class="anchor-alias" aria-hidden="true"></div>

### 8.6 在大 N 下模型调用的收敛

晋升是模型退出循环的机制：为一个新案例支付一次解决者，门槛将该契合准入为处理器，之后相同形状的每个案例都在 G0 或 G1 中关闭（[第 4.2 节](#42-the-gears)）。收敛是指在实时流量下，固定规格下每轮模型调用次数降至零的主张。其测量方法如下。

1. 从公共仓库中至少抽取 1,000 个规格，按语言和大小分层，首次轮次前冻结引擎和解决者。
2. 重放记录的生产流量，每个规格至少 10,000 个事件，以固定大小的轮次进行。
3. 每轮记录：新升级、模型调用、提升、延期和每个关闭任务的焦耳数，每个都进行标注（`est_j`、`reported_j`、`measured_j`）。
4. 主要终点：在 20 轮内达到零模型调用轮次的规格比例，带有 95% 的 Wilson 区间。次要终点：每轮关闭任务的模型调用次数，以及最后一次模型调用的轮次。
5. 报告从未收敛的规格及其原因（一个卡住的输入、一个缺失的依赖、新的意图），并运行卡住输入的延期作为预先注册的臂。

**命题 8（地板方法）。** 随着 G0 和 G1 覆盖范围的扩大，每个解决任务的焦耳数接近应用已知修复并运行测试的黄金地板。阶梯档位和墙计量表下的 Defects4J 留出集测试了这一点。

## 11. 结论

RCE 按设计是一个原生代码生态系统。程序从意图出发，作为 Form 一次性编写：它是状态、事件和纯转换的无损编码，每种目标语言都是它的投影，且必须重放其轨迹。程序可以处于的每个状态都在其 Form 中声明，不适用的事件保持状态不变（定理 T8），因此生态系统中的程序不会偏离其意图，也不需要事后差异比较或错误跟踪。该语言是单一提交下的单一书面规范。参考检查器实现了它，并生成 Rust、Python、JavaScript 和 Scala；规范精确记录了每个定理证明的级别；程序的维度是一个计算出的数字，在针对公开提交的已登记运行中进行了测量，它在一个总体上触发了 RCE-F6，而在其他总体上未触发。在引擎的设计中，每个通过门槛的契合都会被存储和重用，生态系统在正确性单调的门槛（命题 R1）下实现复合增长。其他语言的代码通过提升进入系统，即从每种语言的语法到其语法树再到 Form 的构造。第 3.6 节和第 8.7 节陈述了普遍性命题及其构造的测量方法，第 9 节陈述了将推翻这些主张的观察结果，第 10 节列出了仍需完成的工作，包括正在基于公开代码重建的引擎结果。

<div id="121-seven-areas-of-the-design" class="anchor-alias" aria-hidden="true"></div>

### 12.1 设计的七个领域

**规范形式。** 对于一个完整的、确定性的有限字母表机器，其最小机器在同构下是唯一的，固定遍历顺序将其转换为唯一字符串 [150]。形式提供了完整性和确定性（T1，T2），因此 [§3.8](#38-behaviour-equivalence-and-dimension) 中的有限控制投影具有规范形式。数据组件不具备：符号有限自动机在谓词等价下具有规范最小值 [149]，等式或稠密序上的寄存器自动机允许 Myhill-Nerode 定理 [151]，而由整数算术更新的状态除了该项本身之外没有规范代表。在对共享子项仅计费一次的成本下从 e 图提取是 NP 难的，且无法近似到常数因子 [159]，因此哈希代表必须使用在提取器之间可重现的成本。立场：三个形状键，每个键标明其在哈希输入中的层级（无名项哈希、[§3.8](#38-behaviour-equivalence-and-dimension) 中的控制形式，以及带有饱和预算的 e 类键）；等价性仅定义一次，即双模拟；受保护的步骤体首先通过带测试的受保护 Kleene 代数的近线性判定过程进行检查 [158]。未采用：任何声称最小机器就是带有算术状态的 Form 的唯一规范形式的主张；按共享子项成本选出的哈希代表。开放问题：对于哪个片段，相同含义蕴含相同控制形式（T61 的逆命题）。

**内容寻址的中间表示。** Unison 五年使用哈希标识定义的经验归结为一个不变量（哈希只覆盖语义而绝不覆盖名称）和一项成本（编辑时重新哈希依赖项）[160]；Dhall 对全函数语言的规范形式求哈希 [161]；Nix 对构建输出进行内容寻址的尝试在十五年间一直停留在实验阶段，因为自引用和非确定性破坏了它 [162]。立场：定义由 α 擦除且规范化后的主体的摘要作为键，名称、源位置和字面拼写保存在不参与哈希的表中并由投影渲染；单一发出器通过按目标配置的表遍历中间表示，取代四个遍历表面语法的发出器；每个执行序列化的运行时都针对规范 JSON 测试向量进行检查。未采用：用 RFC 8785（无法携带与浮点数区分开的整数、负零或精确的 64 位无符号整数）或确定性 CBOR（其两份规范在浮点宽度和键序上不一致）取代规范 JSON 作为哈希字节；将发出的产物进行内容寻址作为身份标识；在哈希之前执行完整的 β 规范化，因为递归函数那样就没有有限项。开放问题：相互递归的组件级键。

**日志作为偏序。** 在 Mazurkiewicz 意义下的轨迹是模去独立事件交换后的词，同一配置的所有线性化读取相同的轨迹。一致性即逻辑单调性定理指出了哪些程序不需要协调 [19]，其对读取操作的扩展指出，除非观测呈阈值形状，否则对收敛状态的观测是不安全的 [82]。立场：日志条目对其所属链、序列号、事件及其因果观测到的条目哈希求哈希，状态哈希仅在切割点记录，从而在语义允许的每一种线性化下摘要都相同；单调标签扩展到读取；跨链 `select` 的每个选中分支均记录入日志。任何与依赖关系一致的顺序都会折叠到同一切割状态的定理（T62）已在模型上证明，目前作为提议而非规范性文本。未采用：允许目标选择非单调事件的线性化。开放问题：将模型证明扩展到完整评估器。

**从意图合成。** 验证器仅检查可靠性：恒真的后置条件总能通过验证。规范的完备性必须加以测量，行之有效的度量是规范所拒绝的突变输出比例；在引入该度量的研究中将其从门槛移除后，可验证率降至 1.56% [164]。在等式约束树自动机上进行类型引导枚举，使库搜索基准的解决比例从 64% 提高到 88% [165]，而一旦计入每个正确结果的成本，自我精炼和多数投票很少值得其开销 [166]。立场：将意图表示为带有空洞的程序，附带义务、示例、命名的可用定义集合和预算；一条使义务不排除任何行为的意图需要修改的规则；随每个意图一起报告测得的完备性；每个空洞配备一份推导记录，给出每次检查前后的候选。未采用：按分数晋升；单次模型调用内部的精炼循环。开放问题：不依赖语料库的意图信息量度量。

**能量成本模型。** 测量文献已在 [§6.3](#63-energy) 中总结：在顺序核心上焦耳与操作计数呈线性关系 [152]，在乱序核心上与时间呈线性关系 [153]；片上计数器的质量相差一个数量级 [105, 154, 155]；以太坊所用的那种单位计量与 CPU 时间的相关性仅为 0.51 [156]。立场：三个不同的对象，绝不合并：规范中确定性的、目标盲的预算单位；将校准后的按目标系数向量应用于计数（顺序核心）或时间（乱序核心）所得的估计值；以及保存在独立列中的收据标签。未采用：在预算表中放入焦耳；按语言设定常数；把计数器读数当作墙式功率计实测值。

**为机器作者设计的语言。** 一份收录了 42 种此类语言（其中 36 种于 2026 年首次列出）的目录显示，本文的每一项机制都有同行采用：哈希链证据、拆分为已证明与运行时检查的强制契约、证明助手核心、作为唯一事实来源并带有哈希定义的语法树 [168]。[§3.7](#37-the-language-one-text-costs-and-theorem-status) 的收敛观察依然成立。区分本设计的并非某一项机制，而是重放和单射性是定理（T3、T7）而非运行时承诺，而且示例是建立在与重放相同语义之上的类型化事件轨迹，因此模型无法绕过的预言机就是程序本身。立场：建立带有机器可读诊断和修复计划的版本化规则代码注册表；利用发出器和检查器制造经测试验证的翻译对，这是把 [167] 中恢复低资源语言的配方反过来运行。未采用：任何声称自己是首创或唯一的说法。

**证明工程。** 弥合规范与其机械化模型之间差距的标准，靠的是从单一编写源生成散文、检查器表和定义：WebAssembly 的 SpecTec 在五份提案中发现了十处错误，并被所有后续版本采用 [169]。通过精化证明实现正确的项目为此付出了高昂代价：8,700 行 C 代码耗时约十二人年 [171]。CompCert 的维护者列出了每一个受信任项及其理由 [170]。立场：由单一编写的规则源生成规范文本、检查器表和 Lean 定义，任何分歧都会令检查失败；Lean 核心作为其所覆盖子集的记录执行器，公开未支持构造的数量并以此界定每个定理所声明的范围；专设一章列出每个受信任组件及其测试。未采用：从 Lean 核心到 Rust 解释器的精化证明；以定理数量作为保障程度的度量；对任何事物维护两套人工编写的语义。

### 12.2 编程语言中的形式

分布在十二个家族中的大约一百种语言被放置在八个坐标上（状态布局、事件字母表、转换、顺序、资源、信任、绑定时间和意图），逐一记录是由作者固定、由编译器或运行时选择，还是语言中根本没有对应概念。由此得出三条规律。只有三个家族无需作者费力即可通过三个不同的定理获得全局确定性：同步语言通过因果性检查，流语言和逻辑语言通过单调性，受保护原子动作语言通过带静态冲突分析的单次单规则调度。每个达到安全认证的家族都是靠移除与形式所移除的相同的三个坐标实现的：动态分配、无界递归和非确定性选择。而没有任何家族能很好固定的两个坐标是信任和意图；形式的意图块与示例块及其能力值同时固定了这两者。

距离形式最近的五个设计是：Dedalus，其按时间索引的关系就是日志，其下一步规则就是转换 [15]；Bluespec，其受保护原子规则按编译器选定的顺序调度，并证明等价于单次单规则执行；Elm 架构，即换了名称的形式四组件 [83]；Lustre，其有界内存、静态调度的规范已在大约一百个航空电子系统中获得认证；以及在身份标识上的 Unison [160]。记录还固定了五项约束，每一项都是早期语言曾因相反选择而付出代价的地方。并发任务必须降级为无栈状态机，就像 Rust 的异步函数那样，因为有栈协程无法逐步记录日志。并行组合必须作为结构化步骤发出，而绝不能作为自动机的显式乘积发出，后者在 Esterel 编译器中一旦并发源代码超过约一千行就会失败。效应处理器必须是一次性的，正如 OCaml 5 所选择的那样，其原因在于所有权和完全性界限（每次额外的恢复都会把捕获的状态复制次数取决于数据的若干遍），而不在于可记录性。程序中唯一作为定理成立的维度是其有限控制投影的指数（[§3.8](#38-behaviour-equivalence-and-dimension)）。从图灵完备语言的提升是定义域不可判定的部分映射（[§3.6](#36-one-ecosystem-lossless-and-the-universality-thesis)）。本项目早期工作草稿曾使用过的微分几何词汇（坐标卡、规范、和乐、测地线）在编程语言文献中没有对应物，本文不使用；真正存在的对象是最终余代数、从语法到它的函子、连通分支为 e 类的重写证明群胚，以及用焦耳代替比特的最小描述长度。

[§3.6](#36-one-ecosystem-lossless-and-the-universality-thesis)的普遍性命题通过一个封装标准变得可测量。当形式封装一种语言 $L$ 时，对于固定语料库中 $L$ 的每个程序 $p$，提升后的形式在五个坐标上不比 $p$ 差，并且在至少一个坐标上严格更好：在相同任务和主机上测量的焦耳；根据 [§3.8](#38-behaviour-equivalence-and-dimension) 的冗余性，与 $p$ 声明的状态比特相比；可判定性，即每个为 $p$ 决定的属性也决定形式；往返，即行为协议到指定长度和形状哈希的镜头条件；以及模型达到通过门槛程序的代价，来自相同的意图。声称形式比编程语言更好是该标准在语料库上的联合，每种语言一次注册运行，没有其他内容：它不声称表达能力，因为形式不能比 $p$ 说更多，也不声称可读性，这是投影的属性，也不声称采用。在两种注册运行后，形式在任何坐标上严格比某语言差的语言不被封装，该语言固定而形式未固定的记录成为形式的工作项。

### 12.3 为何人类编写的代码存在冗余

人类编写的代码在媒介无法为作者提供表达意图的通道时，会携带冗余，而这些冗余是每位作者的私人替代方案。实测证据将其分为三个层次。格式化在大括号分隔语言中占 13% 至 15% 的词元，可以删除而不影响十种语言模型的准确性 [136]，而布局对人类理解没有可测量的影响 [135]。唯一能追踪可测量理解负荷的量是文本大小、词汇量和数据流依赖关系的范围，每个的 Kendall τ 约为 0.4，而圈复杂度则什么也追踪不到（τ ≈ 0.09）[133]；97% 的非死锁真实并发错误是未强制的原子性或顺序假设，其中 96% 涉及至多两个线程，因为顺序文本无法陈述偏序，作者只能写出全序 [172]。名称的选择在开发者之间的中位一致率为 6.9%，解码率为 97% [137]；注释在几次提交后就不再追踪它们所描述的代码 [138]；然而当移除标识符时，语言模型的准确性会损失多达 29 个百分点 [139]。另外两个原因是组织层面的。开发者不会删除代码：在三个生产系统中，54% 至 60% 的文件在六到十六个月内从未被执行过，开发者只删除了被指出为不必要代码的 20%，而这种谨慎是合理的，因为检测器的精确度仅为 32% [173]。此外，组织会交付其边界：八项组织指标以 86.2% 的精确度和 84.0% 的召回率预测了易出故障的二进制文件，优于所有代码指标 [174]。

接下来的论述分为四个部分。形式（Form）在状态、事件集和总步骤上分别决定顺序、局部性、习语和可达性。投影（projection）处理布局和习语，按社区呈现，因为专家的优势仅限于用熟悉计划编写的代码，而仅生成正确代码的投影会剥夺他们的优势。意图（intent）保持为结构化、受检查的记录，从中投影（projection）生成名称（[§3.8](#38-behaviour-equivalence-and-dimension)）。规范（specification）由机械的准入检查所控制，因为模型的作者身份提高了提议的频率，但没有改变规则。设计依赖的三个问题在文献中没有测量，并已作为密封协议的实验进行注册：模型是否能像从命名的表面一样准确地从无名形式及其概念记录中进行推理；普通代码中相邻语句在形式依赖下交换的比例，即97%的数字所衡量的松弛成本的大小；以及通过重放检查并可通过一个命令恢复的删除是否能将20%的删除率移动。在项目的工作材料中流传的两个主张没有可追溯的来源，也没有被使用：一项2014年关于语言手册页面数量的研究，以及有经验的程序员编写更少代码的说法，该说法追溯到一篇引用了未命名研究的博客文章。

### 12.4 语言如何增长和收缩

每种保持小型的语言都用关于什么可接受的规则取代了审阅者的品味。Go 的流程倾向于拒绝，在一项研究中依据一套公开的原因拒绝了 1,095 项提议中的 40.9% [175]；Lua“重机制而非策略”的规则使其实现保持在约 25,000 行 C 代码；Elm 停止了增加新特性。不断膨胀的体制也由其自身的主席记录在案：一项特性的收益是私人的、即时的，其成本却是分散的、延迟的，而且唤起对新事物的热情总比反对它更容易 [175]。在 RCE 中，形式（Form）在单一文本内部生长。当程序需要文本所缺乏的形式（包括无人预见的形式）时，该形式直接写入规范本身，没有版本，也没有宏、标志、指令或插件。规范仓库声明了形式进入文本的七条规则，每条都指明了强制执行它的工件。一个构造只有在具备一个被接受的示例和一个需要修改的示例、通过生成的规则表或测试向量与检查器相连的所依赖定理之 Lean 陈述、且无解析冲突时，才能进入规范性语法；任何不足于此的都只是提议。对形式已有表达方式的第二种拼写仅凭这一条理由即予拒绝。变更双向运行：当发现更好的形式时，任何构造都可以修改、泛化、替换或移除，而该变更连同仓库中它所触及的每一个程序、示例和库模块在同一次提交中一起移动，并在账本中留下一行说明改了什么以及为什么。每个接口只有一个决策点，因为穿过接口的组织边界是可预测的缺陷位置 [174]。所有决定及其理由都按固定原因集公布在账本中，因此拒绝率是人人可读的数字。市场不会做修剪，因此已有使用绝不是保留某个构造的理由。模型参与编写改变的是提议速率，而不是规则。

### 12.5 库与计算织物

一种语言是否应该附带一个大型库（“电池已包含”）还是附带一个小型指定核心和一个自由注册表，通常被争论为便利性与灵活性之间的权衡。记录显示，这两种立场在同一点上都失败了 [193]。附带库的语言将其接口绑定到语言的兼容性承诺上，从而失去了灵活性 [195]。一旦存在安装程序，其模块就会被移除：Python增强提案594移除了其中的22个模块，理由是维护成本和从注册表安装的便利性 [194]。自由注册表会产生深层的传递图：在Cargo、npm和NuGet中，一半的依赖包至少有41、21和27个传递依赖 [196]。具有许多实现的规范在其边缘会发散，正如在一种未充分指定的语法上，超过30个JSON解析器的行为不同 [197]。当记录汇聚时，它汇聚到一个经过精心挑选的层级，该层级作为一个单元进行交付和更改。

同样的失败也出现在计算织物中。在图形处理器上，单源模型在流式内核上与本地代码匹配，但在约简操作上表现不佳：在点积操作中，Kokkos、RAJA和SYCL的性能可移植性得分介于0.80到0.91之间 [198]。在FPGA上，一个从CUDA迁移并为GPU优化的SYCL源代码，其速度仅为FPGA优化版本的0.2%到47%，这一比例是根据在最大问题规模下发布的定时数据得出的 [193, 199]。那些在软件和硬件中都实现一个含义的系统，通过将其源语言缩减到硬件所能理解的范围（静态已知大小的状态、硬件部分没有堆或递归、逻辑时钟）来实现这一点，它们的证明只覆盖了链的一部分，而不是全部 [193, 200]。可移植的代码格式在它们固定语义时有效 [201]。在设计时，位相同的结果成本很低 [202]。内存模型的健全性结果是成对的 [203]。除非每个决策都被记录并重放，或者在虚拟时间中模拟运行，否则基于测量成本的放置是非确定性的 [193, 204]。对于机器作者来说，这个问题也是知识的问题：在Python和JavaScript中，16个模型生成的代码命名的包中，有19.7%的包并不存在 [205]。

这两个争论都询问库的含义由谁持有：由一个实现、每个注册表包、通过容差检查的规范，还是由一个织物的供应商二进制文件。RCE立场认为，它由一个文本持有。

- **库是文本的一部分。** 它用语言编写，并构建到每个工具中（规范4.1）。它通过其清单的哈希值固定，程序将其命名为其唯一的依赖项（F.5.3）。
- **它没有平台变体。** 它仅通过适配器进行输入和输出。
- **它的成本是其源代码在每个二进制文件上的成本。** 因此，一个步骤在每个主机上都意味着相同（HC-7）。
- **每个目标的选择属于主机。** 主机仅在对CPU参考进行记录的位精确性探测后，才接受某一类操作的织物（HC-13），并且它记录每个放置以供重放（HC-12）。
- **可用的是工具打印的列表，每个提交时完整，且在相同文本中增长。** 一个函数是否存在变成了查找，而不是回忆。

形式以形状而非门槛实现这一点。记录中的系统将其源语言缩减，因为其表达的内容超过了硬件所能理解的范围。形式 P = (S, E, δ, D, λ) 是每个程序已经具有的形状：它保持的状态、它回答的事件、它的步骤、它的日志和它的输出。这就是为什么其他语言的程序在 [§3.6](#36-one-ecosystem-lossless-and-the-universality-thesis) 所述的定义域内通过提升进入它，也是为什么这一立场的任何部分都不会把程序划分为被准入的程序和需要修改的程序。

形式在每次提交时是刚性的，只有一个文本和一个含义。它在提交之间是灵活的。当程序需要一个形状没有的形式时，形状在文本中获得它，而不是通过宏、标志、指令或插件。一个更改可能扩展、概括或替换一个形式。它与仓库中的程序一起在一次提交中移动，程序哈希、[§3.8](#38-behaviour-equivalence-and-dimension) 的等价性检查和日志记录了移动的内容。行为和等价性（规范6.10）以及主机的织物条目在不改变任何被接受程序的含义的情况下添加到文本中，日志作为部分顺序和带有空缺的意图也被以相同方式提出。根据该提案，硬件遵循相同的规则：引擎读取形式的状态大小和步骤成本以实现它，静态大小的状态存储在寄存器中，而增长的状态存储在电路地址的内存中。

“电池已包含”和“规范与自由”不再成为替代方案：电池是规范的一部分，程序不受任何织物的限制。

该立场的库部分在仓库的主要部分中已经成立：库用该语言编写，构建到每个工具中，并通过哈希固定。其两部分仍有待完成：规范各节之间对标准库的单一定义，以及将 `use` 作为引入目前仍通过指令触及的四个模块的唯一方式。计算织物部分是一份契约和一个已证明可重放的参考执行器，目前仅在 CPU 上运行过。提案“每个计算织物上一个库和一个形式”列出了剩余内容 [193]：

- 标准库的单一定义，以及将 `use` 作为引入库的唯一方式；
- 重放时重新推导的探测证据；
- 每条执行路径上的放置；
- 每个构造一个约简树；
- 校准运行；
- 整数和二进制32操作类；
- 从每个形式的形状中读取的硬件实现；
- 没有操作系统的主机；
- 记录中缺少的两个测量：一个内核在某一边界下跨设备类的能量，以及模型助手重用而非重新实现的库功能比例。

### 12.6 开发中的语言如何规划破坏性变更

[§12.4](#124-how-the-language-grows-and-shrinks) 说明了形式如何变更。本小节将该规则与 2026 年正在演进的若干语言的计划并置对比，依据它们的路线图、发布说明和论坛讨论。各来源的分量不一：凡主张仅依据单篇博客或论坛帖子的，正文均予注明；二手来源意见不一之处，如实报告分歧而不强作裁断。

**Rust：版次（edition），且无第二个主版本。** Rust 通过版次引入破坏性变更。版次按 crate（Rust 的编译与分发单元）选择，不同版次的 crate 仍可链接为同一个程序。Lobsters 论坛上的评论者将版次策略解读为永远不会有 Rust 2.0 的立场 [206]；这一解读来自论坛讨论串，而非项目官方声明。当前版次为 2024，在 Rust 1.85 中稳定。项目内部论坛正在讨论 2027 版次，部分参与者预计它会推迟到 2028 年；区间（range）是候选变更之一，目前尚未敲定任何内容 [207]。2026 年的实质性方向见于路线图“The Borrow Checker Within”[208]。它计划在 2026 年稳定下一代借用检查器表述 Polonius 的 alpha 版，而将其完整的流敏感形式留作后续工作。它还规划了视图类型（view types），允许函数声明其触及的值字段，从而可以同时借用不同字段。一项拟于 2026 年开展的实验仅在编译器中加入视图类型供试用，其语法仍在争论中 [209]。这些目标的进展在 Rust 博客上定期通报，例如 2026 年 4 月的报告 [210]。模式类型（pattern types）和线性类型仅见于二手综述；本次调查未发现二者有任何官方的 2026 年目标。

**Go：单一兼容性承诺。** 不存在 Go 2。Go 1 兼容性承诺依然有效，语言在其框架内演进。2026 年 2 月发布的 Go 1.26 带来了重写的 `go fix`、新的垃圾回收器、`new()` 的表达式形式以及泄漏 goroutine 的检测 [211]。2026 年 8 月 19 日发布的 Go 1.27 新增了泛型方法（带有自身类型参数的方法）、更强的类型推断、goroutine 泄漏剖析以及实验性的 SIMD（单指令多数据）操作 [212, 213]。

**Zig：在能够承诺稳定之前不发 1.0。** Zig 尚未到达 1.0，也没有设定日期。其输入与输出已围绕一个像分配器那样传入的 `Io` 接口重建，由调用者选择多线程执行或事件驱动执行，同时移除了 `async` 和 `await` 关键字 [214, 215]。一篇博客报道带有 `std.Io` 的 0.16 版于 2026 年 4 月发布 [216]；其他二手来源对版本号说法不一，应以项目官网为准。Lobsters 上关于 2026 年路线图的一场讨论报告了两项进行中的工作：用于调试构建的自研 x86 后端（取代其他构建所使用的编译器基础设施 LLVM），以及增量编译 [217]。据一份二手报道称，Zig 创建者 Andrew Kelley 认为只有在项目能够可信地承诺稳定时才会发布 1.0，该报道收集的估计时间介于 2026 年底至 2027 年之间 [218]。

**其他语言。** Mojo 1.0 于 2026 年 8 月 11 日随 Modular 26.5 一同发布，但此后仍可能进行审慎的破坏性变更 [219]。一篇报道称编译器源代码在一周后以带 LLVM 例外的 Apache 2.0 许可证开源 [220]；该说法仅有单一来源。Carbon 仍处于实验阶段，尚无可用工具链。引入内存安全设计将其 0.1 版最早推迟到了 2026 年底，项目自身也称这一日期“极具野心”[221, 222]。据 Herb Sutter 的委员会会议纪行（以下细节仅此单一来源），C++26 已于 2026 年 3 月定稿：契约和加固版标准库随该版本交付，安全配置文件推迟至 C++29，而旨在引入借用检查器的提案 Safe C++ 已被放弃 [223]。至于 Gleam、Roc、Vale 和 Hylo，调查仅找到盘点式文章 [224]，此处不引述其内容。

**两个共同模式。** 这些语言各自都在分阶段加入受检查的所有权：Rust 通过 Polonius 与视图类型，Carbon 通过在 0.1 之前必须具备的安全设计，C++ 则通过当下的契约与未来的配置文件。与此同时，它们各自都让为旧版本编写的代码继续通过编译：Rust 靠可互相链接的版次，Go 靠 Go 1 承诺，Zig 则靠在能够作出同样承诺前暂不发布 1.0。

**立场。** RCE 在设计上站在第二个模式的对立面，并用其他手段守护第二个模式所要保护的价值。

- *无版次，无版本选择。* 只有一种语言，即某一提交处的规范文本（规范 2.7）。`# rce-version:` 标签不作任何选择，也不参与哈希。凡使早期版本的有效程序改变含义的变更，都会成为带有新标签的新发布版本，且已命名的发布版本绝不修改（规范 C.15）。当新增规则时，早期提交接受的程序在后续提交下可能需要修改；规范在概述中已明确说明这一点。版次允许两种方言共存于同一程序中；形式只准入一种。
- *变更与它所触及的代码同行。* 与其让旧形式继续存活，对文本的修改以及仓库中受其触及的每一个程序、示例和库模块都会在同一次提交中一起移动，并在账本中记录改了什么及原因（[§12.4](#124-how-the-language-grows-and-shrinks)）。
- *兼容性在两个工件之间检验，而非靠口头承诺。* `rce api-diff` 根据封闭表将导出的每项变更归类为兼容或破坏性变更（F.4.3）；`rce equiv` 在已探索字母表上判定两个程序是否具有相同行为（[§3.8](#38-behaviour-equivalence-and-dimension)）；`rce change` 结合两者，将变更归类为勘误、含义变更或接口变更（规范 10.11，源自提案 `spec/proposals/one-commit-change.md`）。该判定在已探索界限内成立，而 T59 给出了深度一致所能证明的距离上界。
- *程序指名其受检所依据的对象。* `rce manifest` 写出一份清单，通过规范文本的哈希固定每个模块，并通过标准库自身清单的哈希固定标准库，没有任何版本解析器（F.5.3）。已发布的定义不可变；修正会产生带有新哈希的新定义。因此，程序绝不会被静默升级。

这一权衡是明确的。Go 和 Rust 承诺那些不属于它们所有的外部代码能继续编译。RCE 迁移自己拥有的代码，而对仓库之外的程序则提供哈希固定、指名唯一文本的发布标签以及每次变更的分类结果，但不承诺该程序仍被接受。本文不对这两种设计排定高下；文中没有任何测量评估任一设计给外部程序所有者带来的成本。

在第一个模式上，形式的立场更为精简。语句的足迹（它所读写的位置路径集合）直接由语句本身定义（规范 C.3），且 `par` 的各分支仅在其足迹互不相交时才获准入（W-PAR-1）。Rust 的视图类型通过在函数签名中附加声明来达成类似目的（同时使用同一值的不同部分）；形式无需此类声明。Zig 由调用者选择的 `Io` 则与形式的分工相似：步进函数是纯的、完全的，标准库仅通过适配器执行输入输出，而主机选择计算织物并记录每次放置以供重放（[§12.5](#125-the-library-and-the-compute-fabric)）。在所调查的资料中，没有任何路线图把程序的行为变成可受检查、可重放的对象，也没有按“实际做什么”来比较两个程序。这是对所读路线图的判断而非测量结果，而等价性检查与重放（定理 T3）正是为了填补这一空白而构建的。

## 13. 工作计划及其门槛

2026 年 10 月对公开仓库的两次独立审查得出了相同的诊断。检查器本身未经形式化验证：没有任何证明将 Lean 语义精化到 Rust 解释器，两个 Lean 核心之间也没有关联它们的定理。下面的两个符合性基线来自不同的报告，在此分别点明。

**Lean 核心。** 机械化核心的报告（公开提交 `d91a9fc8` 处的 `conformance/reports/results-lean-core.json`）记录了 1,977 个结果中 210 个测试通过、1 个失败、1,766 个未支持，因此该 Lean 核心报告中约有十分之一处于概述所宣称的定理覆盖之下。公开主分支顶端 `3d38454a28ef`（2026 年 11 月 6 日）处提交的该文件仍保持同一统计：210 个通过、1 个失败、1,766 个未支持，共 1,977 个结果。这一统计是 Lean 核心快照。参考检查器的基线见下一段。

**参考检查器。** 在 `3d38454a28ef` 处，README 以及已提交的报告 `conformance/reports/results-reference.json` 和 `conformance/reports/coverage.json` 记录了覆盖全部 311 条规范性条款中 311 条的 2,236 个测试。参考实现通过 2,221 个、失败 0 个、标记未支持 15 个。该参考报告指明的解释器提交为 `fb4211290198`。Python 和 JavaScript 发出器各自在 1,462 个测试上与参考轨迹逐行一致，0 个失败，而这两个文件中其余 774 个结果为不适用（`conformance/reports/results-emit-python.json`、`conformance/reports/results-emit-js.json` 及 `conformance/reports/parity.md`：1,462 个回答与参考字节完全一致，0 个不同）。已提交的 Rust 和 Scala 结果文件保存的是更早运行的状态，处于这一参考基线之外（`conformance/README.md`）。

生成的代码在每个目标上都是一套动态值运行时，共四个手写运行时，每个约 2,000 行。能量估计无法区分不同目标，因此最小焦耳提取从不作出目标选择。`3d38454a28ef` 处的提升包括针对一种 Go 模式的探针 `spec/lift/go/lift_go.py`，以及针对 Python 3.13 子集的 `spec/lift/python/lift_py.py`，后者承载了固定 Python 语料库 92 个案例中的 6 个（`lang/README.md`）。普遍性主张需要在至少十种语言上进行测量，仍列于 [§10](#10-work-to-finish)。引擎（档位、e 图、重写及其证明、内核及其模型检查，以及提升）尚未公开，因此它所产生的结果只有在逐项基于公开代码重建后才会进入本文；[§10](#10-work-to-finish) 列出了这些结果及其重建路径。对于一个公开声明以可追溯性为开源理由的项目而言，这是整个计划中最大的风险。

2026 年 11 月 6 日，在 openIE-dev/rce `3d38454a28ef` 处，调度（schedule）与构造（construct）已合入主分支。桥接语料库不是生产级编译器。手写发出器仍在遍历语法树。将循环体 `break` 作为循环体标志传递的方案 B 工作以 [pull request #148](https://github.com/openIE-dev/rce/pull/148) 的形式保持开放。

该计划按依赖关系排序：可重复性优先；然后是编码和成本模型，所有后续测量都基于此；然后是证明链；最后才是广度。每个阶段在运行前注册的证伪条件处结束，并报告置信区间；当其门槛观察结果发布时，阶段关闭，而不是基于工作量。门槛在[§9](#9-falsifiers)及下表中陈述。

| 阶段 | 交付成果 | 什么击败该阶段 |
|---|---|---|
| 0 重现 | 每个依赖于引擎的结果，该引擎基于标记提交的公开代码重建，如[§10](#10-work-to-finish)所列；每个重建运行的每任务记录；留出的Defects4J集合完成；每个注册由哈希密封；一个版本字符串；规范勘误关闭；终止、权威和错误的单一拼写；表面冗余（示例语料库中每个形式的独立构造数）的已发布度量 | 本文中无法通过一个命令从公开提交重建的数字 |
| 1 冻结形式 | 内容寻址的定义作为唯一的中间形式；类型化关系作为形式值；每个发射器消耗的单一降级；按目标检查往返条件；按目标校准的成本模型，如[§6.3](#63-energy)所述 | 仅因大小而需要修改的定义；往返改变形状哈希的目标；成本模型将两个目标的排名排得与墙式功率计相反 |
| 2 一个核心，验证门槛 | 一个带有T1到T9重述的单一Lean核心；从检查器的规则表生成的类型规则，使得没有Lean对应规则的构建失败；从Lean提取的检查器和解释器作为门槛使用，Rust检查器作为交叉检查的前端 | 提取的门槛与Rust检查器对任何程序意见不一致；重述定理需要一个未经证明直接准入的步骤；Lean核心符合性报告中未支持测试超过10% |
| 3 以焦耳计价的目标 | 数值工作的唯一拼写为Rank-n数组和批量操作；Zig和Fortran发射器具有固定的浮点和溢出模式；在契合中而非形式中的布局提示；每个发射模块的翻译验证证书；[§8.3](#83-a-wall-meter)中的墙计量协议 | RCE-F3和RCE-F5；没有证书的模块被发射；提取为每对目标选择相同的项 |
| 4 提升作为入口 | 每种语言的提升，Go和Python优先，然后是TypeScript和Rust，然后是C和Zig；在提升冻结下统计每种语言语料库中的每一个程序；[§12.2](#122-the-form-among-programming-languages)中的封装标准按每种语言运行；带有证书的已准入形状哈希的公共、仅追加日志 | 在第二次注册运行后，前四种语言中的任何一种提升覆盖率低于10%；形式在标准的任何坐标上严格更差 |
| 5 生态系统复合 | 从带空缺的意图合成；第一批档位及其验证证书公开；[§8.6](#86-convergence-of-model-calls-at-large-n)中的收敛协议在1,000个公共规范上运行；一个表中的基线，每正确结果的成本以焦耳和美元计 | RCE-F1、RCE-F2、RCE-F4；工具无法检查或发射自身 |

审查与[§12](#12-the-form-against-the-record)的调查存在三个不同之处，如下解决。规范JSON仍然是唯一的哈希编码，原因如[§12.1](#121-seven-areas-of-the-design)所述；二进制编码仅在作为那些字节的双射时，才可在传输中镜像，且需在相同向量上检查。终止的唯一拼写是声明的递减度量，循环和递归限制作为语义；内容寻址形式仍需要递归的有界不动点，度量是其限制。将并发词汇减少到两个原语被记录为开放提议而非决定，因为这两个原语的定理必须首先在检查器上证明，而不是在模型上。完全不在计划中：阶段2之前的自托管编译器，阶段1之前的进一步目标，附录中的任何构造在其定理之前，以及生产编译器，规范自身的概述称文档停止移动之前不应构建。

自审查以来，必须与规范保持一致的六个仓库（书籍、示例程序、标准库、符合性套件、语法包和编辑器）已连同各自的历史合并到规范仓库中，每个都由从同一提交构建检查器的工作流进行检查。项目中没有任何地方固定或内嵌旧规范；编辑器内嵌的落后六次提交的检查器曾是最后一处此类固定。研究站点和实验仓库仍保持独立，并读取规范仓库；规范仓库从不读取它们。
