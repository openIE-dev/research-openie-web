## 摘要

本文描述 Reality Code Engine（RCE）：一种把程序一次写成状态机（称为形式）并由其生成其他语言代码的系统。文中报告在 10,000 个形式上以及公开缺陷数据集上测得的结果，并说明这些论断可如何被证伪。

**用平常话说**

1. 程序只写一次，写成一种精确的形式，计算机从它生成多种语言中的同一程序。
2. 因为形式只允许已声明的内容，破损的输入在入口就被拒绝，而不是事后再修。
3. 通过检查的修复会被保存并复用，同一问题不会再付第二次时间或能量。

## 1. 论题

自主计算机自动化是一个含有许多点位的设计空间。每种路径都落在五条连续轴上的某处：每次正确结果所耗能量；系统在运行时必须消解的熵，以及随之而来的输出确定性；接受结果的验证强度；每个被接受结果被复用并复利的程度；以及对模型的依赖程度。一个大语言模型（LLM，一种统计文本模型）若从提示词为每次改动重新生成，则靠近该空间的一角：它每项任务都依赖模型，每次从高熵分布中取新样本，并在每项任务上再次为生成付费。检索、规则、综合、验证与缓存占据许多其他点位，真实系统往往把它们组合起来。

Reality Code Engine（RCE）是该空间中的一个点位，本文描述并测量它。RCE 把程序建模为数据库函数式状态机。Lopes 与同事测得 GitHub 上约 70% 的代码是更早文件的克隆 [33]，因此 RCE 先尝试检索已有契合、加以适配并检查，仅在没有更便宜路径能关闭任务时才调用模型。

**核心论断。** RCE 是一个完整的代码生态系统，其中程序由意图原生写成。意图只写一次，写成形式：一个状态、一组事件与一个纯的、全定义的转移。形式是该意图的无损编码。每个目标（状态图、Rust、Python、XState、SCXML、WASM）都是形式的投影，且每个投影都按字节重放形式的迹。形式未声明的状态无法被写出，合同之外的输入在入口被拒绝。因此，生态系统中的程序不会像常见语言中的程序那样相对注释、测试或其他实现发生漂移，也不需要事后的差分或错误追踪。每个通过门槛的契合都被存储并复用，生态系统随增长而复利（[§2.4](#24-gated-verified-recursive-self-improvement)）。用其他语言写成的代码是一扇入口：它通过提升进入（[§6](#6-lift-entering-the-ecosystem-from-other-languages)）。

空间中每个点位都面对同一门槛。门槛是正确性：任务的完成性谓词 $C(z)$，在此是任务的测试、证明或一致迹。在通过门槛的运行中，系统按完成所需焦耳 $J^*$ 排序。正确性是约束，不是分数。

RCE 的机制称为档位，按成本顺序运行，第一个通过门槛的档位关闭任务。

能量数字按来源标注。`est_j` 是解析估计值。`reported_j` 是操作系统或片上计数器。`measured_j` 留给墙上电表，本文所有结果中均为空。

**意图是高熵的。** “让结账更快”可有许多含义：更短的页面加载、更少的步骤、更快的刷卡审批、缓存的购物车，或在某一类设备上更快。上下文是隐含的，从未写明。Shannon 测得印刷英语约为每字母 0.6 到 1.3 比特 [1]。字母可预测。含义不可。

**每次转换都丢失信息。** 意图变成规格，上下文丢失。规格变成数百种表面语言之一，备选与边角情形丢失。源码变成中间表示（IR），名称、风格与作者理由丢失。IR 变成机器码，类型变成尺寸，循环变成跳转。

**底板是低熵的。** 每个程序最终都是加载、存储、算术与跳转。目的地只容得下少数形状，代码向它们弯曲。收敛是设计使然。

**边界是含义分叉之处。** 同一行在边缘给出不同答案。在 Python 中，`-3 % 2` 是 1，`-7 / 2` 是 -3.5。在 C 中，`-3 % 2` 是 -1，`-7 / 2` 是 -3，有符号溢出未定义。在每个边界重新生成代码的系统，在每个边界都在猜测。

**各轴，以量陈述。**

| 轴 | 一端 | 另一端 | RCE 所在 |
|---|---|---|---|
| 每次正确结果的能量 | 每项任务再付全价 | 每个新情形付一次，然后是处理器底板 | 在已覆盖任务上处于底板 |

### 2.1 编程即编码理论

本节论题是：编程可读作编码理论。程序员沿两种熵体制之间的梯度转换意图。意图是高熵的，是含义上的分布。代码是低熵的，每个状态一个确定性转移。软件工作的每一步，从需求到寄存器，都是该转换的一步。七十年来，文献以多种语言把这一点分片说出。本节把碎片收成一条论证，并把每个 RCE 档位放在其上。

**度量。** Shannon 定义了信源熵与信道容量 [40]，并测得印刷英语约为每字母 0.6 到 1.3 比特 [1]。Kolmogorov 于 1965 年在俄文的 *Problemy Peredachi Informatsii* 中给出信息量的三种进路，并把算法进路置于首位：对象中的信息是产生它的最短程序的长度 [41]。Solomonoff 已把同一对象当作归纳推理理论 [42]，Chaitin 表明程序大小服从与 Shannon 形式上相同的恒等式 [43]。Rissanen 把这一思想变成选择模型的规则：最小描述长度 [44]。合在一起，它们说程序是码字：对行为的描述，最短的正确者是底板。RCE 的抽取规则（在等价契合中保留焦耳最少者，命题 3）正是以焦耳代替比特的那条规则。

**代码处于低熵体制，且有人测过。** Hindle、Barr、Su、Gabel 与 Devanbu 发现代码“非常重复，事实上甚至比自然语言更甚”，在同一 n-gram 模型下交叉熵更低 [35]。Gabel 与 Su 发现项目中多数行已在别处出现 [34]，Lopes 等发现 GitHub 上多数文件是克隆 [33]。Tu、Su 与 Devanbu 发现代码也是局部的：附近写过的内容预测接下来写什么 [46]。Ray 与同事发现有缺陷的行更不自然、熵更高，且缺陷被修好时熵下降 [45]。2025 年，Yang、Kolak、Hellendoorn 与 Martins 用补丁引起的熵变化来排序修复候选，并把正确补丁与过拟合补丁分开 [51]。Allamanis、Barr、Devanbu 与 Sutton 以自然性之名综述该领域 [47]。结果不只是英语文献的。Prem Devanbu 于 2013 年在印度软件工程会议的主题演讲中陈述了它 [50]。IBM Research India 的 Sridhara、Sinha 与 Mani 在同一会议测量代码周围的自然语言制品，发现提交消息最规整，而 Stack Overflow 散文行为像普通英语 [49]。在中国，《软件学报》于 2022 年发表了代码自然性研究综述，陈述交叉熵度量以及缺陷代码熵更高的发现 [48]。在日本，大阪大学的 Doi、Higo、Arima、Shimonaka 与 Kusumoto 使用 n-gram 自然性，先在日文 IEICE 技术报告、后在 ICPC 2018，区分机器生成与人手写的源文件 [73, 74]。生成代码在熵尺度上甚至低于人手代码，因为生成器是固定转换。在巴西，Arrebola 的博士论文在按项目与维护者分段的 n-gram 与主题模型上构建代码建议，并以交叉熵（编码下一词元所需比特）评估 [75]。两种体制在同一仓库可见：代码周围的散文是高熵的，代码是低熵的。

**度量重要。** Febres、Jaffé 与 Gershenson 从委内瑞拉与墨西哥出发，按消息长度比较英语、西班牙语与程序文本的词汇多样性，发现程序文本更多样 [76]。Rahman、Palani 与 Rigby 发现代码 n-gram 可预测性很大一部分来自语法词元，去掉它们后代码仍重复但少于最初报告，API 使用是最重复的部分 [77]。两项结果都锐化而非推翻论断。符号多样性不是可预测性，低熵体制是下一步条件分布的性质，而确定性转移正是固定它的东西。因此 RCE 的 G0 按形状键控，而非按表面词元。

**意图处于高熵体制。** Zave 与 Jackson 表明需求是关于环境的陈述，规格是关于接口的陈述，其间的缺口只由往往未写出的领域知识填补 [64]。Brooks 把软件难度分成本质与偶然：本质是概念构造，其中大多是规格与设计，而非表示 [61]。Naur 主张程序是程序员所持理论的可见部分，且该理论不能从文本完全恢复 [62]。用 Shannon 来读，三者说的是同一件事。意图携带的不确定性多于任何一个程序，写出程序正是消除它的动作。代码写成后仍留在程序员头脑中的，是意图中代码未曾编码的部分。

**转换是求精，求精是收窄。** Hoare 给程序一种逻辑，其中程序相对前置与后置条件正确 [54]。Wirth 讲授逐步求精：通过相继决定把任务分解为指令，每一步固定规格留下的选择 [53]。Dijkstra 的看守命令把开放选择明示为非确定性，并通过消除它从规格导出程序 [52]。在慕尼黑，Bauer 与 Wössner 的 CIP 项目把程序开发建成从规格到程序的正确性保持变换序列 [58]。在法国，Abrial 的 B 方法及随后的 Event-B 把求精带到工业规模，每步带证明义务 [55, 56]。在芬兰，Back 与 von Wright 给出求精的格论演算 [57]。在各自情形下，规格表示可接受行为的集合，每一步求精缩小该集合，直到留下一个确定性行为。这是每步带证明的熵减。RCE 的形式是该链的最后一环：在数据库状态上的全定义、确定性转移 $\delta$，每个选择都已消解（[§3.2](#32-definitions)）。

**综合是收窄假设空间的搜索。** Gulwani 的 FlashFill 通过表示所有一致程序的集合并与每个新例子求交，从少量输入输出例子学习字符串程序 [59]。Gulwani、Polozov 与 Singh 把程序综合一般表述为在意图约束下对程序空间的搜索 [60]，Solar-Lezama 的草图用求解器填充部分程序中的空洞 [27]。每个例子或约束是一次消除假设的测量。Shannon 的度量计算需要多少次这样的测量。RCE 的 G2 就是那一档。

**转换产物只有一种形状。** Gurevich 证明每个顺序算法在其自身抽象层级上由抽象状态机捕捉 [2]。Codd 使状态成为关系 [5]，事件溯源使状态成为只追加日志的折叠 [14]。在 Curry 与 Howard 之下，证明是程序，命题是类型 [18, 72]，因此已验证的契合是其规格的证明。这些是低熵体制形状很少的原因：目的地是数据库上的状态机，无论表面语言为何。

**没有门槛，低熵会衰变。** Lehman 在数十年大型系统观察中指出，使用中的程序必须持续变化，其复杂度会增长，除非做功去降低它 [63]。Torres、Baltes、Treude 与 Wagner 在 25 个项目的提交历史上测量结构与文本熵，发现二者一同上升 [78]。熵从环境回流进代码。要把代码保持在低熵体制，需要每次变更上的门槛，而 RCE 的门槛是正确性（[§4.3](#43-the-gate)）。

**编译器已经在做信源编码。** Franz 与 Kistler 把程序作为压缩抽象语法树交付并在加载时生成本地代码，这是程序在其自身语法上的信源编码 [67]。Fraser 从语料推断代码的统计模型以压缩它 [68]。Futamura 于 1971 年在日文期刊 *Systems, Computers, Controls* 中表明，把解释器特化到程序得到编译后的程序，特化特化器得到编译器 [70]。新西伯利亚的 Ershov 把同一思想发展为混合计算 [71]。Cousot 夫妇的抽象解释计算对程序每种行为的可靠、更低信息的描述 [69]。与信道编码的类比是本文的解读，而非被引用的定理：类型、测试与证明加入经检查的冗余，使错误程序在运行前被检出，如同奇偶校验检出损坏的码字。

**擦除是焦耳去向。** Landauer 表明逻辑不可逆步骤（擦除一比特）至少耗散 $k_B T \ln 2$ [65]。Bennett 表明计算原则上可做成逻辑可逆，因此界限在擦除而非计算上 [66]。把高熵意图转换成一个低熵程序，丢弃意图所允许的每个备选。那次丢弃是关于备选之信息的擦除，并有热力学底板。RCE 对每个新情形付一次丢弃并存储结果，因此重复情形不再擦除新东西。

### 2.2 RCE 如何转换，以及各档位所在

按编码理论来读，任务作为消息到达，其剩余不确定性是尚无已存契合消解的部分。每个档位以不同代价消除不确定性，档位按该代价排序（[§4.2](#42-the-gears)）。

| 档位 | 它对不确定性做什么 | 上述论证中的谱系 |
|---|---|---|
| G0 查找 | 认出意图已被编码；以处理器底板代价用检索消解 | 重复性与克隆 [33, 34, 35]；局部性 [46] |
| G1 规则 | 应用已知的看守重写；以无搜索方式消解反复出现的残差 | 正确性保持变换 [52, 58]；带证明义务的求精 [55, 56] |
| G2 综合 | 搜索假设空间，并用例子、约束与求解器收窄 | 作为搜索的程序综合 [27, 59, 60] |
| G3 至 G5 模型 | 当更低档位无法弥合缺口时，从学得的代码分布采样；仅作提议者 | 代码的交叉熵模型 [35, 47] |
| 门槛 | 仅在有测试、覆盖与证明证书时接受候选 | Hoare 逻辑 [54]；Curry-Howard [18, 72] |
| 晋升 | 存储被接受的契合，使同一残差下次只需 G0 | 最小描述长度 [44]；Landauer 擦除只付一次 [65] |

第 2 节各轴上的位置差异，在于转换在何处付费。每次任务都对提示词完整分布采样的路径，每次都再付高熵一侧。存储并复用被接受契合的路径，只为残差付费，且只付一次。多数系统介于两端之间，RCE 位于复用一端。

### 2.4 有门槛、经验证的递归自我改进

Good (1965) [111] 把超智能机器定义为能设计更好机器的机器，从而使改进递归。Yudkowsky (2013) [113] 把问题表述为回报：每单位改进使下一单位更便宜还是更昂贵。Schmidhuber 的 Gödel 机 (2007) [112] 给出一个带保证的形式答案：程序仅在证明重写改进其期望效用之后，才重写自身任何部分（包括其自身搜索）。Löb 定理 (1955) [114] 是自我信任的证明者所遇障碍，Yudkowsky 与 Herreshoff (2013) [115] 称之为 Löbian 障碍：系统一般不能证明使用其自身证明系统的后继者的可靠性。近期系统放弃证明要求而按测量分数选择：STOP（Zelikman 等，2023）[116] 改进改进代码的脚手架，Darwin Gödel Machine（Zhang 等，2025）[117] 保留按基准分数选出的自我修改编程智能体档案，AlphaEvolve（Novikov 等，2025）[118] 在自动评估器下演化程序，Voyager（Wang 等，2023）[119] 增长经验证技能库供后续任务复用。

RCE 采取 Gödel 机的结构与 Voyager 的库，并有两点差异以避免对其所晋升对象的障碍。第一，改进的对象不是证明者。RCE 晋升处理器、重写与档位，每一项都对照固定的、单独认证的内核检查：Kani 线束与 SMT 编码在晋升中永不改变，因此任何一步都无需信任后继者的证明系统。第二，门槛是边界上的正确性证明，不是分数。分数可在接口假设破裂时上升；边界上的证明不能被破坏它的变更通过。

**命题 R1（单调正确性）。** 若每个被晋升的变更通过其边界的检查，且其他边界的检查未变，则那些检查在晋升前确立的每条性质在晋升后仍成立。

**命题 R2（复利）。** 设工作负载为任务的多重集，且被晋升的处理器关闭其形状的每项任务。则第 t 轮中的升级次数对 t 非增，且在第 1 轮前晋升的修正按它在每轮后续关闭的升级数降低每个视界的累计升级。在引擎演示的参考工作负载中，八轮累计升级在汇处一次修正后从 21 降到 15，两种情形下最后一轮都达到零，每项任务正确关闭且无晋升被拒绝。

图 4 画出命题 R1 与 R2 的机制及参考工作负载的合计。

![RCE 栈图，从顶部意图经形式、门槛、投影与运行时到硬件与能量共六层。运行时层在通过其边界检查后晋升的修正，以箭头向上穿过其上每一层。旁侧小条形图给出引擎演示参考工作负载八轮累计升级：无修正为 21，汇处一次修正为 15。](/figures/rce/stack-compounding.svg)

**命题 R3（成本下降）。** 由于被晋升的处理器在模型调用之处执行，其成本是按基底表计价的处理器操作计数，因此当升级趋向零时，一轮的能量趋向仅处理器的能量。

Futamura 投影（1971，再版 1999）[120] 与 Turchin 的超编译（1986）[121] 给出该过程的极限。把解释器特化到程序得到编译后的程序；特化特化器得到编译器。RCE 的晋升把一般升级路径特化到实际出现的形状，因此引擎向其工作负载的残差程序收敛：仍须由模型或人提供的计算部分。门槛下的递归自我改进，就是以经检查步骤做出的那种收敛。[RCE 引擎演示](/demos/rce-engine/#compounding) 的复利层在浏览器中运行该工作负载。

### 3.1 “同一形式”的最强形式陈述

定理的范围先陈述。Gurevich 的顺序公设覆盖顺序算法；并行与交互算法需要 Blass 与 Gurevich 的进一步公设 [3]。Blass、Dershowitz 与 Gurevich 主张，没有单一的算法等价关系适合每一目的 [79]，Moschovakis 与 Vardi 阐述了何为算法的争论 [80, 81]。做输入输出的网络处理器落在顺序定理之外。形式处理交互的方式与交互进路相同：每个输入是 $E$ 中的事件，状态机在其上步进。因此“一个形式”是植根于顺序定理并按约定扩展的建模选择，生产先例包括 Elm 架构 [83]、持久工作流事件历史 [84] 以及如 Flo 的流语义 [82]。第 3.4 节的命题为该选择陈述。

Gurevich 的抽象状态机（ASM）定理是每个算法有一种形状的最强形式陈述 [2]。抽象状态机是状态为一阶结构、步进为有限组看守更新的机器。Gurevich 陈述三条公设。顺序时间：算法有状态、初始状态与一步映射 $\tau$。抽象状态：状态是固定词汇上的一阶结构，在同构下封闭。有界探索：有限组项决定每一步。其主定理（定理 6.13）写到：“对每个顺序算法 A，存在等价的顺序抽象状态机 B。”Blass 与 Gurevich 将其扩展到并行算法 [3]。Dershowitz 与 Gurevich 加入第四公理（初始运算可计算）并由此导出 Church 论题 [4]。

<div id="32-definitions" class="anchor-alias" aria-hidden="true"></div>

### 3.2 定义

**定义 1（形式）。** 程序是元组

$$P = (S, E, \delta, D, \lambda)$$

- $S = \Sigma_c \times \Sigma_d$，状态空间：固定词汇 $\Sigma$ 上的结构，分为控制区域 $\Sigma_c$ 与数据 $\Sigma_d$。$\Sigma_d$ 持有逻辑时钟、输入计数与带类型关系（在语言中还包括已声明的区域）。每个状态是 Codd 意义上的数据库实例 [5]。
- $E$，事件字母表，包括逻辑时钟滴答。
- $\delta : S \times E \to S \times O^*$，转移：全定义、确定性且纯，写成有限组看守更新“若 $\varphi$ 则 $f(\bar t) := t_0$”，每步读取有界组位置。它返回下一状态与该步的输出。记 $\delta_1 = \pi_1 \circ \delta$ 为其状态分量。
- $D$，持久日志：条目序列 $\{\mathit{seq}, \mathit{event}, \mathit{prev\_hash}, \mathit{state\_hash}, \mathit{hash}\}$，其中 $\mathit{state\_hash}$ 是该步之后状态的规范 JSON 的 SHA-256，$\mathit{hash}$ 是前四个字段的规范 JSON 的 SHA-256，第一个 $\mathit{prev\_hash}$ 是 64 个零。日志是哈希链，因此改变任何过去条目会改变其后每个 $\mathit{hash}$。
- $\lambda = \pi_2 \circ \delta : S \times E \to O^*$，输出映射。Mealy 机读两个参数 [6]；Moore 机只读状态 [7]。

**定义 2（形式与契合）。** *形式* 是带四条不变量的元组形状：$\delta$ 确定性且纯；探索有界；词汇固定；状态是日志的折叠，

$$\mathrm{state}(D) = \mathrm{foldl}(\delta_1, s_0, D).$$

日志也可携带每个条目的结果、输出与状态。它们是导出的：不被哈希，且必须等于重放（[§3.7](#37-the-language-versions-06-and-07-costs-and-theorem-status) 的 T1 与 T3）。两种拒绝是不同的。在引擎配置中每个事件都被应用，违反其契约的输入产生 `reject` 输出与一条错误行。在语言中，被拒绝的事件使状态不变（T8），并被记录为已拒绝。

*契合* 是填充该形状的数据：词汇 $\Sigma$，字母表 $E$ 与 $O$，定义 $\delta$ 的规则程序 $\Pi$，定义 $\lambda$ 的输出规则，以及初始数据 $s_0$。用 Gurevich 的话说，契合是词汇、ASM 程序与初始结构。用 Codd 的话说，$\Sigma$ 是模式，$s_0$ 是实例。用产品线的话说，契合是特征选择 [8]。用语法引导综合（SyGuS）的话说，契合是满足规格的语法中的项 [9]。

**定义 3（契合等价）。** 两个契合等价，当且仅当对每个事件序列 $L$，它们在 $\lambda$ 下的输出序列相等。

**定义 4（契合语言）。** 其项表示契合的语法。编程语言、SCXML 文档、XState 配置与 `.rce` 规格是契合语言。当 $\Sigma$ 上每个 ASM 程序在其中有项时，契合语言是完备的。

**定义 5（控制投影）。** 把 $\Sigma = \Sigma_c \cup \Sigma_d$ 拆成有限控制符号与数据关系。$P$ 的状态图是 $\delta$ 到 $\Sigma_c$ 上的投影：状态是 $\Sigma_c$ 的值，转移携带事件与对 $\Sigma_d$ 的看守，动作是对 $\Sigma_d$ 的更新。Harel 的状态图给出层次与正交区域 [10]。

**定义 6（契合 e-图）。** 对契合 $F$ 与一组可靠重写 $R$，契合 e-图 $EG(F, R)$ 是 $F$ 的规则项在 $R$ 下饱和的 e-图 [11, 12]。每个 e-类容纳按定义 3 等价的契合。

**定义 7（焦耳成本）。** $\mathrm{cost}_J(t)$ 是在命名基底上运行项 $t$ 一次的估计能量（`est_j`），按期望运行次数加权。

<div id="33-why-database-functional-state-machine" class="anchor-alias" aria-hidden="true"></div>

### 3.3 为何是“数据库函数式状态机”

有限关系结构是数据库实例，因此 Gurevich 状态是数据库，每一步是有界事务。*数据库*：$S$ 是关系结构。*函数式*：$\delta$ 与 $\lambda$ 是纯的。*状态机*：运行是 $\delta$ 在事件上的折叠。Moseley 与 Marks 在架构上画出同一条线 [13]。事件溯源在应用状态上画出它：“把对应用状态的所有变更捕捉为事件序列”[14]。Dedalus 在逻辑上画出它，可变状态是按时间索引的关系 [15]。

### 3.4 命题

**命题 1（形式捕捉每个顺序算法）。** 对每个顺序算法 $A$，存在形式实例 $P$，其运行即 $A$ 的运行。

*证明概要。* 定理 6.13 给出具有 $A$ 的状态、初始状态与一步映射的 ASM $B$。设 $E = \{\varepsilon\}$，$\delta(s, \varepsilon) = \tau_B(s)$，$D = (s_0, \varepsilon^n)$，$\lambda$ 为恒等。$n$ 次滴答后的折叠是 $\tau_A^n(s_0)$。由 Gurevich 的推论 3.3，$P$ 与 $A$ 有相同运行。∎

**命题 1b（交互程序）。** 用在每步前设为 $e$ 的零元输入符号扩展 $\Sigma$；则 $\delta(s, e) = \tau(s[\mathit{in} := e])$ 是扩展词汇上的顺序算法，命题 1 适用。该构造是我们的。

**命题 1c（可计算性）。** 在 Dershowitz 与 Gurevich 公理下，每个形式实例计算 Turing 可计算函数 [4, 16, 17]。形式不增加能力。它给该类中每个程序一种形状。

**命题 1d（证明是契合）。** “对给定命题的每个证明，存在对应类型的程序”[18]。类型是规格，证明是满足它的契合。正确性门槛是该证明或通过接受测试的存在。

**命题 2（一个生成器）。** 一个函数 $G : \mathrm{Fit} \to \mathrm{Program}$ 为每个契合生成可运行程序，且不读领域。*依据：* 每个程序是形式实例，因此 $G$ 发出带类型的存储、事件类型、编译后的规则、带折叠的日志与输出分派器。Rails 生成器、JHipster 与 Yeoman 等脚手架是限制在小契合语言上的 $G$。产品线工程始于“对相关软件系统共性的系统发现与利用”[8]；共性就是形式。

**命题 3（最小能量抽取）。** 用 $\mathrm{cost}_J$ 抽取返回抽取器在 $F$ 的 e-类中找到的焦耳最少的项。*证明概要。* 重写是可靠的，因此 e-类中每一项都有 $F$ 的可观察行为并通过同一门槛。抽取最小化成本，成本是焦耳。∎ 这是 Mixture of Limits（极限混合）应用于代码：保留完成任务的最小契合，其余是浪费。

**命题 4（重放确定性）。** 若 $\delta$ 不读墙上时钟、无名称地排序更新并记录每个输入，则对同一 $D$ 的两次重放在每步给出相同状态哈希。

**命题 5（状态图投影可靠）。** 把运行的每个状态投影到 $\Sigma_c$。结果是在相同事件下发出的状态图的一次运行。

**命题 6（协调预算）。** 标记为单调的规则可在副本上无协调运行；仅非单调规则需要协调点。*依据：* CALM 定理，“具有一致、无协调分布式实现的程序恰是可用单调逻辑表达的程序”[19]。

标签由规则导出，从不声明；IR 检查拒绝存储标签与导出标签不同的形式（规格，附录 D.5）：

| 规则含有 | 标签 | 原因 |
|---|---|---|
| 无 resolve、read、join 或 scan | 单调 | 其写入只增加键并增长计数器 |
| 一个 resolve | 非单调 | 它删除升级行 |
| 读取其自身的汇 | 非单调 | 读取、修改、写入 |
| 一个键控 join | 非单调 | 被连接的行可能现在缺失、之后出现，或被覆盖 |
| 一个 scan | 非单调 | 它观察整个关系，包括缺失的部分 |

标签是可靠的但不完备：对只插入关系的 join 本是单调的，但该配置不证明某关系是只插入的，因此标签不作此声称。当每条规则都单调时，形式是无协调的。每个 read、join 与 scan 看到事件进入时的状态，因此输入事件的后状态不依赖于不同汇的规则的运行顺序；只有输出顺序依赖于它，而输出顺序由内容哈希固定。

**命题 7（智能作为焦耳导数）。** 设 $X$ 计通过门槛的任务，$J$ 为所耗焦耳。$\iota = dX/dJ$ 从记录每个事件及其 `est_j` 的 $D$ 事后读出。在 $\mathrm{cost}_J$ 下的抽取固定门槛且不提高 $J$，因此在相等的 $X$ 下它不降低 $\iota$。

### 3.6 一个生态系统、无损，以及普遍性论题

**构造上无损。** Shannon 的信源编码定理把无损码的底板固定在信源熵 [40]。形式在可检查的窄义上是意图的无损码：形式的规范序列化是单射的，因此在任何状态、事件或转移上不同的两个形式有不同的形状哈希，解码序列化得到同一形式。到目标的每个投影是仅形式的函数。双向变换使往返精确。Foster、Greenwald、Moore、Pierce 与 Schmitt 把透镜定义为带往返条件的 get 与 put 函数对，使视图与其源一致 [122]，Hofmann、Pierce 与 Wagner 把条件扩展到对称透镜 [123]，Czarnecki 与同事在模型工程、数据库与编程语言上综述同一一致性条件 [124]。RCE 的往返条件是整程序层级的 GetPut 条件：把投影提升回来，形状哈希不变。

**构造上正确。** Dijkstra 于 1968 年提出程序与其证明应一同开发，使正确性被设计进去而非事后测试 [125]。Hall 与 Chapman 把该进路带入带形式规格与每步求精的商业安全系统 [126]。Minsky 对类型化函数式编程的规则（使非法状态不可表示）在类型层级说同一件事：不能容纳坏值的类型消除检查它的需要 [127]。Turner 的全函数式编程要求每个函数在每个输入上终止，使程序表示无隐藏失败的数学函数 [128]。RCE 的形式在 Turner 意义上是全的，其合同类型在 Minsky 意义上使未声明状态不可表示，且 [§2.1](#21-programming-is-coding-theory) 的求精链在 Dijkstra 意义上终止于它。后果即 [§1](#1-thesis) 所述：错误在入口被拒绝，因此事后无物可差分或追踪。

**普遍性论题。** 用理论术语陈述，论题是存在一个普遍形式。程序在其中原生写成，每种现有语言作为忠实投影从它可达，每个现有程序通过提升进入它。Gurevich 论题给出根基：每个顺序算法在其自身抽象层级上由抽象状态机逐步捕捉 [2]，并行算法亦然 [3]。形式是数据库状态上的这样一台机器。

**命题 U1（捕捉）。** 若语言 $L$ 中的程序是 Gurevich 意义上的顺序或并行算法，则存在形式，其转移在程序的抽象层级上逐步模拟它 [2, 3]。

**命题 U2（忠实投影）。** 若形式到 $L$ 的投影 $\pi_L$ 在合同内每个输入上保持形式的迹，则形式与其投影对迹的每个观察者可互换，且 $L$ 不添加形式所缺之物。

**命题 U3（构造上提升）。** 使用中的每种编程语言都有形式语法、产生具体语法树的解析器、抽象语法树及其规格或参考实现固定的语义。提升 $\lambda_L$ 按语言分三阶段构建：语法，然后抽象语法树，然后形式，由 $L$ 的语义为 $L$ 的每个构造给出其形式规则。如此构建的提升在行为上满足 $\pi_L(\lambda_L(p)) \equiv p$，在形状哈希上满足 $\lambda_L(\pi_L(F)) = F$，因此该对是 [122] 意义上的透镜，且 $L$ 中的程序作为形式持有而无损失。

**命题 U4（替换）。** 若 U2 与 U3 对语言 $L$ 成立，则无需用 $L$ 写任何程序：它一次写成形式，并在平台要求处作为 $L$ 发出。

U1 是定理。U2 按目标用差分测试检查（[§5.1](#51-differential-testing-across-five-targets)），并在 [§2.3](#23-the-ecosystem-at-large-n) 的大 N 下检查。U3 是构造，按语言从语法向上构建，[§8.7](#87-lift-coverage-across-languages) 说明构造如何随构建被测量。

### 3.7 语言：版本 0.6 与 0.7、成本与定理状态

RCE 语言由书面规格定义，当前为语言版本 0.8 的草案 0.7 文档（[/rce/spec/](/rce/spec/)；源文件在 [rce 仓库](https://github.com/openIE-dev/rce)）。每个模块用首行注释选择其语言版本。没有该注释的模块是版本 0.5，即第 2 至 10 节的语言。声明 `# rce-version: 0.6` 的模块还获得附录 C：`par`、`for ... par`、`with budget`、工作组、LVar、会话与监督者。声明 `# rce-version: 0.7` 的模块具有版本 0.6 的语言，只有一处不同，即下文标准库方法的成本（附录 C.15）。附录 D 定义引擎配置，即本文引擎所运行的处理器规格与契合。版本 0.5 的模块从不看到附录 C，因此每个有效的版本 0.5 程序都被原样接受。

![图示。三张版本卡片。版本 0.5，无声明：第 2 至 10 节的语言，无预算。版本 0.6，首行 # rce-version: 0.6：版本 0.5 加附录 C，其中 23 个词成为关键字，并加入 par、for par、with budget、工作组、LVar、会话与监督者；标准库方法成本为 c_call，即 4。版本 0.7，首行 # rce-version: 0.7：0.6 的语法与规则，只有一处不同，方法成本为 4 加 work(m, n, k)。勘误适用于每个版本。下方是逐调用点规则：预算下的 0.6 模块调用 0.7 模块中一个对 8 个元素排序的函数；该排序被计为 4 加 24，因为它写在 0.7 模块中，所以该调用比对 0.6 函数的同一调用多计 24。](/figures/rce/versions.svg)

*图 5. 版本门槛：首行固定含义。图示：每个模块在首行声明其版本。没有声明的模块是版本 0.5，即第 2 至 10 节的语言，无预算。`# rce-version: 0.6` 加入附录 C（23 个新关键字；`par`、`for ... par`、`with budget`、工作组、LVar、会话、监督者），标准库方法成本为 $c_{call} = 4$。`# rce-version: 0.7` 具有 0.6 的语法与规则，仅方法成本不同，为 $4 + w(m, n, k)$。勘误适用于每个版本。包含调用表达式的模块的版本决定其成本：在 `with budget` 下调用一个导入的、对 8 个元素排序的 0.7 函数的 0.6 函数，比对一个相同的 0.6 函数的同一调用多计 24。来源：规格 2.7、C.6.4 与 C.15；代码清单节选自 `spec/checker/tests/call_site_cost.rs`。提供 [PNG 副本](/figures/rce/versions.png)。*

**预算计数工作。** `with budget` 块按附录 C.6.4 的表为每个操作计固定成本，并在计数耗尽时以 `budget` 陷入。该计数是工作的代理，不是时间或能量的测量；`est_j` 是另一回事。

| 操作 | 成本 |
|---|---|
| 调用用户函数或闭包，$c_{call}$ | 4 |
| 接收者规模为 $n$、首参数规模为 $k$ 的标准库方法 | 版本 0.6 中为 4；版本 0.7 中为 $4 + w(m, n, k)$ |
| 通道发送或接收 | 8 |
| `spawn` | 32 |
| 一个 `par` 分支或 `for ... par` 分块 | 16 |
| 含 $n$ 个结果的列表或映射字面量，或推导式；`[x; n]` | $4 + n$ |
| 索引、切片、成员访问；一元运算符；`and`、`or`；整数、布尔与文本运算符及比较 | 1 |
| 浮点 `+`、`-`、`*` | 2 |
| 浮点 `/`、`%` | 8 |

规模是文本的 UTF-8 字节长度、列表的长度与映射的条目数；其他任何值规模为 0。方法工作量 $w$ 由参考求值器中该方法的复杂度类固定：文本、列表与映射上的线性方法为 $n + k$（映射是有序关联列表），`sort` 为 $n \lceil \log_2 n \rceil$（当 $n \le 1$ 时为 0），其余方法为 0。`map`、`filter` 与 `fold` 对其函数参数的调用另外按调用计费。算术在最大的 128 位整数处饱和，且当 $n$ 或 $k$ 增长时 $w$ 从不减少。参考求值器与发出的 Rust、Python 和 JavaScript 运行时计算同一函数，一项测试检查预算陷入在全部四者中落在同一操作上。

![对数刻度折线图：一次无参数的标准库方法调用的预算成本对接收者规模 n，从 1 到 1,024。在版本 0.6 下，每个方法在每个规模下成本为 4。在版本 0.7 下，文本、列表与映射上的线性方法成本为 4 加 n，在 n = 1,024 时达到 1,028；sort 成本为 4 加 n 乘以 n 的以 2 为底对数的上取整，在 n = 1,024 时达到 10,244。常数类方法在两个版本中成本均为 4。一个标记显示在版本 0.7 中对 8 个元素排序成本为 28，比 0.6 多 24。](/figures/rce/cost-curves.svg)

**哪个版本决定成本。** 一个程序可连接不同版本的模块。方法调用的成本由包含该调用表达式的模块所声明的版本固定，包括写在该模块中的闭包内的调用，而不由被运行函数、其调用者或程序首个模块的版本决定。该规则是词法的，因此链接模块不改变任何成本；规格 2.7 陈述同一规则并指向 C.15。测试在参考求值器以及发出的 Rust、Python 和 JavaScript 程序上，于边界处双向检查它：在 `with budget` 下调用一个导入的、对 8 元素列表排序的 0.7 函数的 0.6 函数，比对一个相同的 0.6 函数的同一调用多计 24。

**定理状态。** 规格陈述定理 T1 至 T34，并准确记录每个的状态。证明以 Lean 4（v4.12.0，无 Mathlib）在一个核心演算上写成。用于结果级别的词如下。*已证明* 指关于语言核心语义的 Lean 证明。*在语义上已证明* 指在 RCE 一个核心的小步语义上的 Lean 证明。*模型* 指关于一个抽象模型的 Lean 证明，该模型未与 RCE 语义或参考求值器相连。*向量* 指参考求值器在生成程序上的结果由 Lean 内核对照模型检查，这是样本上的对应，不是关于求值器的证明。*已测试* 指在陈述输入上的差分测试。*机械检查* 指由程序判定，例如 LALR(1) 表构建器。

## 4. 引擎：档位、门槛与收据

<div id="41-the-engine-is-a-form" class="anchor-alias" aria-hidden="true"></div>

### 4.1 引擎是一个形式

RCE 把软件作为小确定性处理器的图来运行。不能决定的处理器发出升级。解析器回答一次升级，答案被安装为永久处理器，因此同一形状的下一情形无需解析器运行。引擎满足每条形式不变量，每条由 `tests/form_laws.rs` 中的命名测试检查：

| 不变量 | 引擎做什么 |
|---|---|
| 重载是经验证的折叠 | 重载逐字读日志，重算每个哈希与链接，并用 $\delta$ 折叠其余。无物被重新盖戳。断裂的链拒绝加载。 |
| 无名称的滴答顺序 | 处理器按拓扑秩顺序运行，然后按无名称节点键。输出暂存并在所有处理器运行后投递，如 ASM 语义。重命名每个节点在每个入口给出相同的匿名状态哈希。 |
| 无静默丢弃 | 满邮箱把消息保存在有序队列并记录 `Backpressure`。容量为 1 且 10 个任务时，记录 9 条 `Backpressure` 且全部 10 个任务关闭。 |
| 载荷在日志中 | 输入、滴答、外部处理器结果、安装与故障是日志条目。每个条目后的状态哈希与从空引擎折叠匹配，在 1,000 个随机日志上。 |
| 逻辑时钟 | 活性计滴答，不计墙上时间。 |
| 稳定哈希 | 在规范 JSON 上的 SHA-256（安全哈希算法，256 位），每层键排序，用于条目、状态、形状与规则 id。 |

### 4.2 档位

仅当下方档位未通过门槛时才尝试每个档位。该顺序是一条固定级联。

| 档位 | 方法 | 谱系 |
|---|---|---|
| G0 查找 | 按 SHA-256 形状哈希键控的共享处理器库；对代码修复，定位到排序后的函数 | 代码搜索与检索 [21] |
| G1 规则 | 确定性、带看守的修复模板与由模式导出的验证器，每个检查突变敏感性 | PAR、TBar、AVATAR、FixMiner [22, 23, 24, 25]；如 Coccinelle 的代码改造 [26] |

### 4.4 收据

每次晋升、拒绝、推迟与安装都是用 SHA-256 链接的只追加日志中的变更，因此篡改任何过去条目会打断链 [29, 30]。每个处理器的成本由解释器操作计数按 FGIR（flowG 的本地代码后端）的主机成本表计价，并标注 `est_j`。每次工头调用携带其收据。收据写明档位、估计方法（`basis`）、尝试过的候选以及该档位是否解决了升级。其 `est_j` 字段是必需的：它是有限非负数，或 null，且仅当 `basis` 表示 `unpriced` 时才允许 null，例如没有能量数字的模型调用。缺少该字段的收据无法解析。未计价成本从不被读作零，因此对收据的汇总分别报告已计价与未计价的调用，依赖未计价解决的节省被报告为未知。阶梯运行在子样本上加入包能量计数器，标注 `reported_j`。

![图示。上方：三个日志条目，seq 0、1 与 2，每个带字段 seq、event、prev_hash、state_hash 与 hash。第一个 prev_hash 是 64 个零；之后每个 prev_hash 等于前一条目的 hash，以箭头画出。state_hash 是该步之后状态的 SHA-256；hash 是 event、prev_hash、seq 与 state_hash 的规范 JSON 的 SHA-256。下方：一张档位收据，带字段 gear、gear_name、est_j、basis、candidates_tried 与 resolved，旁边是规则：est_j 是必需的，要么是有限非负数，要么是 null，且仅当 basis 表示 unpriced 时允许 null；未计价成本从不被读作零焦耳。](/figures/rce/receipt-chain.svg)

*图 10. 日志是哈希链；每项成本都带依据。图示：持久日志 D 的条目是 `{seq, event, prev_hash, state_hash, hash}`。`state_hash` 是该步之后状态的规范 JSON 的 SHA-256；`hash` 是 `{event, prev_hash, seq, state_hash}` 的规范 JSON 的 SHA-256；第一个 `prev_hash` 是 64 个零，因此改变任何过去条目会改变其后每个哈希。档位收据携带 `gear`、`gear_name`、`est_j`、`basis`、`candidates_tried` 与 `resolved`。`est_j` 是必需的，是有限非负数，或仅当 `basis` 表示未计价时为 null；模型调用收据按同一规则携带以微焦耳计的 `est_uj`。未计价成本从不被读作 0 J。哈希标签是符号性的。来源：规格 6.1 与第 4.4 节。提供 [PNG 副本](/figures/rce/receipt-chain.png)。*

### 4.5 形式编译器

`rce form` 接受规格及其契合，并从同一形式 IR 发出五个目标：

```
.rce spec + fit
  lower ─► normalize ─► egg e-graph, equality saturation (+ admitted proposals)
  ─► extract (cost = est_j) ─► Form IR (typed relations, regions, rules with SHA-256 ids)
     ├─ Rust crate (pure step, typed state, SHA-256 log and fold, tests)
     │  └─ WASM (the same crate on wasm32-wasip1)
     ├─ Python (standard library only)
     ├─ XState v5 machine
     └─ SCXML document, executed by SCION
```

IR 在每个数值边缘固定一种行为：经检查的 64 位整数溢出是错误且永不回绕；整数 `/` 向零截断（$-7/2 = -3$）；`%` 取被除数的符号（$-3 \bmod 2 = -1$）；除以零是错误；浮点是 IEEE 754 binary64，非有限结果是错误；空与缺失不同；时间仅逻辑时钟。每个目标都被生成。无一被手写。

进程、HTTP 或闭包处理器没有项，因此其记录结果编译为按规范输入的 SHA-256 键控的记录预言机。`rce scan DIR --form` 把现有 Rust、Python、TypeScript 与 Go 提升到形式的模式中，每个被提升元素标注为语法提升。

<div id="46-method-the-whole-stack-evaluated-every-interface-assumption-explicit" class="anchor-alias" aria-hidden="true"></div>

### 4.6 方法：整栈被评估，每个接口假设明示

程序是多层栈：词元与语句；处理器；形式，即在 $S = \Sigma_c \times \Sigma_d$（控制区域；数据：时钟、输入计数与带类型关系）上的单步函数 $\delta : S \times E \to S \times O^*$；日志，即 SHA-256 哈希链，其条目记录每个事件、它所产状态的哈希以及前一条目的哈希；变换形式的重写；以及执行它的基底。每层依赖关于其下层的假设。RCE 不把任何层当作固定。它评估整栈，把每个接口假设写成可检查陈述，并在每次运行上检查。

| 边界 | 假设 | 检查 |
|---|---|---|
| 源到处理器 | 输入满足其源合同 | δ 输入事件处的合同检查 |
| 处理器到汇 | 每个 Ok 输出满足输出模式 | 处理器证明（verify::handler_proof），由 Kani 检查的内核求值器保证全定义且确定性 |
| 日志到状态 | 每个条目携带其所产状态的哈希 | 内核折叠，拒绝第一个哈希不匹配的条目（Kani 线束 `fold_rejects_wrong_state`） |
| 重写到形式 | 重写对每个输入保持输出 | 随机化检查，然后用 Z3 的 SMT 证明 |
| 存根到工头 | 不能决定的处理器升级而非猜测 | 存根处理器发出升级；决议仅经晋升路径被晋升 |
| 形式到目标 | 每个发出的目标计算同一 δ | 每个目标携带同一参考迹 |

失败的检查把断裂定位在其发生的边界。修正在该层做出，通过该边界的检查，并被晋升。修正层之上的每一层无需进一步变更即继承修正，因为其上每层仅通过其假设现已检查的接口消费被修正层。这就是修正向上携带并复利的含义。[RCE 引擎演示](/demos/rce-engine/) 在编译为 WebAssembly 的 RCE 核心上于浏览器中运行它：其接口层打破每个假设并显示检出它的检查，其复利层显示修正进入每一后续轮次。

### 5.2 在 Z3 中证明的重写

经验证的重写规则有谱系。Ruler 用相等饱和推断并检查重写规则，环中无模型 [87]。因此第 5.5 节承认的 16 条模型提议规则中的 3 条是关于门槛的陈述（门槛拒绝了 13 条），而不是声称模型是最佳规则来源。

每个内置 e-图重写都在 Z3 SMT 求解器（可满足性模理论）[31] 中对照形式项求值与算术的无量词编码证明：值作为数据类型，带检查溢出的 64 位比特向量，带被除数符号的有符号除法与余数，以及 binary64 浮点。改变溢出、升级顺序或消息的重写得不到证明。提议的等价仅在有证明时进入 e-图。

<div id="53-kani-proofs-of-the-kernel" class="anchor-alias" aria-hidden="true"></div>

### 5.3 内核的 Kani 证明

引擎内核（哈希链、折叠、无名称位置与处理器求值）用 Rust 的 Kani 模型检查器检查 [32]。处理器求值是非递归步进的不动点，Kani 按构造子用结构归纳证明该步进全定义且确定性。十个线束经 Kani 0.67.0 验证，7,425 项检查中 0 项失败：

| 线束 | 性质 |
|---|---|
| `chain_appended_verifies` | 追加的哈希链验证通过 |
| `chain_detects_tampering` | 被改条目打断链 |
| `fold_equals_replay` | 折叠等于重放 |
| `fold_rejects_wrong_state` | 与存储状态不一致的折叠被拒绝 |
| `position_is_name_independent` | 规则位置不依赖节点名 |
| `reason_tokens_are_name_independent` | 原因按整词元无名称 |
| `handler_core_leaves` | 叶处理器全定义且确定性 |
| `handler_core_validate` | 验证全定义且确定性 |
| `handler_core_pipeline` | 流水线全定义且确定性 |
| `handler_core_ifhas` | 看守全定义且确定性 |

### 5.4 证明证书上的晋升门槛

## 6. 提升：从其他语言进入生态系统

<div id="6-importing-legacy-code-from-other-languages" class="anchor-alias" aria-hidden="true"></div>

提升是别处写成的代码进入生态系统的门。它是构造，按语言用每种语言已有的工具做成：形式语法、如 [tree-sitter](https://tree-sitter.github.io/tree-sitter/) 产生语法树的解析器、抽象语法树以及语言服务器工具解析的符号（[Language Server Protocol](https://microsoft.github.io/language-server-protocol/)）。`rce scan DIR --form` 从该树为 Rust、Python、TypeScript 与 Go 构建形式（[§4.5](#45-the-form-compiler)，[§5.6](#56-brownfield-agreement)）。被提升的程序携带其源的缺陷，因此提升包含修复，下文在公开缺陷语料上于给定位置测量。在生态系统内部，这些缺陷无法被写出。

**未决问题：一词元修复率的基线。** L0 各行测量按先验排序的单词元邻域恢复一词元突变体的频率。如果该邻域由产生这些突变体的同一组算子表构建，那么高比率部分反映的是这种重叠，而不是对实际出现的故障的修复能力。本文引用了这一耦合风险，但没有给出其数值。在同一批突变体上运行的朴素算子反转搜索，正是能显示该比率有多少可由此解释的基线。该基线尚未运行，因此此处不给出数字，一词元比率仍面临这一疑虑。

比率可读作意图比特。在 L0，缺失比特几乎全在该行上，按先验排序的单词元邻域以中位 2.3 比特供给它们。在仅块的 L1 行，引擎只看到 7 行块。它关闭比特在块内的类别（Java：改算子 91%，交换布尔字面量 84%，交换参数 82%；Python：改布尔字面量 98.8%，交换参数 99.4%），并留下比特在块外的开放：方法名（22%）与标识符（37%）需要文件及其类型，新合取（3% 到 7%）与整语句重写（Python，占语料 34% 的类别中的 1.2%）是新意图。新意图是供给者（规格、测试、人或本地模型）提供一次之后契合进入索引的东西。

**方法。** 每个语料用固定种子打乱。每次打乱的前 2,000 个位置，以及对 L0 三个整仓库（commons-lang、requests、flask），构成开发划分，档位可在其上调参；开发结果不报告。其余每项任务在测试划分中。测试运行前引擎被提交并记录其二进制哈希，运行中无档位变更。本节每行都是仅在测试任务上、0 次模型调用的冻结引擎结果。预注册（`PREREG.json`）、逐任务行与报告脚本在[公共仓库](https://github.com/openIE-dev/openie-research-experiments/tree/main/rce/bench/ladder/)中。

**门槛。** 在 L0 与 L1，位置给定，门槛是词元同一性：修复后的行或语句必须与开发者的逐词元相等。这比通过测试更严，因为补丁可通过弱测试套件却仍错误。Qi 与同事发现 GenProg 报告为修复的多数补丁是似是而非但不正确的 [92]；对测试的过拟合在基于搜索与基于语义的修复中有记载 [93, 94]，并用生成测试应对 [95]；工具在其调参的基准上得分更高 [96]；故障定位使比较偏倚 [97]。词元同一性消除这些级上的似是而非间隙，给定位置消除定位项，因此比率只测量修复档位。L2 及以上用测试作门槛，并分别报告似是而非与正确计数（第 8.1 节）。

L0 语料是九个真实仓库在钉住提交上每个具有有效替换词元的 PIT 风格突变体 [109]，五个 Java 与四个 Python：547,448 中的 520,821 个测试任务。引擎（提交 `65571d0`，档位 G0-T 与 G1-J）恢复 520,541，比率为 0.9995（95% Wilson 区间 0.9994 到 0.9995），中位搜索比特 2.3。280 个未解中，108 个是浮点字面量内被突变的数字，2 个在 Python 集合字面量内。浮点字面量档位（G0-F，提交 `ecfe5a1`）在四个从未用于调参的仓库上测试（commons-text、commons-io、more-itertools、httpx）：23,015 中的 23,015 个任务，1.0000（0.9998 到 1.0000），中位搜索比特 2.0。突变体是真实一词元故障的替身，Just 与同事发现它们与真实故障耦合 [110]。

### 6.2 L1：来自真实历史的一语句缺陷

L1 使用两个从开源历史挖掘的真实单语句缺陷修复公开数据集。ManySStuBs4J 2.0 [107] 给出 24,072 个 Java 测试任务；引擎（提交 `f2701b7`）解决 9,288，比率 0.386（0.380 到 0.392）。TSSB-3M v1.0.0 [108] 从分片 14 与 15 给出 157,089 个 Python 测试任务；同一引擎解决 27,266，比率 0.174（0.172 到 0.175）。引擎只收到 7 行块，因此该 Java 比率是仅块结果。给定父提交处的整文件，带项目方法与看守条件索引以及改方法名、加参数、看守条件、throws 与修饰符的档位（提交 `62fb7a0`，二进制 sha256 前缀 `3682c6515acdf722`，运行前预注册），引擎在其文件与缺陷语句可定位的 21,320 个 Java 测试任务中解决 13,586，比率 0.637（0.631 到 0.644）。按类别关闭改算子（95.9%）、改操作数（92.1%）、错误调用者（87.9%）、交换布尔字面量（88.4%）、删除参数（85.1%）与交换参数（83.3%）；改方法名达 61.4%，加参数 51.4%，新或收窄条件（43.5% 与 51.7%）仍是主要开放意图。完整分层表在仓库中。这些数据集在本门槛下（仅块、词元同一性、给定位置）无已发表修复排行榜，因此旁侧不设学习修复数字；确有排行榜的 Defects4J 在第 8.1 节与 TBar 比较。

### 6.3 能量

每行携带 `est_j`，即 CPU 秒乘 10 W 的估计：L0 每已解任务 0.40 J，新鲜仓库上 0.13，ManySStuBs4J 上 0.10，TSSB-3M 上 0.27。子样本在 RAPL [105]（处理器片上包计数器）上读取，机器为带 Intel i9-13900H 的 Linux 笔记本（主机名 `jetson-hub`；非 NVIDIA Jetson）。线束在 4 个钉住的 CPU 上运行，`reported_j` 是整次运行（含 Python 驱动）的包增量，减去紧前 10 s 采样的空闲功率再乘运行时长。持续集成运行器在运行，因此空闲为 40 W 到 44 W，不确定性约为 ±1 W 乘时长，这些合计上约 ±10 J。

|---|---|---|---|---|---|---|

| L1，ManySStuBs4J 位置 2,000 到 3,999 | 2,000 | 690 | 377.2 | 17.9 | 0.026 | 8.2 |

每行是引擎的输入。克隆与去重说契合通常存在，这是 G0。反复出现的修复说适配大多是带看守重写的小目录，这是 G1。行级冗余缩小 G2 的搜索空间。生态系统在每个被晋升契合上测量它（第 2.3 节），被提升代码上的修复阶梯在留出划分上大规模测量它（第 6 节）。两点谨慎锐化解读。除非去除，重复会抬高检索与模型分数 [104]。有缺陷的行比修好的更不自然 [45]，因此缺陷本身是查找最难预测的情形；G0 与 G1 必须键控的是修复形状，而非有缺陷的行。大规模做此事的规则挖掘线，从 GenProg 的生成并验证搜索 [88] 与 Prophet 的学得正确性模型 [89]，到 Facebook 的 Getafix [90] 与 Sorald 对静态分析违规的无模型修复 [91]，从不相交历史导出模板并在未见情形上报告精度 [98]。那是第 8.4 节采用的标准。

## 8. 后续事项的测量协议

每个协议在其运行前固定：预注册已提交，种子与求解器提交已记录，每个制品保留。门槛在先，焦耳在后，标注始终。

<div id="81-defects4j" class="anchor-alias" aria-hidden="true"></div>

### 8.1 Defects4J

Defects4J 持有 854 个活动的真实 Java 缺陷，每个带可复现测试 [37]。

1. 在 100 个缺陷子集上离线开发，经 `defects4j checkout`；仅报告留出结果，在运行前冻结的不相交 288 个缺陷集上（`FROZEN-heldout-v1`）。
2. 先运行 G0，然后 G1，然后 G2，本地模型最后。记录关闭每个缺陷的档位。
3. 门槛：触发测试与完整套件通过。分别报告似是而非与正确计数；正确意味着经审阅与开发者补丁等价。
4. 报告每正确修复的模型调用与每正确修复的焦耳，带标注。
5. 参考点：TBar 的 43 个正确修复及其在完美定位下 101 中的 74（数字从 [23] 读取，分母未在此重新核查）。本节是一个协议。本文不报告该引擎的任何 Defects4J 结果。
6. 污染检查：标记每个修复逐字出现在 G0 索引中的缺陷，并报告含与不含被标记缺陷。

<div id="82-swe-bench-lite-offline" class="anchor-alias" aria-hidden="true"></div>

### 8.2 SWE-bench Lite，离线

SWE-bench Lite 是由隐藏测试解决的真实 GitHub 议题的 300 任务子集 [38]。

1. 使用官方 Docker 线束，无网络。
2. 首次运行：仅 G0 与 G1，零次模型调用。这是无模型求解的底板。
3. 第二次运行：加入本地模型作为最后一档。
4. 报告解决率、每已解决任务的模型调用与每已解决任务的焦耳，带标注。
5. 污染检查如 8.1。SWE-Bench+ 发现 32.67% 的成功补丁在议题文本中有解 [39]。

<div id="83-a-wall-meter" class="anchor-alias" aria-hidden="true"></div>

### 8.3 墙上电表

1. 在主机供电上接墙上电表或分流电表，以既定速率记录，时钟与运行日志同步。
2. 空闲机器：CI 运行器与其他构建已停，每个块前检查并记录安静窗口门槛。
3. 减去测得的空闲基线，并陈述方法。
4. 仅从电表填充 `measured_j`。在旁侧分列报告 `reported_j`（RAPL）与 `est_j`。永不跨标注求和。
5. 在电表下重复第 6.3 节的 RAPL 子样本，然后是 Defects4J 留出集。

<div id="84-a-held-out-run-with-the-gears-frozen" class="anchor-alias" aria-hidden="true"></div>

### 8.4 档位冻结的留出运行

这是第 6 节方法向新语料的扩展。

1. 在带标签的提交冻结 G0、G1 与 G2，记录二进制哈希，并公布带撰写时间戳的规则集。
2. 抽取不相交留出切片：Multi-SWE-bench [102] 与 BugsInPy [103] 的 Rust 与 Python 实例，相对 G0 索引去重 [104]。
3. 在首次运行前预注册切片、种子与假设。
4. 分别报告已解决、似是而非与按字节相同计数，每个带 95% 区间。

<div id="85-baselines-in-the-same-table" class="anchor-alias" aria-hidden="true"></div>

### 8.5 同一表中的基线

1. 无模型：`cargo fix` 与 clippy [106]，以及 Sorald 或 TBar 移植 [91]。
2. 便宜模型：带本地模型的 Agentless [99]。
3. 远程模型：带前沿模型的智能体，其能量由提供商披露估计并标注 `est_j`。
4. 对每行以焦耳与美元报告通过成本 [101]，成本控制按 Kapoor 与同事的要求 [100]。

<div id="86-convergence-of-model-calls-at-large-n" class="anchor-alias" aria-hidden="true"></div>

### 8.6 大 N 下模型调用的收敛

晋升是模型离开循环的机制：解析器为新情形付一次，门槛把契合承认为处理器，同一形状的每个后续情形在 G0 或 G1 关闭（[第 4.2 节](#42-the-gears)）。收敛是论断：在固定规格与实况流量下，每轮模型调用降到零。测量如下。

1. 从公共仓库抽取至少 1,000 个规格，按语言与规模分层，并在第一轮前冻结引擎与解析器。
2. 重放已记录的生产流量，每个规格至少 10,000 个事件，按固定大小的轮次。
3. 每轮记录：新升级、模型调用、晋升、推迟与每已关闭任务的焦耳，各带标注（`est_j`、`reported_j`、`measured_j`）。
4. 主终点：在 20 轮内达到某轮零模型调用的规格份额，带 95% Wilson 区间。次终点：按轮的每已关闭任务模型调用，以及最后一次模型调用的轮次。
5. 报告永不收敛的规格及其原因（卡住的输入、缺失依赖、新意图），并把卡住输入的推迟作为预注册臂运行。

**命题 8（逼近底板）。** 随着 G0 与 G1 覆盖增长，每已解任务焦耳逼近应用已知修复并运行测试的黄金底板。阶梯各级与墙上电表下的 Defects4J 留出集检验它。

<div id="87-lift-coverage-across-languages" class="anchor-alias" aria-hidden="true"></div>

### 8.7 跨语言的提升覆盖

<div id="87-coverage-of-real-programs-across-languages" class="anchor-alias" aria-hidden="true"></div>

提升随构建被测量。对语言 $L$，当 $\pi_L(\lambda_L(p))$ 通过程序自身测试并按字节重放其已记录迹，且 $\lambda_L(\pi_L(\lambda_L(p)))$ 与 $\lambda_L(p)$ 有相同形状哈希时，程序计为已提升。样本为至少十种语言、每种至少 10,000 个程序，以固定种子从钉住的公共语料抽取，提升器在每次运行前冻结并记录其二进制哈希，0 次模型调用。每次运行报告已提升份额及 Wilson 95% 区间，每个尚未提升的构造是该语言提升器的工作项，在下次运行前构建并冻结。目标是每种语言中的每个程序。

<div id="11-conclusion" class="anchor-alias" aria-hidden="true"></div>

## 11. 结论

RCE 是原生代码生态系统。程序由意图一次写成形式：状态、事件与纯转移的无损编码，每种目标语言是它的忠实投影。无效状态无法被写出，畸形输入在入口被拒绝，因此生态系统中的程序不会相对其意图漂移，也不需要事后差分或错误追踪。每个通过门槛的契合都被存储并复用，生态系统在正确性单调的门槛下复利。在 10,000 个预注册形式上，用冻结的引擎与 0 次模型调用，每个形式往返到相同字节，每个投影确定性，每个畸形输入与规格在入口被拒绝，Python 投影在 9,999 上重放参考迹。其他语言的代码通过提升进入，那是从每种语言的语法到其语法树再到形式的构造；在被提升代码上，修复档位恢复 520,821 个一词元故障的 99.95% 与 21,320 个单语句 Java 缺陷的 63.7%。第 3.6 节与第 8.7 节陈述普遍性命题及其构造如何被测量。
