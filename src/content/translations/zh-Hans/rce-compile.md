## 摘要

RCE Compile 是一个研究项目，探讨编译的单一定义, , 这里称为编译定律, , 是否对任何编译器都成立，而不依赖于项目所在的 Reality Code Engine（RCE）仓库。候选陈述认为编译是意义保持的在规范表示之间的降阶过程，按成本排序，其下限为兰道尔极限，目标是最短等价程序，过程受验证约束并通过复用复合。本研究将该候选陈述与十二类生产编译器及其背后的研究文献进行检验。该候选作为描述失败：没有受调编译器对无名表示进行哈希，商用编译器的降阶既不完整也未显示保持意义，且没有编译器考虑能量。经重新表述三个条款后，它可以作为规范框架成立，研究以该形式表述：具有两个界限的正规形式，加上相对于它们的测量距离。收敛函数如声明般无法计算或测量，研究用两个可计算并可与测得能量比较的计数代替。随后提出七个带有反例的假设，给出迄今的实验及另外两项的协议。编译器输出在三台机器上逐字节比较；一些差异在工具链路径重映射后仍然存在且未追溯原因，因此关于降阶确定性的假设既未得到支持也未被证伪。擦除和描述长度首次在一台没有能量计数器的机器上对 96 次构建进行统计，随后通过预登记的 Regime-B 扩展读取芯片上 Linux 运行时功率限制（RAPL） `reported_j`（`board_metered = false`，无墙式功率计），在 20 个确定性整数和定点内核以及 14 种编译器和运行时层级（共 280 次构建全部校验 checksum）中进行：从 Python 降阶到 `clang -O3` 在中位数 2,490 次运行后恢复其编译能耗，`-O0` 降到 `-O3` 在中位数 53,464 到 102,720 次运行后回收能量，`-O2` 降到 `-O3` 在 20 个内核中的 4 至 6 个上从未恢复额外编译能量，且时间乘以功率解释的 Regime-B 方差远高于静态中间表示大小（调整后 $R^2$ 为 0.9999 对比 0.1154）。无名哈希, , 所有受调编译器均未实现的标准部分, , 首先在二进制对象和 WebAssembly 模块（16 个内核和 4 个程序）上构建，然后扩展到 185 个 RCE 表单、60 个 C、Rust 与 Python 内核以及 500 个经测试向量验证的语义变体：位置 De Bruijn 哈希在 500 次中产生 0 次（0.00%）误报碰撞，同时在重命名命中上将冷启动 `clang -O3` 和 `rustc -O3` 编译 `reported_j` 分别缩短 167.8 倍和 448.5 倍，而朴素的标识符剥离在 150 次变量绑定交换中全部碰撞（100.0%）。几乎所有外部来源仅被视为搜索结果，并在每条引用中注明。

**用平实语言表述**

1. 问题在于是否所有编译器都遵循同一条规则。真实的编译器并不遵循，因此我们将该规则重新表述为一项标准，使任何编译器都可以据此进行度量。
2. 该标准包含七个部分。大多数编译器具备其中的一部分，但没有一个编译器追踪能耗，也没有一个编译器能证明它对每个程序的翻译都是正确的。
3. 重度编译优化预先消耗芯片能量，以换取每次运行时更少的芯片能量消耗。在20个测试内核上，基于Linux芯片计数器（`reported_j`，而非墙面电表）进行测量，相较于直接运行Python，编译为`clang -O3`大约在2,500次运行后收回成本；而从`-O2`升级到`-O3`，在多达30%的内核上从未收回成本。
4. 对程序进行指纹化时，若将变量名替换为其绑定位置，而不仅仅是抹去变量名，则能够识别245个程序中的重命名副本；在热缓存命中时，可避免168×至449×的重建芯片焦耳能耗；并且在500个注入缺陷的变异体上没有产生任何误匹配，而简单抹去变量名的方法则在每一对被交换的变量上都发生了冲突。

## 1. 问题陈述

编译器将一种语言的程序转换为另一种语言的程序，通常是更接近机器的语言。世界上有数千种编译器，由不同社区构建，这些社区很少共享词汇：系统语言、科学计算、遗留业务语言、高完整性语言、函数式语言以及神经网络张量程序的编译器。每个社区对正确且良好的编译器都有自己的描述。RCE Compile 探究是否存在一条独立于 RCE 的陈述能够涵盖所有这些描述，如果不存在，那么最接近且能够涵盖的陈述是什么。

接受检验的候选陈述来自先前与一个助手系统（Grok）的讨论。它指出：**compilation is semantics-preserving lowering between canonical representations, ranked by a cost whose floor is Landauer's limit and whose target is Kolmogorov-minimal, gated by verification, and compounded by reuse.** 接下来有三个问题。它是否描述了现有编译器的实际情况？如果不能，是否可以重新表述，使其对正确编译器为真且可针对真实编译器进行检验？其物理和数学术语是否能够被测量？提出该候选陈述的讨论还对该领域做出了 55 项事实性断言；这些断言已在[附录 A](#appendix-a-claims-checked) 中得到检验。

## 2. 候选编译定律及其精化

<div id="21-why-the-candidate-fails-as-a-description" class="anchor-alias" aria-hidden="true"></div>

### 2.1 候选者为何无法作为描述

候选者提出了三类主张：关于表示（“规范的”）、关于降低（“语义保持的”）以及关于成本（“下界为兰道尔，上界为柯尔莫哥洛夫最小”）。每一类都无法描述实际交付的编译器，理由详见§3和§4：

- **所调查的每一种编译器均未散列无名中间表示。** 每一种都将其身份标识和缓存建立在具名或文本内容之上。
- **降低既不完备，也未被证明能保持含义。** 模糊测试已在生产级C编译器中发现超过325个错误（Csmith）和1602个错误（EMI项目）[1] [2]，而Zig的默认自托管后端在其2008个行为测试中失败了24个[3]。
- **没有编译器考虑能量。** 发现的所有成本模型均以周期、字节或节点数为单位。
- **所述收敛函数无法按给定方式计算或测量。** 柯尔莫哥洛夫复杂度不可计算；即使是单个固定电路的最小热量，计算也是PP难的[4]；而当今硬件位于兰道尔下界以上$10^6$至$10^{11}$倍。

一个声称每种编译器都遵守、而真实编译器可测量地违反的陈述，作为描述性定律已被证伪。在英文、中文、俄文或日文中均未找到任何同行评议来源命名或证明单一编译定律[NOT FOUND]；对该短语的英文搜索仅返回“compilation”的版权含义[5]。

<div id="22-the-refinement-a-normal-form-with-two-bounds-and-a-measured-distance" class="anchor-alias" aria-hidden="true"></div>

### 2.2 精化：具有两个界和一个测量距离的范式

该候选形式作为规范框架表现得更好：它陈述了一个正确且良好排序的编译器必须满足的条件，任何真实编译器均可置于其下并测量其不足。有三处条款发生变化。“语义保持”成为**声明式契约**，因为既定概念是在前置条件下进行精化，而前置条件因编译器而异。“典范”成为框架对任何表示形式施加的**操作**，因为没有编译器提供它。而“Landauer 底界和 Kolmogorov 目标”则成为**两个可计算计数加一个测量**。结果是一种 Hoare、He 和 Sampaio 意义下的范式（§6），它带有两个界以及到这两个界的测量距离，而非每种编译器均已服从的定律。

<div id="23-the-normative-statement" class="anchor-alias" aria-hidden="true"></div>

### 2.3 规范性陈述

该项目章程对标准的表述如下，文本原样引自其中 [6]：

> **编译器形式。** 编译器是从已声明输入（源代码、标志、工具链，以及重映射之后的任何构建路径）到表示链 R₀ → … → Rₙ 的部分函数。每一步要么停止，要么产生一个输出，由指定的检查器 K 接受，认定其保持某一已声明契约：包括属性类、等价性层级、链接假设以及可信计算基。在被接受的输出之中，给定的成本 C 对候选进行排序。复用 U 以表示及其契约的无名称哈希为键。除非 G 记录了 K 的接受，否则任何结果都不予发布。对于每一个发布的输出，框架报告其与两个界的距离：每次运行中不可逆覆写的比特数（以 k<sub>B</sub>·T·ln 2 标度），以及给定的描述长度代理量；同时给出在该硬件所属机制下测得的能量。

*停止*是一个以诊断信息结束、不产生输出的降级步骤。*已声明输入*是编译器契约所列出的输入。该陈述放弃了“对任意编译器成立”的说法，改用“每个编译器都可以置于其之下进行检验”。本项目仅对其已注册假设（§7）所能经受住的部分主张定律。§3 阐述该陈述所指明的各个组成部分，§4 阐述两个界。

## 3. 编译器形式, R 到 G

<div id="31-the-seven-parts" class="anchor-alias" aria-hidden="true"></div>

### 3.1 七个组成部分

该项目将该框架称为**Compiler Form**。它包含七个部分：

| 部分 | 名称 | 该部分的要求 |
|---|---|---|
| R | Representation | 具有声明等价关系和无名哈希的规范 IR |
| L | Lowering | 每个步骤要么停止（以诊断结束且无输出），要么产生一个保留已声明契约的输出 |
| C | Cost | 声明的成本，用于对等价候选进行排序 |
| K | Checker | 命名检查器，用于认证该契约 |
| U | Reuse | 复用先前接受的结果，以无名哈希和契约作为键 |
| E | Energy | 对每个发布的输出通过计数或计量器进行能量核算 |
| G | Gate | 除非门记录了检查器的接受，否则不发布任何内容 |

来自正确性与 ML 编译器文献的两个细化，使得 L、K 和 G 足够精确以进行检验。

<div id="32-four-equivalence-levels" class="anchor-alias" aria-hidden="true"></div>

### 3.2 四个等价性级别

机器学习编译器将正确性定义为"接近"。XLA、TorchInductor、TVM、TensorRT、Triton 和 IREE 都以绝对容差和相对容差对照参考实现进行测试（PyTorch 对 float32 的默认设置为相对容差 $1.3\times10^{-6}$、绝对容差 $10^{-5}$）[K]。这是因为算子融合、分块、分裂归约以及张量核心累加都会重排浮点求和的顺序，而降低到 FP8 或 FP4 则会有意改变输出 [K]。据报告，启用块稀疏时，FlexAttention 的 FlashAttention-4 反向传播是不确定的 [7]。若"保持"意味着输出比特完全相同，上述编译器都将违反 L。2026 年 9 月的一篇预印本指出，比特级结果取决于编译器所选的累加结构；该文重建了三代 GPU 上 cuBLAS 的累加结构，并给出静态检查器，可在数万种自动调优配置中判定比特等价 [8]。MMA-Sim 则给出了十种架构上张量核心与矩阵核心的比特精确模型 [9]。Halide 已在小规模上体现了这一模式：调度只能通过具名的可重结合归约来改变结果 [K]。

因此，本形式体系要求每一次降低（lowering）都声明四个**等价性级别**之一，并要求其检查器对该级别进行认证：

| 级别 | 含义 | K 必须认证的内容 |
|---|---|---|
| 精确 | 整数、布尔或定点数；输出比特完全相同 | 比特相等 |
| 累加类内比特相等 | 浮点数，归约顺序记录于 R 中；L 与 C 仅在该类内做选择 | 先认证属于同一类，再认证比特相等 |
| 声明误差界内 | 浮点数，给定绝对、相对或 ULP 误差界 | 误差界须由静态误差分析或区间方法证明，而非样本测试 |
| 声明有损 | 量化或精度降低 | 不对相等性作任何认证：这是程序的变更，须予记录，并由 G 作为独立决策予以许可 |

默认规则为"除非有经检验的契约另有规定，否则取精确级别"。这比所有生产级机器学习编译器都更为严格，也与上述累加类的比特级研究相一致。

<div id="33-what-a-gate-must-name" class="anchor-alias" aria-hidden="true"></div>

### 3.3 门必须命名的内容

经典的正确性定理并非“输出等价于输入”。CompCert 的主要定理是 **behaviour refinement under a precondition**：若编译成功且源代码不存在未定义行为，则编译后代码的每一个可观察行为都是源代码的行为 [K]。Patterson 和 Ahmed 证明，除非定理明确指出输出可以与哪类目标代码链接，否则“编译器是正确的”是模糊的 [10]。安全编译进一步指出，编译器可以在 CompCert 意义上保持意义，同时允许目标层的攻击者破坏源代码的抽象：*full abstraction*（源等价组件编译后成为目标等价组件）和 *robust property preservation* 标准是不同的、更强的保证 [11]。此外，CompCert 的证明并未覆盖预处理器、汇编器和链接器；Csmith 正是在这些阶段发现了静默误编译，而在已验证的中端没有发现 [1]。

基于以上，形式化文档中的每个 gate 必须声明三项内容：

1. **The property class it preserves**：跟踪属性、超属性、鲁棒变体或等价性。
2. **The linking assumption**：输出可与何种其他代码进行链接。
3. **The trusted base**：保证所依赖的语义、证明内核、汇编器、硬件模型或多样化编译器。

全抽象编译通常需要运行时检查或隔离，因此更强的属性类会增加成本 [K]。

2026 年 11 月 2 日，在任何 gate 被度量之前，项目章程在上述三项之外新增了两条声明 [6]：

4. **The authority of its evidence**：检查器接受背后证据必须达到的层级。
5. **The digests its verdict is bound to**：声明输入、发布的输出以及接受检查的检查器的 `SHA-256`（*digest*），以及所检查合约的版本。绑定到特定 digest 的裁决仅适用于其生成时的确切字节。

该宪章从 REA（Reverse Engineer Anything，一个开源逆向工程项目）[6] 的重构账本中获取权限级别。两个级别是*观察到的*证据：*固定*，其中以工具链 SHA-256 命名的编译器在声明的输入上运行，其输出逐字节比较；以及*重放*，其中先前记录并以其 SHA-256 绑定的输出逐字节比较。*证明的*证据是检查器对其片段每个输入的证书：证明内核的证明、翻译验证器的裁决，或 SMT 求解器发现否定合约无法被满足。*派生的*证据遵循引用其来源的陈述规则，例如引用其段落的已文档化门行为。*推断的*证据是模型的陈述、启发式或随机提议者，或不引用更高层级记录的摘要。门仅在其声明的权限证据成立且绑定到其声明的每个摘要时才接受输出；绑定到其他字节的裁决，或无法读取的证据，不释放任何内容。推断的证据从不使门接受。观察到的证据表明合约在运行的输入上成立或失败；只有证明的证据才能为其片段的每个输入认证它。不声明全部五个的门被记录为具有未声明保证的门。

### 3.5 逐部分发现

**R在各处均不存在，正如范式所述。** 每个生产级编译器均通过一系列IR链进行降低，而非单一规范形式。Zig采用AST → ZIR → AIR → 各后端MIR [3]；rustc采用AST → HIR → THIR → MIR → LLVM IR、Cranelift的CLIF或GCC的GIMPLE之一 [12]；Go采用语法 → IR → SSA → Plan 9风格指令 [13]；GHC采用Core → STG → Cmm [K]。规范*形式*确实存在（GHC Core、LFortran的ASR、Futhark的SOACS、Lean的LCNF、Flang的FIR和HLFIR），而e-graph的e类则是等价项的规范*集合*。最接近“规范表示”条款的结果是Bryant的论文，它将编译视为到范式的规范化 [14]。以下有两个限定条件。Morris的正确性方阵仅需各方*某种*语义，而非规范性 [K]。而且往返仅在IR与其自身序列化形式之间成立（LLVM的文本和位码、CLIF文本、MLIR的泛型形式），绝不返回源代码，因为每个编译器都会丢弃注释、名称和语法糖 [K]。证伪者显而易见：GHC的接口指纹、OCaml的接口摘要、rustc的稳定哈希、Go的动作ID、Julia的源码哈希、Lean的Lake踪迹以及Taichi的内核哈希，均为具名或文本内容的哈希 [K]。Wasm二进制最接近，因为名称位于可选的自定义段中 [K]。因此R必须转变为框架应用于任意IR的操作（将绑定名称重命名为位置、剥离路径，然后哈希），而非编译器据称具备的性质。该项目的实验E5以两种形式实现了该操作，并在一个小型语料库上进行了度量（§8.3）。

**L作为描述失败；缺陷计数即为证据。** Csmith在C编译器中发现了超过325个此前未知的缺陷 [1]。EMI在其最初11个月内发现了147个已确认缺陷，并在GCC和LLVM中总共发现了1602个缺陷，其中1007个已修复 [2]。Alive2作为LLVM的有界翻译验证器，发现了47个新缺陷（28个已修复），并促使对LLVM语言参考手册进行了8次补丁；后续对LLVM内存模型的编码又发现了21个 [15]。Zig的自托管x86-64后端（自0.15起成为Debug构建的默认后端）在2008个行为测试中通过了1984个（该项目开发日志给出的是1987对1980，相对于LLVM；两个来源不一致）[3]，因此降低在出货编译器中并非全函数。CompCert和CakeML表明L可作为定理成立：CakeML将其保证下推至五种指令集的机器码，并已在HOL4逻辑内部完成了自我编译 [16]。两者均非所调研语言的生产级编译器。L仅作为规范存活：要么某步产生其检查器可接受的输出，要么停止，而生产级编译器则以其差距有多大来衡量。

**C 存在但局部化。** 每个编译器都有代价模型，但几乎都是局部启发式：内联预算、LLVM 的目标代价查询与调度模型、GCC 的代价钩子 [K]。Cranelift 的无环 e-graph 是我们找到的唯一一个生产级案例，它对显式等价类中的成员进行排序并抽取代价最低者，并且有意地只在预算范围内饱和一次 [17]。研究型等式饱和的收益并不均衡：TENSAT 报告最高提升 16% [18]，而 XLA 内的等式饱和平均提升 3.45%，在某一模型上峰值达 56.26% [19]。我们只找到一项关于某个 pass 的*性能*保证的机械化结果，针对的是 Rocq 中的一个内联启发式 [20]。所有找到的代价均以周期、延迟、字节或节点数计量，没有一个以焦耳计量；而且，当循环展开、向量化或查表使代码变长却变快时，最短的程序并不等于最省的程序 [K]。

**K 是最强的部分，但它主要守护源码，而非降低（lowering）过程。** 类型系统、Rust 的借用检查器与新的 trait 求解器 [21]、GHC 的 Core Lint、LFortran 的 ASR 验证器、MLIR 操作验证器、Futhark 的带类型 IR、Lean 的内核，以及 SPARK 的 GNATprove 证明等级 [22] 和 Erlang 的代码验证器 [K]，都是真实存在的检查器。有三点限定尤为重要。其一，对降低过程本身的检查只以零散形式存在：Alive2 针对部分 LLVM 窥孔优化，SMT 验证针对部分 Cranelift ISLE 规则，此外还有机械化的 Wasm 规范 [K]。其二，许多 IR 检查器仅用于调试：Core Lint 需要显式开启，而 LLVM 验证器在 pass 之间的运行在发布构建中通常是关闭的 [K]。其三，有界检查器可能漏掉缺陷：Alive2 将循环展开至某个界限 [15]，而 EMI 与 Csmith 能发现缺陷，却无法证明缺陷不存在。机器学习编译器的检查属于对样例输入的容差测试，这些是测试，而非证书。

**U 是最常见存在的部分，但其键值基于名称与路径的哈希。** Go 的构建缓存将动作 ID（即某一步骤全部输入的哈希）映射到输出 [23]；rustc 使用增量指纹；LLVM 的 ThinLTO 缓存、Wasmtime 的模块缓存、JAX 的编译缓存、Triton 的内核缓存以及 TVM 的调优数据库，均以哈希为键 [K]。复用已验证的工作会累积信任：CakeML 在逻辑内部编译了它自己已验证的二进制文件 [16]；“Compiling by Proving”将证明转化为经过优化的重写规则 [24]；DDC 在既定假设下抵御了“信任之忧”攻击 [25]。仍有两点限定。其一，这些键对名称和路径取哈希，因此内容相同但名称不同的程序会错失缓存。其二，TensorRT-LLM 放弃了其已序列化、仅验证一次的引擎，转而将 PyTorch 作为唯一后端 [26]：当硬件与模型的变化快于制品能够重建的速度时，存储的制品便输给了更灵活的 eager 路径。

**E 在任何地方都不存在。** 在十二个家族的所有编译器中，没有一个考虑能量 [K; NOT FOUND for any counterexample]。能量在编译器之外测量：通过机器（2026 年 6 月 Green500 第一名的每瓦 73.28 GFlops [27]）以及 RAPL、NVML 等计数器 [K]。关于能量感知编译的研究规模有限：编译器标志的选择可以把能量改变数十个百分点，且能量与运行时间“大致相关，虽不总是如此” [28]；2025 年的 Fortran 研究发现 gfortran、ifx、ifort 三者在能量上“差异极小”，并随运行时间追踪 [29]。唯一被发现将能量视为一等公民的编译器是研究语言 Eel，它将可逆操作视为免费，仅对比特的创建与销毁计费 [30]。要么 E 不是编译定律的必要组成部分，要么整个领域未能满足该定律。本研究持第二种解读：E 是框架加入的部分，由外部测量仪提供。

**G 仅在部分编译器中出现。** rustc 在类型或借用错误后不生成代码；Go 拒绝未使用的 imports 和变量；Wasm 引擎在加载时拒绝无效模块；Erlang 的验证器在写入之前检查生成的代码 [K]。SPARK 只有在项目的 CI 要求 GNATprove 且没有未证明的检查时才充当门槛；编译器本身并不拒绝 [K]。在其他情况下 G 关闭或部分开启。tsc 除非设置了 `noEmitOnError`，否则即使有类型错误也会输出 JavaScript；LLVM 和 GCC 在提交后测试和回滚时从主干发布，而不是在合并前作为门槛；Zig 懒惰分析，因此从未被引用的代码从不检查 [K]。ML 编译器采用回退而非门槛：TorchDynamo 中的图断裂除非 `fullgraph=True` 将其转为错误，否则会回退到即时 Python；ONNX Runtime 将不支持的节点发送给其 CPU provider [K]。

## 4. 收敛函数

<div id="41-landauer-and-kolmogorov-as-conceptual-bounds" class="anchor-alias" aria-hidden="true"></div>

### 4.1 Landauer 极限与 Kolmogorov 复杂度作为概念性界

候选者的收敛函数认为，已编译程序的代价存在一个由 Landauer 极限给出的下界，以及一个以 Kolmogorov 最小尺寸为目标的上限。**Landauer 极限**是擦除一个比特时，向温度为 $T$ 的环境释放的最小热量 $k_B T \ln 2$：在 300 K 下约为 2.871 zJ（在 298.15 K 下为 2.853 zJ）[K, 算术]。它限定的是每擦除一个比特所释放的热量，而非每次操作的热量，并且只有在无限缓慢的极限下才能达到；加速擦除会付出更高代价，对于擦除时间 $\tau$，大致与 $1/\tau$ 成正比 [K]。单比特实验在该极限下证实了这一界限，分别是胶体微珠实验（Bérut 等，2012）与纳米磁性存储实验（Hong 等，2016）[31]。**Kolmogorov 复杂度** $K(x)$ 是能够输出 $x$ 的最短程序的长度。两者都是真实的物理学或数学结论，作为界限，它们表达的都是真命题：没有任何已编译程序能耗散少于其擦除所需的热量，也没有任何已编译程序能比等价的最短程序更短。

<div id="42-why-neither-is-computable-or-measurable-as-stated" class="anchor-alias" aria-hidden="true"></div>

### 4.2 为什么如所述，两者既不可计算也不可度量

**Kolmogorov 目标不可计算。** $K(x)$ 是不可计算的（Kolmogorov、Chaitin、Solomonoff）；压缩器仅能给出上界，而程序等价性（目标所处的约束）一般而言根据 Rice 定理是不可判定的 [K]。编译器编写者的充分就业定律使这一点具体化：没有编译器能总是生成最小的等价程序，因为那将判定停机 [K]。超优化器在 SMT 或测试向量检查下逼近短的无循环片段的目标，但从不提供保证。

**Landauer 底限同样不可计算，且远低于当今的成本。** 根据一篇 2026 年论文的摘要，对于一个固定电路计算最优热函数是 PP 完全的，乘性近似是 NP 难的，而只有加性近似存在多项式时间的随机化算法 [4]；正文据称论证了 PP 困难性，因此 PP 中的成员资格仍有待检验。在等价电路之间进行选择，即编译问题，则叠加于其上。在通常引用的 45 nm 数据下，32 位整数加法约耗费 0.1 皮焦耳，**约为 $3.5\times10^{7}$ 倍** $k_B T \ln 2$，或若 32 位被覆写则每个擦除位约 $10^6$；一次 640 皮焦耳的 DRAM 读取是底限的 **约 $2.2\times10^{11}$ 倍**；而一条乱序指令的开销约 70 皮焦耳，是 **约 $2.5\times10^{10}$** [32]。当今的差距因此为 $10^6$ 至 $10^{11}$，其中几乎全部来自连线、存储和控制，而非逻辑擦除。

**两项重叠。** Bennett 证明任何计算均可做成逻辑可逆，因此 Landauer 底限仅适用于程序有意丢弃的信息 [K]。Zurek 以及 Bennett 及其同事证明，擦除字符串 $x$ 的最小热力学代价约为 $k_B T \ln 2 \cdot K(x)$，而将 $x$ 转换为 $y$ 的代价约为它们的信息距离 [K]。擦除的 Landauer 代价已是一个 Kolmogorov 量，因此联合最小化两者是在对同一事物计数两次。另外三个问题依然存在。短小性与低能耗存在权衡，因此没有给定权重的联合目标是一个 Pareto 前沿而非函数。时间在表述中缺失。而用于编译的能量可能超过节省：在 2026 年 10 月的一项研究中，模型自精炼的 44 个配置中有 42 个比参考解多消耗 4% 至 886% 的执行能量，仅有两个例外在大约 $10^6$ 至 $10^7$ 次执行后才达到收支平衡 [33]。

一项结果从核心上支持这一想法。Wolpert 和 Kolchinsky 的“电路 Landauer 损失”表明，计算同一函数的两个电路可具有不同的最小耗散 [34]，而失配代价结果给出了电路的严格正下界 [35]。电路结构（即编译器所选择的）确实会改变物理底限。

### 4.3 可度量的替代方案

该替代方案保留两个术语，并使二者都可计算：

1. **ε，擦除计数**：运行过程中被不可逆覆写的比特数，由 IR 计算得出（即被覆写或丢弃且未被复制输出的比特）。$\varepsilon \cdot k_B T \ln 2$ 即该次运行的 Landauer 界。
2. **λ，声明的描述长度代理量**：IR 节点数、二进制字节数、压缩字节数，或相对于某个指定模型类的 MDL 码长。代理量须在测量之前声明，测量之后不得更改。

两者均在可判定片段上经过等价性检验后计算，并与**实测焦耳数**并列报告，报告时按硬件所属的能量区间进行划分：

| 区间 | 能量正比于 | 典型硬件 |
|---|---|---|
| A | 计数操作数 | 顺序执行核心、FPGA |
| B | 时间乘以功率 | 乱序 CPU、GPU |
| C | 熵产生 | 热力学硬件，或对其的模拟；唯一可直接应用 Landauer 单位的区间 |

区间 A 与区间 B 仅为近似：即便是顺序执行核心，静态功耗也随时间缩放 [K]。由此，该主张获得了可检验性：降低 ε 与 λ 能否预测各区间内实测能耗的降低？目前未检索到任何将真实编译程序的擦除内容与其能耗进行对照的已发表测量 [NOT FOUND]，因此无论结果如何，该结果都将构成新的证据。那些声称以 $O(1/\sqrt{N})$ 速率收敛至 Landauer 极限的未经同行评审的自出版预印本，其速率描述的是估计工作量的统计量，而非程序趋近某一下限的速率 [36]；本文不将其引作支持性证据。

## 5. 齿轮阶梯与 98/2 拆分

RCE Compile 将其自身的编译步骤组织为 **齿轮阶梯**，共六个层级，G0 到 G5，按成本顺序尝试。G0 通过哈希复用已存储的结果；G1 应用事先证明正确的重写规则；G2 从 e-graph 中提取最便宜的形式。这三者是确定性的。G3 至 G5 是随机提议者，它们产生的每个输出必须通过门控才可发布；章程仅将 G3 至 G5 视为一个整体，且它们的独立定义仍未确定 [6]。（层级写作 G0 到 G5；Form 的门称为 G。）该阶梯所附的设计原则是一个拆分：至少 98% 的工作为确定性，至多 2% 为随机，并且全部经过门控。

没有任何来源对任何编译器的决策数量、CPU 时间、成本或能耗进行过此类拆分的测量 [NOT FOUND]。已验证的系统则分别位于两端。Equality saturation、Souper、Cranelift 和 MLGO 在编译时完全确定性；MLGO 的策略是固定的并编译进 LLVM，它决定一类选择（内联与否、淘汰哪个寄存器），收益在 0.3% 到 7% 之间 [37]。在另一端，一位随机作者在确定性门后几乎编写所有内容：2026 年 10 月的报告中，一个模型编写约 1.8 亿行 Rocq 证明，Rocq 检查器全部接受或拒绝 [38]；AdaCore 的 GNAT Foundry：Intersection demonstrator 让代理编写 SPARK，而确定性工具生成全部发布证据 [39]。通过作者努力，这一拆分被反转，而门控是完整的，因此任何关于 98/2 的声明必须首先说明计量对象。某分类法将混合工作流的确定性比例放在 14% 到 56% 之间，但这只是分类，而非测量 [40]。

文献确实支持拆分之下的两条原则。**全部门控**：SuperCoder 的最佳配置仍有 5% 的测试检查输出失败，该论文中最强的商业基线仅通过 51.5% [41]；STOKE 将随机搜索与 SMT 验证器配对 [K]。**首先确定性复用**：Compiled AI 将所有随机工作移入一次性编译阶段，在约 17 次运行后即可收支平衡 [42]；Progressive Crystallization 将重复的代理运行提升为确定性工作流 [43]。有一点需要注意：在 Veritas 和 CktFormalizer 中，门控将随机输出与其自身规范（CNF 条款、硬件类型）对比，而规范中的错误则位于门控之外 [44] [45]。

因此，98/2 拆分是一个已登记的假设，列于 §7，而非已测量的结果。它应逐层测量，使用声明的单位并由门控记录。候选单位包括被接受的决策、被接受的重写、CPU 秒和焦耳；每项单独报告，因为它们可能不一致。

## 6. 现有技术

未发现更早的文献为编译定律（§2.1）命名单一法则。最接近的早期主张各自涵盖了七个部分中的少数几个。

- **Morris (1973)**，继Burstall和Landin (1969)之后，并经ADJ小组（Thatcher、Wagner和Wright，1979至1981年）完善，将编译器正确性表述为代数同态构成的交换方形：先编译再解释等于先解释再编码[46] [47]。即L和K。本范式中表述的降低重述了该内容，并未在此处宣称新颖性。
- **Futamura (1971)**指出，对解释器针对程序进行特化可得到已编译程序，对特化器针对解释器进行特化可得到编译器，对其自身进行特化则可得到编译器生成器[48]。**Ershov**的诺沃西比尔斯克学派以“混合计算”[49]的观点得出了相同结论。即L和U，这是最强的早期主张，认为编译器是推导而非设计的。
- **Hoare、He和Sampaio (Acta Informatica, 1993)**将编译视为通过编程的代数定律将源程序归约为一种范式，该范式反映目标机器，正确性由定律得出；该工作为Hoare和He的《编程统一理论》(1998)[50]提供了基础。这是将编译称为“由定律支配”的最接近的先前工作，也是与本研究采用的范式框架最接近的工作。
- **Cousot和Cousot (POPL 1977)**将静态分析统一为格上的不动点，并随后将其扩展到程序变换[51]。即K，以及C中的精度序。
- **Eel (Tyagi、Lynch和Demaine，MIT，2016)**是发现的唯一一种将代码与能量下限绑定的编译器，它通过对位的创建和销毁收费[30]。即E。

UNCOL (1958)曾尝试给出一种通用的R但未能成功；MLIR通过多层级回应了该失败，但不持有语义[52]。E-图已在单一结构中结合了规范集合、按代价排序的提取和可靠重写[53]。

**两个主要来源尚未全文阅读：Hoare、He和Sampaio (1993) [50]以及Ershov的《论编译的本质》(1977) [54]。**两者均依据记忆引用[K]。任一来源都可能包含对该框架或措辞的先例，且在RCE Compile对任何内容宣称优先权之前，两者都必须阅读。根据现有证据，剩余的新颖部分在于其组合：一个将物理下限和信息论目标绑定到经过验证的、可复用复合的降低的单一陈述，其中能量作为排序量。

## 8. 实验

### 8.1 E1: 降低的确定性，已测量

**方法.** E1 测试 H1 [6]。每个 *configuration* 指的是使用单个标志设置的单个编译器，并指定一个或两个小程序。对于每个程序，测试框架会进行四对构建，每个构建在仅包含复制源代码的全新目录中：同一目录两次；两个具有不同长度的绝对路径的目录；对同一两个目录使用工具链文档中规定的路径重映射；以及在未设置 `SOURCE_DATE_EPOCH` 的情况下，同一目录两次，间隔至少 1.1 秒。除最后一对外的所有构建均在声明的环境下运行（`LC_ALL=C`、`TZ=UTC`、`SOURCE_DATE_EPOCH=1735689600`），每次构建均使用全新的空编译器缓存，因此每对中的第二次构建是真正的重新编译。对于每一对，测试框架记录每个输出文件的字节位置差异计数，并且对于 ELF 文件，还记录这些字节在各个段中的分布数量。计数基于位置，因此路径长度的变化导致文件其余部分整体移动时，所有移动的字节都会被计入。路径重映射使用 `-ffile-prefix-map`（针对 gcc、g++、clang、clang++、gfortran 和 gnatmake）、`--remap-path-prefix`（针对 rustc）、`-trimpath`（针对 Go）、`+deterministic`（针对 erlc）以及 `BUILD_PATH_PREFIX_MAP`（针对 ocamlopt）；Go 1.21 被其开发者描述为 “the first Go toolchain with perfectly reproducible builds” [55]。在矩阵中 Julia 没有使用重映射：其重映射运行会在不包含源代码行的情况下写入代码。未发现 Lean、`wasmtime compile`、Zig、GHC 或 GnuCOBOL 的重映射，因此未对它们的重映射比较进行测试。`go build` 被测量了三次：模块模式（Go 的默认模式）；GOPATH 模式下在命令行指定源文件名；以及在 GOPATH 模式下将源文件放置于 `GOPATH` 中并通过其导入路径 `e1` 构建。对于每个 Go 配置，测试框架会在每个目录中再次使用 `GODEBUG=gocachehash=1` 进行重映射构建，该设置会使 `go build` 打印出它在每个操作 ID 中哈希的所有输入，并记录标识构建目录的行。测试框架还会记录每个输出的 SHA-256，以便在两台机器上运行时能够比较, , 前提是工具的版本字符串在两台机器上相同。结果由测试框架写入，随后通过脚本生成报告；其中没有任何图形是手工绘制的。

**发现。**

1. **同一目录。** 在本地机器上，无论时钟固定还是自由运行，同一目录中的两次构建之间没有任何配置存在差异。在 CI 运行器上，时钟固定时有三种配置存在差异：默认模式下的 `zig build-exe`（差异主要位于调试信息段）（`zig build-exe -O ReleaseSmall` 则完全相同）；`cobc -x`，差异为 28 字节（其中 20 字节位于 `.note.gnu.build-id`）；以及 Julia 运行，差异为一个 LLVM IR 文件中的 168 字节。对于这三种配置，其输出并非由 E1 所声明的输入所决定。在 macOS 笔记本上，有七种配置存在差异：C、C++ 和 Fortran 的每一种 `-g` 配置，差异为 37 或 38 字节的可执行文件内容（在可执行文件大小相同的前提下；对于在 `hello.c` 上运行的 `gcc -O2 -g`，可执行文件差异为 85 字节，DWARF 文件差异为 16 字节）；默认模式下的 `zig build-exe`，差异为 402 字节；以及 Julia 运行，差异为 148 字节。`rustc -O -g` 及其他十二种配置则完全相同。

2. **两个目录。** 在三台机器上，凡是在两个目录之间存在差异的配置，其输出中都写入了构建目录。在不做路径重映射的情况下，跨目录保持相同的配置包括：三台机器上的 `gcc -O2`、`rustc -O` 和 `gfortran -O2`；本地机器和 macOS 笔记本上的 Lean 与 Wasmtime；CI 运行器和 macOS 笔记本上的 `zig build-exe -O ReleaseSmall` 与 `ghc -O1`；以及 macOS 笔记本上的 `cobc -x`。对于其余配置，默认情况下构建路径是一个未声明的输入。

3. **两个目录，启用路径重映射。** 在本地机器上，路径重映射消除了所有差异，唯独 Go 的 GOPATH 模式仍有差异，分别为 58 字节和 59 字节，文件大小相同，且输出中已不再包含构建目录的副本。在 CI 运行器上，同一配置的差异为 59 字节和 60 字节；另有两种配置在重映射后仍存在差异：`gnatmake -O2 -g`，其重映射后的输出中仍保留两份构建目录副本，且两个 `.ali` 文件存在差异；以及 Julia 运行，其重映射后的运行在一个 LLVM IR 文件中仍有 146 字节的差异，但已不再包含构建目录的副本。在声明了导入路径的 GOPATH 模式下，两台 Linux 机器上重映射后的构建在跨目录时完全相同。在 macOS 笔记本上，路径重映射并未消除 C、C++、Fortran 和 Rust 的 `-g` 构建中的构建目录副本：无论是否启用重映射，每个程序的输出中都计数到三份副本，且启用重映射后的差异字节数与未启用时相差不超过一个字节。Go 的 GOPATH 模式在重映射后仍有差异，分别为 119 字节和 120 字节，文件大小相同，且已不再包含构建目录的副本；`ocamlopt -g` 的差异为 669 字节，仍保留一份副本；Julia 运行的差异为 114 字节，且不再包含副本。Go 的模块模式，以及声明了导入路径的 GOPATH 模式，在启用重映射后跨目录构建完全相同。

4. **时钟。** 仅有 CI 运行器上的 `gnatmake -O2 -g` 与 macOS 笔记本上的 `cobc -x`，在同一目录中设置 `SOURCE_DATE_EPOCH` 时构建完全相同，而未设置时则存在差异，差异分别为 3 字节和 50 字节；对于这两种配置，时钟是一个输入。

5. **跨机器.** 在本地机器和 CI 运行器之间，只比较工具版本字符串相同的配置：gcc、g++、clang、clang++ 和 gfortran 的配置，共七种配置在 14 个程序上，通过每台机器一次构建的所有输出的 SHA-256，在不同的绝对路径目录中。使用重映射后，gcc、g++ 和 gfortran 的输出在两台机器上完全相同。`clang -O2 -g` 和 `clang++ -O2 -g` 在所有四个程序上即使使用重映射也在机器之间存在差异，尽管在每台机器上它们的重映射构建在目录之间是相同的。Go 和 rustc 未进行比较，因为它们的版本字符串在两台机器之间不同，而且其他工具链仅在其中一台机器上安装。macOS 笔记本仅在 Zig 0.17.0 和 GHC 9.14.1 上与 CI 运行器共享版本字符串，在本地机器上没有任何工具共享。Zig 和 GHC 的输出在 CI 运行器和笔记本之间不同，因为它们面向不同的系统和指令集（Linux x86-64，macOS arm64），因此此比较未能检验 H1 跨机器的情况。

**这对 H1 的意义.** Go 的 GOPATH 模式结果是一个在目录之间经过重映射仍然存在的字节差异，项目仓库在注册的变更表中记录了对此的判决，日期为 2026 年 11 月 2 日 [6]。其原因已命名。所有不同的字节位于 `\.note.go.buildid\` 和 `\.note.gnu.build-id\` 节中，代码和数据完全相同。`gocachehash` 跟踪显示编译和链接操作 ID 对构建目录进行哈希，因为 GOPATH 模式为一个位于每个 `GOPATH` 之外的文件提供了一个由导入路径 `_` 加上其绝对目录命名的包，而 `-trimpath` 并未移除它；一旦目录作为占位符写入，两目录的哈希输入就相同。仅在该输入改变的情况下，放置在 `GOPATH` 中并通过其导入路径构建的包没有哈希输入指向目录，重映射构建在不同目录之间在字节上是相同的，而原始配置仍然不同。该判决使用已注册的条件：伪造者是指在声明的输入相等时仍能在重映射后存活的差异，而这里输入并不相等，因为导入路径是 `go build` 从目录衍生的输入。因此结果并非 H1 的伪造者。导入路径可以被命名并受控，因此将其加入 H1 的声明输入后，H1 对于带名称的导入路径的 Go GOPATH 模式依然成立；而对于位于每个 `GOPATH` 之外的文件的 GOPATH 模式构建，`-trimpath` 本身并不是一次重映射。

其他经重映射后仍存留的差异没有记录的裁决。在 CI 运行器上，`gnatmake -O2 -g` 与 Julia 运行在重映射后跨目录存在差异，而 E1 并未确立声明的输入在两个构建之间是否不同。在跨机器比较中，`clang -O2 -g` 和 `clang++ -O2 -g` 在重映射后的差异是具有相同工具版本字符串的构建之间的差异；E1 未记录其起因的任何踪迹，且仓库未对它们记录裁决。对于 macOS 笔记本电脑，变更表记录该运行尚未有裁决，以及它所确立的内容 [6]。其重映射构建将构建目录命名为工具未记录的路径：系统临时目录位于 `/var/folders` 下，通过符号链接 `/var` 指向 `/private/var`，而 Go 的追踪以 `/private` 前缀命名该目录。在 Linux 上对 gcc、clang 和 rustc 的检查发现，将链接路径命名的重映射会在输出中留下真实路径。因此，macOS 重映射比较并未检验 H1 的重映射条件。自该运行以来，E1 以真实路径命名构建目录，将不同的 Mach-O 字节归因于区域，并添加了三个仅在 macOS 上运行的配置：两个配置中 clang 分两次调用进行编译和链接，且链接器被指示从其调试映射中丢弃构建目录，其中一个还设置 `ZERO_AR_DATE=1`，Apple 的链接器读取该值以对目标文件时间写入零 [K]；以及带有相同链接器选项的 rustc。仓库中尚未有应用这些更改的重新运行；变更表将该重新运行命名为裁决的证据。在这些起因被追踪之前，H1 作为整体既未被 E1 支持也未被 E1 证伪。研究会话中较早的一次探测（每种语言一个程序）在单台机器上发现了 gcc、clang、rustc、默认模式的 Go 以及 gfortran 的同目录和跨目录模式 [M]。

**局限。** 这些程序规模较小，每种语言一至两个，因此仅在大程序中才会出现的差异未被检验。链接时优化、基于配置文件的构建以及超出 rustc 默认值的并行代码生成均未纳入矩阵。E1 比较字节；它未检查含义是否被保留，而这正是 H3 和 H7。macOS 运行仅说明每个文件中差异的字节数，而未指明差异位于文件的哪一部分。

### 8.2 E2 到 E4：协议、E4 的擦除计数和 E4 能量（`reported_j` 与回报期限）

E2 和 E3 的协议已在仓库中，但尚未运行。E4 在没有能源计数器的主机上执行了原始的 96 行擦除计数运行 [6]，并且在 20 个确定性内核和 14 个编译器与运行时层级上预注册了 Wave 4 Linux RAPL `reported_j` 扩展（`board_metered = false`，`measured_j = None`）。

**E2，门控审计（H2）。** 对每个编译器，准备一组固定的小型程序，每个程序注入一个故障，并配有一个仅在故障处有所不同的正确对照程序。各编译器的故障类型如下：所有编译器均为类型错误；rustc 为借用错误；Go 为未使用的导入或变量；LLVM 的 `llc` 为无效 IR 模块，`wasmtime compile` 为无效 WebAssembly 模块；契约类故障为失败的契约（Lean 定理的证明无法通过检查，或 GNATprove 无法证明的 Ada 前置条件）；Erlang 的验证器则为生成代码故障。每个故障程序及其对照程序分别在默认标志和各文档所述会改变门控行为的标志集下构建（例如 tsc 的 `noEmitOnError`、TorchDynamo 的 `fullgraph=True`、gcc 与 clang 的 `-Werror`）。测试工具记录退出状态、写出的每个产物及其 SHA-256 值，以及诊断信息的第一行；若对照程序无法构建，则该案例作废。每个编译器及每种故障按以下三类之一进行划分：*默认情况下不输出任何内容*、*默认输出而配置后不输出*、*始终输出*。每个门控的属性类别、链接假设及可信基则依据编译器自身的文档进行记录，或加以引用，或注明为“未说明”。误判计数为观察行为与文档所述行为不一致的案例数量。张量编译器回退到急切执行或回退到 CPU 提供者的情形，单独作为一类记录。自 2026 年 11 月 2 日的变更起，每条记录均为权威性证据的固定凭据（§3.3）：它与程序、编译器可执行文件及每个产物的 SHA-256 值绑定，并与标志集绑定；若记录的摘要与其案例不符，则该记录作废，并重新运行该案例。每个门控的文档陈述还包括其检查器所接受证据的权威性，以及该接受是否被记录为与摘要绑定。文档陈述属于派生证据，绝不会被提升为观察结果，因此编译器所属类别以观察记录为依据；若门控所接受的证据属于推断性证据（例如由启发式选择的回退策略），则其接受情况记为未定。

**E3，等价层级审计 (H3)。** 每个编译阶段或标志在运行前被分配一个层级：`-O0`、`-O2`、`-O3` 精确；`-ffp-contract` 设置在声明的误差界限内；重新关联（`-fassociative-math` 配合向量化、`-ffast-math`、`-Ofast`）在声明的误差界限内，且界限需明确；在 GPU 运行环境下，拆分归约并降至 FP8 被声明为有损。语料库包含整数内核（通过构造保证精确）以及浮点内核，后者包括求和、点积、多项式求值和归约，使用的固定输入涵盖次正规数、符号零、无穷大和 NaN（非数字）值。精确参考是相同的有理算术计算，最终仅四舍五入一次；声明的程序是使用严格 IEEE 754 语义的 `-O0` 构建。度量包括不同的位数、最大的 ULP 距离、最大的绝对误差和相对误差，以及静态检查（针对无循环代码的 SMT 求解器，或区间/误差分析工具）是否对该层级进行认证。静态工具尚未确定。自 2026 年 11 月 2 日的更改起，每条差异测试记录都是固定的证据，绑定到内核源码的 SHA-256、编译器可执行文件、构建的二进制文件以及输入：任何观察到的超出分配层级的变化都是反例，即 H3 的否定者，而对所有输入的一致性并不能证明任何东西。只有在有已证明的证据的情况下，层级才被视为已认证，即静态工具的判决绑定到所检查的二进制或 IR 的 SHA-256、工具本身以及声明的层级；仅由启发式或模型分配的层级将被记录为未决定。张量编译器以及 FP8、FP4 格式需要 GPU 运行环境，而项目目前尚未拥有。

**E4，抹除与描述长度相对于测量能量的比较 (H4)。** 语料库是一组程序，每个程序在多种配置下编译，而 E3 的检查器在精确层级上接受这些配置为等价，从而能量差异来源于降级而非程序的改变。ε 通过对每次运行进行插桩计数：每一次对寄存器或内存位置的写入都会将先前值中未被复制出来而被覆盖的位数加入计数。λ 在运行前通过声明的代理进行计算。每次运行的能量（以焦耳为单位）在若干区间内测量，分为 A 区段（使用带供电计量的 FPGA 或顺序执行核心；已执行的操作作为基线）、B 区段（使用带 RAPL 的 x86 主机，或带 NVML 的 GPU；时间乘以功率作为基线）和 C 区段（熵产生的模拟）。编译时能量也会记录。分析事先声明：对每个区段使用普通最小二乘模型，给出解释的方差比例以及针对程序的 95% bootstrap 区间；当该区间不包含零时，ε 和 λ 解释了方差。没有仪表读数的能量数值标记为模型估计。

**E4，在读取任何能量之前声明**（2026 年 11 月 2 日）[6]。语料库包含八个内核（`sumsq`、`collatz`、`sieve`、`sort`、`crc32`、`matmul`、`fib` 和 `popcount`），每个内核均为针对 32 位无符号整数的函数 `run(n)`，不使用任何库，以 C 和 Rust 编写：共 16 个程序，每个程序在六种优化级别下构建（`clang -O0`、`-O1`、`-O2`、`-O3`、`-Os` 和 `-Oz`；`rustc` 的 `opt-level` 为 0、1、2、3、s 和 z），总计 96 行。由于 E3 的检查器尚不存在，因此通过较弱的测试显示这些配置相等：每个配置在其内核的五个声明输入上给出参考值，原生执行和 WebAssembly 执行均如此。ε 由为 E4 编写的 WebAssembly 解释器计数，并由其 SHA-256 固定，对每个内核在该行优化级别下为 WebAssembly 构建的版本进行计数；因此，它是针对配置的计数，而非针对读取能量的原生代码，并且是以字节粒度对一次运行丢弃的比特数的上界。主要 λ 是内核模块中 WebAssembly 指令的数量。能量仅在 B 体制下读取，来自 Linux 上的 RAPL 和 macOS 上的 `powermetrics`；两者均为芯片或操作系统报告的计数器，而非电源上的仪表，且测试宿主均无针对 A 体制或 C 体制的计数器。分析使用调整后的 R²（可降至零以下），其 95% 区间来自对整个程序的 2000 次重采样；当该区间位于零以上时，ε 和 λ 解释方差，而在 B 体制下，仅当基线调整后 R² 减去它们的区间位于零以上时才支持 H4，若位于零以下则证伪 H4。

**E4，仅计数、不计能量。** 该测试框架于 2026 年 11 月 2 日（UTC）在一台 Linux x86-64 机器上运行（Intel Xeon 2.80 GHz，4 个 CPU，Ubuntu 24.04.5），使用 clang 18.1.3 和 rustc 1.97.0。该机器没有 `/sys/class/powercap` 接口，因此第一份结果文件中的所有能量字段都记录为未测量：该文件不包含焦耳数值，也未基于它进行能量分析，H4 在该处未被检验。

16 个程序在每种配置下、对每个声明的输入，无论是原生运行还是以 WebAssembly 运行，都给出了参考值，并且 96 行数据全部统计了 ε。每次调用的 ε 范围从 272,048 比特（C 中 `-O2` 和 `-O3` 下的 `popcount`，以及 Rust 中 `opt-level` 为 1、2、3 时的结果）到 10,057,528 比特（Rust 中 `opt-level=0` 下的 `matmul`），对应 300 K 下建模的兰道尔界限为每次调用 7.81×10⁻¹⁶ J 至 2.89×10⁻¹⁴ J。16 个程序中每一个的最高 ε 都出现在等级 0。优化体积并不总是降低 ε：C 中 `-Oz` 下的 `popcount` 计数为 3,540,016 比特，约为其 `-O2` 计数的 13 倍，并且每次调用执行 488,404 条 WebAssembly 指令，而 `-O2` 下为 19,530 条。

**E4-能耗（第4波），Linux RAPL `reported_j`，编译成本与回报期 $N^*$。** 在运行之前（`PREREG_rce_compile_wave4.json`，SHA-256 `165a12cda4d9c304…`），一个20内核的确定性精确整数和定点套件已在C、Rust、WebAssembly、Python和RCE（`openIE-dev/rce` at `1762fb4b`）上锁定：`sha256_block`、`chacha20_block`、`q32_orbital`、`crc32_ieee`、`lz77_match`、`dijkstra_grid`、`ntt_butterfly`、`matmul_i32`、`bst_probe`、`sortnet_16`、`ringbuf_sim`、`token_bucket`、`fnv1a_sip`、`sieve_primes`、`collatz_bounded`、`popcount_swar`、`edit_levenshtein`、`rle_codec`、`modexp_mont`和`kalman_q16`。所有构建和运行均在一台32-CPU Linux x86-64主机（AMD Ryzen AI Max+ 395，Zen 5，Ubuntu Linux 7.0；GCC 15.2.0，Clang 21.1.8，rustc 1.100.0，Node v22.22.1，Python 3.15.0）上执行，通过`sched_setaffinity`固定至CPU 0，即`/sys/class/powercap/intel-rapl:0:0/energy_uj`（核心`MSR_CORE_ENERGY_STAT`）的域主导CPU，同时记录`/sys/class/powercap/intel-rapl:0/energy_uj`（APU封装；`basis = "reported"`，`board_metered = false`，`measured_j = None`）。所有280个内核-层单元（20个内核×14个层）在2000个种子上的64位无符号批校验和匹配，失配数为0 [M]。

**优化回收期 $N^* = \lceil \Delta E_{\text{compile}} / \Delta E_{\text{run}} \rceil$。** 从 Python 字节码降级到 `clang -O3` 或 `rustc -C opt-level=3`，在全部 20 个内核上均可回收成本，所需调用次数的中位数分别为 **2,490**（范围 648 至 10,141）与 **5,263**（范围 851 至 16,692）。在原生编译器内部，从未优化的 `-O0` / `opt-level=0` 升级到 `-O2` 或 `-O3`，在全部 20 个内核上均可回收成本，有限 $N^*$ 的中位数分别为：`rustc 0 -> 2` 为 **38,262**，`rustc 0 -> 3` 为 **53,464**，`clang -O0 -> -O2` 为 **61,637**，`clang -O0 -> -O3` 为 **81,004**，`gcc -O0 -> -O3` 为 **102,720**。相比之下，从 `-O2`（或 `-Os`）升级到 `-O3` 时，在任何部署规模下往往都无法回收成本：`clang -O2 -> -O3` 有 6/20（30%）的内核出现 $\Delta E_{\text{run}} \le 0$（$N^* = \infty$），`rustc 2 -> 3` 为 6/20（30%），`clang -Os -> -O3` 为 7/20（35%），`gcc -O2 -> -O3` 为 4/20（20%）。而确实获得收益的内核，需要中位数 **106,920** 至 **244,165** 次调用才能使 `-O3` 收回其额外的编译能耗（在 Clang 的 sha256_block 上高达 **3.87×10⁶** 次，在 GCC 上高达 **1.39×10⁷** 次）。`rustc --target wasm32-unknown-unknown -C opt-level=3` 构建的 1.6 KB 可移植模块，核心编译能耗为 0.485 J（core 口径），在 Node 中每次调用执行能耗为 1.64 µJ。因此，原生 `rustc -O3` 需要中位数 **871,412** 次调用，才能摊销其额外的 0.667 J 原生链接与代码生成开销。对于 RCE（`1762fb4b`），执行 `rce check` 并输出全部五个标量目标（`core`、`rust`、`python`、`js`、`scala`），中位数成本为 0.851 J（core 口径，97.9 ms）。而在 `rustc -O3` 下，于每个输出的 Rust 文件内编译独立的 1,400 行 RCE 值运行时前置代码（prelude），成本为 56.29 J（core 口径），需要中位数 **31,080** 次调用（20 个内核中 18 个为有限值，2 个永不回收）才能超过直接在 Node 中运行输出的 JS。

**H4 体制-B 在 Linux RAPL 上的检验。** 在 140 个使用独立 WebAssembly IR 模块的 Clang 和 Rust 行（40 个按语言划分的内核系列，2,000 个全内核自举重采样）中，静态 WebAssembly IR 描述长度 $\lambda$（`ir_nodes` 和 `wasm_bytes`）解释了调整后 $R^2$ 为 **0.1154**（95% 区间 **[0.0654, 0.4058]**），而体制-B 基线（`run_wall_s × mean_core_power_w`）解释了 **0.9999**（**[0.9987, 1.0000]**），正差值为 **+0.8845**（**[+0.5979, +0.9352]**）[M]。这与 H4 在 Linux RAPL 上的体制-B 预测相符，同时也与先前的 macOS `macmon` 运行结果（`HYPOTHESES.md`）一致；H4 作为一个整体仍保持开放，直至体制 A 和 C 得到检验，并且安静的专用主机与共享主机运行进行比较（此主机上未绑定的核承载了协租户负载平均值 18.97 至 36.42）。

### 8.3 E5：一种无名称哈希，已测量

**方法。** E5 测试 H5 并实现编译器范式的 R 部分为两个操作 [6]。其协议和测试平台的日期为 2026 年 11 月 2 日，早于首次运行，并且登记记录在同一天在 H5 下记录了 E5 的预测和证伪。每个操作在去除程序绑定的标识符名称后对构建产出进行哈希。

- *在机器码层面*，按照 E5 协议引用的 WARP 已发布描述的相应部分，对未链接的目标文件进行计算：x86-64 ELF 目标、arm64 Mach-O 目标以及 WebAssembly 目标。每个函数被划分为基本块；每条指令如果被重定位记录（即链接器需要在此处打补丁的标记）指向，则用零字节替代；不执行的指令以及全宽寄存器自赋值的指令被省去；对每个块进行哈希，函数的标识符为其块哈希的哈希。由此得到两个键：内核函数 `run` 的标识符，以及所有函数标识符排序后的哈希，其中不包含任何名称。

- *在 IR 层面*，对链接后的 WebAssembly 模块在 α-等价（两个程序在对绑定标识符进行一对一重命名后相同）的模下进行哈希，写入每个模块的规范形式并使用 `SHA-256` 进行哈希。在该形式中，类型索引成为其签名，局部变量按位置和首次使用编号，函数按调用图的形状排序，独立定义进行排序，自定义节（如存放名称的节）被省略。一个键覆盖整个模块，另一个键覆盖 `run` 能达到的部分。协议将基于 α-等价的哈希思想归功于 Maziarz 等人（PLDI 2021），并说明其规范形式并非其算法。

两个基线键对应第 3.5 节 U 小节中描述的两类缓存键：输出字节的 `SHA-256`，以及去除构建目录后的源文本和构建命令的 `SHA-256`。H5 的度量命名为编译器自己的键；E5 不读取编译器的缓存键，而使用这两个基线键代替，表格中的变更记录了这一替换。E5 比较键值；它不进行缓存。

**语料与配对。** 语料由 E4 的 16 个程序在六个层级上的版本构成，每个版本有四种输出：一个 x86-64 目标文件，一个仅针对 C 程序生成的 arm64 Mach-O 目标文件，一个 WebAssembly 目标文件，以及 E4 链接得到的 WebAssembly 模块。E1 的 C 程序和 Rust 程序（`hello.c`、`sort.c`、`hello.rs` 和 `generic.rs`）同样处于这六个层级，但仅生成 x86-64 目标文件。每个源码分别从目录 A 构建，从目录 B 构建其相同字节的副本，并从目录 N 构建一个重命名副本。三条路径的长度相等。重命名器为程序绑定的每个标识符赋予一个新名称，该名称由原名称的 SHA-256 派生，并删除注释。一个重命名源码与原程序相同的证据是其行为：三个变体的链接模块在 E4 的每个声明输入上都给出 E4 的参考值（每个变体 96 个中有 96 个一致），且 E1 的四个程序在重命名前后输出的字节完全相同。A 与 B（*两个目录*）以及 A 与 N（*重命名*）的配对被声明为相等。同一工具链的任意两个层级之间的配对、同一内核在匹配层级上的 C 版本与 Rust 版本之间的配对，以及两个不同内核的任意两个构建之间的配对，均被声明为不相等。*变异*配对同样被声明为不相等，包括：每个链接模块与其自身之间的比较，其中一条操作码被替换为同类中的另一条操作码；或某个常量被改变；或某个内存偏移被改变。

一个*命中*是指两个目录配对或重命名配对上的键相等。一个*误命中*是指两个不同内核的构建之间键相等，或变异前后 IR 哈希保持不变。两个层级之间的键相等，或同一内核的 C 版本与 Rust 版本之间的键相等，应予报告但不计为误命中，因为这类配对计算的是同一个函数。若在重命名配对上，每个 R 哈希的命中率都高于两个基线，且不存在误命中，则 H5 获得支持；若出现任何误命中，或在重命名配对上没有任何 R 哈希的命中率高于两个基线，则 H5 被证伪。

**机器环境。** E5 于 2026年11月2日（UTC）在一台 Linux x86-64 机器上运行，该机器配备英特尔至强处理器（主频 2.80 GHz，4 个 CPU），操作系统为 Ubuntu 24.04.5，使用 clang 18.1.3 和 rustc 1.97.0。它共构建并哈希了 360 个 x86-64 目标文件、144 个 Mach-O 目标文件、288 个 WebAssembly 目标文件和 288 个链接模块。其 x86-64 解码器找出的指令边界，与 LLVM 的 `llvm-objdump` 在目录 A 中构建的 x86-64 目标文件所含全部 386 个函数上的结果一致。

**结果。** 相等键的数量，相对于所比较的配对总数。R 哈希对于目标文件是机器码标识符，对于链接模块是 IR 哈希。

**发现。**

1. **未出现错误匹配。** 在 26,208 次不同内核构建的比较（每个输出和键 4,032 对，每个 Mach-O 对象 1,008 对）中，没有任何 R 哈希相等；在 9,328 次针对 96 个链接模块的变异（4,712 次针对操作码，3,564 次针对常量，1,052 次针对内存偏移）中，也没有出现 IR 哈希保持不变的情况。  
2. **重命名对的收益。** 对于重命名对，R 哈希在其九种输出和键的组合中，命中率均高于两种基线：机器码标识符为 100%，相较于输出字节的 45.8% 至 70.8% 和源键的 0% 至 50.0%；IR 哈希为 90.6%，相较于 79.2% 和 0%。  
3. **结论。** 按照已登记的条件，H5 在本语料库上得到支持。变更表记录了该结论以及未成立的预测，并将其限定于本语料库、两个工具链和一个 IR [6]。  
4. **IR 级别的遗漏。** 在 96 对两目录对和 96 对重命名对中，各有 9 对的 IR 哈希不相等：所有八个内核在 `opt-level=0` 下的链接 Rust 模块，以及 `opt-level=1` 下的 Rust `sort`。在每种情况下，规范形式的唯一差异在于数据部分，并且每个模块保存了其构建目录路径的一份副本。已登记的 IR 哈希将数据字节视为常量且不剔除构建路径，而 Form 的 R 会移除该路径。首次运行后添加的诊断键在数据中写入该路径作为占位符，且不用于结论判定，在所有 96 对两目录对以及 96 对重命名对中的 92 对上相等。剩余四对为 `opt-level=0` 下的 Rust `fib`、`matmul`、`sieve` 和 `sort`，同样出现在数据中。对于 `fib`，在 harness 之外的检查发现两个数据段在 Rust 溢出信息的定位记录列号上不同：重命名标识符更长，导致同一表达式起始列号更后。  
5. **其他未成立的预测。** 在 E1 程序的 24 对重命名对中，源键在 12 对相等，因为两个 hello 程序未绑定任何标识符，重命名器未对其进行修改。WebAssembly 对象中 `run` 的机器码标识符在 C 和 Rust 的 `fib` 构建的五个匹配层级（1、2、3、s 和 z）以及 `popcount` 的 s 层级上相等，共计 48 对中的 6 对；每对计算一个函数，因此不构成错误匹配。对于链接模块，所有 48 对 C 与 Rust 的 IR 哈希均不同；其规范形式的函数部分在 48 对中有 6 对相等，内存部分则全部不相等。  
6. **层级。** 在同一工具链的不同优化层级对中，R 哈希的相等率为 10.0% 到 21.7%，输出字节的相等率为 10.0% 到 12.5%，如登记所示：大多数对不相等，已报告且未计入相等对。

**E5 未展示的内容。** 相等的机器码标识本身不建立等价关系：零指令在对象链接后可以调用或加载不同的符号，而标识并不知道是哪一个。WARP 的约束能够区分此类函数，但未实现，因此机器码命中只是一个候选复用，需要检查器进一步接受，而协议对这些标识不赋予任何属性类。相等的 IR 哈希表示两个链接模块在α等价的前提下（除 SHA-256 碰撞外），协议将其视为在 WebAssembly 语义下整数结果的精确层级；它不涉及从相同源代码生成的本机代码。不同的哈希并不说明不等价：一对层级在不同哈希下计算同一函数，且两个α等价的模块若在规范顺序中出现平局，可能会被不同排序，因为平局被计数而非解析。若 IR 哈希在 G0 层级上进行键控复用，协议的门声明将等价于模块的精确层级，由主机通过其导入和导出名称链接，而该主机不读取自定义段，使用 E5 自身的读取器、规范化器和哈希代码、Python 的哈希库以及 WebAssembly 规范作为可信基准。未出现错误命中并不说明这些哈希在其他程序上也没有错误命中：初始 E5 语料库仅包括 16 个内核和 4 个程序，来源于两个均通过 LLVM 降级的工具链，运行在同一台机器上，且 IR 为 WebAssembly，而非 LLVM IR。而且由于 E5 不读取任何编译器的缓存键，它也未证明任何编译器的缓存会获得命中。

有三项实证结果值得注意：

1. **为什么 De Bruijn 位置优于朴素标识符剥离。** 将每个用户标识符替换为单个匿名 `ID` 标记可在 alpha 重命名上达到 100% 命中率，但**在 150 个中的 150 个（100.0%）变量绑定交换错误上发生碰撞**（`x - y` 和 `y - x` 均投影为 `ID - ID`），在 500 个已验证错误中产生 30.0% 的总体误命中率。将每个绑定出现替换为其绑定槽（`v0 - v1` 与 `v1 - v0`）可产生**0 个中的 0 个（0.00%）** 假阳性碰撞和**0 个中的 29,890 个** 跨程序碰撞，在规模上支持 H5。
2. **在 `1762fb4b` 处 `rce fmt nameless` 的真实格式化器行为。** 由于 `rce fmt nameless` 被设计为发出带有注释保留（`nameless.rs`）的有效、可检查 RCE 源文本，其原始 stdout 在插入 `#` 注释时发生变化（注释添加的格式化偏移为 0 个中的 0 个，在 alpha 重命名上为 185 个中的 128 个，其中 50 个零绑定器或外部字段 Form 回退到注释偏移），并且在相邻 `event` 声明交换顺序时发生变化（23 个中的 0 个，因为 `e0, e1` 遵循声明顺序）；在对 `rce fmt nameless` 进行哈希前剥离 `#` 注释可在注释偏移上恢复 185 个中的 185 个（100%）。
3. **避免的编译 `reported_j`。** 在固定 CPU 0 上将热 De Bruijn 源缓存置于 alpha 重命名重建之前，可将每个内核工作从 **1.166 J** 核心（143.8 ms）降低至 **2.60 mJ**（288.1 µs）（在 `rustc -C opt-level=3` 上，**448.5×** 减少，避免每次命中 1.163 J 核心），从 **0.682 J** 核心（82.0 ms）降低至 **4.07 mJ**（342.0 µs）（在 `clang -O3` 上，**167.8×** 减少，避免每次命中 0.678 J 核心），并从 **78.71 mJ** 核心（9.85 ms）降低至 **4.59 mJ**（0.74 ms）用于 `rce check` 加 5 目标 `rce emit`（**17.15×** 减少）[M]。读者可在伴侣观测站的 [`/living/rce-compile/`](/living/rce-compile/) 处测试实时片段并检查所有 280 个 E4-Energy 单元。

## 9. 本研究的局限

- **几乎所有外部证据均为 [S] 或 [K]。** 保存原文的主机在研究期间无法访问，带路径过滤器的 GitHub 提交 API 被拒绝，国家数据库（ACM DL、CNKI、J-STAGE、eLibrary.ru、HAL）只能通过通用网页搜索获得。在超出草稿的正式发布前，需要按以下顺序阅读原文：Hoare、He 与 Sampaio（1993）；Ershov（1977）；CompCert 手册中的定理陈述；arXiv:2610.33193，以检查 PP 完全性相对 PP 难度；arXiv:2609.11356；以及 Zig 发布说明。
- **针对特定法则的负向搜索在某些语言中仍未完成。** 未逐一检索中文、俄文、法文和德文中“编译定律”的本土术语。
- **分段表格为定性描述。** 它概括了架构和文档情况；并非对每个编译器的测量。
- **能耗读取为 Regime-B 在共享主机上的 `reported_j`，而非供电功率计的 `measured_j`。** E4-Energy 在单台 32 核 Zen 5 主机上记录 Linux RAPL 核心和 package 的 `reported_j`（`board_metered = false`, `measured_j = None`），该主机的非固定核心承载了共租工作负载（§8.2）；Regime A（顺序/FPGA 供电分流）和 Regime C（热力学熵产生）仍未测量，因此 H4 作为三体制假设尚未关闭。
- **语料库范围。** E1 为每种语言构建一至两个程序；E4-Energy 覆盖 20 个独立的整数和定点内核，未使用多 crate 链接时优化或 GPU 内核；E5-Scale 的源码级 De Bruijn 标准化器涵盖 RCE Forms（`185`）以及单文件 C、Rust 和 Python 内核（`60`），未覆盖完整的多翻译单元 C++ 或 LLVM IR（§8.3）。
- **98/2 的划分已登记，但尚未测量。** 它是假设 H6（§5, §7），其测量计划按步进行并声明具体单位。

## 10. 结论

以真实编译器为基准衡量，这一候选方案可分为两类内容。表示、代价、检查器、复用与门控描述的是该领域已经存在、但应用程度参差不齐的实践。降级（lowering）、收敛函数和能量则描述的是目前没有任何已发布编译器能够满足的标准。正是这一区分促使我们将该候选方案重新表述为一种范式：将 gcc、rustc、Go、GHC、XLA 等编译器置于同一份声明式契约之下，该契约包含去除路径影响的确定性、命名门控、明确的等价层级，以及与两个可计算界限之间的实测距离。由此，来自不同社区的编译器获得了一把共同的标尺。初稿中有两项实证缺口，现已用 Regime-B 数据加以补充。第一，E5-Scale 在 245 个程序和 500 个经验证的语义变异体上表明，部分 R 必须以 De Bruijn 位置替换约束标识符，而不能仅仅去除名称。基于位置的哈希产生 0/500 的误判命中，并使冷启动 `clang -O3` 与 `rustc -O3` 重建时的 `reported_j` 分别降低 167.8 倍和 448.5 倍；相比之下，朴素的标识符去除在所有变量绑定交换上都发生 100% 碰撞（§8.3）。第二，E4-Energy 在 20 个精确整数内核和 14 个编译器层级上表明，编译焦耳显著改变了哪一个优化层级胜出。从 Python 降级到 `clang -O3` 的收益在中位数 2,490 次运行后回本；`-O0` 到 `-O3` 需要 53,464 至 102,720 次运行才能回本；在 20% 至 30% 的内核上，`-O2` 到 `-O3` 的额外编译焦耳则从未被回收。在 Regime B 中，时间乘以功率对 RAPL `reported_j` 方差的解释力远超静态 WebAssembly IR 大小（分别为 0.9999 与 0.1154，§8.2）。由于硬件能耗高出理论下限 $10^6$ 至 $10^{11}$ 倍，以全生命周期 `reported_j` 对编译器排序（若接入硬件分流计量表，则同时提供 `measured_j`），并将 Landauer 界保留为物理下界，便使部分 E 转化为可操作的决策规则。98/2 原则也需要同样处理：在进行首次测量之前，必须先选定并公布其计量所用的单位。
