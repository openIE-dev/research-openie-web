## 要旨

複数のエージェント評価でタスク解決率や消費エネルギーが異なる場合、その差はモデル自体ではなく、モデルを包むハーネスの設計やホスト側カウンタの帰属規則から生じることが多い。`Terminal-Bench 2` では外側のハーネスを入れ替えただけで `Gemini 2.5 Pro` の解決率が `17` ポイント変動し、またドリフトするアイドル電力を差し引いたり共有レールをプロセッサ時間で比例配分したりすると、エネルギー帰属が `30%` 以上歪む。本研究は Satiation Benchmark（`SATB`）の評価契約を規定し、`Apple M5 Max`（`128 GB` ユニファイドメモリ、`macOS 27.2.1`）上で実証検証を行う。固定逐次 Rust ハーネス（`Lane B`：モデル呼び出しゼロでウィンドウ `80%` 超過時に古いツール出力を省略する `ContextRule_v0` と `8 + 8 KiB` 切り詰め `Truncate_v0`）、ループバックプロキシブリッジ（`Shapes D, M, H, I`）、5 ブロックのシステム指紋、12 項目の適合性テスト（`C1` から `C12`）、および 5 階層テレメトリ（`L0` から `L4`、ラベル `A1` から `N`）を備え、オンチップカウンタを `reported_j`、非公開クラウド API のサーバー電力を厳密に `not_available` として記録する。

**平易な言葉で言うと**

1. プロンプトのループや文脈圧縮、ツールの隔離条件はモデルの差し替えと同じくらいスコアを左右するため、`Lane B` はその外側を決め打ちの Rust で固定し、`Lane O` は外部エージェントを単一の監査済みプロキシに通す。
2. エネルギーは実際の物理境界（壁コンセント、基板入力、チップパッケージ、OS のプロセス推定、論理トークン台帳）ごとに生のまま記録し、ラベルなしの一つの数値に混ぜたり事業者のフリート中央値で代用したりしない。
3. `Apple M5 Max` での実測により `12/12` の適合性テスト合格（リプレイ差分 `0` バイト、プロセスツリー `SIGKILL` 回収平均 `2.07 ms`）、クラウド 3 社で `temperature = 0` でも出力が一致しない事実、観測者オーバーヘッド（境界読み取り `0.011 mW` 対 `10 Hz` 周期 `66.44 mW`）、およびプロセッサ時間比例配分が逐次境界カウンタから `32.59%` から `35.86%` 乖離することが確認された。
