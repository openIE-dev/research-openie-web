## 要旨

RCE-VC は Rust で実装されたバージョン管理の設計かつ小規模なリファレンスである。多数のライター、すなわち人間あるいはプログラムが共有状態に対して変更を提出する。名前付きチェックが結果を受理すれば変更が反映され、受理されなければ変更は拒否され、その理由が保持される。ライターは Git 上に留まることができる。このリファレンスは Reality Code Engine 言語ではない。フレーミングは同一であり、Form、総ステップ、ハッシュ連結ログ、名前なしキー、そして最後にモデルが置かれるギアの階層から構成される。

**平易な言葉で**

1. 任意の数の人間およびプログラムが同時に書き込むことができる。名前付きチェックが結果を受理したとき、変更は共有履歴に組み込まれる。チェックが受理しなければ、変更は除外され、その理由が記録される。書き込んだ者が決定権を持つわけではない。

2. 同一の対象に触れない変更は互いに待つ必要がない。対象が重なる場合、事前に記載された価格が合格した結果の順位付けを行い、解決済みの競合を含め一度受理された結果は再利用される。モデルはより安価なステップが失敗した場合にのみ問い合わせられ、其の回答もチェックを通過しなければならない。

3. リファレンスは通常の Git 履歴を読み書きし、Rust および Python ファイルを名前なしのトップレベル項目（`rcevc-keys`）に分割するので、ライターは Git を離れる必要がない。Apple M5 Max 上の `aba99fce` において、100,000 単位のリポジトリに対する変更の受理は `69.7-73.6 µs`、`317-365 µJ` のオペレーティングシステムプロセスカーネル `ri_energy_nj`（`reported_j`）で測定された。受領 `est_uj` フィールドは整数テーブルとして保持され（同一ワークロードで平均 `424,153 µJ`）、外部ハードウェアレールや壁面モニタは接続されていなかった（`measured_j = None`、`board_metered = false`）。

## 用語とラベル

<ul id="terms">
<li>SHA: SHA-256。リファレンスがキー、コンテンツダイジェスト、ログに用いるハッシュ関数である。</li>
<li>BLAKE3: 内部キーの設計目標として名指しされた暗号学的ハッシュ関数である。リファレンスはまだこれを用いていない。</li>
<li>HAMT: hash array mapped trie(ハッシュ配列写像トライ)。リポジトリの状態を保持する永続写像である。</li>
<li>UTF: UTF-8。Git ファイル写像が受け入れるテキスト符号化方式である。</li>
<li>MSRV: 最小サポート Rust バージョン(`rcevc-core` および `rcevc-proj-git` では `1.85`、`rcevc-keys` では `1.90`)。</li>
<li>CI: 継続的インテグレーション(`rustc 1.100.0` 上での `cargo test --locked --offline --all-targets`)。</li>
<li>CAS: compare-and-swap による参照更新(`CasRef` および `GitDir::compare_and_swap_ref`)。</li>
<li>FIPS: Federal Information Processing Standards(連邦情報処理規格)。SHA-256 の検証には FIPS 180-4 のテストベクタを用いる。</li>
<li>RFC: Request for Comments。inflate の実装は RFC 1950 および RFC 1951 に従う。</li>
<li>SATB, CPU, GPU, PID, SMC, SoC: Satiation Benchmark テレメトリの規律、中央処理装置、グラフィックス処理装置、プロセス識別子、System Management Controller、system-on-chip をそれぞれ表す。</li>
<li>VC1, VC2, VC3, VC4, VC5: リファレンスが検証する5つの命題であり、その検証テストは以下で示す。</li>
<li>CONGRA: プロジェクトノートにおいて将来のリプレイ対象として挙げられたコーパスである。本ページでは略称の展開を行わない。</li>
<li>README: リファレンスリポジトリに同梱された概要ファイルである。</li>
</ul>

- **Measured (wall time and counts)** は、リリースビルド（`aba99fce` が Apple M5 Max 上で、README ベースラインが `8bf9c9af` に印刷されたもの）から得られる実時間、命令カウントまたはパスカウントである。

- **Reported (`reported_j`: L2 and L3 counters)** は、Apple M5 Max（`macOS 27.2.1`）上の OS またはオンチップカウンタの測定である：全チップ `IOReport` を `macmon` 経由で取得（L2、共有ホストラベル `A2`、Falsifier 6 により `<= 5.0%` の事前/事後アイドルドリフトでゲート）および PID 毎のカーネル `proc_pid_rusage(RUSAGE_INFO_V6).ri_energy_nj`（L3、ラベル `D`）。外部ハードウェアレールまたは壁プラグ電力プローブは接続されていない（`measured_j = None`、`board_metered = false`）。

- **Stated (`est_uj` / `est_j`)** は、`rcevc-core` 内のレシートにコピーされるデフォルト整数コストテーブルである。これはソースコードに記述された分析テーブルであり、カウンタや壁メータの測定値ではない。

## 1. 参照とは何か, および参照ではないもの

本プロジェクトの目的は, 多数の人間およびエージェントが同時に書き込める歴史であり, 書き手にGitの使用を止めるよう求めるものではない. プロジェクトノートにおける枠組みは, 分岐・差分・単一のメインブランチへのマージという古いインターフェースであり, 互換性がそのインターフェースを維持し続けている要因であり, 可能な限り決定論的規則が判断し, 最後にモデルを用いるべきである, というものである.

Reality Code Engine (RCE) は本サイトの別論文で研究されているプログラミング言語である. RCE-VCは当該言語の上に構築されたものではない. それはRCEプログラムを構文解析したり, 出力したり, RCEチェッカーを呼び出したりはしない. 両者が共有するのは枠組みのみである：リポジトリのためのForm, 完全決定論的ステップであるδ, 状態をその畳み込みとするハッシュ連鎖ログ, 名前を持たない鍵, およびモデルが最後に実行され信頼されない歯車階梯である.

コミット `aba99fce` (`13 November 2026`) 時点で, 公開ワークスペースはバージョン0.1.0であり, **3つ**のクレートを保持している：

1. `rcevc-core` は決定論的中核である：時計も乱数もI/Oもなく, 依存関係もなく, `#![forbid(unsafe_code)]` (MSRV `1.85`) である. 現在は `rcevc-core::assure` も含まれており, これは保証境界であり, 検査済み動作が当該リポジトリのログに既にある結果からのみ鋳造され, 検査されたheadおよびgateに対してのみ適用されることを保証する. また `CasRef` は1つの操作識別子を再試行するため, 別の書き手の同一対象が成功と誤認されることは決してない.
2. `rcevc-keys` はRust (`.rs`) およびPython (`.py`) ソースファイルをトップレベル項目に分割する. これにはベンダリングされた `tree-sitter 0.27.2`, `tree-sitter-rust 0.24.2`, `tree-sitter-python 0.25.0` を用いる (MSRV `1.90`, `vendor/` からオフラインでCコンパイラを用いて構築され, ネットワーク取得は一切行わない). 各項目の識別子は正規化されたトークン本体の名前を持たない中核鍵であり, 項目の改名, 空白, コメントに対して不変である. 一方, 元の正確なバイト列は `parts` に保持され, `project` がそれらを損失なく連結して戻す. 非`.rs`/`.py` パスまたは構文解析エラーツリーの場合は, 元のバイト列に対する単一リーフへきれいにフォールバックする.
3. `rcevc-proj-git` はGit投影 (`#![forbid(unsafe_code)]`, MSRV `1.85`) であり, 独自のSHA-1, zlibおよびGitオブジェクトコードと `GitDir::compare_and_swap_ref` を保持し, これにより中核は依存関係から解放されている.

CIは `rustc 1.100.0` 上で `cargo test --locked --offline --all-targets` および `cargo clippy --locked --offline --all-targets -- -D warnings` を実行し, **49個のオフラインテスト** (`rcevc-core` に `29`, `rcevc-keys` に `8`, `rcevc-proj-git` に `12`, `git 2.43` に対して検証済み) を実施する. VC5を超える命題は本ページでは述べられていない.

## 2. バージョン管理の法則

参照実装は次のように記述している。同じ段落は、リポジトリの README とクレートのドキュメントの冒頭にも掲げられている。ここでは一度だけ引用する。

> バージョン管理とは、名前を持たない正準的なリポジトリ状態への変更の採択である。各変更は、指名された検査器が宣言された契約のもとで事後状態を受理した場合にのみ採択され、さもなくば記録された理由とともに拒否される。依存閉包が充足しない変更は、調整なしに採択される。採択可能な統合候補のうちでは、明示された費用が候補を順位付けする。そして、解決されたすべての競合を含め、採択されたすべての結果は再利用される。

本節の残りでは、参照実装 `aba99fce` が何を実装しているか、その上で何を測定したか、そしてまだ何を行えないかを述べる。上記の記述は参照実装が目指す基準であり、既存のバージョン管理ツールがすでにこのように振る舞うことを報告するものではない。

## 3. 量

**単位**とは本文と依存スロットのリストからなるものである。依存リストが空の場合、単位は葉であり本文はリテラルテキストであるため、シェルスクリプト中のドル記号はドル記号のままとなる。リストが空でない場合、ドル記号の後にインデックスが続くとその依存を選択し、2つのドル記号はリテラルのドル記号である。

**鍵**とは名前を持たない単位の同一性である。改名は名前が束縛されるスロットを変更するが、鍵は変更しない。参照は次のように定義する

$$
\mathrm{key}(u) = H(\texttt{rcevc/unit/v1},\; \mathrm{body}(u),\; \mathrm{key}(d_0), \ldots, \mathrm{key}(d_{m-1}))
$$

ここで$H$はバージョン付けされドメイン分離されたエンコーダを通したSHA-256であり、$d_i$は依存単位である。**内容ダイジェスト**（トライがハッシュする値）は別の値であり、$H(\mathrm{body}, \text{dependency names})$である。

**ドラフト**とは未検証のマップであり、創世時および外部から読み込んだあらゆるものに用いられる。ドラフトを封印すると検証が行われ**状態**が生成される。状態は整形式である：依存は解決され、本文中のあらゆるインデックスは束縛されており、依存グラフに循環はない。状態は3つの永続マップを保持する。単位マップはMerkle HAMTである。鍵マップと逆依存インデックスは永続的でありMerkleルートの一部ではない。状態の複製とルートの読み出しは$O(1)$である。2つの状態はルートが等しいときに等しい。差分はハッシュが異なる部分木のみを走査するため、そのコストはリポジトリの大きさではなく差分に従う。鍵は変更されたが自身の単位は変更されていない依存は、意図的に差分から除外される。後述する閉包はそれらの依存を含む。差分にそれらを含めると、共有された依存が偽の衝突に変わってしまう。

**編集**はスロットを変更し、最後に1回だけ逆依存閉包全体に対して検証を行う。編集内の状態は整形式でなくてもよい。これは意図的な設計であり、例えば削除の後にputを行う場合などに必要である。

**変更**は不透明な書き手ラベル、基底状態、レベル、操作のリスト、およびメッセージを保持する。操作はput、delete、renameである。レベルは名前のみ、訂正、意味変更、およびインタフェース変更である。名前のみのレベルはカーネルによって検査される：鍵の多重集合は不変でなければならない。変更識別子はすべてのフィールドをカバーする。メッセージは表明された意図であり、例えばコミットサブジェクトである。受理はメッセージを読み取らず、書き手ラベルにも依存しない。

状態$s$に対する変更$c$について、

$$
\mathrm{writes}(c, s) = \mathrm{diff}(s,\; \mathrm{apply}(s, c)).
$$

読みはputの依存およびrenameのソースである。状態内および後状態内における$c$の閉包は、書き、変更前の依存、変更後の依存、および読みである。2つの変更が$s$上で可換であるとは、それぞれの書きが他方の閉包と交わらないことである：

$$
\mathrm{commutes}(a, b, s) \iff \mathrm{writes}(a) \cap \mathrm{closure}(b) = \emptyset \;\land\; \mathrm{writes}(b) \cap \mathrm{closure}(a) = \emptyset.
$$

まず、参照テストは、可換な変更が両方の順序で適用されても同一のルートを与えることを検証している。

ステップ **δ** は `submit` である。これはユーザ入力に対して全域的であり、受理と受領書の組、または拒否と理由の組のいずれかを返す。いずれの場合も、ハッシュ連鎖されたログエントリを一つ追加する。ヘッドはそのログの畳み込みである。リプレイはチェーンを検証し、すべてのエントリを再統合する。競合に対しては記録された解決を用いる。提案者は呼び出さない。各事前状態ルート、各事後状態ルート、および各拒否理由を検査する。

## 4. リポジトリ形態

The README は実装形態を 9 つの部に区分し、さらに `rcevc-keys` アイテム分割器と `rcevc-core::assure` 境界を含む。

| 部 | 位置 | 機能 |
|---|---|---|
| R、名前なしキー | `model.rs`, `rcevc-keys` | 上記のキー; `rcevc-keys` は `.rs` と `.py` ファイルをトップレベル項目に分割し、ロスレスのバイト投影を行う。名前変更はキーを変更しない。 |
| S、永続状態 | `hamt.rs`, `model.rs` | Merkle HAMT。クローンおよびルートは $O(1)$ で、差分は差異のサイズに比例し、トライ形状は正規形である。キーと逆依存インデックスは編集時に更新され、リポジトリ全体では更新されない。 |
| Δ、型付き変更 | `change.rs` | 宣言された基底とレベルに対して put、delete、rename を行う。名前のみのチェックはカーネルによって行われる。 |
| X、可換性 | `change.rs` | 書き込みは実際の差分である。クロージャは前後に依存項目を追加し、読み込みも行う。互いに重ならないクロージャは可換である。 |
| K と G、チェッカーとゲート | `gate.rs` | 各チェッカーはプロパティクラス、リンク仮定、信頼基底、権限、スコープ、ダイジェストを示す。 |
| δ、ラダー | `repo.rs`, `assure.rs` | 参照、可換性、構造的マージ、再検証、提案者、さらに CAS 参照保証 (`CasRef`) を行う。ゲートはすべてのパスで実行される。 |
| D、ログ | `repo.rs` | ハッシュ連鎖エントリ。ヘッドは折りたたみである。リプレイは提案者なしで再構築する。 |
| U、再利用 | `repo.rs` | 解決は名前なし競合シグネチャの下に保存され、ゲートが受諾した後にのみ利用される。 |
| C、コスト | `repo.rs` | 述べられた各段テーブル (`est_uj`)。レシートは合計を保持する。 |

チェッカーの権限は pinned、replay、proved、derived、inferred のいずれかである。そのスコープは三種類のうちの一つである。**Unit**: デルタ内のユニットを再チェックする。**Closure**: 判定はユニットとそのトランジティブ依存に依存するため、ゲートは依存項目も再チェックする。**Global**: 全状態をチェックする。前回のヘッドが合格し、宣言されたスコープが真であれば、スコープ付き再チェックは完全チェックと一致する。テスト `delta_gate_agrees_with_full_gate` は 600 回の試行でその一致を記録し、100 回以上の拒否があった。スコープについて虚偽を述べるチェッカーは VC2 を破壊する。スコープは信頼される。今回のバージョンでは、残りの状態を隠すことでスコープを強制する仕組みは存在しない。

ゲートのダイジェストはすべてのチェッカーのステートメントを包含し、そのダイジェストがジェネシスハッシュに供給される。トライ形状は正規形であり、プレフィックスは何も保持せず、単一のリーフ、あるいは二つ以上のキーを持つブランチとなる。ルートは到達した順序履歴に依存しない。ハッシュ化されるすべては `rcevc/<thing>/vN` 形式のバージョン付ドメインタグを伴うエンコーダを通過する。タグがカバーする内容を変更するとバージョンを上げることになる。

<div id="5-the-transition" class="anchor-alias" aria-hidden="true"></div>

## 5. 遷移

`submit` は常に以下のいずれかの経路を取る。歯車の名称は領収書に記載されたものである。

1. **G0, 参照。** 同一の変更識別子が同一の head に対して既に拒否済みの場合、保存された拒否を返す。その再試行の明示的なコストは G0 行のみである。この挙動はテスト `g0_identical_retry_costs_one_lookup` によって記録されている。
2. **Base。** 基底スナップショットが存在しなければならない。存在しない場合は未知の基底である。基底に対して操作を適用できなければならない。適用に失敗した場合は適用エラーまたは不正形式ユニットである。名前のみの主張であって、多重集合のキーを不変のままにしないものは拒否される。
3. **G1, 交換。** 移動集合を基底から現在の head への差分とする。変更の閉包が基底および head においてその集合を欠落する場合、変更は head に直接適用される。マージは行われない。
4. **G2, 構造マージ。** それ以外の場合、参照は head 上で移動したものと変更自体が変更したものの和集合について、スロットごとにマージする。一方が不変であれば他方を取る。両者が等しければいずれかを取る。その他のスロットは衝突である。
5. **Conflict。** 署名は $H(\mathrm{key}_{base}, \mathrm{key}_{head}, \mathrm{key}_{theirs})$ であり、スロット名は使用しない。G0 再利用は当該署名に対する保存済み解決を返す。保存されていない場合、G4 は提案者に問い合わせる。提案者が存在しないか、何も返さなかった場合、変更は衝突したスロットとともに拒否される。再演時には記録された解決が使用され、提案者は呼び出されない。
6. **G3, 再検証。** マージされた代入は well-formedness 検査付きで head 上に構築される。その検査に失敗した場合、変更は不正形式として拒否される。
7. **Gate, すべての経路（G1 を含む）において。** 候補と現在の head からの差分が gate に渡される。検査器が失敗した場合、変更は拒否され、検査器の名称が記録される。
8. **Accept。** 提案者による解決はここに至って初めて再利用ストアにコピーされる。新たな head がスナップショットされる。領収書は使用された歯車、gate の証拠、解決、および `est_uj` を記録する。

拒否もまたログに記録される。head は移動しない。

## 6. テストが保持する命題

コミット `aba99fce` において `cargo test --offline` は 49 件のテストを実行する (`29` core, `8` keys, `12` git)。以下の命題との対応を示す。

| 主張 | リポジトリ内のテスト名 |
|---|---|
| VC1, 全域性, 行き詰まりの不在: すべての提出は理由付きで受理または拒否され, 記録される | `vc1_every_submission_is_accepted_or_refused_and_logged` |
| VC2, 帰納による緑性: すべての head は整形式であり, ゲートを通過する | `vc2_every_head_is_well_formed_and_passes_the_gate` (400 件のランダムな提出, 古い基底, 汚染された変更を含む) |
| VC3, 可換性は任意の順序で同一の結果を含意する | `vc3_commutation_implies_order_independence` (3,000 回のランダム試行, 500 組を超える可換対) および `vc3_disjoint_writers_integrate_at_g1_in_either_order` |
| VC4, テキストが衝突しない場合でも意味的衝突は検出される | `vc4_identical_edits_merge_and_semantic_conflicts_are_caught_at_g3` (新しい呼び出し元に対する引数個数の変更) |
| VC5, 解決済みの衝突は名前を含まないシグネチャによって再利用される | `vc5_resolved_conflicts_are_reused_by_name_free_signature` |
| モデルの出力結果は候補である | `model_output_is_a_candidate_never_trusted` |
| 状態はログの畳み込みである | `replay_reproduces_head_without_any_proposer` |
| 改名はキーを変更せず, 名前のみの変更は検証される | `renames_change_no_keys_and_name_only_is_verified` |
| G0 の冪等な再試行は 1 回の参照のみを要する | `g0_identical_retry_costs_one_lookup` |
| 範囲限定ゲートは完全ゲートと一致する | `delta_gate_agrees_with_full_gate` (600 回の試行, 100 件を超える拒否) |
| スナップショットは後続の編集の影響を受けず, 増分計算は全件再計算と一致する | `snapshots_share_structure_and_diff_is_exact`, `hamt.rs` 内の HAMT テスト |
| SHA-256 は公開されたテストベクタと一致する | `hash.rs` 内の FIPS 180-4 テストベクタ |

VC5 のテストは, 提案者を経由して衝突を受理させた後, 同一の衝突を別のスロット名で提出する。二度目の受理は G0 の参照段階を用い, G4 は用いず, 提案者を再度呼び出さず, その `est_uj` は提案者経路の受領記録の 100 分の 1 未満である。この比率は, 申告された受領コストの比較である。

別のテストでは, 提案者に汚染された結果を与える。ゲートはこれを拒否し, head は変更されず, 拒否された解決は再利用のために保存されない。

## 7. 測定された壁時間

ワークロードは、スウォーム例が実装しているように、各ラウンドのすべてのライターがそのラウンドの開始ヘッドに対して提出を行うため、ラウンド内の後続提出は陳腐化する。5人に1人のライターがホットモジュールを編集し（`below(5) == 0`）; 50件に1件の提出が禁止トークンを含む（`below(50) == 0`）――これはREADMEが示す2%の毒性率である。例のプロポーザは、二つのボディを結合する決定的な代替物であり、学習モデルではない。例では各モジュールに10単位を格納する。例の固定シードは `0x5eed` である。

## 9. Git への射影

この射影はマイルストーン M2 に属し、`rcevc-proj-git` において実装される。葉単位はファイルのバイト列そのものである。依存関係を持つ単位は、短いヘッダを付したファイルとして書き出される。参照実装は、これを UTF-8 ファイルの上の全単射として扱う。

```
#rcevc-unit v1
#dep <slot>
#body
<body>
```

各依存関係につき 1 行の `#dep` が書かれる。

**出力.** `export` は `main` 上に受理されたエントリごとに 1 つのコミットを書き込む。著者は writer ラベルであり、件名は変更メッセージ、またはメッセージが空の場合は変更識別子とギアを列挙した行となる。受理された各コミットはトレーラ `RCE-VC-Change`, `RCE-VC-Pre`, `RCE-VC-Post`, `RCE-VC-Path`, `RCE-VC-Evidence`, `RCE-VC-Resolved`, `RCE-VC-Est-uJ` および `RCE-VC-Entry` を保持する。`RCE-VC-Est-uJ` は測定値ではなく、宣言されたマイクロジュール総量である。リファ `refs/rcevc/log` にはログエントリごとに 1 つのコミットがあり、拒否も含まれ、拒否コミットは `RCE-VC-Reason` を保持する。同一のログと同一の時間基準が与えられた場合、`export` は同一のコミット識別子を生成する。

**入力.** `ingest` は tip から親コミットをたどり、`RCE-VC-Post` トレーラがスナップショットであるコミットを見つけるまで続く。そのスナップショットが基底となる。tip ツリーはその基底に対して 1 つの変更（追加と削除）となる。内容のマルチセットが変化しない場合、レベルは名前のみである。ブランチは提案であり、ラダーが決定する。writer はリベースを求められない。

README はこれらの検査を git 2.43 に対して記録している。検査は `tests/git_interop.rs`（`rcevc-proj-git` の `aba99fce` にて 12 テスト）で実施された。

| チェック | README に記録された結果 |
|---|---|
| `git fsck --full --strict` がエクスポートされた履歴に対して | クリーン |
| `main` 上のすべてのコミットがその `RCE-VC-Post` トレーラでルートに再インポートされる | はい |
| 異なるディレクトリで同一のログを 2 回エクスポートした場合 | 同一のコミット識別子 |
| Git のトレーラパーサがレシートを読み取る | はい |
| 基底が古くなったブランチ上の 2 つのプレーン Git コミット | 1 つの変更として取り込まれ、G1 で承認され、`main` が前進する |
| Git 自身が書き出したオブジェクト（dynamic-Huffman デフレートを含む） | 読み取り |
| 禁止トークンを含むプレーン Git コミット | 拒否され、`refs/rcevc/log` に記録され、`main` は移動しない |

この投影の制限は README に記載されているとおりである。対象は緩めのオブジェクトと緩めのリファのみであり、出力時のファイルモードは 100644 であるため、実行権限ビットはまだ単位属性として扱われない。シンボリックリンク、サブモジュール、非 UTF-8 ファイルは理由を付して拒否され、推測は行われない。

プロジェクトは Mergiraf という名前の構造化マージ手法を言及している。Mergiraf は tree-sitter を利用し、構文形成されたファイルの処理を目的とした作業である。この観測は収束的である。本ページはそれに対する参照スコアを付けず、他のバージョン管理システムに対しても参照スコアを付けていない。

## 10. 本バージョンの限界

コミット `aba99fce` において:

1. `rcevc-keys` は Rust (`.rs`) および Python (`.py`) ファイルをトップレベル項目に分割する (依存関係は同一ファイル内のそれより前の項目のみを指す) が、TypeScript 分割および 50 パッケージ / 1,000 リポジトリの往復評価はまだ実装されていない。他のファイル種別は全体ファイルの葉単位のまま残されている。
2. Git ストレージは loose object および loose ref である。packfile も packed ref も存在しない。エクスポートはモード 100644 のみ書き込む。シンボリックリンク、サブモジュール、非 UTF-8 ファイルは拒否される。
3. エクスポートされるコミットごとに木全体を再構築する。
4. 逆依存集合は更新時に複製される。依存者が多数存在する単位ではその更新が大きくなる。
5. 鍵の計算は再帰的である。約 10,000 単位を超える依存連鎖はスタックオーバーフローを引き起こす可能性がある。
6. 完全内容ルートは単位数に対して線形である。取り込みではこれを名前のみのレベルを推測するためだけに用いる。カーネルの名前のみの検査は diff を走査する。
7. スナップショットはメモリ内に保持され、保持ポリシーも独立したストアも存在しない。
8. `submit` は単一スレッドである (`CasRef` が ref スワップを保護する一方、`submit` は可換な変更を逐次的に受け入れる)。リースは構築されていない。
9. チェッカーはそのスコープについて真実を述べるものとして信頼される (Wasmtime サンドボックスによる M3 はまだ構築されていない)。
10. オンチップの `reported_j` (`317-365 µJ` per `100,000`-unit admission) はカーネル `ri_energy_nj` を介して外部に記録されているが、リポジトリ内の receipt フィールドは依然として記載された `est_uj` 表を保持しており、外部ハードウェアレールの `measured_j` (M6) は未解決のままである (`measured_j = None`, `board_metered = false`)。

- **M2（BLAKE3 による内部鍵と `gix` によるパックファイル）の完了。** 内部ハッシュ計算を BLAKE3 へ移行する。その際、FIPS 180-4 の SHA-256 テストベクトルは独立したテストとして維持し、ドメインタグを更新する。また、Git オブジェクトの格納を `gix`（`gitoxide`）によるパックファイルおよびパック済み参照へ移行する。続いて、1,000リポジトリの履歴に対する往復検証を実施する。
- **M3（Wasmtime 上の `rcevc-gate`）。** 検査器を燃料制限付きかつ決定論的な WebAssembly モジュールとして実行し、固定されたダイジェストを用いる。宣言された範囲のみを公開することで、宣言されたスコープを強制する。
- **M4（リースと単調チャネル）。** 調整を伴わずに単調な変更を並行してストリーミングする仕組みを実現する。
- **M5（競合コーパスの再生）。** Merge-Bench、CONGRA、AgenticFlict を梯子に通して再生し、G0、G1、G2、G3、G4 の各段階における解決件数を集計する。
- **M6（`rcevc-meter`）。** `est_uj` を、較正済みの `reported_j` および外部ハードウェア電源レールによる `measured_j` に置き換える。
